Apologies in advance to all patch managers and security teams that thought they might get a break this week. The PHP Foundation will release a “critical” security update on Thursday between 14:00 and 14:30 UTC.

While we don’t have many details about the latest vulnerabilities – these haven’t been [leaked](https://www.theregister.com/security/2026/10/22/php-blames-supply-chain-security-biz-chainguard-for-putting-huge-chunks-of-the-web-at-risk/5304611) like last month’s [critical PHP2Shell flaws](https://www.theregister.com/security/2026/10/21/php-devs-publish-critical-bug-fix-as-site-owners-warned-pull-em-offline-if-youre-unpatched/5304519) – a Wednesday advisory said the highest-severity bugs in the upcoming release are rated critical.

“The issues rated critical require either non-default configuration or uncommon setups,” the foundation [said](https://www.php.net/index.php#2026-11-18-1), urging PHP users to “prepare to upgrade promptly once the releases become available.”

REG AD

We do know that one of the vulnerabilities is another remote code execution (RCE) flaw, tracked as CVE-2026-115560.

REG AD

In October, the PHP Foundation told The Register that it had reserved this CVE identifier for another RCE bug, but added it would not get an emergency fix like the earlier two PHP2Shell vulnerabilities because the third one doesn't pose the same risk.

CVE-2026-115560 “requires a very unlikely combination of configuration and specific PHP application code, which we do not expect to occur in practical use of PHP,” Elizabeth Barron, executive director of the PHP Foundation, [told](https://www.theregister.com/security/2026/10/23/theres-a-third-php2shell-bug-but-it-wont-get-an-emergency-fix/5305208) The Register at the time. “The issue can be mitigated with a configuration setting. So for the moment the PHP Security Team has only published an informational advisory on the PHP website, explaining exactly this situation.”

The earlier informational advisory [urged users](https://www.php.net/index.php#2026-10-21-5) to “set session.upload\_progress.enabled=0 until the next regular bugfix release, to fully protect from an unlikely RCE vector.”

These unlikely RCE attacks require an application to set “session.serialize\_handler to php\_binary or php\_serialize in its configuration and then switch it to php at runtime with ini\_set() before calling session\_start().”

Additionally, the session upload progress feature must be enabled, which the PHP Foundation said is very unlikely in real-world applications.
