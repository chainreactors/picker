PHP2Shell is the name given to two critical PHP vulnerabilities, CVE-2026-109618 and CVE-2026-109619, each rated 9.2 under CVSS 4.0, that allow unauthenticated remote code execution against every common PHP web deployment from PHP 5.4 onward. PHP shipped fixes on 21 October 2026 in versions 8.2.35, 8.3.36, 8.4.27 and 8.5.12, but Amazon’s honeypots had recorded exploitation attempts from 17 October, four days before the patches existed. In a question-and-answer piece published by [Security Affairs](https://securityaffairs.com/) on 24 October, the site’s founder [Pierluigi Paganini answers the questions operators are asking](https://securityaffairs.com/201662/hacking/pierluigi-paganini-answers-questions-about-the-php2shell-flaws.html): how serious the flaws are, why attackers moved first, and what to do this week. This article summarises his answers and adds the version, exposure and mitigation detail from the vendor advisories.

## What is PHP2Shell?

PHP2Shell is a pair of memory-handling bugs in the PHP interpreter itself, not in WordPress, Laravel or any other application written in PHP. According to Cloudflare, the flaws were disclosed on 21 October by researchers at Calif.io, Wiz, OpenAI and Quarkslab. Datadog Security Labs, which reproduced both bugs, describes CVE-2026-109618 as a failure to handle memory exhaustion during request initialisation, which leaves half-built internal state that later code treats as valid, and CVE-2026-109619 as stale state carried from one request into the next when a worker process is reused, reachable through PHP’s session upload-progress feature and, on PHP 8.5 only, through fatal-error backtraces. Both end in command execution on the server. Datadog lists the Apache module, PHP-FPM, php-cgi, FrankenPHP and LiteSpeed as affected, with default configurations vulnerable.
