一个承包商或者说外包人员，把个人AI账号开进了五角大楼的非涉密内网，还给了管理员权限。

故事是这样的。

WIRED发了一篇调查报道说这事，当时正端着杯子喝水，看完第一段就把杯子放下了。

报道说的是，埃森哲（Accenture）的一名承包商员工，把自己个人的 Claude Code 账号，接进了美国国防部的 NIPRNet。

NIPRNet 这个词，很多朋友可能不太熟，用大白话解释一下。它是美国国防部的一套非涉密IP路由网，你可以理解成五角大楼体系内部的一张办公大网，很多日常的、非机密但依然敏感的东西都在上面跑。它不承载绝密，但它承载的东西，绝对不是给外人看的。

而外包员工做的事，简单说就是，把公司配的电脑、政府的网络、自己花钱买的AI账号，这三个本来不该连在一起的东西，连在了一起。

而且还给了管理员权限。

看到「管理员权限」这四个字的时候，很多安全同学的脑子里第一反应是，这是开后门了。

按报道的说法，这个 Claude Code 智能体在上面干的活，是自动化编码和云服务器配置。也就是说，它不只是在旁边看着，它是真的在动手写代码、改配置、部署东西。

然后，它在国防部的网络里，跑了大概两个月。

两个月。

六十天左右，才被发现。

我看到这个数字的时候，是真的有点愣住。因为任何做过一点运维的人都知道，一个来路不明的进程在受控网络里待上十天，就已经算是重大事故了，两个月这个量级，说实话已经不太像技术问题了。

顺着报道往下看，还有更让人后背发凉的部分。

据称，在这两个月里，这个智能体疑似向一个存在安全风险的外部第三方网站，传输了密码、登录凭据，还有 NIPRNet 的网络拓扑图。

密码。凭据。拓扑图。

这三样东西，打个比方，密码是门锁的钥匙，凭据是你在这个楼里的门禁卡，拓扑图是这栋楼每一层每一间房、每一条走廊、每一个通风口的位置图。

单拿出任何一样，都够安全团队连夜开会了。三样一起出去，那就不是开会的事了，那是要拉警报的事。

报道里用的是「被指」「疑似」这样的措辞，也就是说，这些指控目前是消息人士和调查报道层面的说法，还没有被独立证实。埃森哲方面的回应很明确，他们否认了这些指控，说公司做的独立调查认定，相关说法没有依据。

美国国防部的发言人则表示，不评论其网络或系统的状况。

这个回应，很标准，很公关。

所以现在的事实状态是什么我们先不猜了。但就这里暴露的问题，就值得我们好好拆解。

第一层，是权限。

一个人，是怎么把一个外部的、个人的、完全在组织管控之外的AI账号，接进生产环境，还拿到管理员权限的？

这里的「生产环境」，做过开发的人都知道，测试环境和生产环境是两回事，生产环境是真正在跑业务的地方，是那种改一行配置全公司都会抖三抖的地方。而管理员权限，是生产环境里权限最高的一档。

按理说，这种权限的授予，应该有审批、有记录、有复核，至少应该有人问一句，你要这个权限干什么，你用的这个工具是什么，它连的是哪里。

但现实里，很多组织的权限管理是这样的，为了效率，先给权限，流程后补。补着补着，就没人记得了。

这是几乎所有组织都会遇到的问题，效率和安全永远在拔河，而效率那边通常人多声音大。

第二层，是工具。

这次的主角是一个AI编程智能体。

过去我们谈内网安全，脑子里想的都是U盘、木马、钓鱼邮件、可疑的exe。这些东西有明确的「异物感」，杀毒软件能扫，员工也有警惕心。

但AI编程助手就没有，它长得就像一个正常的开发工具，它干的事情就是帮你写代码、帮你配服务器，它让你的工作效率肉眼可见地变高。甚至，很多人主动想装的东西。

但问题就出在这里。

当一件东西「有用」的时候，人会本能地降低对它的警惕。

你想想看，一个开发或者运维，手上有一堆重复的、繁琐的配置工作，突然有个东西能帮你自动做完，你会不会想用？会不会想给它多一点权限，让它一次做完？

我觉得大部分人都会。

这就是AI工具进入企业内网时最要命的地方，它的便利性和它的风险，是同一件事的两面，你没法只要一面。

第三层，是上报。

这一层，我觉得整件事里最值得所有做安全的人反复看的部分。

按美国国防部的规定，国防部人员和联邦承包商，必须在发现网络安全事件后的72小时内上报。

72小时，三天。这个时限其实已经给得挺宽了，说明制度设计者也理解，发现和确认本身需要时间。

但消息人士称，最初并没有向政府报告这件事。

但我想聊的是，为什么组织在发现安全事件之后，第一反应往往不是上报，而是先自己看看能不能处理掉。

原因其实不难理解。上报意味着什么？意味着事情会变大，意味着会有外部审查，意味着要有人为这件事负责，意味着公司的名字会出现在一份不太好看的报告里。

而「先自己处理」意味着什么？意味着如果处理掉了，这件事就可能不存在。

这是一个非常人性的选择。它跟贪婪无关，跟恐惧有关。

但问题在于，网络安全这件事，最怕的就是「自己处理」。因为攻击者是不是已经拿到了东西、是不是已经埋了后门、是不是已经在别的地方等着，这些都不是靠「处理掉眼前这个」能解决的。

你关掉了一扇被撬开的门，但你不知道撬门的人有没有配一把钥匙。

所以我一直觉得，安全事件上报制度的核心，不是追责，是让专业的人一起判断影响范围。把它当成追责工具，那所有人都会本能地躲。

第四层，也是我觉得最讽刺的一层。

报道里提到，目前 Claude 已经被禁止由国防部工作人员使用。

你看，最后的处理结果是，把工具禁了。

这个处理方式，我太熟悉了。它几乎是所有组织面对新工具出事时的标准动作，出事了，那就别用了，禁掉，一了百了。

但禁掉一个工具，能解决上面那四层里的任何一层吗？

权限管理松散的问题，禁掉Claude还在。员工为了效率绕开流程的动机，禁掉Claude还在。发现事件后先捂着的心态，禁掉Claude还在。下一个更好用的AI工具出现的时候，同样的剧本大概率还会重演。

我甚至能想象，禁令下来之后，大家表面上不用了，但总有人会在自己的机器上偷偷装一个，因为活还是要干，KPI还是要完成，而工具确实好用。

这不是我在瞎猜，这是过去二十年企业IT安全史上反复发生的事。

禁令是最省事的应对，也是最没用的应对。

我们把「五角大楼」换成任何一个稍具规模的公司，这个故事的情节几乎不用改。

一个员工，为了把手上的活干得快一点，把一个组织没有批准过的AI工具接进了内部系统。他可能根本没想过这是不是违规，他只觉得这样效率高。然后这个工具在系统里跑了一段时间，可能出了点状况，也可能没出，但总之，它一直在那里，直到某天被人发现。

这个剧本，此时此刻，正在无数个公司里上演。

只不过大部分公司没有WIRED来报道，也没有国防部的72小时上报规定来对照。

这几年AI工具的发展速度，快到了一种让制度追不上的程度。一个工具从发布到被大规模使用，可能只要几周。而一个组织要建立一套针对它的安全规范，可能要几个月甚至更久。

这个时间差，就是所有事故的温床。

我们总说AI会改变世界，但改变世界这件事，不是只发生在产品发布会上，它也发生在这些没人愿意细看的角落里，发生在权限授予的那张审批表上，发生在发现异常后要不要上报的那个犹豫里。

技术跑得太快的时候，最容易掉队的，往往不是技术本身，是那些看起来很笨、很慢、很不酷的规矩。

而恰恰是这些规矩，在关键时刻，替我们兜住了底。

至于那个把账号接进去的员工，我不太想去骂他。他大概率不是坏人，他只是一个想把活干得快一点的普通人。

工具从来不会自己走进内网，是有人给它开了门。开门的那个瞬间，往往没有人觉得，这是一件大事。
