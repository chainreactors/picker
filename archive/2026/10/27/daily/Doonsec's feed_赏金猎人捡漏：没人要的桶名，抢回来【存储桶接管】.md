先理解下面这段话，它会帮助你吸收后面的内容：

一个存储桶的名字被释放了，可它的"门牌号"还留在别人的系统里。谁先抢到这个门牌号，谁就能冒充原来的主人。

在 SRC 和众测里见过太多次这种"阴差阳错"了，公司自己把桶删了，代码却没改，结果被路人甲抢注，官网瞬间变成钓鱼站。听着像段子，其实是高危漏洞。下面把它掰开揉碎讲。

## 一、先搞懂"存储桶"是啥

你把阿里云 OSS、腾讯云 COS、AWS S3 这些云存储，想象成一个巨大的公共仓库区。每个仓库就是一个"存储桶"（Bucket），桶名全球唯一、先到先得。比如你注册了 mycompany-backup-2024，别人就永远用不了这个名字。

关键点来了：桶可以被删除，删了之后这个名字就回流到"可注册"池子，谁都能再抢。

这就埋下了雷。

## 二、漏洞到底怎么来的

很多系统的代码、配置文件、CDN 回源、DNS 的 CNAME 里，会写死一个桶地址，例如：

```
https://mycompany-backup-2024.oss-cn-hangzhou.aliyuncs.com
```

后来这个桶因为项目下线、迁移或者手滑误删，没了。但下面这些地方还留着它的地址：

* 前端 JS 里写死了这个 URL
* 后端配置、环境变量里还有
* DNS 的 CNAME 还指向它
* CDN 回源配置还指向它

于是链条就接通了：

1. 攻击者发现这个桶名现在没人注册
2. 用自己的云账号注册同名桶
3. 原来系统里所有指向这个地址的请求，全打到攻击者的桶里

这就是"存储桶接管"，本质上就是子域名接管在云存储场景下的变种。

一个类比帮你看穿它：你家原来的快递柜编号是"A-001"，你搬走后柜子被回收了，可你的快递单上还写着"A-001"。新搬来的人租了 A-001，你的所有快递就都送他手里了。桶名就是那个"A-001"，写死的地址就是那张没更新的快递单。

## 三、什么样的场景容易中招？认信号

记住几个"红灯"，扫一眼就知道八成有戏。

信号 1：系统里存在指向云存储的地址，长这样

```
xxx.oss-cn-xxx.aliyuncs.com# 阿里云xxx.cos.ap-xxx.myqcloud.com# 腾讯云xxx.s3.amazonaws.com# AWSxxx.bcebos.com# 百度云
```

或者自定义域名 CNAME 到了上面这些地址。

信号 2：这个桶当前是"未注册"状态。直接浏览器访问，返回类似：

```
NoSuchBucketThe specified bucket does not exist
```

或者一个带着云厂商错误码的 404。

信号 3：系统还在引用它。网页 JS 写死、后端配置里有、DNS CNAME 还指着、CDN 回源还指着、App 接口返回的 JSON 里还带着这个地址，这几处任意一个中招都算。

信号 4：桶名可被外部注册。绝大多数云厂商桶名全局唯一、先到先得，删了就释放，这正是能被接管的根本条件。

一句话特征：地址还在用，桶已经没了，名字谁都能抢。

## 四、怎么把它找出来

小白理解思路就行，不用自己造轮子。

方式 1：被动观察（最省事）逛网站时点 F12 开开发者工具，切到 Network，看页面源码和网络请求里有没有上面那些云存储域名。找到后直接在浏览器访问，看返回什么。若返回 NoSuchBucket/does not exist，就可疑了。想进一步确认，可以去云厂商控制台试着注册同名桶【但只在你授权测试的范围内做，别真去注册别人的名字】。

方式 2：DNS 层面排查查域名的 CNAME 记录，如果指向 xxx.oss-xxx.aliyuncs.com 这类地址，而那个桶实际不存在，这就是典型信号。

方式 3：子域名枚举 + 批量检测安全研究员常用工具枚举子域名，然后批量请求，看哪些返回云存储的"桶不存在"错误码。那个错误码就是判断依据。

方式 4：代码/配置审计翻代码仓库、配置文件、CI/CD 流水线，找硬编码的存储桶地址，逐个验证桶还在不在。

方式 5：公开情报HackerOne 等平台上有大量已公开的接管报告，别人的发现路径是最好的教材。

核心动作其实就两步：① 找到还在被引用的云存储地址；② 验证该桶当前不存在、且名字可注册。

## 五、抢到桶之后，攻击者能干啥

提前给大家强调下：下面只用于理解风险，实测必须在合法授权范围内。

注册同名桶后，危害取决于这个桶在原系统里"扛什么活"：

1. 内容劫持 / 钓鱼。原来系统加载的图片、JS、CSS、下载包，全变成攻击者控制的了。可以放恶意 JS 偷 Cookie、token；可以做钓鱼页冒充原站；可以挂虚假公告、带马的安装包。
2. 窃取上传数据。如果系统还在往这个桶传文件（用户证件、日志、备份），数据直接进攻击者的桶——等于明文泄露。
3. 篡改业务逻辑。前端从该桶加载的配置文件、规则文件被替换，业务行为就可能被悄悄改掉。
4. 配合其他攻击。用被接管的桶托管恶意脚本，能绕过原域名的 CSP 或信任链，升级成供应链式打击。
5. 拒绝服务。攻击者故意让桶返回错误，依赖该资源的页面或功能直接瘫掉。

一句话：只放静态图片，危害有限；放 JS、配置文件、用户上传数据，危害就很大。这个分级思路，写报告时也能帮你定严重级别。

## ![](https://mmbiz.qpic.cn/mmbiz_png/qg1MKHx3jGFMU2IvziatMj8y0jD59YFGgficE4FaUdvqQSCQxicHu0giajAtic2XiaJ1DH5lCjvKZh7LYeIc4VpqfqpmEjfBEKic11v5b7HGA8WB20/640?wx_fmt=png&from=appmsg)六、给小白的防御清单

顺手说防，免得看完只会攻不会守。

* 别轻易删还在用的桶；删之前全局搜一遍引用。
* 删桶之后，清理所有引用：代码、配置、DNS CNAME、CDN 回源，一个都不能漏。
* 桶名加随机后缀，降低被猜中和被抢注的概率。
* 能保留就保留：部分云厂商支持删除后保留桶名一段时间。
* 定期监控：扫自己域名/配置里指向的云存储地址，验证桶还在不在。
* 权限最小化：桶策略不要开放匿名写。

存储桶接管 = 系统还在用一个云存储地址，但这个桶已经被删、名字被释放；攻击者抢注同名桶后，就能冒充原桶接收请求、投递恶意内容或窃取数据。

想练手的同学，建议先在自己的云账号里完整走一遍：建桶 → 引用 → 删桶 → 观察返回 → 再抢注同名桶。这一遍走完，理解会非常扎实。但切记：不要对未授权的真实系统做注册测试，那已经越界了。
