本文分析AI Agent任务链攻击致WAF零告警的错位问题，提出基于资源归属校验与会话级行为评分的检测方案。

## 一、蓝队值守第七天，WAF 一条告警都没有

最近几天攻防特别多，我不仅参加了多场攻防，也应急了很多的事件。

先说一个自己遇见的场景。

蓝队值守这几天，值班表上写的是凌晨两点到八点。态势感知和阿里云WAF 面板很安静：拦截量比平时低，告警数是个位数，规则命中前三位还是那几个老面孔——`/.env`、`/wp-login.php`、`/actuator/env`。

![image-20261120213131231](https://xzfile.aliyuncs.com/2026/11/20/2154/9aabb764-a6e.png)

在交接白班的时候，甲方侧报上来一件事：在昨天有个账号在前一天夜里导出了三千多条订单，跨了七个租户。

回头看（nginx）的日志，这些请求是长这样的：

![image-20261120173005877](https://xzfile.aliyuncs.com/2026/11/20/2154/ab45faa8-695.png)

每一条都合法。带会话、参数正常、返回 200、没有 SQL 关键字、没有路径穿越、速率也没有特别大

WAF 的判断是没有攻击，因为它判断的对象是**单条请求**。而那天夜里发生的事，是**一大的串请求**，我就很奇怪了，为什么连日志都没有。

这是这次蓝队的一些小细节。

![image-20261120211557703](https://xzfile.aliyuncs.com/2026/11/20/2154/6a9ebee5-827.png)

​ 三条叠起来，正好落在所有单点检查都合规的区间里。

这一篇想讲的就是这个错位：AI 把攻击从一个请求打一个点变成了一串请求完成一个任务，而蓝队的检测体系还停在第一个范式上。

## 二、蓝队现在靠的三层判据

一般一个公司的流量走向模式是

![image-20261120214115353](https://xzfile.aliyuncs.com/2026/11/20/2154/9afb7c51-fe1.png)

1. **CDN** 静态资源加速，同时做基础缓存、基础 CC 防护；只处理静态内容，API 类动态请求会回源到后端负载均衡。
2. **负载均衡 SLB** 分发流量、做四层负载；在这里可以开启流量镜像（复制一份流量，不影响原始请求），送给旁路分析设备。**镜像流量只用于分析，不能实时拦截**。
3. WAF（有云waf，也有别的waf）
4. **IPS 入侵防御系统** 网络层、传输层、应用层协议异常检测，侧重底层漏洞利用、恶意 payload，和 WAF 能力互补，同样也是基于流量特征，不理解业务权限。
5. **API 网关** 路由转发、参数校验、签名校验、基础 token 解析；**传统部署下这里一般不做会话级 / 身份级速率聚合**（这就是 Agent 多实例绕过的关键点）。
6. 认证鉴权服务 AUTH

   整个架构里

   唯一可以判定权限的组件

   ：读取 token/session，拿到用户身份，查询权限表，判断A 用户是否允许读取订单 2001。

   * 越权（IDOR）攻击在这里才可以被识别；
   * 但是：很多线上鉴权是**单次权限校验**，不做同身份全局的频率统计。
7. **业务应用服务 APP + 数据库 / 缓存** 执行业务逻辑，读写数据；产生业务日志（订单操作、导出操作、角色变更日志）。

把 WAF 和网关上的检测拆开，判据其实只有三层，主要看特征，就是规则匹配。

![三层判据与 AI 攻击的三处偏移](https://xzfile.aliyuncs.com/2026/11/20/2154/69f00ce5-469.png)

​ 三层里最成熟的是第一层，规则集有一万条也不止；

​ 第二层靠算术，简单有效；

​ 第三层最难，因为合理要靠业务知识定义。

三层的维护成本差得很远：

| 层 | 初始投入 | 日常维护 | 失效方式 |
| --- | --- | --- | --- |
| 特征层 | 低（规则现成） | 低（社区更新） | 规则覆盖不到新形态 |
| 频率层 | 极低 | 极低 | 阈值被稀释 |
| 语义层 | 高（要业务知识） | 高（随业务变） | 规则跟不上业务 |

​ 第三列的差别解释了为什么大多数团队只做前两层：不是不知道语义层重要，是它需要持续的业务输入，而这件事没有装个设备那么省事。

![image-20261120211813843](https://xzfile.aliyuncs.com/2026/11/20/2154/5a41a6ad-049.png)

AI 驱动的攻击恰好落在第三层的空白里，而且不是绕过了第三层，是**根本不需要经过前两层**。

| 偏移 | WAF 的假设 | AI 攻击的实际 |
| --- | --- | --- |
| 粒度 | 一条请求 = 一个动作 | 一个任务 = 几十条合法请求 |
| 时间 | 秒级窗口 | 突发 1-14 个请求，停 25-31 秒，再突发 |
| 判据 | 请求像不像攻击 | 请求能不能达成目标 |

为什么是现在？因为三件事同时成熟了。

| 能力 | 五年前 | 现在 | 对三层的影响 |
| --- | --- | --- | --- |
| 生成合法请求 | 要人写脚本 | 模型直接生成 | 特征层看不到 |
| 控制节奏 | 定时器能做，但不懂退让 | 会等、会停、会换目标 | 频率层看不到 |
| 理解业务 | 几乎没有 | 能从接口文档推语义 | 语义层被绕过 |

​ 第三行是关键。以前的自动化工具不懂这个 id 属于谁，只能做无差别扫描；现在模型读得懂 OpenAPI 描述，知道哪个参数是资源 id、哪个是租户，于是它能变的有意义的扫描有针对性地合法访问。

## 三、为什么396 条规则里，没有一条管授权

第一组实验量的是规则集覆盖到了什么。

我下载了 OWASP CRS v4.0.0 的十个核心规则文件，统计规则数量与分类。

![CRS v4.0.0：396 条规则的类型分布，越权类为 0](https://xzfile.aliyuncs.com/2026/11/20/2154/66078866-be5.png)

分布很清楚：全部集中在攻击语法上。SQL 注入 74 条、XSS 43 条、RCE 53 条，光这三类就占了四成。

再查一个东西：规则集里有没有授权越权归属相关的判断。

```

## 四、30 个业务请求，关键词层 0 命中

第二组换一个角度：如果攻击者的请求里根本没有恶意语法，规则集会怎么判。

我构造了 30 个业务逻辑异常请求，全部结构合法、参数正常：

| 类型 | 例子 | 条数 |
| --- | --- | --- |
| 越权读取 | `GET /api/v1/orders/2001`（别人的订单） | 8 |
| 分页枚举 | `GET /api/v1/orders?page=3&size=200` | 5 |
| 批量导出 | `POST /api/v1/export {"scope":"all"}` | 2 |
| 价格篡改 | `POST /api/v1/cart {"price":0.01}` | 2 |
| 状态跳过 | `POST /api/v1/orders/2001/status {"status":"paid"}` | 3 |
| 角色提升 | `POST /api/v1/users/2001/role {"role":"admin"}` | 2 |
| 他人报表 | `GET /api/v1/reports/daily?uid=2002` | 3 |
| 其他 | 删除地址、取消订单、跨租户审计 | 5 |

用一个从 CRS 规则里摘出来的关键词集合去匹配（`union select`、`<script`、`../`、`etc/passwd`、`${jndi` 等 21 个），同时跑三个真实的攻击样本做阳性对照。

| 样本集 | 条数 | 命中 | 命中率 |
| --- | --- | --- | --- |
| 业务逻辑请求 | 30 | 0 | 0% |
| 攻击样本（SQLi / XSS / RCE） | 3 | 3 | 100% |

![同一套判据：攻击样本 3/3，业务请求 0/30](https://xzfile.aliyuncs.com/2026/11/20/2154/93eb5977-d47.png)

这个对照说明两件事。

第一，匹配器是有效的：三个攻击样本全部命中了对应关键词（`union select`、`<script`、`etc/passwd`）。

按类型拆开看，更能看出为什么不可见：

| 类型 | 条数 | 命中 | 请求里有什么可疑的 |
| --- | --- | --- | --- |
| 越权读取 | 8 | 0 | 只有一个别人的 id |
| 分页枚举 | 5 | 0 | `size=200` 是合法的 |
| 批量导出 | 2 | 0 | `scope=all` 是合法参数值 |
| 价格篡改 | 2 | 0 | `price` 是正常字段 |
| 状态跳过 | 3 | 0 | `status` 取值在枚举范围内 |
| 角色提升 | 2 | 0 | `role` 是正常字段 |
| 他人报表 | 3 | 0 | `uid` 是正常参数 |
| 其他 | 5 | 0 | 删除、取消、跨租户查询 |

八种类型，共同点是一样的：**每一处异常都发生在字段值的语义上，不在字段的形态上。**

![规则统计与命中结果（脚本真实输出）](https://xzfile.aliyuncs.com/2026/11/20/2154/06034857-a70.png)

第二，业务逻辑请求在这套判据下**完全不可见**。它们和正常请求的唯一区别是id 不属于当前用户金额不合理状态跳过了流程，这些信息不在请求文本里，而在业务数据和会话的对照关系里。

顺便说一句这套实验的边界：这是关键词层近似，不是跑真实的 ModSecurity。真实的 CRS 还有变量、变换、异常分数，但它的判据来源仍然是请求文本。这一点不会因为实现精细而改变。
