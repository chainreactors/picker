AI 智能体（AI Agent）正在把大模型从"会回答"推进到"会执行"。当智能体获得文件读写、命令执行、网络访问与工具调用能力后，企业端点环境里出现了一类全新的行为主体——它既不是传统意义上的人，也不是逻辑确定的软件，而是具备任务理解、步骤规划与持续执行能力的半自主执行体。这类主体带来了一项结构性的安全挑战：它的行为在传统遥测维度上与合法用户高度同形。

本报告聚焦 AIDR（AI Detection and Response）体系中的端点侧防线，系统论证"智能体守护（Agent Guard）"的设计方法与落地路径。报告共分十章：第 1 章定义问题空间与威胁模型；第 2 章给出 AIDR 能力模型与 Agent Guard 的体系定位；第 3 章确立设计目标、原则与约束；第 4 章展开 A–F 六大能力域及其功能细项；第 5 章给出关键技术实现路径与性能预算；第 6 章定义统一事件数据模型；第 7 章说明与云端控制面的协同机制；第 8 章以四类典型攻击场景验证检测响应闭环；第 9 章给出三阶段落地实施规划；第 10 章讨论风险、合规与演进方向。

报告的核心主张是：端点是可实施同步阻断的最后一道边界。云端网关擅长内容检测，但一旦动作已经落到端点文件系统或网络栈上，事后告警无法挽回损失。因此需要在系统调用授权路径内完成判定与拦截，并同时引入身份、意图、上下文与调用链四个新维度，才能把智能体风险从"可见"推向"可控"。

第 1 章　研究背景与威胁态势

本章从执行主体的变化入手，界定端点侧新增的五类风险，并以公开披露的真实事件与漏洞验证威胁的现实性；在此基础上指出既有终端防护体系的能力缺口，引出 AIDR 这一代际方向。

1.1 执行能力跃迁：智能体成为端点上的新型行为主体

过去数年的终端安全演进由威胁形态驱动。第一代以文件特征为核心，回答的是"这个文件是不是已知恶意样本"；第二代以行为遥测为核心，回答的是"终端上发生了什么、攻击链如何展开、发现异常后如何处置"。这两代能力体系建立在同一个隐含假设之上：端点上的执行主体只有两类——人类用户与被明确编写的软件。

AI 智能体的普及打破了这一假设。当前智能体已在办公、研发与业务终端广泛落地，典型形态包括编码智能体、办公助手、浏览器操作智能体与 RPA 增强流程。它们能够读取文件、调用工具、访问系统、执行命令，乃至连续完成跨系统的复杂任务。产业界对一个端点上究竟运行了多少 AI 应用给出了量化的观察：据某国际端点安全厂商披露，其端点传感器在客户设备上识别出超过 1800 种不同的 AI 应用，对应约 1.6 亿个独立应用实例[1]。这一数字说明 AI 执行体已不再是零星试点，而是规模化的存量事实。

由此产生的核心问题是：当端点部署 AI 智能体后，传统 EDR 是否仍然适用？ 答案是部分适用但不足以覆盖。EDR 的检测范式围绕"进程、文件、网络、命令、注册表"五类遥测构建，其判别逻辑是"这段行为看起来像不像攻击"。而智能体带来的风险恰恰隐藏于自然语言指令、工具调用、上下文污染与权限越界之中——这些行为在五类遥测上往往呈现为完全合法的技术动作。

1.2 端点侧五类新增风险

结合产业界对智能体运行时的威胁建模成果与真实的漏洞披露记录，本报告将端点侧风险归纳为五类。需要强调的是，这五类风险并非并列关系，而是可串联形成完整攻击链。

| 编号 | 风险类别 | 触发位置 | 风险本质 | 在传统遥测上的表现 |
| --- | --- | --- | --- | --- |
| R1 | 提示注入 | 输入面（内容、工具描述、记忆） | 不可信内容被当作指令执行，劫持智能体目标 | 无异常进程、无恶意文件 |
| R2 | 工具投毒 | 工具与依赖供应链 | 工具描述或返回值被篡改，形成隐蔽指令通道 | 调用的是已批准的白名单工具 |
| R3 | 权限越界 | 执行面（工具调用与授权） | 作用域蔓延与意图漂移，执行未被授权的动作 | 动作本身在权限范围内 |
| R4 | 数据外泄 | 影响面（数据与出网） | 经合法通道将敏感数据外发 | 流量指向合法域名与 IP |
| R5 | 宿主逃逸 | 执行面与宿主边界 | 沙箱突破后向宿主机与内网横向移动 | 与正常容器运维操作难以区分 |

R1 提示注入是攻击链的起点。OWASP 发布的 MCP 安全风险清单将其列为独立风险项，指出这一风险与经典的注入类攻击（如 XSS、SQL 注入）性质相同，区别在于"解释器"变成了模型，而"载荷"是文本或任何经 OCR 处理后成为文本的内容；由于模型被设计为遵循自然语言指令，这类攻击既强力又隐蔽[2]。

R2 工具投毒的严重性在于它绕过了所有基于"信任边界"的既有假设。OWASP 将工具投毒细分为三种子技术：rug pull（可信工具的恶意更新）、schema poisoning（破坏接口定义以误导模型）、tool shadowing（引入伪造或重复工具以劫持交互）[2]。这意味着即便工具来自可信发布者，其行为仍可能在某个版本后发生静默改变。

R3 权限越界在智能体场景下获得了新的表现形式，即"意图漂移"（Intent Drift）。智能体经过多步自主行动后，可能在每一单步都合理的情况下，整体偏离用户最初设定的目标。相关分析将其定位为 AI 应用安全的前沿趋势之一，指出防御需要在内容安全检查的基础上，进一步验证指令来源、落实最小权限，并检查行为是否符合用户意图[3]。

R4 数据外泄与 R5 宿主逃逸则是攻击链的收敛点。前者利用的是智能体被明确授予的对外通信能力，后者利用的是智能体执行任意代码所需的高权限运行环境。

1.3 真实攻击事件与漏洞溯源

理论风险已经在生产环境中被反复验证。下表汇总了具有公开披露记录的代表性案例，所有条目均可溯源至公开报告。

| 编号 | 时间 | 案例名称 | 技术性质 | 风险定量 | 来源 |
| --- | --- | --- | --- | --- | --- |
| E1 | 2025 | Anthropic MCP Inspector 远程代码执行 | MCP 控制面组件缺陷 | CVE-2025-49596，CVSS 9.4 | 公开披露[3] |
| E2 | 2025 | 恶意提示经 Slack MCP Server 改写 Cursor 配置 | 间接注入 → 配置篡改 → 代码执行 | CVE-2025-54135，CVSS 8.6 | 公开披露[3] |
| E3 | 2025 | Microsoft 365 Copilot 零点击数据泄露 | 隐藏指令嵌入邮件内容 | CVE-2025-32711（EchoLeak），CVSS 9.3 | 公开研究[4] |
| E4 | 2025 | mcp-remote 包远程代码执行 | 诱导连接恶意 MCP Server | CVE-2025-6514，CVSS 9.6，包下载量超 43.7 万 | 公开研究[4] |
| E5 | 2024 | AutoGPT 供应链缺陷影响大量仓库 | 第三方依赖投毒 | CVE-2024-6091，CVSS 9.8 | 公开研究[5] |
| E6 | 2025 | Miasma 蠕虫行动 | 在 73 个 GitHub 仓库植入恶意 MCP 配置 | 开发者打开即触发凭据窃取 | 公开披露[3] |
| E7 | 2025 | postmark-mcp 恶意 npm 包 | 邮件集成工具被植入后门，自动密送外发 | 首例野生活体恶意 MCP Server | 公开研究[6] |
| E8 | 2025 | WhatsApp MCP 集成数据外泄 | 恶意 MCP Server 污染工具描述，静默重定向消息 | 全量消息历史可被提取 | 公开研究[6] |
| E9 | 2025 | GitHub MCP 私仓信息泄露 | 恶意 issue 注入指令，经生成 PR 外带私密数据 | 私有仓库信息间接泄露 | 公开研究[6] |
| E10 | 2025 | Asana MCP 集成跨租户风险 | 早期 MCP 部署缺陷 | 功能下线近两周并重置全部用户连接 | 公开研究[6] |

这些案例揭示了若干共性规律，值得在设计阶段就予以吸收。

规律一：攻击者无需突破传统安全控制。 上述案例中绝大多数并非利用企业网络边界或终端防护的缺陷，而是让智能体"读取并执行恶意内容"。E3 的零点击特性尤其说明问题：该攻击针对的是拥有专职安全团队与专用防御能力的生产级 AI 系统，且利用的是对人类读者不可见、但会被 AI 处理的内容。

规律二：合法通道是首选外发路径。 E7 通过邮件密送、E8 通过即时通信、E9 通过代码提交，攻击者全程使用企业明确批准的出站通道。传统的出站流量黑名单对此类行为基本无效。

规律三：信任边界在 MCP 生态中相当薄弱。 公开研究指出，MCP Server 之间的信任边界薄弱，看似孤立的缺陷可以组合成完整的远程代码执行链；即便是官方或可信的 MCP Server 也必须被视为不可信组件[6]。

规律四：可见性缺口是最大短板。 在针对客户环境的 MCP 安全评估中，被反复确认的现状是：安全运营中心对 MCP 活动"基本不可见"——工程师的回答通常是"我们不记录这些"或"我们记录了，但没有进 SIEM"[4]。

智能体生态的暴露面同样在快速扩张。公开数据显示，全网已有超过 8000 个公开暴露的 MCP Server 实例，其中 492 个因缺少认证或加密而存在被滥用风险，累计下载量超过 1.5 亿次[3]。与此同时，非官方注册表索引的 MCP Server 数量已超过 16000 个，且与 npm、PyPI 不同，这些注册表基本未实施安全扫描[4]。一个恶意 Server 完全可以正常运行并静默外传其处理的每一次查询——工具工作正常，用户看到的是预期行为，攻击者则在持续积累数据。

1.4 传统终端防护体系的能力缺口

将上述威胁映射到既有终端防护能力上，可以清晰识别出四类结构性缺口。

| 缺口 | 传统能力现状 | 智能体场景下的失效原因 | 本报告提出的补足方向 |
| --- | --- | --- | --- |
| 身份缺口 | 以用户与进程为身份主体 | 无法回答"这是哪个智能体、代表谁、以什么授权在行动" | 建立智能体身份档案与归属图谱（能力域 A） |
| 语义缺口 | 以特征与行为模式为判别依据 | 风险载体是自然语言与上下文，无恶意特征可匹配 | 引入语义检测与意图一致性校验（能力域 C） |
| 上下文缺口 | 单事件独立判定 | 单步行为合法、多步链路偏离，需链路级因果推理 | 贯通调用链与任务上下文（能力域 B、C） |
| 时效缺口 | 异步告警 + 事后处置 | 智能体执行速度为机器级，事后阻断无法挽回 | 内核态同步拦截（能力域 E、F） |

需要特别指出的是时效缺口。传统用户态审计架构（如 auditd 与基于 kprobe 的追踪器）在处理安全告警时，系统调用已经完成。在高速度的智能体执行下，敏感凭据可以经由原生 TCP 套接字在极短时间内完成外发，远早于用户态守护进程发出终止信号；此外，用户态模式匹配针对的是原始命令参数，而非 VFS 解析后的真实 inode，因此无法识别路径穿越变体、软链接竞态与空字节注入等规避手法。相关安全工程实践已将这一模式概括为"内核强制隔离"（Kernel-Enforced Containment），其核心是消除检测到阻断之间的竞态窗口[7]。

1.5 AIDR：检测响应体系向 AI 资产的延伸

产业界对这一代际变化的共识正在形成。Gartner 已将 Agentic AI Security 列为新兴安全赛道，其魔法象限报告对端点防护的评估中，明确将"当组织采用可在 SaaS 应用、浏览器与云环境中执行动作的 AI 智能体后，端点成为现代安全的关键控制点——人类意图与 AI 执行在此交汇"作为核心判断[1]。

在概念层面，AIDR（AI Detection and Response）正被提出为 EDR 之后的下一代检测响应范式：EDR 关注终端上的人与软件，AIDR 则在同等深度上关注 AI 智能体与 AI 应用。相应地，国内安全厂商也提出了"智能体感知时代"的终端安全第三阶段划分，其核心命题从"终端上发生了什么"升级为"终端上的 AI 智能体是谁、调用了什么工具、访问了哪些资源、执行意图是否发生偏离、是否存在越权操作"[8]。

本报告接受并延展这一界定，在后续章节中给出面向工程落地的完整设计。

第 2 章　AIDR 与 Agent Guard 的定位与总体架构

本章给出 AIDR 的能力模型与 Agent Guard 在其中的体系定位，说明“端点实时、云端全局”的分工依据，并厘清与既有安全体系的能力边界。

2.1 AIDR 能力模型

本报告将 AIDR 的能力内核归纳为四个相互支撑的部分，如图 2 所示。

![](https://mmbiz.qpic.cn/mmbiz_png/8SYXzUAIerTz7JTibRZTU2xQ7YOknpSzMDxHCqhV4UsAWmYgc43feRmpTWgyhsS1em1Eic0s7CGNCwVbJXTcFttpgnUOribmWUCOicv5oQWK1iag/640?wx_fmt=png)

其一，AI 资产可见性。 检测响应的前提是清点。AIDR 要求发现终端上运行的全部 AI 应用、智能体进程、模型服务与 MCP 连接，并为其建立身份与归属档案。这里的"资产"不仅是可执行文件，更包括智能体所持有的凭据、可访问的工具集合与数据范围。缺乏这一层，后续所有行为判定都无从锚定主体。

其二，行为意图检测。 这是 AIDR 与 EDR 最本质的分野。判别标准从"是否恶意"转向"意图是否偏离、权限是否越界、链路上游是否被污染"。这一层次要求系统同时理解自然语言语义与系统调用语义，并在二者之间建立映射。

其三，运行时响应。 AIDR 的响应必须发生在动作生效之前。这意味着检测与执行不能是异步的两段，而需要在同一决策路径上闭环。响应动作包括放行、告警、阻断、熔断、降权与隔离六个层级。

其四，全链路审计。 智能体事件的可解释性要求远高于传统安全事件。一次判定必须能够还原"用户意图 → 模型决策 → 工具调用 → 系统动作"的完整证据链，否则运营人员无法判断是真实攻击、模型幻觉还是业务误伤。

2.2 Agent Guard 在 AIDR 体系中的位置

在 AIDR 的分层实现中，Agent Guard 承担端点数据面执行者的角色，负责"最后一米"：就地采集智能体运行时遥测、就地完成检测判定、在动作生效前执行同步阻断，并将结构化证据回传云端控制面。

这一角色定位带来两个重要的架构推论：

推论一：检测必须下沉到端点。 若将检测逻辑全部放在云端，则每个系统调用都需要一次网络往返，既无法满足同步拦截的时延要求，也无法在断网场景下保持防护有效性。因此端点必须持有完整的本地检测能力与策略缓存。

推论二：策略与知识必须上收到云端。 端点的算力与视野都是受限的——它只能看到单机行为。跨端点的关联分析、威胁情报匹配、工具信誉评级与行为基线训练，必须由云端完成后再下发。

二者的结合构成了"端点实时、云端全局"的分工格局。

云端 TAS 控制面由四个功能组件构成。策略中心负责策略模板化、灰度下发与版本回滚；云端检测负责跨端点行为关联与威胁情报匹配；AI 行为知识库沉淀智能体画像、工具信誉评级、注入特征与行为基线模型；运营门户提供告警研判、事件调查与合规报表能力。

端点 Agent Guard 数据面由采集引擎、检测引擎、决策执行引擎与本地审计仓构成，其内部分层在后文第 5 章详述。

管理控制台面向安全运营人员，提供策略配置、资产视图、事件调查与报表导出能力，同时作为与企业既有安全体系的对接入口。

架构右侧列出了需要对接的六类外部系统，这一设计遵循"不重建、只增强"的原则：企业既有的 SIEM、SOAR、EDR/XDR、IAM、DLP/CASB 与 MCP 注册中心均通过标准接口接入，Agent Guard 不替代它们，而是补齐它们在智能体场景下的能力缺口。

2.4 与既有安全体系的关系

明确 Agent Guard 与既有系统的边界，是避免重复建设与责任真空的关键。

| 既有系统 | 既有职责 | Agent Guard 的增强点 | 边界界定 |
| --- | --- | --- | --- |
| EDR/XDR | 进程、文件、网络行为检测 | 补齐智能体身份维度与语义检测维度，共享进程血缘与终端上下文 | Agent Guard 不重复实现终端基础遥测，通过接口复用 |
| 网络侧网关（如 AI 网关/SWG） | 流量内容检测与访问控制 | 补齐端点侧"动作落地前"的阻断能力 | 网关管南北向流量，Agent Guard 管端点内执行 |
| DLP/CASB | 数据标签与出网管控 | 补齐 AI 上下文中的数据流动识别与智能体主体识别 | Agent Guard 提供智能体侧的数据流动上下文 |
| IAM/零信任 | 身份认证与授权 | 补齐非人类身份（智能体身份）的登记与最小权限下发 | Agent Guard 上报智能体身份，IAM 执行授权 |
