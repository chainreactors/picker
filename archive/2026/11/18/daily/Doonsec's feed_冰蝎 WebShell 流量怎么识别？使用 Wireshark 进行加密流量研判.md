## 一、收到一条可疑 POST 告警，怎么判断是不是冰蝎？

假设你正在进行安全运营，突然收到一条告警：某外部 IP 多次向内网 Web 服务器发送 POST 请求，请求目标是一个 `.php` 文件。打开数据包后，却发现请求体和响应体都是一串看不懂的字符，没有明显的命令，也没有常见的恶意代码。

这时候就需要警惕了：这可能不是普通的业务请求，而是攻击者正在通过 WebShell 控制服务器。其中，冰蝎（Behinder）就是一种常见的 WebShell 管理工具。它的一个重要特点是：**通信内容经过加密**，即使拿到网络流量，也很难直接看到攻击者执行了什么命令。

那么，冰蝎的流量有什么特征？能不能通过 Wireshark 进行识别？

## 二、什么是冰蝎？为什么它的流量难以识别？

冰蝎是一款 WebShell 管理工具。攻击者通常会先通过漏洞上传或写入 WebShell，再使用冰蝎连接服务器，实现命令执行、文件管理等操作。

简单理解：**WebShell 是留在服务器上的一个恶意脚本入口，冰蝎是用于连接和管理这个入口的工具**，加密通信让攻击者与 WebShell 之间传输的内容不容易被直接识别。

冰蝎不同版本的通信方式存在差异：

| 版本 | 主要通信特点 |
| --- | --- |
| v2.0 | 存在 GET 密钥协商，后续使用 POST 通信 |
| v3.0 | 主要使用 POST，请求内容加密 |
| v4.0 | 仅使用 POST，不再进行 GET 密钥协商，支持自定义传输协议 |

本文重点分析冰蝎 4.0 的默认通信特征。需要注意：冰蝎支持自定义协议，如果攻击者修改了默认配置，部分特征可能发生变化。

## 三、冰蝎 4.0 有哪些典型流量特征？

虽然请求和响应内容经过加密，但通信过程中仍然可能留下 HTTP 层面的行为特征。

### 1. 请求方法：以 POST 为主

冰蝎 4.0 默认只使用 POST 请求，不再像早期版本那样通过 GET 请求进行密钥协商。因此，如果发现某个 WebShell 文件被反复 POST 访问，就值得进一步检查。

### 2. 请求头存在一些固定特征

默认配置下，冰蝎可能出现以下请求头：

| 字段 | 典型特征 |
| --- | --- |
| Content-Type | `application/x-www-form-urlencoded` |
| Accept | `application/json, text/javascript, */*; q=0.01` |
| User-Agent | 部分较旧的 Chrome、Firefox 或 IE 浏览器标识 |
| Connection | `Keep-Alive` |

其中，User-Agent（UA）就是客户端向服务器声明的浏览器身份信息。冰蝎内置了一些较旧版本的浏览器 UA，例如 Chrome 89、Firefox 87、IE 11 等。如果当前环境中的请求长期使用这些旧版本标识，可以作为辅助判断依据。

> 但要注意：这些字段都可以被修改，单独出现某一个特征，并不能直接认定为冰蝎。

### 3. 请求体和响应体都是加密数据

这是冰蝎最值得关注的特征之一。正常业务请求通常能看到 JSON、表单字段或其他有意义的内容，例如 `username=admin&password=123456`。而冰蝎默认协议下，请求体通常是 **AES 加密后再经过 Base64 编码**的数据，看起来像一串没有明显语义的字符。

AES 是一种常见的对称加密算法，可以简单理解为：通信双方使用约定的密钥对数据进行加密和解密。由于 AES 采用分组加密，解码 Base64 后得到的密文长度通常需要满足 16 字节的整数倍。

因此，反复出现的 POST 请求、无明显语义的加密数据，以及符合 AES 分组长度特征的密文，值得重点关注。

## 四、使用 Wireshark 如何进行研判？

拿到流量包后，可以按照下面几个步骤进行分析。

### 第一步：过滤 POST 请求

在 Wireshark 过滤栏输入：

```
http.request.method == "POST"
```

重点观察：请求目标是否为 `.php`、`.asp`、`.ashx` 文件；同一个 URI 是否在短时间内被反复访问；请求来源是否为可疑外部 IP。

也可以使用组合过滤器：

```
http.request.method == "POST" &&
(http.request.uri contains ".php" ||
 http.request.uri contains ".asp" ||
 http.request.uri contains ".ashx")
```

### 第二步：检查 HTTP 请求头

重点查看以下字段：`Content-Type` 是否为 `application/x-www-form-urlencoded`；`Accept` 是否符合冰蝎默认特征；`User-Agent` 是否出现在冰蝎内置 UA 列表中；`Connection` 是否为 `Keep-Alive`。如果多个字段同时符合默认特征，就可以提高可疑流量的优先级。

### 第三步：分析请求体

选中可疑 POST 数据包，展开 HTTP 层，查看请求体内容。也可以右键数据包，选择 `Follow → TCP Stream`，查看完整 TCP 会话。

如果请求体是一串无明显语义的字符，且没有正常表单字段，就需要进一步分析。对于 Base64 数据，可以提取后进行解码，再检查解码后的密文长度是否为 16 字节的整数倍。

> **注意：** 这里检查的是 Base64 **解码后的密文字节长度**，而不是直接要求 Base64 字符串长度为 16 的倍数。

### 第四步：检查服务器响应

找到对应的 HTTP 响应，重点观察：状态码是否为 200；响应体是否同样是不可读的加密数据；请求与响应是否呈现持续交互的模式。

冰蝎 4.0 默认响应体也采用 **AES-ECB** 加密后再进行 Base64 编码。如果请求和响应都呈现类似特征，且目标 URI、请求头也符合冰蝎特征，就更值得怀疑。

### 第五步：分析请求行为

不要只盯着单个数据包，还要观察整个通信过程：

* 是否在短时间内多次 POST 到同一个 URI？
* 是否没有正常的页面浏览和静态资源请求，只有反复的 POST 交互？
* 是否存在请求较短、响应较大的情况？
* 不同请求的密文长度是否变化，但解密后的密文仍符合 AES 分组特征？

这些行为组合起来，比单独检查某一个请求头更有价值。

## 五、如何进一步确认？

如果需要更深入地确认，可以尝试使用默认密钥进行解密验证。手册中给出的默认 AES 密钥为：

```
e45e329feb5d925b
```

可以提取请求体中的 Base64 数据，先进行 Base64 解码，再尝试使用 **AES-128-ECB** 解密。如果成功解密并得到可读的代码或命令内容，就能为冰蝎默认配置提供较强的确认依据。

但如果解密失败，也不能直接排除冰蝎。因为攻击者可能修改了连接密码或自定义传输协议。

## 六、哪些情况容易误报？

并不是所有 POST 请求和加密数据都是冰蝎。

| 场景 | 区分思路 |
| --- | --- |
| 正常 API 接口 | 检查是否存在正常的 JSON 结构和业务字段 |
| 文件上传接口 | 关注是否使用 `multipart/form-data` |
| Base64 图片或文件 | 检查是否存在正常的数据格式、MIME 信息 |
| 正常长连接 | 结合目标 URI、请求频率和请求体内容判断 |

> 所以，研判时不要因为发现一个旧 UA，或者一个 Base64 请求体，就直接下结论。

## 七、给安全人员的快速研判 Checklist

| 检查项 | 研判重点 |
| --- | --- |
| 请求方法 | 是否以 POST 为主 |
| 目标 URI | 是否指向 PHP、ASP、ASHX 文件 |
| 请求头 | Content-Type、Accept、UA 是否符合默认特征 |
| 请求体 | 是否为无明显语义的加密数据 |
| 密文长度 | Base64 解码后是否满足 AES 分组长度 |
| 响应内容 | 是否返回类似的加密数据 |
| 通信行为 | 是否短时间内反复访问同一 URI |
| 深度验证 | 是否能通过默认密钥成功解密 |
| 入侵路径 | 是否存在前置文件上传或漏洞利用流量 |

## 八、总结

冰蝎最麻烦的地方，不是它使用了 WebShell，而是它通过加密通信隐藏了攻击者的操作内容。但**加密并不意味着没有痕迹**。

在实际流量研判中，我们可以重点关注三个方向：

* **第一，看请求**：是否反复 POST 到同一个 WebShell 文件。
* **第二，看内容**：请求体和响应体是否呈现加密数据特征。
* **第三，看行为**：是否存在持续、异常的交互模式。

最后需要强调：冰蝎支持自定义协议，默认 UA、请求头和加密特征都可能被修改。因此，流量特征只能作为发现线索，最终还需要结合服务器日志、WebShell 文件、进程行为以及前置攻击记录进行综合判断。

对于安全运营人员来说，真正重要的不是记住某一个固定特征，而是学会从**请求、内容和行为**三个层面还原一次可疑通信。
