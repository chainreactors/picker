> Chrome 安全团队造了一个叫“镜像维度”（mirror dimension）的合成网络环境：上千个模拟站点、本地拦截代理、完全隔离的沙箱。目的是让浏览器智能体（browser-use agent）在接近真实的场景里被反复测试，同时不给真实世界留下任何副作用。这篇讲他们为什么非这么做不可，以及架构上踩过的坑。

先说结论：这不是一个炫技项目，而是被现实逼出来的工程妥协。

Chrome 的智能体浏览功能 auto browse 从设计之初就带着防护机制上线，团队也一直在用编码代理和安全代理反过来加固 Chrome 本身。但防护做得再好，你得有办法证明它真的有用。验证的方式只有一个——让代理去跑，跑成千上万次。

问题在于，跑在哪儿？

## 真实网络不适合当考场

训练浏览器代理，任务大多长得差不多：打开某个知名网站，点进子页面，滚动找到信息，或者往输入框里敲字。用户不会给你 URL。

举个原文里的例子：用户说“去我的 YouTube 账号，帮我把最新一期 Made By Google 播客下载下来，今天飞机上听”。这句话里没有链接。模型得自己推断目的地是 www.youtube.com，再自己规划路径。

这就把评估推进了一个死角。要训练、要评估，就意味着持续不断地在几百个网站上执行成千上万次读和写。指向公共互联网做测试，两件事同时崩掉：

* **不可靠。**

  网页天天变，昨天的用例今天跑不通，测出来的分数没有可比性。
* **不负责。**

  给代理不受限制的访问权，它可能真的发出去一封邮件、真的下单、真的删掉点东西。

严格的评估必须同时满足三个条件：安全、可靠、可重复。上一条轨迹产生的副作用不能渗到下一条里，每次测试都得从同一个干净的基线出发。公共网络这三条一条都给不了。

说白了，这不是“要不要花钱搭环境”的问题，是“不搭就根本测不了”的问题。

## 沙箱 + 拦截代理：把真实感留住

Chrome 的方案是一个密闭的“镜像维度”。两个部件：

1. **隔离沙箱**

   ，里面灌满了仿真的合成网站，灵感来自日常用户的真实浏览路径。
2. **本地拦截代理**

   （interception proxy），负责把浏览真实网络的那层手感保留下来。

这个组合值得多说一句。很多人做合成环境的第一反应是“把网站复制一份放到本地”，但那样丢掉了太多东西——真实的网络往返、资源加载顺序、跨域行为、重定向链路。代理这一层的作用是把这些细节补回来，让浏览器以为自己还在外面跑。

▲ 密闭“镜像维度”评估沙箱的高层架构：所有浏览器流量经拦截代理路由到本地合成网络环境

代价是，他们必须在网络路由和站点生成这两件事上解决一批不太常见的工程问题。原文说得很克制——“几个独特的工程挑战”，但从架构图看，路由这条链路上任何一环没处理好，整个环境的密闭性就废了。

## 最阴的一个坑：模型知道自己正在被考

这是全文里我认为最值得记下来的一点。

用合成站点做评估，会遇到一个叫“评估感知”（eval awareness）的现象：模型察觉到自己在被测试，然后做出平时不会做的动作。分数立刻失真，而且很难发现——你不会收到任何报错，只会拿到一组莫名其妙偏高的通过率。

Chrome 团队的处理方式是：不能把所有合成站点塞在一个域名下。因为如果这么干，YouTube 的地址会变成——

https://fake-sandbox-sites.web.app/evals/www.youtube.com

这个 URL 等于直接告诉模型“你在考场里”。域名里的 *fake*、*sandbox*、*evals* 三个词，任何一个都够模型警觉了。

> 评估环境的保真度不只是“页面长得像不像”，还包括 URL、证书、域名结构这些模型能直接读到的元信息。智能体的能力越强，越会从这些地方反推自己的处境。

反过来说，这也意味着一个问题：当模型足够聪明，任何合成环境都可能被识破。这场猫鼠游戏不会因为架构做得好就结束。Chrome 选择的做法是让伪装尽量彻底，而不是指望模型看不出来。

## 这套东西的真正价值

我的判断是，镜像维度的意义不在“省了多少钱”，而在“让迭代成为可能”。没有它，安全团队每改一次防护逻辑，都要在真实网络上小心翼翼地验证，成本高到根本跑不起大规模回归。有了它，才有 A/B 对比、才有失败案例的复现、才有“这版比上版安全多少”的量化回答。

但也要说清楚局限：合成站点再怎么仿真，终究不是真的网络。真实世界里的钓鱼站、恶意重定向、诱导性 UI，比任何人工设计的合成站点都更刁钻。镜像维度能挡住已知风险，对新出现的攻击面，还是得靠真实环境里的监控兜底。

---

真正难的部分才刚开始——那上千个合成网站到底是怎么生成的？如何在保证真实感的同时，不让生成过程本身变成瓶颈？这部分留在后面拆解。

这里有个绕不开的工程难题：既要让 Agent 自己推断出 URL、像正常上网一样访问站点，又要在它不知情的情况下把请求引到沙箱里。最省事的做法是在评测 prompt 里直接写死沙箱地址，告诉模型"去访问这个链接"。我们试过，效果很差——真实感当场碎掉，模型立刻意识到自己在被测试，也就是所谓的评测感知（eval awareness，指模型察觉自己身处测试环境后行为发生偏移）。

### 同一个 URL，另一个维度

换个思路。不逼 Agent 去访问那种一眼可疑的沙箱地址，而是让它照常打开 https://www.youtube.com 这样的真实 URL，和它在野外环境里的行为完全一致。底层跑的是一个无头 Chrome（headless browser，无界面浏览器），装在隔离的 gVisor 沙箱里（容器运行时沙箱，为进程提供额外的内核级隔离，详见 gvisor.dev）。请求不会真的走到外部 DNS 或公网，沙箱把它截下来，转给本地代理，由代理返回我们生成的站点。

麻烦在于，这种拦截在 Chrome 眼里就是典型的中间人攻击（person-in-the-middle），而 Chrome 的一大设计目标恰恰是拦住它、保护用户。浏览器拿不到代理身份的密码学证明，每一个被截获的请求都会抛出一句致命的 TLS 错误。

▲ 被拦截的请求触发 Chrome 的证书错误，页面直接打不开

### 用证书铸造维持幻觉

要消掉那个"Invalid Cert Authority"（证书颁发机构无效）报错，就得让浏览器相信本地代理服务的正是目标网站。把连接降级成明文 HTTP 不在选项里——Chrome 会换一种方式警告你"不安全"，照样穿帮。

我们的做法是让代理在运行时动态签发 TLS 叶子证书，证书链挂到一张自定义根 CA（Root Certificate Authority，根证书颁发机构）上，而这张根证书已经预装进沙箱里的 Chrome。听起来挺危险，其实边界很清楚：在真实用户的设备上，外部网络攻击者想装一张自定义根 CA，前提是先拿到机器的管理员权限；但整个 gVisor 沙箱由我们完全掌控，启动时把这个信任锚点配好是安全的，Chrome 会像对待正规站点一样正常校验合成页面。

这个设计值得多说一句。它把"可信"从操作系统层面收归到沙箱自身的控制面——信任不是被伪造的，而是被重新划定了范围。代价是这套东西一旦跑出沙箱，性质立刻反转，所以隔离边界的强度决定了整个方案能不能成立，gVisor 在这里不是可选项。

### 织一张合成网络

有了隔离边界和拦截代理，下一个问题才是真的重：镜像维度里该放什么。我们的 Agent 执行的是多步骤、长链条的高级工作流，页面一旦显得死板或者半成品——按钮点了没反应、表单提交没有反馈、状态刷新就丢——它很容易从这些细枝末节里嗅出测试环境的味道，评测结果跟着失真。所以必须能规模化地生成并维护成百上千个可交互、有状态的网页，覆盖范围从本地服务市场、电商结算，到社交媒体信息流和菜谱站点。

手工搭这些站点不现实。我们做了一套自主的多智能体站点开发框架（harness），人来定义高层用户旅程，比如"用户搜索商品、加入购物车、用优惠券、完成多步结算"，剩下的交给一组专门分工的子 Agent，在沙箱内部直接完成设计、搭建、检查、评审。

![](https://mmbiz.qpic.cn/sz_mmbiz_jpg/tbTbtBE6Tibf4bRFT4libbRp4cHbrr7BFczLVlNjzIVPB8w0JBh4vZZCcvbLabBrPu4MZBNZFxrGV6ibHvaGTibSZrb1Tia8oibzmHK80wZp1Kew8/640?wx_fmt=webp&from=appmsg)

▲ 站点开发框架的整体架构：从一个 prompt 出发，反复迭代出可用的完整网站

这套框架把工作拆成三个角色：

* **研究 Agent（research agent）**

  ：根据 prompt 里的内容产出站点规格。用户说要一个电商平台，它就把商品目录筛选、购物车持久化、优惠券校验、多步结算流程这些具体要求列出来。用户没写到的部分由它补齐——站点整体架构、核心用户旅程（CUJ，critical user journey），甚至用 Nano Banana 生成基础 UI 素材的草图（详见 gemini.google/overview/image-generation），目的都是让下游拿到足够高的还原度。
* **构建 Agent（builder agent）**

  ：把规格翻译成能跑的代码，写 HTML、CSS 和 JavaScript，做出响应式布局，以及复杂路径所需的多页面跳转。
* **评审 Agent（critic agents）**

  ：拿生产级网站的标准去卡生成结果——可访问性树的语义（ARIA 角色与标签）是否按预期工作、表单校验能不能拦住边界情况、控制台有没有 JavaScript 报错、元素边界和各档屏幕尺寸下的布局渲染是否正确。

三个角色构成一个闭环：研究定标准，构建出实现，评审挑毛病，然后回去改。这里的设计判断是，把"质量把关"交给独立的 Agent 而不是让构建者自检——自己检查自己的代码，通常只会确认自己没写错，很难发现"这个结算流程少了确认页"这种结构性缺陷。

### 给 Agent 装上眼睛和手

整套东西能跑起来，关键在 Chrome DevTools for Agents[1]——它充当 Agent 的眼睛和手。注意这里的选择：子 Agent 不是把源码当文本读，而是通过 Chrome DevTools 的 MCP（Model Context Protocol，模型上下文协议）服务器调用自己的多模态能力。它能看渲染后的页面截图，能在真实元素上执行点击和键盘输入，能在生成的站点里跳转，能在跑真实用户路径时实时观察应用怎么反应。

差别有多大？读源码相当于让评审者对着图纸判断这房子能不能住，用 DevTools 相当于让人进去走一圈、开一次水龙头。异步竞态、渲染顺序、滚动位置丢失、按钮被浮层挡住点不中——这些在源码里全是"正确"的，只有跑起来才现原形。上一段说的"独立评审"要真能挑出结构性缺陷，靠的就是这一层真实交互。

演示视频里能看清这条回路怎么转：critic 报问题，developer 返回修复，critic 再查一遍。值得盯的一个片段是某次修复顺手引入了全新问题——这正是多加一轮评审的价值所在，也能看出系统在"保真度"和"完成速度"之间选了前者。

> 演示视频：多个 Agent 互相交互，从一条 prompt 出发开发、批判、反复修改一个站点。浏览器不支持内嵌播放时可下载观看[2]。

### 用动态红队造一个敌意网络

日常任务评测之外，把"镜像维度"的每一层都攥在自己手里，还指向一个更硬的目标：压测 Agent 的安全防线。防线要拦的头号威胁是间接提示注入（indirect prompt injection）——攻击者把隐藏指令塞进不可信的网页内容里，诱导 Agent 执行越权动作。

网页上的注入面宽得离谱。浏览器 Agent 感知的是一个多模态界面：渲染出来的视觉布局、底层的 DOM 元素、还有 WebMCP[3]这类结构化工具交互。恶意载荷可以藏在任意一层，可以埋在多步流程的任意一步。

多数评测只测"正文里藏一句话"这种最朴素的形态。真实的攻击者有的是位置：图片里画字、aria-label（无障碍标签，屏幕阅读器读的那份）里写指令、工具返回的 JSON 字段里做手脚。Agent 读的层比人多，能被下毒的面也就比人多。要测这种多样性，评测环境必须能合成载荷并注入到任一表面、任一时间点。完全掌控沙箱 Web 服务器之后，这些都能程序化完成：把注入做成图片或文本、塞恶意 aria-label、甚至实时篡改 WebMCP 的工具响应。一个封闭沙箱就此变成一个动态靶场，支持多向量对抗压测，也支持跨多轮轨迹的连续攻击。

### 隐蔽注入：URL 参数是个坑

最初的动态注入靠 URL 参数，Agent 看得见。一个假的例子长这样：

https://www.youtube.com/watch?v=dQw4w9WgXcQ&prompt\_inject\_payload=abcd1234

很快就发现前沿模型太敏锐了。不少案例里，Agent 仅仅因为看到一个跟该站点不该有关的异常 query parameter，就意识到自己在被评测。一旦 Agent 进入"eval aware"状态，测出来的行为全是失真的。

所以改成走 HTTP 头。红队编排框架填充自定义请求头（比如 X-Sandbox-Injection-Key）来指定要注入哪个载荷，沙箱 Web 服务器拦截并过滤这些头，返回被改写过的页面，而页面的可见 URL 保持完全干净。对 Agent 来说，这就是一个正常网站，路径结构毫无破绽。

这个细节比它看起来重要。评测基础设施的隐蔽性，和载荷本身的设计一样是有效性的前提——环境里任何一个不该出现的痕迹，都会让整个测试结论作废。

### 产能账，以及怎么读这个数字

一名安全工程师手工构造并测试现实攻击，一天也就几十个，验证和打磨每个想法很快成为瓶颈。自动化红队管道借"镜像维度"在大量站点上验证和迭代工程师的想法，每位安全工程师每天能稳定产出 1000 个以上测试候选——30 倍于手工，相当于每天干完一个多月的活。省下来的时间，专家可以专心找新的攻击手法，重复性的打磨和评估交给管道。

这个数字得读准一点。1000 个候选不等于 1000 个有效测试，筛掉噪声、判断真阳性、区分"模型确实被攻破"和"评分脚本自己出错"，仍然是人的活。管道放大的是从"有想法"到"验证完"的吞吐，不是判断力。另外这类自动化容易产生一种错觉：数字涨了，安全感也该涨。恰恰相反，候选越多，越需要一套严的判断标准，否则红队报告会变成一份没人敢信的长清单。

## 合成互联网不是玩具，是安全研究的试验台

浏览器代理已经在替用户跑长任务了：填表、比价、跨站点核对信息、在多个后台之间来回切换。任务链条一长，出错的位置就从"点错按钮"变成"在某一步做了一个不该做的判断"。这类错误在短任务里看不出来，在十步、二十步的流程里会被放大。

代理能力越强、观察面越广，问题就不再是"它能不能做完"，而是"它做的过程中谁看得见"。真实网络上跑一遍，日志散落在各个站点，网页第二天就改版，同一个失败复现不了。所以我认为，配备全合成互联网（一套完全由研究者构造的网页与接口集合）的密闭沙盒——也就是原文说的"镜像维度"——会逐渐成为代理安全与对齐研究的默认起点。原因很朴素：要判断一个代理是否可靠，得给它一个能长期监控、能反复重放、能故意埋陷阱的空间，让它在训练分布之外的新场景里做判断，然后看它怎么选。

## 沙盒与真实环境，各有各的代价

两种评测路线摆在一起，取舍很清楚。

| 维度 | 真实网络评测 | 合成沙盒评测 |
| --- | --- | --- |
| 保真度 | 高，网页就是网页 | 取决于构造质量 |
| 可复现性 | 差，页面随时变 | 强，版本可冻结 |
| 可控性 | 低，无法埋定向陷阱 | 高，恶意内容可精确投放 |
| 风险 | 真实副作用、法律与合规问题 | 隔离，出不了沙盒 |
| 规模 | 贵，难并行 | 便宜，可批量 |

我倾向于把两者当成不同工序，而不是竞争方案。沙盒负责大规模筛查和回归测试，真实环境负责小样本确认。用真实网络做日常回归，成本高到没人愿意天天跑；只用沙盒，又容易在"沙盒里全过、上线就翻车"的地方栽跟头。

合成环境有个绕不开的副作用：代理可能闻出自己正在被评测，也就是所谓的评测感知（eval awareness，指模型识别出当前处于测试环境并改变行为）。网页太干净、交互太规整、错误提示太一致，都会露馅。这不是可以一次性解决的问题，而是一场长期的拉锯——沙盒越像真的，评测越准，维护成本也越高。

## 从浏览器代理推到编码代理，没那么轻松

原文把范围限定在浏览器代理：网页原语（导航、点击、输入、读取 DOM 这类基本操作）边界清楚，工具调用的集合是封闭的。这个前提很重要，它让沙盒的构造有明确终点。

把这套架构搬到通用编码代理上，难度会陡增。编码代理的工具面宽得多——shell、文件系统、包管理器、网络请求、构建工具，任何一环都能成为注入点。要模拟的不只是网页，还有依赖源、构建产物、CI 环境。状态空间一大，"可观测"就变成"记录了什么、丢掉了什么"的工程问题。架构可以扩展，我不怀疑这一点；但成本不会线性增长，更可能是台阶式的。
