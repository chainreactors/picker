嵌入式发行版的分析![图片](https://mmbiz.qpic.cn/mmbiz_jpg/NGIAw2Z6vnLKuKAwMiaYedpTAYugKibaTBsHzf5pDuztECgfIgOfpG5DRF31jzhosMEj23dlx186q0zgLaIZj9lA/640?wx_fmt=other&wxfrom=5&wx_lazy=1&wx_co=1&randomid=2c2qx2ig&tp=webp#imgIndex=2)**** 一个带有 Python Software Foundation 有效签名的解释器，是否就意味着整套运行环境可信？这个样本给出的答案是否定的。攻击者几乎没有碰那些最容易被检查的 EXE 和 DLL，而是把 CobaltStrike Beacon 加载逻辑塞进了解释器启动时默认读取的标准库。 ![图片](https://mmbiz.qpic.cn/mmbiz_png/NGIAw2Z6vnLSsTccx7j0fJVU0OOoqKA8lvpAJHElQA6DiaJniaZb0daO3Kppz9ndV9Z2hHsjMuH61r2hu0jesGSg/640?wx_fmt=png&wxfrom=5&wx_lazy=1&wx_co=1&randomid=hhvjiwep&tp=webp#imgIndex=3) 一、最危险的伪装，是大部分文件都是真的 样本目录看起来与官方 Python 3.10.9 Windows 嵌入式发行版高度一致：python.exe、pythonw.exe、python310.dll、\_ctypes.pyd 以及 VC++ 运行库一应俱全。本次静态核验显示，目录中的 Python 二进制均带有 Python Software Foundation 的有效签名，两个 VC++ 运行库也带有 Microsoft 的有效签名，文件版本信息同样指向 Python 3.10.9。 这恰恰构成了它的迷惑性。代码签名只能回答“这个二进制文件是谁签的、签名是否完整”，却不能证明旁边的压缩标准库没有被替换。真正的异常位于标准库python310.zip。 ![](https://mmbiz.qpic.cn/mmbiz_jpg/Zjic54DsBHbEqPZffNBboqtIk3eLMZT0dbZ1Uj1ELv2yKx6qyialUkyef0BNaV40xdoDweSAyBseA3LnY06sEPYGOzd30wJ7ssJQklF45xoAg/640?wx_fmt=jpeg&from=appmsg) 图注：恶意入口位于 python310.zip 中启动时自动导入的 site.pyc 从文件树可以看到，目录中没有额外出现名为 loader.py 或 payload.bin 的可疑文件。攻击者保留了嵌入式运行时的常见结构，再把载荷藏进 python310.zip。解释器启动后读取标准库时，恶意代码便与正常初始化逻辑一起进入内存。 ![图片](https://mmbiz.qpic.cn/mmbiz_png/NGIAw2Z6vnLSsTccx7j0fJVU0OOoqKA8lvpAJHElQA6DiaJniaZb0daO3Kppz9ndV9Z2hHsjMuH61r2hu0jesGSg/640?wx_fmt=png&wxfrom=5&wx_lazy=1&wx_co=1&randomid=hhvjiwep&tp=webp#imgIndex=3) 二、431 KB 的 site.pyc，为何是一记重锤 将官方版和篡改版解压目录中的 630 个文件逐一计算 SHA256 后，文件名集合完全一致，只有 site.pyc 的内容不同。官方文件为 11,886 字节，修改时间为 2022 年 12 月 6 日 20:26:24；篡改版为 431,200 字节，修改时间为 2025 年 11 月 30 日 15:53:36，体积放大约 36.3 倍。官方模块包含 31 个代码对象，篡改版多出 1 个混淆加载函数；顶层字节码也由 300 字节增至 350 字节。 ![](https://mmbiz.qpic.cn/sz_mmbiz_jpg/Zjic54DsBHbGzlXoSWF58tm1LSc0kCk2UCqDs2icj2fwyAchVN8SgIpTTNmw88GqOJIR1yPPpaLu7gvcntHOOF0OvPN2qY6lFQ3PN9TmjB51g/640?wx_fmt=jpeg&from=appmsg) 图注：官方版与篡改版 site.pyc 的静态基线对比 PYC 头部也留下了重编译痕迹：官方文件采用基于源文件哈希的校验模式，篡改版改为基于时间戳的模式。篡改版头部记录的编译时间为 2026 年 1 月 28 日 09:55:28，与文件系统显示的 2025 年 11 月 30 日并不一致。这说明样本至少经历过重新编译或再次封装，单一时间戳不能直接当作攻击发生时间。 site.pyc 的位置比它的体积更关键。Python 正常启动时会自动导入 site 模块，用于处理路径、用户目录和 site-packages。攻击者把恶意逻辑拼接到这个模块中，就能让用户在没有运行额外脚本、没有看到明显命令行参数的情况下触发载荷。 使用独立的 Python 3.10 解释器，以 -I -S 模式仅对字节码做反序列化和反汇编，可以看到篡改模块顶层新增 base64、ctypes、encoded\_code、b64decode、bytearray 等名称，以及高度混淆的函数名。顶层指令导入两个模块、解码一段 409,612 字符的 Base64 数据，并立即调用新增函数。 新增函数再次对 encoded\_code 做 Base64 解码，将 3,796 个字符还原为 2,847 字节的 Python 代码，然后通过 exec(decoded\_code, globals()) 展开下一层。对这段文本继续做静态解码，可以直接看到 ctypes.WinDLL、VirtualAlloc、RtlMoveMemory、CreateThread 和 WaitForSingleObject；另一段 Base64 则还原为 307,209 字节的二进制载荷，开头具有连续的 0x90 NOP 指令。 ![](https://mmbiz.qpic.cn/sz_mmbiz_jpg/Zjic54DsBHbHjicTzYlZs3fib9iccaqbf4icpWYibIkODdUPW1gibdKLMXg6tAB6xCLgrzzibyZ5VV5s719pXNJPrSiaakqfHLlLhhzgnXDrPs8emibbI/640?wx_fmt=jpeg&from=appmsg) 图注：PYC 反汇编与静态解码得到的关键加载指令 这组证据说明，exec 不是孤立的可疑字符串，而是三层加载链的枢纽：第一层利用 site 模块的自动导入获得执行机会，第二层解码并展开内层 Python 代码，第三层再把 Shellcode 复制到可执行内存并创建线程，整个过程中不需要额外的脚本入口。 ![](https://mmbiz.qpic.cn/mmbiz_jpg/Zjic54DsBHbHoX2oZDqXHORzjgWsYoBBjzwO6Ey9zFkDsELURlJlnvZLw1r90WuVLI3DBEgzia2D6zJr8mlvJz0BeeI0kjUGKQI0OqyRhBJ04/640?wx_fmt=jpeg&from=appmsg) 图注：从解释器启动到 C2 通信的完整触发链 ![图片](https://mmbiz.qpic.cn/mmbiz_png/NGIAw2Z6vnLSsTccx7j0fJVU0OOoqKA8lvpAJHElQA6DiaJniaZb0daO3Kppz9ndV9Z2hHsjMuH61r2hu0jesGSg/640?wx_fmt=png&wxfrom=5&wx_lazy=1&wx_co=1&randomid=hhvjiwep&tp=webp#imgIndex=3) 三、从静态异常到真实 C2：证据如何闭环 解码后的代码通过 ctypes 获取 kernel32.dll，并设置 VirtualAlloc、RtlMoveMemory、CreateThread、WaitForSingleObject 等函数原型。其基本流程是申请内存、复制 Shellcode、创建线程并等待执行。此外，样本还使用了 NtProtectVirtualMemory 将相关区域调整为 PAGE\_EXECUTE\_READ，这种“写入后再转为可执行”的方式比一次性申请 RWX 内存更不显眼。 3.1 为什么它容易绕过“只看文件”的检查 ![图片](https://mmbiz.qpic.cn/mmbiz_png/NGIAw2Z6vnLSsTccx7j0fJVU0OOoqKA8WFHRW8Evk0zcqAPJSmSRktqm69UXCNGtz8L1sz1g1Wg3sEYViamG90Q/640?wx_fmt=png&wxfrom=5&wx_lazy=1&wx_co=1&randomid=ywon68xm&retryload=2&tp=webp#imgIndex=5) 第一，解释器和核心 DLL 本身没有明显异常，白名单或签名信任策略很容易放行。第二，触发点位于 site.pyc，属于解释器的默认启动流程，不需要单独的恶意脚本文件。第三，最终载荷以 Shellcode 形式在内存中运行，不必落地为带有 MZ 头的 PE 文件。第四，通信使用 HTTPS，并将请求伪装成常见的 JavaScript 资源路径 /v3/js/jquery-3.3.1.min.js。 因此，这不是简单的“恶意 Python 脚本”，而是一种针对运行时信任边界的投毒：攻击者借用合法解释器完成加载，借用标准模块自动导入完成触发，再借用内存执行和 HTTPS 完成隐蔽通信。 3.2 动态证据与静态推断相互印证 ![图片](https://mmbiz.qpic.cn/mmbiz_png/NGIAw2Z6vnLSsTccx7j0fJVU0OOoqKA8WFHRW8Evk0zcqAPJSmSRktqm69UXCNGtz8L1sz1g1Wg3sEYViamG90Q/640?wx_fmt=png&wxfrom=5&wx_lazy=1&wx_co=1&randomid=ywon68xm&retryload=2&tp=webp#imgIndex=5) 四、防守不能只校验可执行文件 面对这类样本，最有效的检测不是寻找某一个永远不变的域名，而是把文件完整性、进程内存和网络行为串起来。 文件侧：对下载的发行包做整体 SHA256 校验，并与可信源发布的哈希或组织内部基线比对；同时监控 python310.zip 内标准库的体积、时间戳和哈希。仅校验 python.exe 的签名远远不够。 行为侧：关注 python.exe 或 pythonw.exe 调用 VirtualAlloc、NtProtectVirtualMemory、CreateThread 的组合，尤其是出现 RX 内存、匿名可执行区域和异常线程起始地址时。 网络侧：将 Python 进程、DNS 查询和 TLS 连接做关联分析。一个嵌入式解释器在启动约几十秒后访问陌生域名，并请求伪装的 jQuery 路径，本身就值得提升风险等级。 结语：签名可信，不代表供应链可信 这个样本最值得警惕的地方，不是它使用了多么新奇的 Shellcode 技术，而是它准确利用了我们的验证习惯：看到熟悉的目录结构、官方版本信息和有效签名，便默认整套软件可信。 真正可靠的软件供应链防护，需要把信任从“某个 EXE 是否签名”扩展到“整个包是否来自可信渠道、内部文件是否符合基线、运行行为是否符合预期”。当解释器本身成为载荷的掩体时，只有包完整性和行为检测同时在场，才能识别这个看似正常的 Python。
