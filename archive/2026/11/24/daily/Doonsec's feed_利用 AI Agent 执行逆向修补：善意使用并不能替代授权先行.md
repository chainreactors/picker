2026年简直就是漏洞年。拜 AI 所赐，互联网各类基础设施都爆出高分漏洞，各种 XX2SHELL 层出不穷，连笔者都被牵涉其中而应急修补了三套网站系统。而且，不仅是开源代码发现漏洞，即使闭源软件，在以 REA 为代表的各类 AI Agent 逆向工程工具的作用下，也迎来了漏洞爆发潮。

REA 这类工具通过把传统人手工具与大模型相结合，能够自动完成反编译、控制流还原、接口推断乃至代码生成，使“在没有源代码的情况下理解并修改已部署软件”这件事从少数安全专家的能力，逐渐变为可被普通开发者调用的工程流程。

其实年初已经有人实现了让 OpenClaw 操作 Kali Linux 执行渗透测试，REA 实质就是进一步的提高版：不仅完成渗透，还通过逆向还原继而实施修补。

但在笔者职业身份的角度来看，真正需要关注的是当这种能力被用于修补加固、漏洞缓解或运行时热修复时，组织是否仍保有清晰、可审计、可追责的合规边界。

| **一、法律对逆向工程的例外定义** |

首先需要澄清一个常见误解：逆向工程并非当然违法。合法取得产品并通过独立技术手段进行分析，在一定条件下可作为商业秘密侵权的抗辩事由。我国《著作权法》第五十条亦为安全性能测试、加密研究和软件反向工程研究设置了技术措施例外。

但“存在例外”不简单等于“可以自由使用”。EULA 中禁止反编译、反汇编、逆向工程的条款，在司法实践中通常仍会被作为合同义务审查。若分析对象属于闭源商业软件，且协议明确禁止逆向，即便动机是安全加固，也可能同时触发违约、著作权侵权、技术措施规避乃至不正当竞争风险。

而且，如果要引用这一条，必须连其但书内容一起看。第五十条同时写明：避开技术措施，不得向他人提供避开技术措施的技术、装置或者部件，也不得侵犯权利人其他权利。法律豁免的是“避开”这个动作，不是“改软件”这个结果，也即为研究而绕过保护措施这一步可能不追责，并不等于之后的修补措施都被一并兜底。

| **二、笔者的一次实例** |

就实际情况来说，“逆向+修补”的动机和结果是多种多样的。例如笔者在较早之前身兼数职的时候（见：没有资源的情况下如何熬过攻防演练？），就曾应急处置过类似的情况。

事情的起因是上级监管机构在对重点对象执行日常扫描时，发现笔者任职单位部署的某系统的互联网登录页面未明示 ICP 备案号，口头通知立即整改。

熟悉相关监管要求的朋友都清楚，若未能及时修改，将会面临被通报的后果。

笔者通过自身技术能力，快速发掘出该页面在已部署系统内为一 JSP 单元页面，代码未作混淆，因此可立即修改增加 ICP 备案号完成快速修正，迅速消解了事件。

回到本文主题。笔者这个例子会产生如下问题：

1、这是否逆向？

很显然是。因为即使是 JSP 单元是明文代码，对其进行观察和分析即属于逆向。

2、是否违反 EULA？

按 EULA 字面任何修改都是违反 EULA 的。

3、是否侵害厂商知识产权权利？

关键在此。这个问题的答案当然是否定的。因为添加 ICP 备案号不仅和厂商知识产权权利无关，而且实质是该产品的缺陷导致客户陷入被动：ICP 备案的要求已经人所共知多年后，该产品依然没有提供给客户自主设定在登录页面上显示 ICP 备案号的功能。这实际就是置客户于违法风险之中而不顾。

4、是否应该沿常规途径向厂家报 SR 处理？

很显然不能。等到软件系统厂家安排处理完毕（懂的都懂），大概率通报都走完几个上级单位的发文办文流程了，事态已经不可挽回。

到这里就需要引出《计算机软件保护条例》第十六条第三款，这是对修补行为有利的条款：软件的合法复制品所有人“为了把该软件用于实际的计算机应用环境或者改进其功能、性能而进行必要的修改；但是，除合同另有约定外，未经该软件著作权人许可，不得向任何第三方提供修改后的软件”。

鉴于网络安全也同属于使用者的环境因素，所以该法条是给“使用者为适配自己的环境动手改软件”开了个正面口子，但同时也明确收口指出，未经软件著作权人许可，不得向任何第三方提供修改后的软件。

笔者思维的边界同样基于此条：为自用而改，正当性来自作为合法所有人的身份。

就以上分析，在具备条件时，立即在用户一侧主动实施修补是必然的结论。但该做的事情依然不能少：笔者随后也照样向厂家驻场人员说明情况，提交了 SR 并重点指出缺失该项设置的严重性，让厂家自行安排实现设置和显示 ICP 备案号的功能。

| **三、 AI Agent 使情况更复杂** |

而到了现在，情况更为复杂。因为 AI Agent 的出现，改变了传统逆向工程的过程证据结构。

在过去，软件的逆向工程常用“净室开发”证明是独立实现：一组人员分析软件的功能和编写规格说明，另一组人员在未接触逆向获得的代码的情况下按规格说明重新实现软件。这种做法放到逆向修补也是同样可行的。

但 AI Agent 很大程度上改变了这一过程：

如果在同一闭环中完成分析、推断、生成修补代码与注入到运行中的软件执行，这就使“读”和“写”的隔离无法成立。

如果在分析过程中还将二进制片段、接口逻辑、字符串资源发送至外部模型服务，这就无可置疑地引入了第三方，进而难以确证不存在被分析的软件的商业秘密外泄。

如果模型服务商也有自己的专门针对逆向工程的EULA要求，还会因此而衍生出更多合规冲突问题。

即使把工作流程拆分为两套相互隔离的 AI Agent，使用运行在本地的大模型，两套 Agent 之间使用 MARKDOWN 等载体传递设计要求，执行者也依然要面对载体中的信息如何在送出前执行前置审查才能确认不破坏 Clean Room 的要求：因为不审查 AI Agent 的设计就不能100%确保设计信息中不包含逆向获得的代码片段。

| **四、如何合理利用 AI Agent 实施逆向修补** |

在用户一侧如何合理利用 AI Agent 实施逆向修补，实质是一件相当讲究的事情。在笔者观点，除了需要按实施过程的具体属性，结合信息安全 CIA 三属性（重温课本：机密性 Confidentiality、完整性 Integrity 和可用性 Availability）进行区分研究以确定实施方式之外，还应考虑如下必要的实施前准备：

1、预先确定执行逆向的必要性和时效要求。

此项可进一步细分为外部合规监管要求、内部业务运作关键影响和其它共三种情况，简单罗列如下：

* 外部合规监管要求：第一时间直接实施逆行修补，同时通报厂家。
* 内部业务运作关键影响：与厂家商讨获得授权，评估所需时间长度和构成损失程度综合决定是否先执行逆向修补。
* 其它：应先获得授权再实施。

2、预先确定待逆向对象的权属。

此项需要按问题复杂性细分为权属归产品厂商、权属归用户和权属归第三方。

权属归产品厂商是不存在争议的情况。而权属归用户就需要仔细分辨。如果授权文件明确了知识产权整体归用户所有那也没有争议，但有些情况是厂商向客户提供源代码但客户不拥有其知识产权，即仅拥有知识的副本，且还会带有各种限制条款，在执行逆向之前就应对这些限制条款进行拆解以获得对应的授权。

需要十分慎重的情况是权属归第三方，因这种情况多为隐性。典型例子是软件厂商采购了第三方软件组件在自己的产品中嵌入运行，而要修补的对象恰恰就是该组件。这种情况需要先深入追溯确定厂商和第三方之间的权属责任划分。

3、预先确定逆向实施过程中的保密措施

由于要使用大模型执行分析过程，这就因除了本地和云端两种大模型的使用方式。

很显然地如果是使用在本地部署的大模型，那问题必然比引入云端要少。但审慎无论如何都是必要的。因为各种错误的环境配置都可能造成分析过程数据出域。

至于使用云端大模型服务执行逆向过程就要慎重了。不仅传输的途径需要合规受控，不使用任何中转站服务，还需要在法务上先行确认云端服务商在EULA中声明的保密措施和使用限制条款。尤其是待分析对象若包含有用户自身的商业机密，云端执行逆向就成为了新的暴露面，这是要极力避免发生的。这种情况最典型就是待逆向的对象软件没有建立测试数据库，仅有一套生产数据库，于是就在逆向中直接连接生产数据库（毫无疑问这已经是作死行为）或简单地建立一套数据副本用于逆向。

4、确定对修补负载的闭环管理措施

本来在等保中就已经有漏洞和补丁管理的要求，但很明显对于新情况，旧有的管理要求并不能完全覆盖。所以用户并不能等待合规要求更新才考虑执行新的管理措施。

要明确脱离了厂家产生的修补负载是独立于厂家补丁之外的版本线，需要能清晰地和修补对象的版本、厂家补丁的版本等主线关联。在厂家未执行修补但执行了软件升级时，要对已有的修补负载进行校验确认其适用性，及时更新版本关联信息。在厂家正式提供修补补丁进行应用的同时，要撤销修补负载的部署和更新版本关联信息以确定不再使用。所有的文件变更和修补负载均应具备可追溯性，简单说就是留有副本和能进行基于校验和的核验。

如果修复动作本身缺乏授权、未经测试、不可回滚，则所谓“加固”反而可能削弱系统的可管理性与可防御性。

只有在完成以上四项的准备后，这件事才算“出师有名”。

| **五、最终要落到信息系统审计合规评估实务** |

最后把话题升级到信息系统审计实务场景上来。信息系统审计师的立场不能直接否定逆向分析，而是要坚持明确例外、授权先行、边界清晰、证据完整等基本审计原则。

若组织确需对第三方软件开展安全分析，应优先通过厂商漏洞披露渠道、授权渗透测试、隔离沙箱验证和合同化安全例外来处理；对生产环境执行热修补，应坚持厂商签名、变更审批、回归测试和回滚预案。善意动机可以解释行为目的，但不能替代合同授权、技术措施合规和变更治理。目的是在 AI Agent 降低逆向工程门槛的同时要提升执行者对审计责任的认识：

越是容易做到的事，越需要被严格约束。

以下是笔者让 AI 按本文的分析和思路架构，拟了一份逆向修补合规评估清单，供读者参考。

---

AI Agent 逆向修补合规评估清单

适用场景：组织拟使用 AI Agent 或基于AI的自动化工具，对无源代码（或非自主可控代码）的已部署软件进行逆向分析、漏洞验证、修补加固或运行时热修复。

使用方式：本清单按笔者所述“四项实施前准备”为主轴排列，列明隐蔽情形与闭环治理项。任一高风险项未获书面确认时，应暂停进入生产环境。

本清单不替代法务意见。

主轴一 · 逆向必要性与时效分级（准备事项一）

□ 是否已把本次逆向的必要性归入下列三档之一，并留存归因依据？

□ （A）外部合规监管要求：监管通报、限期整改等。判定为第一时间在用户侧直接实施修补，同时向厂家通报，不因等待授权而贻误整改窗口。

□ （B）内部业务运作关键影响：与厂家协商获得授权，并评估"等待厂家所需时长"与"自行修补构成损失程度"后综合决定是否先自行逆向修补。

□ （C）其它一般情形：应先取得授权再实施，不享受时效豁免。

□ 时效豁免仅覆盖"先行动"，不覆盖"不通报"：即便走（A）档，是否仍同步提交 SR / 漏洞告知厂家并留痕？

风险判定：必要性归因缺失、或（B）（C）档未经协商/授权即先行动 → 高风险。

主轴二 · 待逆向对象的权属三分（准备事项二）

（一）权属归产品厂商

□ 知识产权整体归厂商。此时逆向修补的合规性完全取决于授权与法定例外，按主轴一、三、四继续判断。

（二）权属归用户

□ 授权文件是否明确知识产权整体归用户？若是，争议最小。

□ 若厂商仅向客户提供源代码、客户不拥有其知识产权（仅持有一份知识副本）：是否已逐条拆解许可协议中的限制条款（禁止反编译、禁止修改、保密、外发限制等），并在执行前取得与之匹配的授权？

（三）权属归第三方（最需慎重，多为隐性）

□ 待修补对象是否为厂商从第三方采购、嵌入本产品运行的组件？若是，需先追溯确认厂商与该第三方之间的权属与许可责任划分，再决定修补边界。

□ 是否已核查该第三方组件自身的许可证（尤其开源组件 Copyleft / 网络条款）与厂商 EULA 之间是否存在冲突？

风险判定：权属未澄清即修补，尤其落入"归第三方"隐性组件 → 高风险。

主轴三 · 逆向实施过程的保密措施（准备事项三）

（一）本地部署大模型

□ 本地模型权重、插件、依赖库与更新渠道是否可信、可审计？

□ 是否已验证不存在因环境配置错误导致分析过程数据出域（外网调用、遥测、云端兜底、API 回退）？

（二）云端大模型服务

□ 是否不使用任何中转站 / 代理中转服务，传输途径合规受控？

□ 法务是否已先行确认云服务商 EULA 中声明的保密措施与使用限制条款，并确认其自身对"逆向工程"另有无冲突性要求？

□ 待分析对象若含用户自身商业机密：云端执行逆向是否引入了新的暴露面？是否已极力避免？

（三）数据环境隔离

□ 是否已建立与生产隔离的测试数据库？

□ 是否严禁在逆向过程中直接连接生产数据库？无测试库时是否已先建立最小化的数据副本，而不是直连生产？

□ 分析日志、提示词、生成代码与中间产物是否纳入访问控制与留存？

风险判定：向任何外部服务发送未公开协议 / 鉴权逻辑 / 商业机密，或逆向过程直连生产库 → 高风险。

主轴四 · 修补负载的闭环管理（准备事项四）

□ 是否已把"脱离厂家产生的修补负载"视为独立于厂家补丁之外的版本线，不与厂家主线混为一谈？

□ 修补负载是否清晰地与修补对象的版本、厂家补丁版本等主线建立关联标识？

□ 厂家未修补但执行了软件升级时，是否对已有修补负载重新校验其适用性，并及时更新版本关联信息？

□ 厂家正式补丁应用的同时，是否撤销对应修补负载的部署并更新版本关联信息，以确定不再使用？

□ 所有文件变更与修补负载是否均具备可追溯性（保留副本 + 可基于校验和核验）？

风险判定：修补负载无版本线、无校验、不可回滚、随厂家升级未复核 → 中高风险，需管理层书面接受。

主轴五 · Clean Room 在 AI 时代的成立性与证据结构

□ 若在同一 AI Agent 闭环中完成分析、推断、生成与注入，"读"与"写"的净室隔离无法成立——是否已确认此场景不再援引"净室开发 / 独立实现"作为抗辩？

□ 若拆分为两套相互隔离的 Agent、使用本地大模型、以 Markdown 等载体传递设计：是否已对载体信息在送出前执行前置审查，确认不含逆向获得的代码片段？（不审查 Agent 设计即无法 100% 确保设计信息不含逆向代码片段）

□ 把二进制片段、接口逻辑、字符串资源发送至外部模型服务商，是否已承认这无可置疑地引入了第三方，从而难以确证商业秘密未外泄？

□ 被分析样本中可能嵌入 Prompt Injection 指令（诱导模型越界、泄露或伪造授权），分析不可信样本时是否已设护栏？（注1）

风险判定：以"净室独立实现"抗辩但实际为单一 AI 闭环，或载体未经前置审查 → 高风险。

主轴六 · 法务前置审查触发条件

出现以下任一情形，应进入法务前置审查：

□ EULA 明确禁止逆向，但业务仍拟开展分析或修补；

□ 分析对象权属涉及第三方权利人（含厂商嵌入的第三方组件）；

□ 拟向外部 / 云端 AI 服务商发送代码片段、二进制数据或接口逻辑；

□ 拟在生产环境实施热修复、内存修改或运行时注入；

□ 拟对外提供可复用修补负载、逆向结论或把逆向能力封装为工具（触及《网络安全法》第二十七条）；

□ 修补可能影响许可证校验、计费机制、访问控制或数据保护功能。

注1：关于分析样品中嵌入 Prompt Injection 或者其它技术以破坏使用 AI 进行逆向分析的情况，网络上相关讨论已有很多，故本文未涉及，但建议纳入评估。
