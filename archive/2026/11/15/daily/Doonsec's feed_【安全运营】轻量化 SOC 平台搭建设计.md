    在总内存 12GB、全开源、单宿主机虚拟化的约束下，一套 SOC（Security Operations Center，安全运营中心）能否被真正"搭起来并跑通"——不是三个各自为政的工具箱，而是一条从采集、分析到处置建议的完整数据链。本文以三节点实测环境为样本，给出架构设计、组件选型与联动验证的完整链路。

▎三个核心思考

思考一：SOC 的瓶颈不是工具数量，而是数据能否收敛到同一条时间轴。

实测环境中三台设备在 24 小时内共产出 4,017 条告警。这个量级用任何单一日志工具都能存下，真正困难的是：同一次 SQL 注入，在网络层（Suricata）、应用层（ModSecurity）、SIEM 规则层（100610/100630/31103）各留下一条记录，而这三条记录必须能按时间、按源 IP、按目标 URL 对齐。不能关联的多源告警，只是把噪声从三个地方搬到了一个地方。

思考二：开源选型的胜负手不是功能强弱，而是整体部署的成本。

Ubuntu 20.04 仓库无 libnginx-mod-http-modsecurity，Nginx + ModSecurity 路线需要 1 核机器编译近一小时；同版本仓库亦无 suricata 包。最终落地的 Apache + ModSecurity 2.9.3 与 OISF PPA 的 Suricata 8.0.8，功能上并无妥协，但部署成本差了一个数量级。

思考三：联动是否成立，不看"有没有告警"，而看同一次攻击能否在多层的证据互相印证。

第一轮 WAF 验收曾给出 4 个 403，看起来完美——但攻击 URL 打在了不存在的路径上，拦截的是 404。改为「同一页面、正常参数 200 + 恶意载荷 403」的成对基线后，4 组对比全部成立。没有基线的"拦截成功"不可信，没有对照的"联动生效"不成立。

## 1　问题定义与设计约束

本章界定边界：在什么资源约束下、为了什么目标、以什么标准判定"搭成了"。

### 1.1　资源约束下的可行性边界

约束条件来自硬件而非预算：单台 PC 上的 VMware Workstation，可分配给虚拟机的内存上限为 12GB，磁盘为单块 SSD。Wazuh 官方对一体化部署的建议是 4GB 内存起步、8GB 舒适，而 Elastic 官方对 Elasticsearch 的建议是 8GB 起步——这一条直接决定了 SIEM 选型的可行域。

| 维度 | 约束值 | 工程含义 |
| --- | --- | --- |
| 宿主机内存 | 12GB（可分配） | 三节点上限 5.8 + 2.7 + 2.5 GB，留 1GB 给宿主与预留位 |
| 单节点 CPU | 1～4 vCPU | 编译型安装（Nginx+ModSec v3）被排除 |
| 磁盘 | 单盘 48GB / 29GB / 19GB | 告警保留策略必须配，否则两周写满 |
| 网络 | 仅内网 192.168.202.0/24 | 无法依赖云服务、威胁情报订阅 |
| 授权 | 零商业授权 | 全开源，且必须是仓库可装的稳定版 |

### 1.2　为什么"单机全能"方案不成立

一个自然的想法是：Wazuh 一个软件就能采集、分析、存储、展示，为什么还要三台机器？

▎ 不是"一台机器跑不动"，而是"一个角色承担不了两种立场"

从企业网络划分场景来说，一般企业分为生产网络环境和办公网网络环境，生产网环境更多以WAF+HIDS（主机安全）两方面进行覆盖检测响应；办公网环境更多是全流量+主机安全（EDR+杀毒）。

因此架构被拆成"一个分析中枢 + 两个能力前端 + 一个预留响应位"，各角色的故障域互相隔离。

### 1.3　设计目标与验收指标

架构设计如果不预设验收标准，最后很容易变成"装完就算完成"。本项目的验收指标在动手前即固定，且全部可量化：

| 编号 | 验收维度 | 判定标准 | 实测结果 |
| --- | --- | --- | --- |
| A-1 | 平台可用性 | 四服务 active、集群 green、控制台可登录 | 达成 |
| A-2 | 主机检测覆盖 | 文件改动产生 FIM 告警；四类攻击被网络层命中 | 达成（4/4） |
| A-3 | 应用防护有效性 | 同页面正常参数 200、恶意载荷 403 | 达成（4×200 / 4×403） |
| A-4 | 跨层可对账 | 同一次攻击在 SIEM 可按 agent + rule.id 还原 | 达成（4 条证据链） |
| A-5 | 资源可持续 | 三节点连续运行无 OOM，内存余量 > 30% | 达成（余量 63% / 71% / 83%） |

### 1.4　术语与指标口径

| 术语 | 本报告中的定义 |
| --- | --- |
| 中枢 | 承担告警汇聚、规则匹配、存储与展示的节点（.129） |
| 前端 | 部署在被保护对象侧、产生检测或拦截数据的节点（.130 / .131） |
| 联动 | 前端产生的数据在中枢可检索、可分类、可与其它前端交叉比对 |
| 对账 | 同一次攻击在多源日志中按时间戳与五元组可相互印证 |
| 告警等级 | 采用 Wazuh rule.level 0–15，≥10 视为需人工介入 |

## 2　分层检测架构设计

本章给出两套并行的架构视图：物理视角回答"装在哪"，逻辑视角回答"数据怎么流"。

### 2.1　四层参考模型

企业级 SOC 的纵深防御被压缩到三个节点后，仍然需要保留四个功能层，缺一层就意味着对应类型的攻击完全不可见：

| 层 | 回答的问题 | 缺失后果 |
| --- | --- | --- |
| 网络检测层 | 线上流量里有没有攻击特征？ | 端口扫描、横向移动、C2 心跳全部不可见 |
| 应用防护层 | Web 请求是否恶意？ | SQLi / XSS / 命令注入直达业务，且无拦截 |
| 主机检测层 | 主机上发生了什么？ | 文件篡改、提权、异常进程无迹可寻 |
| 分析与存储层 | 上述数据如何关联与追溯？ | 三份日志各自为政，无法还原攻击链 |

### 2.4　信任边界与数据流向

▎ 单节点 SOC 的安全假设必须写清楚，否则它就是新的攻击面

* 三节点均只在内网可达，中枢 9200（索引器）不对全网开放；
* 前端节点不存储任何集中凭据，注册密钥由中枢在 1515 一次性下发；
* 控制台 443 使用自签证书，仅实验环境可接受，生产必须换正式证书；
* 所有前端到中枢的流量走 1514 加密通道，不走明文 syslog（514 端口未启用）。

## 3　开源组件选型

选型章节不列"候选清单"，只记录排除过程——被排除的理由比被选中的理由更有信息量。

### 3.1　SIEM：四选一的排除法

表 3-1　SIEM 候选方案对比

| 候选 | 优势 | 致命短板 | 结论 |
| --- | --- | --- | --- |
| ELK 三件套 | 检索能力最强，生态成熟 | 告警规则与关联分析需自建；官方建议 8GB 起 | 排除（内存） |
| Graylog | 日志聚合体验好 | 无主机检测（FIM/rootcheck）能力，需再加一套 HIDS | 排除（能力缺口） |
| Security Onion | 功能最全，开箱即用 | 发行版级方案，16GB 起步 | 排除（内存） |
| Wazuh 4.14 | 采集/解码/规则/FIM/漏洞/MITRE 一体，5GB 可跑 | 复杂聚合弱于原生 ELK；单节点无高可用 | 选中 |

3.2　办公网场景检测：三类数据，三个组件

| 数据类别 | 问题 | 组件 | 是否可替代 |
| --- | --- | --- | --- |
| 主机事件 | 文件被改？有可疑进程？ | Wazuh Agent（FIM/rootcheck/日志） | 不可替代（联动通道） |
| 网络流量 | 线上有攻击特征？ | Suricata（53,495 条 ET Open 规则） | 不可替代（唯一网络视角） |
| 资产状态 | 这台机器现在长什么样？ | osquery（SQL 查进程/端口/用户） | 可以砍（与 syscollector 重叠） |

▎ 组件不是越多越好，每留一个都要有理由

实测发现 osquery 与 Wazuh 自带的 syscollector 模块在"资产快照"上高度重叠。保留 osquery 的理由只有两个：临时深度排查（一行 SQL 查全机内核模块）与演示"针对快照数据写检测规则"。如果目标是纯检测，砍掉它可省约 50MB 内存与一个维护面。

### 3.3　生产网环境Web 防护

表 3-3　WAF 引擎接入方案对比

| 方案 | 可行性 | 成本 | 结论 |
| --- | --- | --- | --- |
| Nginx + ModSecurity v3 | 需源码编译 ModSec + 连接器 | 1 核机器约 1 小时，成功率不保证 | 排除 |
| Apache + libapache2-mod-security2 | 仓库直装 | 三条命令，秒级 | 选中 |
| 雷池 / BunkerWeb 等自带 UI 方案 | 需 Docker | 1 核 2.5GB 资源吃紧 | 排除 |

装出结果为 ModSecurity 2.9.3 + OWASP CRS 3.2.0（31 个规则文件全量）。拦截引擎与规则集与 Nginx 路线完全同一套，"换 Web 服务器"换的是承载方式，不是检测能力。

### 3.4　选型结论

| 判定维度 | 结论 |
| --- | --- |
| 可装性 | 全部来自 apt 仓库或官方 PPA，无源码编译 |
| 可跑性 | 三节点峰值内存 < 分配值 40% |
| 可维护性 | 配置集中在 6 个文件内，无跨组件依赖 |
| 可对账 | 三类数据统一经 Agent 上行，格式可归一 |

## 4　三套环境的实现与能力边界

本章给出每一层的"装了什么、调了什么、能做什么、不能做什么"。能力边界比能力清单更重要，因为它决定了告警该不该信。

### 4.1　分析中枢（.129）：5.8GB 的生存法则

一体化安装最大的风险不是装不上，而是装完被 OOM 杀掉。本项目做了三处硬调优：

| 调优项 | 默认值 | 调整值 | 原因 |
| --- | --- | --- | --- |
| indexer JVM 堆 | 1GB | 2GB | 减少 GC 抖动，同时给系统留余量 |
| dashboard Node 堆 | 未限制 | 512MB | 控制台进程常驻，不限会缓慢吃满 |
| 告警索引 | 3 分片 + 自动副本 | 1 分片 0 副本 | 单节点副本无意义，纯占磁盘 |

另有 ISM 策略将告警保留期固定为 7 天（wazuh-7d-retention），到期自动删除。没有保留策略的 SIEM，一定会在某个周一早上把磁盘写满。

### 4.2　办公网环境检测（.130）：三类证据的采集面

| 能力 | 配置要点 | 产生的告警 |
| --- | --- | --- |
| 文件完整性 FIM | `/etc` realtime + report\_changes；`/usr/bin` 等 12h 全量 | 文件新增/修改/权限变更 |
| 网络入侵检测 | ens33 抓包、threads 1、HOME\_NET 改内网段 | ET Open 规则命中（4 类攻击） |
| 资产快照 | `<wodle name="osquery">` 托管调度 | 规则 24010（进程/端口快照） |

数据来源：/var/ossec/etc/ossec.conf 配置项 + 24 小时告警实测。

▎ 需要注意的坑：localfile 采集 osquery 结果未成功

绝大多数教程教用 localfile 采 osqueryd.results.log，实测永远不触发 24010——该规则要求 location 以 osquery 结尾，而 localfile 传入的是完整路径。正确写法是启用 agent 自带的 wodle 块（默认 disabled=yes）。这类"配置看起来对、日志也有、就是不告警"的问题，只能靠对着规则定义反查。

### 4.3　生产网环境Web 防护（.131）：拦截模式的三道门槛

| 阶段 | 配置 | 目的 |
| --- | --- | --- |
| 观察期 | `SecRuleEngine DetectionOnly` | 只记录不拦截，收集误报 |
| 排除期 | `SecRuleRemoveById` 置于 CRS 之后（after 目录） | 消除 920350 等环境性误报 |
| 拦截期 | `SecRuleEngine On` | 正式阻断，误报即业务中断 |

▎ 排除规则写在哪，决定它有没有用

SecRuleRemoveById 必须在目标规则加载之后执行。写在 CRS 之前，等于对着还没进场的规则喊话——现象是"改了配置、重启了服务、噪声照旧"。唯一可靠的位置是 Include 链末尾的 after 目录。

### 4.4　能力矩阵：谁不可替代

表 4-3　三套环境的能力覆盖与不可替代性

| 能力 | 中枢 | 主机检测 | Web 防护 | 不可替代者 |
| --- | --- | --- | --- | --- |
| 日志汇聚与规则匹配 | ✅ | — | — | 中枢 |
| 文件完整性监控 | — | ✅ | — | 办公网环境检测 |
| 网络流量检测 | — | ✅ | — | 办公网环境检测（Suricata） |
| Web 攻击拦截 | — | — | ✅ | 生产网环境Web 防护 |
| 资产快照 | 部分（syscollector） | ✅ | — | 二者之一即可 |
| 跨源关联与追溯 | ✅ | — | — | 中枢 |

## 5　联动验证与实测数据

本章只回答一个问题：这套架构到底能不能支撑验证。所有结论均给出来源，可复现。

### 5.1　验收方法论：成对基线与多层对账

| 方法 | 做法 | 为什么必须这样做 |
| --- | --- | --- |
| 成对基线 | 同一 URL、同一会话，仅替换参数为恶意载荷 | 排除"403 其实是 404"这类假阳性 |
| 应用降级 | 靶站安全级别调至 low，应用自身不设防 | 确保拦截来自防护层，而非应用 |
| 多层比对 | 同一次攻击在 ≥2 个数据源留痕，按时间戳比对 | 证明联动而非"各自有日志" |
| 量化收口 | 统计 rule.id 分布，而非只看"有告警" | 证明分类规则真的生效 |

### 5.2　办公网主机侧：四类攻击的网络层命中

向目标主机的临时 HTTP 服务发起四类请求（SQL 注入特征、目录穿越、扫描器 UA、XSS 探测），Suricata fast.log 四条全部命中。

▎ NIDS 检测的是"线上流量"，不是"攻击意图"
