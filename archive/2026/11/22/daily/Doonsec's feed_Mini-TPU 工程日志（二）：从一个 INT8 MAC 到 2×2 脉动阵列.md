MINI-TPU  ·  工程日志 02

#

最近开始做一个小型硬件工程项目：Mini-TPU。

名字听起来有点大，实际上目前距离真正意义上的 TPU 还很远。

项目的目标也不是造一块能够运行大模型的 AI 加速卡，而是尝试从数字逻辑的基础开始，亲手实现一个简化的矩阵乘法计算单元。

我想弄清楚一件事：

**一个神经网络计算加速器，究竟是怎样从最基本的乘法器、累加器和数据通路，一步步构建出来的？**

这次不打算直接使用现成的 FPGA IP，也不急着购买开发板。先在软件仿真环境中完成 RTL 设计、功能验证和逻辑综合，建立一套可以复现的工程基线。

目前，项目已经从独立 MAC 模块推进到了 2×2 Output-Stationary Systolic Array（输出驻留脉动阵列）。

记录一下这个阶段的工作。

•   •   •

## 一、先从最小的计算单元开始：INT8 MAC

神经网络中的矩阵乘法可以拆解成大量乘加运算：

*C*ij=∑*k**A*ik*B*kj

最基本的硬件单元就是 MAC（Multiply-Accumulate），即乘法累加器。

它每次接收两个输入：

* A：有符号 INT8
* B：有符号 INT8

执行一次乘法，再把结果累加到 INT32 累加寄存器中。

*ACC*next=*ACC*current+*A*×*B*

看起来非常简单，但硬件实现并不只是写一个乘法表达式。

首先，需要明确整数的表示方式。

本项目采用：

* 输入：8-bit 二进制补码有符号整数
* 乘积：16-bit 有符号整数
* 累加器：32-bit 二进制补码
* 溢出：32-bit 模 232回绕，而不是饱和截断
* Overflow：采用 sticky 标志，发生溢出后保持置位，直到清零

为什么要专门定义这些？

因为硬件中的整数运算和 Python 中的整数运算并不完全相同。

Python 整数可以自然扩展位宽，而硬件寄存器的位宽是固定的。

例如：

231−1+1=−231

在 32-bit 二进制补码运算中，这不是一个需要阻止的操作，而是一次正常的模 232回绕，同时应该记录数学意义上的有符号溢出。

如果不提前明确这些语义，后面的参考模型、RTL 和测试平台就可能各自采用不同的计算规则。

因此，INT8 MAC 阶段首先解决的是计算语义问题，而不仅仅是实现一个乘法器。

## 二、验证比写代码更重要

完成 `int8_mac.sv`后，我没有立即开始堆叠更多硬件模块，而是先建立 Python Reference Model。

参考模型负责定义预期结果，Cocotb 负责驱动仿真和检查 RTL 输出。

整个验证链路是：

Python Reference Model → Cocotb Testbench → Verilator → SystemVerilog RTL

重点检查：

1. 正负数乘法是否正确。
2. INT8 边界值是否正确。
3. INT32 累加是否正确。
4. 正溢出和负溢出是否正确。
5. Reset 和 Clear 是否具有正确的优先级。
6. Invalid 输入时状态是否保持。
7. Overflow 是否符合 sticky 语义。

这里有一个容易被忽视的工程问题：

**不能因为 RTL 仿真通过，就认为设计一定正确。**

如果参考模型和 RTL 使用了相同的错误假设，那么两边完全可能得到相同的错误结果。

所以，测试需要有明确的边界条件、独立的计算模型，以及能够覆盖不同状态转换的测试用例。

经过代码审查、定向测试和随机测试，INT8 MAC 的基础实现完成了第一阶段验收，并正式归档。

这意味着后续模块可以把它作为已经明确计算语义的基础单元，而不需要每次重新讨论乘法和累加的规则。

## 三、从 MAC 到 PE：让计算单元开始协作

单独一个 MAC 并不能构成矩阵乘法加速器。

下一步是 PE（Processing Element，处理单元）。

一个 PE 可以理解为一个局部计算节点，负责：

* 接收 A 数据。
* 接收 B 数据。
* 执行乘法累加。
* 将 A 转发给下一个节点。
* 将 B 转发给下一个节点。

这里开始引入一个重要概念：数据流（Dataflow）。

与传统处理器反复从寄存器或存储器读取操作数不同，脉动阵列让数据按照预定方向在计算单元之间流动。

本项目采用 Output-Stationary 数据流。

简单来说：

* A 数据沿水平方向传播。
* B 数据沿垂直方向传播。
* 每个 PE 将自己的部分累加结果保存在本地。
* 计算完成后，各 PE 输出对应的矩阵元素。

这样做的好处是减少部分和的搬运，让累加操作尽可能在本地完成。

当然，数据流方向确定之后，时序问题也随之出现。

A 和 B 并不是同时到达所有 PE。

为了让正确的两个操作数在正确的时钟周期相遇，需要对输入数据进行 Skew（错位）。

对于二维阵列，输入时序可以表示为：

*A*(*i*,*k*)@(*k*+*i*)

*B*(*k*,*j*)@(*k*+*j*)

也就是说，不同行的 A 数据和不同列的 B 数据需要按照各自的位置延迟进入阵列。

这不是简单地把几个 MAC 摆在一起，而是开始涉及真正的硬件数据通路设计。

## 四、当前阶段成果：2×2 Output-Stationary Systolic Array

目前已经完成了第一个 2×2 脉动阵列的 RTL 实现。

阵列结构如下：

![](https://mmbiz.qpic.cn/sz_mmbiz_jpg/fNR1ygo0YuXocl82sFPVRnPeQfCkkTicAXwMib1wBichOdIK7XGicNPNqE5D490DtTc4FZvxcRkoAYJ8ptZdMvVJJQkLAzS4v93wawNicxef1L5I/640?wx_fmt=jpeg)

更准确地说，A 在每一行中从左向右传播，B 在每一列中从上向下传播，每个 PE 独立完成乘加并保存自己的累加结果。

这个阶段主要解决了几个问题：

1. 数据转发

PE 不仅需要完成计算，还需要把输入操作数传递给下一个 PE。

数据转发和本地累加必须在时钟边界上保持正确关系。

2. Valid 信号传播

数据是否有效不能只依赖数据本身。

因此，A 和 B 分别维护自己的 Valid 传播路径，避免把无效数据误认为有效计算输入。

3. 输入错位

阵列需要按照行列位置对输入进行时序错位，保证矩阵乘法中的操作数能够正确相遇。

4. 累加状态

每个 PE 都有自己的累加状态，不能因为其他 PE 的数据到达或状态变化而破坏本地计算。

5. Reset 和 Clear

阵列需要能够正确初始化，并支持清除累加状态。

目前，2×2 阵列已经通过 Verilator + Cocotb 的主要功能仿真，完成了基础数据流和计算结果验证。

这意味着项目已经从单个乘加单元进入了多计算节点协同工作的阶段。

但需要强调，2×2 阵列通过功能仿真，并不等于已经完成完整的硬件验收。更大规模阵列、复杂连续输入、吞吐率和时序性能仍然需要进一步验证。

## 五、综合：让 RTL 从代码变成逻辑结构

功能仿真之外，还需要确认 RTL 能否被综合工具正确理解。

目前已经使用 Yosys 对 INT8 MAC 进行了综合验证。

这一步的意义在于：

SystemVerilog 不只是能够被仿真器执行，还需要能够转换为硬件逻辑结构。

综合过程会将 RTL 中描述的运算、寄存器和控制逻辑转换成相应的逻辑网络。

对于当前阶段，我更关心的是：

* 是否存在无法综合的结构。
* 是否存在意外的锁存器。
* 寄存器和组合逻辑是否符合预期。
* 综合结果是否与设计意图一致。

INT8 MAC 已经完成这一轮综合基线验证。

后续还需要对整个 2×2 阵列进行综合，并进一步观察资源规模和逻辑结构。

暂时不急于讨论 TOPS、算力密度或者能效。

在没有实际硬件实现、时钟频率和功耗数据之前，这些指标没有太大意义。

## 六、为什么不直接做一个更大的 TPU？

这是一个值得思考的问题。

实际上，直接写一个 8×8 甚至 16×16 的阵列并不困难。

真正困难的是确保每个计算单元在正确的时钟周期收到正确的数据，并且整个系统在连续输入、暂停、清零和复位等情况下仍然保持正确。

如果一个 2×2 阵列存在数据错位问题，那么扩大到 16×16 只会让问题更难定位。

所以目前采用的是逐级扩展的方式：

![](https://mmbiz.qpic.cn/mmbiz_jpg/fNR1ygo0YuUw7bAlN2xLFoCRG6ianxDt80rqMFF9L5X7BDhpINZ6S0zI3O8zykCQBVBYxBYbHf1XZIib2AlNvHp6M2SfJC8C21cppWEicWlaCY/640?wx_fmt=jpeg)

每完成一级，都应该建立对应的参考模型和验证基线。

这也是我希望这个项目能够坚持的原则：

**先证明一个模块是正确的，再让它成为更大系统的一部分。**

## 七、下一阶段计划

接下来不会急于增加阵列规模，而是先完成当前阶段的工程收尾。

主要工作包括：

1. 完成 PE 和 2×2 阵列的边界条件审查。
2. 补充连续输入、Bubble、Back-to-Back 等时序场景。
3. 检查 Reset、Clear 和 Valid 在阵列中的传播行为。
4. 完成 2×2 阵列的 Yosys 综合。
5. 建立完整的矩阵乘法参考模型，对照阵列输出。
6. 记录综合资源和后续性能评估所需的基线数据。

之后再考虑扩展到 4×4 阵列。

在此基础上，才有必要讨论输入缓冲、权重存储、数据复用和更完整的矩阵计算流水线。

•   •   •

## 最后

这个项目目前没有 FPGA 开发板，没有实际芯片，也没有可以展示的算力数字。

目前拥有的东西主要是一些 SystemVerilog 文件、Python 测试代码、仿真日志和综合报告。

但我觉得这恰恰是一个有意思的开始。

以前接触 AI，更多是在软件层面调用模型、部署推理服务，或者研究模型的安全问题。

这次想换一个方向，从计算本身往下走。

一个 INT8 乘法如何实现？

一个累加器如何处理溢出？

多个计算单元如何通过数据流协同工作？

矩阵乘法为什么适合脉动阵列？

这些问题看起来都很基础，但把它们真正落实为可以仿真、可以检查、可以综合的硬件逻辑，需要处理不少细节。

Mini-TPU 目前还只是一个很小的实验。

不过，至少现在已经有了一个可以继续向上搭建的工程起点。

**先让 2×2 正确工作，再考虑 16×16。**

这大概就是这个项目现阶段最重要的进展。
