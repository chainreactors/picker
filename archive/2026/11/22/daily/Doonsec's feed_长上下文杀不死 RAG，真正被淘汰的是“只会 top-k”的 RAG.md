长上下文杀不死 RAG
真正被淘汰的是“只会 top-k”的 RAG

从检索增强到证据编排：Agentic RAG 的真正分水岭。

· 全文约 7000 字　· 9 节拆解　· 18 篇一手文献　· 2026-11-22

过去两年，关于 RAG 的“讣告”越来越频繁。

理由看起来也很充分：模型上下文从 128K 涨到 1M，甚至更长；既然可以把整本书、整个知识库都塞进模型，为什么还要切块、向量化、召回、重排？

但这类判断，把一个系统问题误当成了模型参数问题。

上下文窗口解决的是“能放多少”，RAG 解决的是“该放什么、从哪里来、谁有权看、错了怎么证明”。前者是工作台的大小，后者是供应链和质检体系。工作台再大，也不能代替仓库、权限和审计。

我的判断是：RAG 没有死。死的是“切块 + 向量 top-k + 一次性生成”的旧范式。 长上下文反而把 RAG 推向了更高阶的形态——从“检索增强生成”，走向“证据编排”。

01先拆掉一个伪命题：上下文窗口不是知识库

“长上下文会取代 RAG”最诱人的地方，是它把复杂系统简化成了一句话：都放进去不就行了？

现实里有五道墙。

1.1 标称上下文不等于有效上下文

模型说支持 128K，不代表它在 128K 时还能同等清晰地使用信息。

2023 年的经典研究《Lost in the Middle》发现，当关键信息位于长上下文中部时，模型表现会明显下降；到了 2025 年，ICML 的 NoLiMa 测试更不客气：13 个声称支持至少 128K 上下文的模型里，在 32K 长度时，有 11 个掉到短上下文基线的一半以下；即便是当时表现最好的 GPT-4o，也从 99.3% 降到 69.7%。

RULER 的结论类似：17 个长上下文模型中，只有一半能在 32K 长度维持令人满意的表现。

更微妙的是 2026 年一项长程 Agent 实验：在 100K token 的编程会话里，即使缓存策略保留了超过 99% 的关键 token，随着“定义”和“使用位置”的距离从 2K 拉到 90K，后续步骤准确率仍从 93% 跌到 64%。

关键 token 还在上下文里，不等于模型真的用得上。这就像把所有文件摊在一张桌子上：桌子够大，不代表你能在三十秒内找到那份三年前的补充协议。

1.2 更多上下文，可能带来更多噪声

检索领域有一个反直觉结论：不是召回越多越好。

2024 年的《Long-Context LLMs Meet RAG》发现，对很多长上下文模型来说，随着检索段落数量增加，生成质量会先升后降，罪魁祸首之一是“hard negative”——看起来相关、实际上会误导模型的段落。

长上下文模型并不会自动变成“事实过滤器”。你给它 100 份文档，它可能同时看到正确条款、过期版本、互相矛盾的解释，以及一份写得很像答案的错误材料。

上下文越多，证据选择越重要。

1.3 成本不是按“能不能放”算，而是按“每次调用”算

长上下文推理的 prefill 阶段，注意力计算近似随长度二次增长；KV cache 又会随上下文线性膨胀。即使用 PagedAttention、稀疏注意力、prompt caching 优化，成本也不会消失，只是被延后和摊薄。

Prompt caching 很有用，尤其适合稳定前缀：同一份长文档反复问，缓存能显著降本提速。但它救不了“每个用户、每个租户、每个问题都不同”的动态场景。你不可能为每一次查询都重新灌入一个百万 token 的知识库。

一个很朴素的算术：如果每轮只送 8K token 的高质量证据，和每轮送 500K token 的全量文档，输入成本相差几十倍；再乘上每天成千上万次调用，差距就是实打实的毛利。

1.4 权限、时效和删除，是模型参数解决不了的

企业知识库不是互联网文库。它包含薪酬、合同、客户数据、工单、源代码和未公开战略。

把全量知识塞进上下文，意味着什么？

?谁能保证张三看不到李四的薪酬？

?一份合同今天被撤稿，模型明天怎么“忘记”？

?一条知识来自哪个系统、哪个版本、谁批准的？

?监管问询时，如何证明答案只基于有权限的证据？

这些不是“模型更聪明”就能解决的问题。它们需要检索层做 ACL（访问控制列表）、元数据过滤、来源追踪、版本管理和审计日志。

RAG 的第一性原理不是“模型记不住”，而是“知识需要被治理”。

1.5 长上下文里，冲突不会自动消失

真实知识库从来不是一份干净的事实清单。旧政策和新政策并存，销售口径和法务口径冲突，英文文档和中文文档版本不一致。

长上下文可以把所有版本一起放进去，但“放进去”不等于“解决冲突”。系统仍然需要判断：哪份证据更新？哪份权限更高？哪份是正式发布版？哪些冲突需要向用户显式暴露？

这恰恰是检索与证据编排层的工作。

02长上下文确实赢了，但只赢在特定战场

说了这么多，不是要否定长上下文。相反，长上下文是过去三年最重要的能力进步之一，它在一些场景里确实比 RAG 更合适。

2024 年 EMNLP 的一项系统比较给出了很平衡的结论：当资源足够时，长上下文模型在平均表现上可以超过 RAG；但 RAG 的成本显著更低。研究者因此提出 Self-Route：让模型自己判断，这个问题该走 RAG，还是直接读长上下文。

这其实已经说明了未来：不是二选一，而是路由。

长上下文更适合这些任务：

**✓**知识总量不大，约几百页以内，且相对静态；

**✓**需要通读整本书、整份合同、整组会议纪要，做全局总结；

**✓**问题需要跨文档做“大局观”推理，而不是精确查某个字段；

**✓**调用频率不高，延迟不敏感；

**✓**数据可以安全地放进单次上下文，不涉及复杂权限。

Anthropic 在介绍 Contextual Retrieval 时也给过一个很实用的边界：如果知识库小于 20 万 token，约 500 页材料，直接放进 prompt 往往更简单；配合 prompt caching，速度和成本都可以接受。但知识库继续变大，问题就不再是“读不读得完”，而是“该读哪一段”。

长上下文还带来一个容易被忽略的好处：它让 RAG 的检索单元可以变长。

传统 RAG 常把文档切成 100 词左右的碎片，检索很轻，但上下文被切碎。LongRAG 把 Wikipedia 语料组织成 4K token 的“长单元”，用更少的单元做检索，再交给长上下文 reader，在 NQ、HotpotQA 上取得了与全训练 SOTA 相当的结果。

这说明长上下文不是 RAG 的敌人，它可以让 RAG 从“碎片检索”升级为“文档级、章节级检索”。检索的粒度变粗了，但对证据组织的要求更高了。

一句话总结：

长上下文是阅读能力，RAG 是供应能力。阅读能力再强，也不能替代“把正确的书放到桌上”。

03RAG 没有消失，它在 2026 年变成了四层栈

今天再谈 RAG，不能只想到“向量数据库 + top-k”。更准确地说，RAG 已经演化成一套分层架构。

3.1 L1：Naive RAG，固定流程的“检索后生成”

文档切块 → embedding → 向量检索 top-k → 拼接 prompt → 生成。

优点是简单、便宜、容易上线；缺点是脆弱：query 稍微模糊就召回失败，chunk 切碎后语义断裂，检索错了也没有补救机制。

这是最容易被长上下文“替代”的一层，也是最容易被误当成“RAG 全部”的一层。

3.2 L2：Advanced RAG，把检索质量做扎实

在 L1 之上加入：

混合检索：BM25 稀疏检索 + dense 向量检索；

查询改写、扩展、澄清；

元数据过滤、权限过滤；

重排 rerank；

上下文切块优化，例如 Contextual Retrieval、late chunking；

上下文压缩，去掉无关句段；

引用与溯源。

Anthropic 的 Contextual Retrieval 是一个代表：在把 chunk 送入索引前，先为它补上所属文档的上下文，再用 Contextual Embeddings 和 Contextual BM25 检索。公开结果显示，失败检索减少 49%；加上 rerank 后减少 67%。

这类技术的价值很朴素：别让检索器在失去上下文的情况下猜。

3.3 L3：Structured RAG，用结构解决“全局问题”

当问题从“这份合同的违约金是多少”变成“这批合同的主要风险主题是什么”，普通 top-k 就不够了。你需要结构。

代表性路线包括：

GraphRAG：先抽取实体关系，构建知识图谱，再预生成社区摘要，回答需要全局理解的问题；

RAPTOR：递归聚类、摘要，形成层次树；

文档树 / 目录导航：按章节、页面、表格结构检索；

多模态文档检索：直接理解页面布局、表格、图表，而不只是 OCR 成文本。

GraphRAG 的论文明确指出，传统 RAG 在“针对整个语料的全局问题”上会失效，因为这不是一个简单的片段检索任务，而是 query-focused summarization。它在百万 token 级数据集上，相比传统 RAG 提升了答案的全面性和多样性。

但结构不是免费的：图谱构建贵、实体消歧难、更新复杂。GraphRAG 不是“更高级”，而是“更适合全局和多跳问题”。

3.4 L4：Agentic RAG，从开环管道变成闭环系统

这是当前最热的一层，也是最容易被误解的一层。

Agentic RAG 不是在 L2 上多挂几个 Agent，而是把检索变成一个由模型动态控制的闭环：

AGENTIC 检索闭环

01理解任务

↓

02制定检索计划

↓

03选择工具

↓

04执行检索

↓

05观察结果

↓

06判断证据是否充分

↓

07不足则改写查询/换工具/继续检索

↓

08证据足够后生成

↓

09校验引用与冲突

↓

10输出或升级人工。

2025 年的 Agentic RAG 综述把它概括为：在 RAG 管道中嵌入自主 Agent，利用反思、规划、工具使用和多 Agent 协作，动态管理检索策略、迭代修正上下文理解。

这里的关键词不是“多 Agent”，而是动态控制。

一个单 Agent，只要它能规划、能调用多种检索工具、能根据证据缺口继续搜索、能在证据足够时停止，它就是 Agentic RAG。反过来，三个 Agent 按固定顺序跑一遍，仍然只是 workflow，不是真正的 agentic。

04Agentic RAG 和普通 RAG，差的不是“多几个 Agent”

把两者的区别压缩成一张表：

|  |  |  |
| --- | --- | --- |
| 维度 | 普通 RAG | Agentic RAG |
| **控制方式** | 固定流水线，开环 | 动态规划，闭环 |
| **查询处理** | 用户 query 直接检索 | 拆解、改写、澄清、生成子问题 |
| **检索次数** | 通常一次 top-k | 多轮、多源、按需 |
| **工具范围** | 主要是向量库 | 向量库、BM25、SQL、图数据库、网页、API、文件系统 |
| **证据判断** | 默认 top-k 就是答案依据 | 显式判断证据是否充分、是否冲突、是否过期 |
| **失败处理** | 检索不到也硬答 | 继续搜、换工具、缩小范围、承认不知道或升级人工 |
| **记忆** | 基本无状态 | 工作记忆、会话记忆、长期记忆、过程记忆 |
| **输出** | 一段答案 | 答案 + 证据链 + 引用 + 置信度/待确认项 |
| **成本** | 低且稳定 | 高且波动 |
| **适用任务** | FAQ、制度查询、单跳问答 | 多跳研究、跨系统分析、复杂工单、尽调、深度检索 |

更本质的区别，是失败模式。

普通 RAG 的典型失败是“没检索到”：召回错了，模型只能基于错误上下文硬答。

Agentic RAG 的典型失败则是“以为自己检索到了”：它可能带着不完整、过期或互相矛盾的证据继续行动，甚至调用工具产生副作用。后者更危险，因为它有行动能力。

所以，Agentic RAG 的核心部件不是“更多 Agent”，而是四个东西：

1**Planner**：把任务拆成可验证的子问题；

2**Tool layer**：知道每种知识该去哪里找；

3**Verifier**：判断证据是否足够、是否冲突、引用是否真的支持结论；

4**Memory**：记住已经查过什么、还缺什么、哪些结论已被证伪。

其中最重要的是 Verifier，也就是“停止条件”。

没有停止条件的 Agentic RAG，只是一个会烧钱的循环。

05别神化 Agentic RAG：它更容易错，也更贵

Agentic RAG 很强，但它不是默认答案。

2025 年 EMNLP 的一篇论文给行业泼了一盆冷水：在匹配 token 预算的条件下，一个非常简单的 DOS RAG（Document’s Original Structure RAG）——保留文档原始顺序、检索后直接读——在多个长上下文 QA 基准上，能够匹配甚至超过 ReadAgent、RAPTOR 等更复杂的多阶段流程。

这不是说复杂方法没用，而是说：复杂性必须被证明有价值。

Agentic RAG 的代价很现实：

**!**多轮检索带来更高的 token 成本和延迟；

**!**每一步都可能引入错误，错误会沿链放大；

**!**工具调用扩大攻击面；

**!**评测从“答案对不对”变成“过程是否合理、证据是否充分”；

**!**没有 trace 的系统，出了问题很难定位。

更别忘了安全。2026 年的 RAG 安全综述把语料投毒、后门、隐私泄露和公平性问题列为系统性风险。Agentic RAG 还会让模型根据检索到的内容去调用工具——这意味着网页、邮件、工单里的恶意指令，可能不只是“污染答案”，而是“诱导行动”。

检索层必须被当作安全边界，而不是一个普通数据库。

我建议用三个“不要”做刹车：

**✕**不要用 Agentic RAG 做高频、简单、单跳的 FAQ；

**✕**不要用多轮检索掩盖 retrieval 本身的质量问题；

**✕**不要在没有评测、没有 trace、没有权限控制的情况下上生产。

什么时候值得上？一个简单判据：

**适用判据**如果一个问题需要 3 个以上来源、2 轮以上验证，且错答成本明显高于额外检索成本，才值得上 Agentic RAG。

如果一次高质量检索加一次生成就能答对，先进的普通 RAG 往往更划算。

06未来三年，我的五个判断

以下不是预言，而是基于当前技术轨迹的判断。

6.1 判断一：RAG 会作为独立产品类别消失，但“能力”会保留

未来很少会有人单独买一个“RAG 系统”。检索会嵌入 Agent runtime、企业知识平台、办公套件和业务系统，成为看不见的基础设施。

就像今天没人会说“我的网站用了 TCP/IP 产品”，但它无处不在。RAG 会从一个产品类别，变成一种系统能力。

6.2 判断二：竞争焦点从“上下文长度”转向“上下文 ROI”

未来比拼的不是谁能塞进 1M token，而是谁能用更少的 token，证明更可靠的结论。

会出现更多围绕以下指标做优化的技术：

**◆**证据密度：输入 token 中有多少真正被答案引用；

**◆**证据召回：回答所需的事实是否都被检索到；

**◆**引用精度：引用的来源是否真的支持结论；

**◆**冲突发现率：互相矛盾的来源是否被识别；

**◆**每个被验证答案的成本；

**◆**权限泄露率，理想值是零。

“上下文工程”会成为和 prompt engineering 同等重要的工程学科。Anthropic 在 2025 年已经把 context engineering 定义为：在推理过程中，对进入模型的 token 集合进行策展和维护。这个定义的重点不是“更长”，而是“更优”。

2026 年的 CoRA-Bench 还提醒了一件事：在固定 token 预算下，不同上下文选择器的证据保留率差异很大。压缩上下文时，最怕的不是“压得不够短”，而是把答案真正需要的证据一起压掉。省 token 的前提，是别把证据省没。

6.3 判断三：Agentic RAG 会从“提示词编排”走向“策略学习”

今天的 Agentic RAG 很多还是手写 workflow：先查 A，再查 B，不够就查 C。

下一步会出现更多：

用强化学习训练检索策略，让模型学会何时搜、搜什么、何时停；
