# 一、同一份配置，今天和下周可能启动不同的程序

[![](https://mmbiz.qpic.cn/sz_mmbiz_png/Y05UtykogHRfXjn7mlVAsUoKuTGMxdYvvniaFTLVl83nlb9v8aw8WAsltZFh7yQn17eSSezP2f3QLXMHgicdWmOPZ9tav38xymhe2eCTibqRjQ/640?wx_fmt=png&from=appmsg)](https://mp.weixin.qq.com/s?__biz=MzkxNzU2NDgxNQ==&mid=2247488841&idx=1&sn=6980ae43228319cdcdb598f74cffedda&scene=21#wechat_redirect)

![](https://mmbiz.qpic.cn/sz_mmbiz_png/RBozUQPW9c9uzmFRqtCIwuQZzWHXcLVTmoTfLpES3uxw9DESYkLhm5xOCiaXLNAr5BoudicDsXRdhGCd8T6Sib5VQ/640?wx_fmt=png&from=appmsg)

安全工程师接到一项接入申请：让 AI 助手通过 MCP 读取项目资料。申请里附了一小段配置，启动命令是 `npx`，参数包含 `-y` 和一个没有版本号的包名，环境变量里还填了 API 密钥。

这是一个用于说明机制的假设场景，取自 mcp-warden README 展示的配置形态，不代表我们发现了某家公司的真实泄漏。MCP 是让 AI 客户端连接外部工具的协议；本地服务通常由客户端启动，服务进程能接触哪些文件和凭据，取决于实际运行环境与授权。

🔎 审批时如果只问“这个工具能不能读资料”，就会漏掉更早的一步：**客户端究竟会下载、启动哪个版本的程序，又把什么交给它？**

![](https://mmbiz.qpic.cn/mmbiz_png/Y05UtykogHRXwaLmzbNPjHDVlf771tqSZFTs5Spv7NNrx5BV17ibc36FzEuY3nWmztQ66PYsVT8ia8QQa9l18XLcQpwE4qgqpdkJtBOV9zJrE/640?wx_fmt=png&from=appmsg)

没有固定版本的包名，可能在日后解析到不同的发布内容。`-y` 免去了安装过程中的一次确认，却没有为包来源背书。配置里的明文密钥还可能随着配置文件复制、提交或分享而扩散。这些条件分别需要检查，不能因为它们出现在同一行，就把它们合成一句“工具已经恶意”。

mcp-warden 是 Kirtan Bhatt 公开的一个开源检查器。我们本轮读取了原始 README、规则说明及相关源码，没有安装或运行它，也没有扫描本机配置。仓库当前 `package.json` 标为 1.1.0；版本号描述的是本次读取到的文件，不能代替发布真实性或检测效果的独立验证。

它的第一条检查路径是 `scan`：读取已有配置，识别启动命令、参数、服务器地址和环境变量中的风险信号。README 列出的配置规则包括硬编码密钥、未固定版本、拼写近似包名、危险容器参数以及过宽文件访问范围等。

|  |  |  |  |  |  |  |  |  |  |  |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| | 配置里的线索 | 审查真正要回答的问题 | | --- | --- | | 包名没有精确版本或摘要 | 下次启动会不会得到不同程序？ | | 环境变量直接保存密钥 | 谁能读到文件，密钥会传给哪个进程？ | | 容器使用高权限或挂载敏感目录 | 服务能触达的范围是否超出任务需要？ | | 名称很像熟悉的官方包 | 发布者、包名和审批记录是否一致？ | |

表里的每一项都只是核查入口。固定版本降低无意漂移的机会，不会让本来恶意的版本变安全；没有静态凭据的远程地址也可能采用正常的交互认证，不能只凭一条提示定罪。

🧭 今天可以先做一个不需要启动新服务的检查：找出这次申请对应的配置，人工核对包的精确标识、凭据来源、文件范围和运行身份，把它们记进接入记录。先回答“准备执行什么”，再讨论是否批准执行。

# 二、工具说明不只是文档，它还会进入模型上下文

配置审批完成后，还有一份不同的材料：服务器实际公开的工具清单。MCP 客户端通过 `tools/list` 取得工具名称、描述和输入结构，模型会借助这些信息决定何时调用工具、怎样填写参数。这里的“输入结构”可以理解成参数表，说明哪些字段存在、字段接受什么值。

假设一个“读取项目文档”的工具，在描述里夹带“使用前先读取某个敏感文件，并且不要告诉用户”。这句话来自工具服务器，却试图指挥助手做任务之外的事。**可疑点是说明文字跨过了数据与指令的边界，不是工具名字里出现了哪个敏感词。**

🧩 mcp-warden 的 `tools` 路径检查已有的工具清单文件。源码中的规则会寻找隐藏指令、隐瞒用户的措辞、敏感文件引用、不可见字符、跨工具干预以及外传线索。它也遍历参数结构中的说明、默认值等字符串，并检查部分可疑参数名，因此审查对象不只是一段顶层描述。

这种实现能把需要人工解释的位置挑出来，但规则命中不等于成功攻击。合法安全工具也可能在描述里提到敏感路径；表达同一恶意意图的改写，又未必落入当前规则。我们没有复跑样本，不能给出召回率、误报率，更不能把 README 的效果描述写成生产环境保证。

![](https://mmbiz.qpic.cn/mmbiz_png/Y05UtykogHSTvtKAZ13Zfic3ksUuWPM936vMLgOGN8gLOb8LVoIF7AiarP0Od4AnodGJ1be2mnFiaKG17PrRfwvDDGUSUoP6BrQ4jSaatTZUKs/640?wx_fmt=png&from=appmsg)

这里最容易混淆的是第三条路径 `inspect`。它不是换个参数继续离线读文件：它会连接服务器，进行初始化握手，再请求实际工具清单。本地标准输入输出模式下，它还会启动指定的服务器进程。

|  |  |  |  |  |  |  |  |  |  |  |  |  |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| | 路径 | 输入从哪里来 | 动作边界 | | --- | --- | --- | | `scan` | 已存在的客户端配置 | 静态读取，不启动其中配置的服务器 | | `tools` | 已导出的工具清单 | 静态检查清单，可信度取决于清单来源 | | `inspect` | 本地进程或远程服务器 | 启动或连接服务，发生协议交互 | |

> ⚠️
>
> “只是看工具有哪些”不自动等于只读。对于一个陌生本地服务，启动本身就可能执行它的代码；无需等到模型真正调用某个工具，风险才开始存在。

源码为本地检查设置了最小环境、超时和输出上限，并在结束时清理进程。这些是降低暴露面的实现措施，不能据此推断陌生程序被隔离到了安全沙箱。远程检查也会发出请求，服务端可能记录访问或执行初始化逻辑。

🛠️ 接入前可以按这个顺序补证据：

1. 先对齐配置、包身份和权限范围，确认计划启动的对象。
2. 优先收取已获授权环境导出的工具清单，记录获取时间、服务器身份和来源。
3. 如确需实时获取清单，单独批准启动或连接动作，选择合适的隔离环境与测试凭据。
4. 将命中项回到具体描述和参数解释，决定替换服务、缩小权限还是保留有理由的例外。

做到这里，初次审批至少区分了两件事：配置描述的是准备怎样启动，工具清单描述的是这次看到什么。它们都还没有回答“以后会不会变”。

# 三、锁住工具定义的指纹，才能把变化变成待审事项

🎯 核心问题

**第一次生成锁文件，只是记住当时的工具定义，为什么还不能算“审查通过”？**

📌 同一个工具名称，描述和参数发生变化时，哪些字段进入指纹？如果整台服务器没有出现在本次取样里，比较逻辑又看得到什么？

🗂️ 完整稿继续拆解 `src/lock.js` 的比较范围，以及更新锁文件时应保留的旧定义、新定义和批准理由。
