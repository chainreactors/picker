随着大模型选择越来越丰富，如何在不同模型与不同线路之间灵活切换，也成为实际使用中的常见需求。CloudRouter 提供统一的接入方式，让不同模型可以在同一套调用体系下使用。

无论使用哪种模型，都可以通过统一的 API 接入。对于模型所在分组不同的场景，CloudRouter 提供两种灵活的路由方式。

---

## 统一接入，从分组开始

创建 API Key 时需要绑定一个分组。不同分组对应不同的线路与价格，是模型调用时的基础路由单元。

完成绑定后，该分组内包含的模型可以直接通过模型名调用，无需额外配置。

模型、分组与调用之间的关系：

![Key、分组、模型的关系示意](https://mmbiz.qpic.cn/sz_mmbiz_png/39bwlg7QlUPN1GxCkox92P7QibibSwrNODSHGhINm0Yp9HNGR8hFcfBTvDzt0wk87iaWMKsrqvN5cuoJvCxDic6DbLZb2fYjMGaa3vIExcP6uhE/640?wx_fmt=png&from=appmsg)

当目标模型不在当前绑定分组中时，可以通过以下两种方式灵活指定调用线路。

---

## 两种路由方式

两种方式都可以实现跨分组调用，区别在于分组信息是在调用前配置，还是在请求时指定。

| 对比 | 方式一：默认模型配置 | 方式二：分组标识调用 |
| --- | --- | --- |
| 核心思路 | **提前** 在后台配好路线 | 调用时**当场**点名路线 |
| `model` 怎么写 | 只写模型名，如 `kimi-k3` | 写"标识/模型名"，如 `A2C4E6G8/kimi-k3` |
| 要不要提前配 | 要，配一次长期有效 | 不用，直接写在调用里 |
| 要不要开开关 | 不用，随时能用 | 要，主用户先开"分组标识路由" |
| 适合谁 | 配一次，以后省心 | 随时切换分组，不想动配置 |

一种适合预先固定模型与线路，另一种则更适合在请求侧灵活控制。

---

## 默认模型配置：让模型自动走指定线路

默认模型配置的核心，是建立模型与分组之间的默认路由关系。

> ⚠️ "默认模型配置"**不是**"设置一个默认调用的模型"。

它的作用是为某个模型指定一个默认分组。即使该模型不在 API Key 当前绑定的分组中，调用时仍可直接填写模型名，由平台自动路由到预设线路。

生效逻辑：

1. 1. 调用时，平台**优先走 Key 绑定的分组**；
2. 2. 只有绑定分组里**没有**这个模型，才会去用「默认模型配置」里配好的分组；
3. 3. 模型既不在绑定分组、又没配过默认分组 → 用模型名调用会**失败**。

> 🔑 **一个容易踩的坑：绑定分组里"已有"的模型，默认模型配置改不动它。**
> 例子：Key 绑的是分组 A，分组 A 里本来就有 `kimi-k3`。这时哪怕你在默认模型配置里把 `kimi-k3` 指到了分组 B，调用仍然走分组 A。
> 原因：绑定分组能供的模型，优先级永远最高。想强制走别的分组，只能用下面的**方式二（当场点名）**。

配置入口：控制台 →「默认模型配置」

* • 搜到你要的模型 → 给它选一个你有权使用的分组 → 立即生效；
* • 支持"按供应商批量设置"，一次把某家供应商的所有模型都配好（有二次确认，**覆盖不可撤销，别手滑**）。

![默认模型配置页面截图](https://mmbiz.qpic.cn/mmbiz_png/39bwlg7QlUMGqtZ3bwjZ4B0phJXiaDfjSDNibF8XTKzPyx5BZZIQGTaM55A369vguGTlIbuVibzKUYNW1YICsvGL5QdHUyPh9TF1aStMT6hoDc/640?wx_fmt=png&from=appmsg)

配好之后，调用写法和平常一样，**model 只填模型名**：

```
{
  "model": "kimi-k3",   ← 只写模型名
  "messages": [{"role": "user", "content": "你好"}]
}
```

> 🚨 **默认模型配置，救不了"没绑分组"的 Key。**
> Key 压根没绑分组的话，调用会被直接拒绝，平台不会去查默认模型配置兜底。所以第一步永远是：Key 必须先绑一个分组。

这种方式适合希望统一管理模型路由、减少调用侧配置的场景。

---

## 分组标识调用：按请求灵活指定线路

无需提前配置模型默认路由。平台会为每个分组分配一个 8 位的「分组标识」（比如 A2C4E6G8，创建后固定不变），调用时将标识加在模型名前面即可。

```
{
  "model": "A2C4E6G8/kimi-k3",   ← 分组标识/模型名
  "messages": [{"role": "user", "content": "你好"}]
}
```

该请求会固定使用标识对应的分组，不受 API Key 当前绑定分组或默认模型配置影响。

**使用前提：**

1. 1. **主用户必须先开启「分组标识路由」开关**（入口在控制台「API Key」页顶部，或「子用户管理 · 设置」里）。子用户跟随主用户，不需要单独开。没开的话带标识的调用会被拒。
2. 2. **分组标识从「调用指南」页直接复制，别自己拼。**开关一开，调用指南页里每个模型就会多出一个带标识的调用名，一键复制即用。
3. 3. 能点名的分组仍限于你账户**有权使用**的范围，不是所有分组都能随便点。

![调用指南页面截图，显示带分组标识的调用名](https://mmbiz.qpic.cn/sz_mmbiz_png/39bwlg7QlUOib9STibQWyjRFiaHiajbvSSfMb6NZibdj9dibwaRStoCxHDKt4dQJAiadDMb1eALiagpNGIhMELfBuyxd1iaGJcZ25er1oJ0YmTdRI7zs/640?wx_fmt=png&from=appmsg)

这种方式适合需要在不同分组之间灵活切换，或希望在代码中精确控制请求线路的场景。

---

## 两种方式如何选择？

* • **想一次配好、以后越简单越好** → 方式一，之后永远只写模型名。
* • **想随时切换分组、不愿动配置** → 方式二，调用时当场点名。
* • **两种能一起用吗？**能。互不冲突，你配好默认分组，随时也可以用标识覆盖某条请求。

如果模型与线路相对固定，可以使用默认模型配置；如果需要按请求灵活控制线路，则可以使用分组标识调用。

---

## 入口速查

| 我要做什么 | 去哪里 |
| --- | --- |
| 给 Key 绑定分组 | 控制台 → API Key → 创建/编辑 Key 时选分组 |
| 配置某个模型的默认分组（方式一） | 控制台 → 默认模型配置 |
| 开启分组标识路由开关（方式二前提） | 控制台 → API Key 页顶部，或子用户管理 · 设置 |
| 复制带分组标识的调用名（方式二） | 控制台 → 调用指南 → 开关开启后每个模型多出带标识的写法，一键复制 |

---

## 常见报错速查

| 报错 / 现象 | 原因 | 怎么解决 |
| --- | --- | --- |
| 403 / 提示未绑定分组 | 这把 Key 没绑分组 | 去 API Key 页给 Key 绑一个分组 |
| `fingerprint_routing_disabled` | 分组标识路由开关没开 | 主用户在控制台开启开关 |
| `group_not_allowed` | 点名的分组不在你账户可用范围 | 换成有权使用的分组，或找主用户授权 |
| 模型名调用报"找不到 / 不支持" | 模型既不在绑定分组，也没配默认模型配置 | 去默认模型配置给它配个分组 |

---

## 总结一下

核心逻辑并不复杂：统一 API 接入不同模型，并根据实际需求选择对应的分组与路由方式。

* • **方式一 · 默认模型配置**：提前配好，以后调用只写模型名，省心。
* • **方式二 · 分组标识调用**：不用配，调用时写"标识/模型名"，灵活点名。

在控制台「调用指南」中，可以直接查看并复制各模型的调用方式，降低接入与配置成本。
