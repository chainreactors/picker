Log4j 事件之后，云安全领域流传着一句话：**「云原生环境没有边界。」**这句话对也不对。不对的部分是——云环境有严格的 IAM 边界；对的部分是——**IAM 边界是由一行 JSON 定义的，而大多数人从来没有真正读懂过那一行 JSON 写的意思。**

这一章的主角是 **CloudGoat**，Rhino Security Labs 开源的「天生脆弱」云环境部署工具。它用 Terraform 在**你自己的 AWS 账号里**搭出一整套配置错误、权限过宽、外网暴露的资源，让你在自己的云上，安全地做一次真实的云渗透。

**🛡️ 授权声明**　⚠️ **本篇涉及成本与安全双重风险**：CloudGoat 会在你的 AWS 账号中真实创建资源并产生真实费用，同时这些资源是**真实可被入侵的**。必须使用独立测试账号，切勿在生产账号或含敏感数据的账号中部署。实验结束后务必执行清理脚本。

## 01云安全的核心命题：身份即边界

传统数据中心的安全模型建立在一个直观假设上：**网络隔离 = 安全边界**。内网机器比外网机器可信，所以我们用防火墙、VLAN、ACL 把危险挡在外面。

云计算打破的不是这个模型的前提，而是它的**成本结构**——在云上，「划一条网络边界」比「建一道防火墙」贵得多，而且很多服务（尤其是 Serverless 与托管数据库）根本没有传统意义上的网卡。于是所有防护逻辑被迫向一个点集中：**IAM 身份与策略**。

**💡 提示**　这就是 AWS 架构中反复出现的那句话：**「Everything is an API.」**云上没有机器，只有 API 调用；而每一条 API 调用都要携带一个身份。攻击面因此被重新定义：不再是「哪个 IP 在打哪个端口」，而是「哪个身份持有什么权限」。

CloudGoat 的设计哲学正是围绕这一点展开的。它的每个场景都在回答同一个问题：**「如果这条 IAM 策略由一个赶时间的人类工程师写出，而且他没走变更评审流程，会出什么问题？」**

## 02CloudGoat 是什么：与本地靶场的根本区别

| 维度 | 本地靶场（DVWA 等） | CloudGoat |
| --- | --- | --- |
| 运行环境 | 本机 Docker / 虚拟机 | 真实公有云账号 |
| 攻击是否真实 | 模拟，攻击可被随时重置 | 真实，影响真实资源 |
| 核心变量 | 应用代码 | IAM 策略与资源配置 |
| 恢复方式 | docker compose down | 执行 cleanup 脚本并核对账单 |
| 风险类型 | 代码漏洞 | 配置错误、权限过宽、边界失效 |
| 典型受众 | Web 渗透学习者 | 云安全工程师、架构审计人员 |

关键差异必须说透：**在 CloudGoat 上，你的「攻击」是真的**。你获取的凭据是真的，你读取的对象存储数据是真的，你调用的 API 权限是真的。你只是在**一个你完全拥有、且不承载任何真实业务的账号里**这么做。

**⚠️ 注意**　账号隔离是使用 CloudGoat 的**第一原则**。具体要求：用全新注册账号、绑定独立邮箱、开启 MFA、不绑定任何生产相关的 IAM 角色、设置预算告警（Budget Alert）作为成本刹车。

## 03环境准备：账号、工具链与成本预期

| 依赖项 | 用途 | 备注 |
| --- | --- | --- |
| AWS 账号 | 承载被测资源 | 必须是全新隔离账号 |
| Python 3.9+ | 运行 CloudGoat 脚本 | 脚本入口为 Python |
| Terraform | 声明式创建云资源 | 需 init 对应场景目录 |
| AWS CLI v2 | 与 AWS API 交互 | 需正确配置凭证 |
| jq / curl | 结果处理与 HTTP 测试 | 常规命令行工具 |

关于成本，说句实在话：**CloudGoat 单个场景的资源开销通常在几美元到十几美元之间，主要来自 EC2 实例和 NAT 网关的按小时计费。**NAT 网关是最容易被忽略的成本黑洞——它按流量计费，且在你忘记清理时会一直扣钱。所以「用完立刻清理」不是建议，是纪律。

基础工具链与凭证配置

```
# 安装 AWS CLI v2（Windows PowerShell 示例） msiexec.exe /i https://awscli.amazonaws.com/awscli-exe-x86_64.msi  # 配置凭证（强烈建议使用测试账号专属的 profile） aws configure --profile cloudgoat # AWS Access Key ID: [填写测试账号密钥] # AWS Secret Access Key: [填写测试账号密钥] # Default region name: us-east-1 # Default output format: json  # 后续所有命令都指定 profile，避免误操作到默认账号 $env:AWS_PROFILE = "cloudgoat"
```

**💡 提示**　使用独立 profile 的意义在于：**它让你的错误操作有了明确的作用域边界**。哪怕命令写错，也只会作用在这个 profile 指向的测试账号上。这是基础设施安全里最基本的「隔离优于防护」思想。

## 04部署流程：从 vulnerable.tf 到资源落地

CloudGoat 的每个场景都是一个独立的 Terraform 目录。整体流程是：进入场景目录 → terraform init → 用 CloudGoat 的部署脚本初始化 → 记录攻击线索 → 实验 → 清理。

标准部署流程

```
# 1. 获取 CloudGoat git clone https://github.com/rhinosecuritylabs/cloudgoat.git cd cloudgoat  # 2. 查看可用场景 ls scenarios/  # 3. 进入目标场景目录 cd scenarios/<scenario-name>  # 4. 使用 CloudGoat 的部署入口（推荐，脚本会处理初始化） python3 /path/to/cloudgoat.py <scenario-name>
```

如果你的环境中 Terraform 版本与 CloudGoat 存在兼容问题，可以手工执行 Terraform 流程。这一条链路的关键理解点是：**CloudGoat 场景目录里的 Terraform 变量文件（vulnerable.tf）就是「被故意写错的配置」本身**——它里面藏着这个场景要演示的每一个漏洞点。

手工 Terraform 流程与清理

```
# 手工执行流程 cd scenarios/<scenario-name>  terraform init terraform apply -auto-approve  # 部署完成后 CloudGoat 会输出 INFO，可据此展开攻击 # 实验结束后清理 python3 /path/to/cloudgoat.py <scenario-name> cleanup
```

## 05场景解剖：每个场景在演示什么误配

CloudGoat 的场景不是随意堆砌的 CVE 集合，它们共同覆盖了云环境中最高频的六类配置错误：

| 配置错误类型 | 典型表现 | 对应场景方向 |
| --- | --- | --- |
| 过宽的 IAM 权限 | 策略里出现 Action: "\*" 或 Resource: "\*" | 权限提升与横向访问 |
| SSRF 可达元数据服务 | Web 应用可被诱导访问 169.254.169.254 | 云凭据窃取 |
| 存储桶公开可读 | Bucket Policy 未限制 Principal | 敏感数据泄露 |
| 安全组开放过宽 | 0.0.0.0/0 放行管理端口 | 服务直接暴露公网 |
| Serverless 权限失控 | Lambda 执行角色权限过大 | 无服务器环境横向移动 |
| 凭据硬编码 | 密钥写入实例启动脚本或环境变量 | 凭据泄露与提权 |

这张表本身就值得单独收藏。因为在真实的云安全评估报告里，**这六类几乎能覆盖 80% 的高危问题**，而且它们全部可以通过配置审计与策略分析发现，不需要任何漏洞利用。

## 06实战一：SSRF 打穿 EC2 元数据服务

### 一、原理：为什么元数据服务是云上的头号目标

EC2 实例内部有一个特殊地址 `169.254.169.254`，它是云厂商提供的**实例元数据服务（IMDS）**。通过它，运行在实例上的程序可以查询到：

* 当前实例的角色信息与临时凭据
* 网络配置与安全组
* 用户自定义的实例启动数据
* 操作系统与主机名等基础信息

而最致命的一点是：**访问这个地址不需要任何认证**。只要有网络连通性，任何能发 HTTP 请求的代码都能拿到凭据。这就让 SSRF 从「信息泄露」瞬间升级为**「云账号权限提升」**。

IMDS 凭据获取的原理链路（仅限授权靶场）

```
# IMDSv1：直接请求可拿到角色名 curl http://169.254.169.254/latest/meta-data/iam/security-credentials/  # 若返回角色名（如 my-instance-role），继续取临时凭据 curl http://169.254.169.254/latest/meta-data/iam/security-credentials/<role-name>  # 返回结构包含： # { #   "AccessKeyId": ..., #   "SecretAccessKey": ..., #   "Token": ... # }  # 拿到后即可以该身份调用任意 AWS API aws sts get-caller-identity --profile attacker
```

**💡 提示**　完整链路：外部攻击者 → 恶意请求参数进入 Web 应用 → 应用服务端发起请求 → SSRF 打到 169.254.169.254 → 返回实例角色临时凭据 → 攻击者用该凭据调用云 API。**关键认知：漏洞发生在服务端，攻击者是「借」应用的手去拿云凭据。**

### 二、IMDSv2 的防御意义

AWS 后来推出了 IMDSv2，要求请求必须先通过 PUT 请求获取会话令牌，后续请求携带该令牌。同时它还引入了**跳数限制（Hop Limit）**与**响应大小限制**，专门用来阻断「从外部 SSRF 进来」的路径。

但必须清楚一点：**IMDSv2 不是万能药。**如果应用本身就运行在实例内，或者攻击者已经获得了某种代码执行能力，IMDSv2 同样挡不住。它真正防的是「跨越信任边界的 SSRF」，而不是「实例内部的横向移动」。

## 07实战二：IAM 权限过宽与权限提升链路

### 一、通配符策略的危险

最常见的过宽策略：管理员权限直接授予

```
{   "Version": "2012-10-17",   "Statement": [{     "Effect": "Allow",     "Action": "*",     "Resource": "*"   }] }
```

这份策略在现实中的使用频率高得惊人。它通常出现在这些场景里：**开发期临时配置忘了回收、为了「先跑起来」临时复制了 Administrator、自动化工具生成的策略模板过于宽松**。

它的危险性在于**可传递性**：一旦一个主体具备创建或修改 IAM 策略的权限，它就能给自己或任何其他人授予完全控制权，形成经典的权限提升闭环。这也正是 AWS 推荐的**「设置权限边界（Permissions Boundary）」**机制存在的原因——给身份设置一个无法突破的上限。

**⚠️ 注意**　云安全里有一条与本地环境截然不同的原则：**「能改 IAM 策略的身份，就等同于账号所有者。」**评估一个云环境时，第一件事永远是「谁能修改权限策略」，这个问题的答案往往决定了整个环境的安全下限。

### 二、权限提升的典型路径

1. 利用 SSRF 或实例内代码执行获取临时凭据（低权限角色）
2. 用低权限身份枚举可访问的资源
3. 寻找可修改策略、可创建密钥、可附加角色的高危权限
4. 自我提权或横向到更高权限的主体
5. 最终获取账号级控制能力

## 08实战三：S3 存储桶公开可读与数据泄露

存储桶权限是云安全里最经典、也最容易在评审中被放过的环节。一个 Block Public Access 配置遗漏，就可能让一个承载客户数据的桶对全互联网可读。

| 检查项 | 健康配置 | 风险配置 | 风险后果 |
| --- | --- | --- | --- |
| Block Public Access | 四个开关全开 | 存在关闭项 | 桶可被公网匿名访问 |
| Bucket Policy Principal | 限定具体账号 | Principal: "\*" | 任意主体可读/写 |
| 加密方式 | SSE-KMS 或强制加密 | 未加密或依赖默认 | 数据泄露后无第二道防线 |
| 版本控制 | 开启 | 关闭 | 误删或恶意覆盖无法回滚 |
| 访问日志 | 开启 | 关闭 | 泄露事件无法溯源 |

这里有一个反直觉但非常重要的现实：**在很多组织里，存储桶权限问题导致的泄露事件数量，远高于代码漏洞导致的事件数量。**原因很简单——代码漏洞需要攻击者找到入口，而一个公开可读的存储桶只需要一个链接。

**💡 提示**　防守建议：把「存储桶公共可访问检测」做成**每日自动化巡检任务**，而不是上线前的一次性检查。因为配置错误的引入成本极低，而它的引入往往来自一次「方便调试」的操作。

## 09实战四：Lambda 与无服务器环境的攻击面

无服务器架构打破了传统的资产清单模型。函数没有常驻实例、没有固定 IP、没有安全组，它的「攻击面」是一个很难用传统方法描述的概念。

CloudGoat 中涉及 Serverless 的场景，重点演示三类问题：

* **执行角色权限过宽**

  ：每个 Lambda 都挂着一个 IAM 角色，开发者常图省事直接给管理员权限，而这个角色的影响范围往往远超函数本身的业务需要。
* **触发器配置不当**

  ：公开的 API 网关触发器意味着任何人都能调用函数逻辑，哪怕函数内部有校验，校验失败时的错误信息也可能泄露内部结构。
* **环境变量与代码包泄露**

  ：密钥写在环境变量里看似安全，但只要有任何一处能读到进程环境或调试输出的能力，所有密钥一起曝光。

无服务器安全的核心原则是**「假设函数一定会被任意人调用」**，在函数入口做完整的鉴权与输入校验，并把执行角色权限压缩到该函数真正需要的最小集合。这是「默认拒绝」原则在云上的直接落地。

## 10攻击链总览：从一台机器到整个账号

把前面四个实战串起来，你会看到一条非常典型的云上攻击链。它的可怕之处在于**每一步都是合法的云 API 调用**：

1. **入口**

   ：Web 应用存在 SSRF 或 RCE，攻击者获得服务端请求能力。
2. **凭据获取**

   ：通过 IMDS 拿到实例角色临时凭据。
3. **身份枚举**

   ：用该身份遍历自己可访问的 S3、SQS、Lambda、EC2 等资源。
4. **数据发现**

   ：发现公开桶中的敏感文件或内部配置。
5. **权限提升**

   ：发现可修改 IAM 策略的权限，实现自我提权。
6. **持久化**

   ：创建新的访问密钥或部署后门函数。
7. **横向与破坏**

   ：获取更高权限主体，控制更多云资源。
