第1章 “实现安全治理的原则和策略”笔记

1.1 安全101

这个101主要是建立**信息安全的核心底层认知的。**

安全应被视为业务管理的一个要素，是一种业务管理工具。

IT只是执行安全措施的技术手段，但安全决策的出发点必须是业务目标和业务风险。

IT/IS是业务的手脚，安全是业务的管理工具

安全的重要性最终体现在：保护组织的生存能力和业务连续性。

应该采用安全框架来为安全的实现提供一个起点（a starting point）。

启动安全后，则通过评估来微调安全。基本的方法就是风险评估、漏扫+渗透了。

安全应具有成本效益。安全是一段旅程，没有终点线。

**1.2 理解和应用安全概念

安全管理概念和原则不是空理论。概念与原则 → 指导安全策略 → 落地为安全解决方案。

CIA 三元组是安全工作的总纲——保密、防篡改、保可用。几乎所有安全控制措施，最终都可以归结为在保护这三个目标。

1.2.1 保密性

好的保密性控制不是“一刀切禁止访问”，而是：该看的能看，不该看的看不了。安全不是追求零风险，而是“风险权衡”。

先判断敏感性 → 再看关键性 → 用判断力决定要不要披露 → 如果决定不披露，用隐藏/保密/隔绝/隔离来保护 → 涉及个人信息时，还要考虑隐私。

机密性是一个需要“设计”的东西，不是一个可以“买来”的东西。 你得先想清楚要什么，再去选工具，而不是反过来。**因为实现一种机密性的工具和技术，可能不支持、甚至不允许另一种机密性。**

**1.2.2 完整性**

完整性就是：数据自己内部不矛盾（内部一致性），和外部现实及其他系统对得上（外部一致性），能真实反映现实世界，并且任何关联关系都有效、一致、可验证。

最大的完整性威胁，往往来自内部，来自日常操作，来自管理和配置的疏忽。

****1.2.3 可用性

可用性 = 合法用户能及时、不间断地访问，并靠冗余、备份、监控、防DoS和BCP来消除单点故障，同时它依赖完整性和保密性，还要求好用、可访问、低延迟。

1.2.4 DAD 、过度保护、真实性、不可否认性和AAA服务****

CIA是目标，DAD是反面，过度保护是陷阱，真实性/不可否认性/AAA是补充和落地手段。

1.2.5 保护机制

主要就是讲了纵深防御、抽象、数据隐藏、数据加密。

安全的目标不是“绝对防止”，而是“提高攻击者的成本，直到他不划算”。

纵深防御：**假设每一层都会失败，所以要让各层独立，且失败方式不同。**

**抽象：把风险藏起来了，也把风险的责任转移了。每一层抽象，都是一次信任的让渡。**

所有机制都建立在信任假设上，而安全本身永远是权衡，不是最优解。

1.3 安全边界

安全边界就是“控制起止、信任切换、责任转移”的那个点，必须清晰定义、物理和逻辑分开做、以边界为单位部署纵深防御。

1.4 评估和应用安全治理原则

安全治理的本质，是让安全成为业务的一部分，而不是业务的对手；是建立一套“谁负责、依据什么、如何对齐业务”的框架，而不是堆砌技术控制。

安全治理的目标，不是“安全本身”，而是“让业务能安全地维持、增长、扛住打击”。

安全治理 = 定义安全方向 + 指导安全执行 + 评估安全效果 + 提供资源支持，这一整套实践的集合。

它的核心不是“做技术”，而是“管方向、管责任、管资源、管效果”。

安全治理理想上由董事会做，小组织可由 CEO 或 CISO 代行；但无论谁做，治理都是“定方向、配资源、评效果”的高层职责，不是日常安全管理。

审计和验证要求来自政府法规和行业最佳实践；跨国经营时，不同国家法律可能不一致甚至冲突，这是最大的合规难题。项目组自己搞不定，组织层面必须统一给方向、指导和工具，目标是业务不停、损失最小。

安全是业务问题，全组织都要管——建流程、定责任、做评估。

1.4.1 第三方治理

分两个方向：外部监督你，你监督别人。

外部监督你：一定有外部的人来查你。合规项目里，第三方审计是必选项，标准是外部定的。审计员代表谁，决定你该怎么配合。第三方治理是尽职关怀的证据。第三方治理是成本，也是门槛。

你监督别人：**第三方的风险，不会停在第三方那里，会沿着依赖关系传导给你。**

现场评估要亲自去看、按规范执行、带检查清单；文档交换要双方充分开放，组织要知道全部要求、提交安全策略和自评估报告，目的是对齐认知、减少未知要求和不切实际期望；交材料不是终点，评审才是重点。

1.4.2 文件审查

文档评审是“筛选器”。文档不过关，现场评审就没意义；文档过关，现场评审才有明确焦点。

|  |  |
| --- | --- |
| **对照什么审？** | **标准、框架、合同义务** |
| **审什么？** | **业务流程和组织策略** |
| **审什么维度？** | **逻辑上是否成立、实务上是否可行** |
| **审的目的是什么？** | **确保实用、高效、成本合理** |
| **最核心的目的是什么？** | **支持安全目标：减少脆弱性、管理风险** |
| **用什么方法审？** | **风险管理、风险评估、风险处置** |

1.5 管理安全功能

安全是业务的一部分，必须靠治理来管；管理的抓手是风险评估驱动策略，证明有效要靠指标度量；最终落脚点，是信息安全战略的开发和实施。

1.5.1 与业务战略、目标、使命和宗旨相一致的安全功能

安全管理计划就是“怎么把安全管好”的整体打法。它要求安全必须对齐业务目标，考虑预算和资源现实，用“业务论证”来证明项目值得做；在落地时，必须采用“自上而下”的方法——高层定策略，中层定标准，技术人员落实配置，最终用户遵守。而“自下而上”（IT自己说了算）是行不通的。

策略开发团队要教育高层：安全措施做了，风险也不会归零。

1.5.2 组织的流程

**安全不是IT部门的“家事”，而是董事会的“国事”**。“收购”和“剥离”都会让风险飙升，安全治理必须强势介入，如资产被“退役”时，要删除和销毁存储介质，因为介质净化处理技术不能保证残留数据不会被恢复。人员离职时，**审查保密协议（NDA），做****法律意义上的“最后警告”和“权利重申”**。

所有这些动作，都不是IT能干的。

——在考虑兼并／收购成本时，重要的是考虑产品部署的整个生命周期内的总成本，而不只是考虑初始购买和实施费用。

这一节是在教我们怎么做“安全界的婚前财产公证和女婿背景调查”——结婚（收购）前不仅要查对方有没有欠债（漏洞），还要签好协议（SLA）规定出轨了怎么赔（赔偿条款），并且买房装修的钱（总成本）不能只图便宜，要看未来70年住得安不安全。最后别忘了，家里管钱的账本（数据分类）和拆墙装修的审批单（变更控制）自己也要管好。

1.5.3 组织的角色与责任

把角色定义清楚，就能分清谁最终背责（liability）、谁具体干活（responsibility），以及谁向谁汇报、什么活可以往下委托。

**高级管理者：安全最终由高级管理者负责。没有高级管理者的授权和支持，安全政策就是一张废纸。

安全专业人员：实施者，不制定决策。

资产所有者：高级管理层，对特定资产负责。

托管人：执行具体保护措施。

用户：最小权限，遵守政策。

审计人员：查、验证、出报告。不负责实施，不负责整改。**

**1.5.4 安全控制框架

**安全规划的第一步：选一个安全控制框架。**

**COBIT = 一套 IT 治理和管理的框架，帮你把安全和业务对齐。**

| 框架 | 来源 | 侧重点 | 适用场景 |
| --- | --- | --- | --- |
| **COBIT** | ISACA | IT 治理与管理 | 需要 IT 治理框架、审计标尺的组织 |
| **ISO 27001** | ISO | 信息安全管理体系 | 想建 ISMS、拿认证的组织 |
| **ISO 27002** | ISO | 安全控制实践指南 | 配合 27001，提供控制清单 |
| **NIST CSF** | NIST（美国） | 网络安全框架 | 想快速建体系、按五功能落地 |
| **NIST SP 800-53** | NIST（美国） | 安全控制目录 | 政府、军工、需要详细控制清单 |
| **NIST SP 800-100** | NIST（美国） | 安全治理指南 | 管理者建治理体系 |
| **PCI DSS** | PCI 安全标准委员会 | 支付卡数据安全 | 涉及支付卡业务的组织 |
| **等保 2.0** | 中国 | 网络安全等级保护 | 中国境内运营的组织 |
| **GDPR** | 欧盟 | 个人数据保护 | 涉及欧盟用户数据的组织 |

## ****1.6 安全策略、标准、程序和指南******

**安全是业务的一部分，要一直做。为了少出事，把安全写成一套分层文档：策略、标准、流程、指南。四层都写、都落地，安全基础设施就扎实了。**

1.6.1 安全策略

**安全策略是最高层的安全文档，定义组织需要什么安全、保护什么资产、达到什么程度。它是强制性的，是标准、基线、指南、程序的源头。组织级、特定问题、特定系统，是它的三种类型。**

****系统级策略关注具体系统，规定硬件软件、加固方法和安全控制。策略是宏观源头，标准、基线、指南、程序从它衍生，越来越具体。标准是策略之下的下一层级。****

1.6.2 安全标准、基线和指南

安全标准就是"必须统一这么做"，安全基线就是"每个系统至少得达到这条底线，不达标不准上线"，安全指南就是"建议你这么做，但不强制、可以灵活调整"。

1.6.3 安全程序

安全程序是安全策略文档体系最底层、最具体、需随系统更新而持续维护的分步操作文档，整个体系呈"顶层少、下层多"结构，分开管理便于按需知悉和局部更新，文档越完整越能支撑决策、培训、响应和预测。**

1.7 威胁建模

这里突然让我意识到，原来我们现在项目中做的源代码审查、渗透测试内核都是威胁建模。但这个属于被动式威胁建模——威胁狩猎，也被称为对抗性方法。

而在系统开发的早期阶段进行防御式威胁建模才是成本效益更高的方式。

1.7.1 识别威胁

威胁建模的最终目标是对危害组织有价值资产的潜在威胁进行优先级排序。

1. STRIDE：STRIDE 是微软提出的六类安全威胁分类法：**S**poofing（假冒身份）、**T**ampering（篡改数据）、**R**epudiation（抵赖）、**I**nformation disclosure（信息泄露）、**D**enial of service（拒绝服务）、**E**levation of privilege（权限提升）。

2. PASTA：七阶段、以风险为中心、系统化偏重，适合关键系统深入分析。

**3. VAST**：可视化、敏捷、简单，适合快速迭代的开发环境。

1.7.2 确定和绘制潜在的攻击

**威胁建模的这一步，是先画出系统的组件图、数据流和权限边界（复杂系统可多画几张、分层放大），再识别图中每个元素涉及的技术和可能遭受的攻击（逻辑/技术、物理、社会工程都要考虑），为下一步简化分析做准备。**

1.7.3 执行简化分析

简化分析（即分解应用程序/系统/环境）就是把产品拆成更小的单元，弄清各单元的输入、处理、存储、输出和交互，并重点识别五个关键概念——信任边界、数据流路径、输入点、特权操作、安全声明/假设——从而更容易发现脆弱性和攻击点，再完整记录每个威胁的手段、目标和后果。

1.7.4 优先级排序和响应

有以下几个方法：概率＊潜在损失”排序、高／中／低评级或 DREAD 系统。

1.8 将基于风险的管理理念应用到供应链

这里主要理解SLR和SLA的区别。

**SLR 是“安全需求”（Security Requirements，要做什么），SLA 是“服务级别协议”（Service Level Agreement，承诺做到什么水平）——前者是需求定义，后者是对外/对内的服务水平承诺。**

1.9 本章小结

一个组织的安全，不是靠买几个安全设备堆出来的，而是靠一套自上而下的治理体系“管”出来的。

安全必须由管理层驱动，从上往下推。如果从下往上推，没有管理层支持，安全做不成。

安全是一个自上而下的治理体系：管理层定方向（治理/政策），用 CIA 定目标，用标识/认证/授权/审计/加密等机制做控制，明确角色责任，通过五层策略结构落地，用威胁建模预判风险，并把供应链和采购也纳入风险管理。
