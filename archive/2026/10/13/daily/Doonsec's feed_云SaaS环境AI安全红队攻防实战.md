## 一、概述与威胁景观

### 1.1 云/SaaS AI 应用的架构演进

现代云/SaaS AI 应用的架构经历了从简单到复杂的演进过程，每一层架构演进都引入了新的攻击面。

**第一代：API 调用模式**。应用通过调用 LLM API（如 OpenAI API）实现智能功能。架构简单，攻击面主要在 API 调用层——提示注入、API 密钥泄露、速率限制绕过。

**第二代：RAG 增强模式**。应用引入检索增强生成，从向量数据库检索相关文档增强 LLM 上下文。攻击面扩展到向量数据库层——数据投毒、嵌入反转、访问控制绕过。

**第三代：Agent 自主模式**。应用使用 LLM Agent 自主调用工具、执行操作、编排多步任务。攻击面显著扩展——工具滥用、权限提升、递归消耗、横向移动。

**第四代：多 Agent 协作模式**。多个 Agent 协作完成复杂任务，Agent 间通过消息传递协调。攻击面进一步扩展——Agent 间注入、信任链攻击、级联失败。

每一代架构的攻击面增长不是线性的而是**超线性的**——新组件不仅自身成为攻击面，还与已有组件产生新的交互攻击面。形式化地，若系统有  个组件，攻击面大小约为 （考虑组件间交互），而非 。

### 1.2 云/SaaS AI 的分层架构

```
┌─────────────────────────────────────────────────────┐
│                    前端应用                          │
│              (Web/Mobile/Chat UI)                    │
├─────────────────────────────────────────────────────┤
│                  API 网关层                          │
│          (认证/限流/路由/审计)                        │
├──────────┬──────────┬──────────┬───────────────────┤
│ LLM API  │ Agent    │ RAG      │ 模型托管          │
│ 服务     │ 平台     │ 服务     │ (HF/Replicate)    │
├──────────┴──────────┴──────────┴───────────────────┤
│              云基础设施层                            │
│  (IAM/VPC/K8s/对象存储/密钥管理/元数据服务)          │
├─────────────────────────────────────────────────────┤
│              数据层                                 │
│  (向量DB/关系DB/文档DB/消息队列)                     │
└─────────────────────────────────────────────────────┘
```

每一层都有独特的威胁模型和攻击面：

* **前端层**：XSS、CSRF、客户端注入
* **API 网关层**：认证绕过、限流规避、路由劫持
* **AI 服务层**：提示注入、Agent 滥用、RAG 投毒、模型供应链
* **基础设施层**：IAM 提权、网络横向、容器逃逸、元数据服务滥用
* **数据层**：数据泄露、SQL/NoSQL 注入、向量数据库攻击

### 1.3 威胁模型分类

云/SaaS AI 环境的威胁模型比传统应用更复杂，攻击者可以位于架构的不同层级：

| 攻击者位置 | 能力 | 典型场景 | 影响范围 |
| --- | --- | --- | --- |
| 外部用户 | API 调用、文件上传 | 通过输入注入攻击 | 单租户 |
| 同租户用户 | 共享资源访问 | 跨租户数据泄露 | 多租户 |
| 内部员工 | 内部 API、管理接口 | 内部威胁、配置错误 | 全系统 |
| 云平台管理员 | 基础设施控制 | 云平台威胁 | 多租户 |
| 供应链攻击者 | 模型/依赖控制 | 供应链投毒 | 全用户 |

**多租户隔离的挑战**：SaaS 应用通常是多租户的，租户间隔离是核心安全属性。但 AI 应用的多租户隔离面临独特挑战——模型推理的共享资源（GPU、模型权重）、向量数据库的共享索引、Agent 的共享工具集都可能成为跨租户泄露的载体。

### 1.4 红队测试的必要性

传统安全测试（自动化扫描、合规审计）难以覆盖 AI 应用的独特攻击面。红队测试通过模拟真实攻击者的思维和行为，发现自动化工具无法检测的复杂攻击链。在 AI 安全领域，红队测试的必要性体现在：

* **攻击空间的不可枚举性**：AI 攻击空间是连续的语义空间，无法穷举扫描
* **攻击链的组合性**：单个漏洞影响有限，组合攻击链影响严重，需要红队思维发现组合
* **上下文依赖性**：同一漏洞在不同上下文中影响不同，需要红队评估上下文影响
* **概率性漏洞**：AI 漏洞是概率性的，需要多次尝试和创造性方法触发

## 二、云安全模型的理论基础

> **跨档引用**：信任边界、信息流控制、零信任架构、多租户隔离形式化详见高级篇09《架构安全的理论基础》；形式化验证与可证明安全框架详见高级篇10。本节聚焦于**AI SaaS特有的共享责任模型、责任边界模糊性、KV缓存隔离挑战、云原生AI攻击面扩展**，这些是高级篇通用架构理论未覆盖的云SaaS特化内容。

### 2.1 共享责任模型的形式化

云安全的共享责任模型定义了云提供商和客户各自负责的安全范围。形式化地，系统安全属性集  被划分为提供商责任  和客户责任 ：

系统整体安全要求双方各自履行责任：

**AI SaaS 的共享责任复杂性**：AI SaaS 引入了传统 SaaS 不存在的责任维度：

| 责任维度 | IaaS | PaaS | AI SaaS | AI PaaS |
| --- | --- | --- | --- | --- |
| 基础设施安全 | 提供商 | 提供商 | 提供商 | 提供商 |
| 应用安全 | 客户 | 共享 | 共享 | 共享 |
| 模型安全 | N/A | N/A | 提供商 | 共享 |
| 训练数据安全 | N/A | N/A | N/A | 客户 |
| 提示/输入安全 | N/A | N/A | 客户 | 客户 |
| 输出处理安全 | N/A | N/A | 客户 | 客户 |

**责任边界的模糊性**：AI SaaS 的责任边界存在模糊区域——模型行为由提供商的训练和客户的提示共同决定，安全责任难以明确划分。如提示注入攻击：载荷由客户提供（客户责任），但模型的抗注入能力由提供商训练（提供商责任），攻击成功是两者共同作用的结果。

### 2.2 信任边界与信息流

云/SaaS AI 应用的安全依赖于正确识别和实施信任边界。

**信任边界**：信任边界是系统中不同信任级别之间的分界线。信息穿越信任边界时需要验证和净化。云/SaaS AI 应用的信任边界包括：

* **用户-应用边界**：用户输入到应用，需要输入验证
* **应用-LLM 边界**：应用构造的提示到 LLM，需要指令-数据分离
* **LLM-工具边界**：LLM 输出到工具执行，需要输出验证和权限控制
* **应用-云服务边界**：应用到云服务调用，需要认证和授权
* **租户-租户边界**：多租户间的逻辑隔离，需要数据隔离

**信息流控制**：每个信任边界都应实施信息流控制——确保信息只沿允许的方向流动，且穿越边界时经过适当的净化。形式化地，对于信任边界  和信息流 ：

**AI 应用中信息流的特殊性**：传统应用的信息流是结构化的（API 参数、数据库查询），可以精确控制。AI 应用的信息流是**语义化的**——LLM 将多条信息融合为语义表示，信息流控制需要在语义层面实施，远比结构化控制困难。

### 2.3 多租户隔离的理论要求

多租户隔离是 SaaS 安全的核心属性，要求一个租户的操作不影响其他租户的数据或行为。

**隔离的形式化定义**：给定租户集合  和系统状态 ，隔离要求对任意租户  的操作 ：

即  的操作对  的数据无影响。

**隔离级别**：

| 级别 | 机制 | 保证 | AI 应用适用性 |
| --- | --- | --- | --- |
| 物理隔离 | 独立硬件 | 最强 | 成本过高，仅用于高安全场景 |
| 虚拟隔离 | 独立 VM/容器 | 强 | 适用于模型推理隔离 |
| 逻辑隔离 | 共享资源+访问控制 | 中 | 适用于数据层隔离 |
| 语义隔离 | 共享模型+提示隔离 | 弱 | 当前多数 AI SaaS 的实际状态 |

**AI 多租户隔离的挑战**：

* **模型共享**：多租户共享同一模型实例，模型内部状态（KV 缓存、注意力）可能泄露跨租户信息
* **上下文泄露**：若上下文处理不当，一个租户的上下文可能影响另一租户的推理（"上下文串扰"）
* **侧信道**：推理延迟、输出分布等侧信道可能泄露跨租户信息
* **向量数据库共享**：共享向量索引可能导致跨租户检索

**KV 缓存泄露**：LLM 推理的 KV 缓存存储了先前 token 的注意力键值对。若多租户共享推理实例且 KV 缓存未正确隔离，一个租户的推理可能访问到另一租户的缓存数据。这是 AI SaaS 特有的隔离风险，传统 SaaS 不存在。

### 2.4 云原生 AI 的攻击面扩展

云原生技术（容器、微服务、Serverless）与 AI 的结合引入了新的攻击面。

**容器化 AI 的攻击面**：

* **模型容器逃逸**：若模型在容器中运行且容器配置不当，攻击者可能逃逸到宿主机
* **模型镜像投毒**：AI 模型容器镜像可能被投毒，包含恶意模型或后门
* **GPU 共享侧信道**：多租户共享 GPU 时，可能通过 GPU 侧信道泄露信息

**Serverless AI 的攻击面**：

* **冷启动信息泄露**：Serverless 函数的冷启动可能保留前一次调用的状态
* **事件源注入**：触发 Serverless AI 函数的事件源（如 S3 事件、API Gateway）可能被注入
* **并发限制绕过**：Serverless 的并发限制可能被绕过导致资源耗尽

**微服务 AI 的攻击面**：

* **服务间注入传播**：微服务架构中，注入载荷可以通过服务间调用传播
* **API 网关绕过**：若微服务直接暴露（未通过 API 网关），可能绕过网关的安全控制
* **服务发现攻击**：攻击者可能通过服务发现机制访问未授权的 AI 服务
