Sony cameras (e.g. ILCE-7CM2) write HIF files whose `colr` nclx box declares limited range while the HEVC SPS VUI says `video_full_range_flag=1`, and the samples are full range. `colorInfo` lets nclx replace the VUI whole, which is right per the spec, so these decode with expanded range: crushed blacks and clipped highlights.

libheif hits the same files and handles them with an opt-in `--auto-correct`. Its own warning on one of them:

```
colr box NCLX (1/13/5/limited) disagrees with bitstream signalling (1/13/5/full)
Autocorrecting full-range flag to ON (colr=limited, bitstream=full)
```

This adds `Options.AutoCorrect` to do the same:

* Only the limited-colr / full-bitstream mismatch is corrected. Default off, so spec behaviour is unchanged.
* `ColorInfo.FullRange` reports the range actually used, so callers can see when it applied.
* Callers can't fix this after decoding: above 8 bits the output is NRGBA64, already converted with the wrong range.

On an A7C II HIF, mean luma (8-bit) is:

| decode | mean luma |
| --- | --- |
| `heic.DecodeColor` | 15.1 |
| `heic.DecodeColor` with `AutoCorrect` | 27.9 |
| `heif-convert --auto-correct` | 27.9 |

The encoder doesn't write a VUI, so I couldn't build a synthetic end-to-end fixture. The test is a `TestColorInfoPrecedence` case covering correction on, off, a limited bitstream and a nil picture. `go test ./...` passes.
