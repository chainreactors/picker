Password credentials listed RC4 ahead of AES in get\_supported\_enctypes, so get\_preferred\_enctype selected RC4 for pre-auth and the KDC issued an RC4 TGT session key even when AES was available. On top of that, get\_TGS offered [kerberos\_cipher\_type, 23] -- copying the TGT session-key etype into the service-ticket request -- and S4U2self/S4U2proxy/dmsa/U2U did the same (U2U hardcoded [23]). The result: service tickets were requested with RC4 even for AES-capable hosts, and failed against RC4-disabled DCs (asyauth#19).

Changes:

* creds.py: order password enctypes AES256, AES128, RC4, DES (preference).
* get\_TGS / S4U2self / S4U2proxy / dmsa / U2U (sync + async): request [18, 17, 23] instead of the TGT session-key etype. The service ticket's session-key etype is independent of the TGT's; the KDC picks a supported one, AES preferred.
* Drop now-dead supp\_enc computations that could raise spuriously.

Tests:

* test\_credential.py: assert password prefers AES256 over RC4.
* test\_tgs\_checksum.py: expect the [18, 17, 23] request list.
* test\_kdc\_live\_windows.py: env-gated live Windows/GOAD integration tests covering TGT, get\_TGS, RC4-TGT->AES ticket, ccache and U2U, skipped when no DC is reachable.
