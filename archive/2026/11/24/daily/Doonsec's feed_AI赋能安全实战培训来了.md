AI赋能安全实战：从挖SRC、攻防演练到应急响应，我把AI用进了这四个环节

攻防演练+SRC的复盘。没有“一键日站”，只有真实的时间账、踩过的坑，和留下来的工具。

开篇：先说结论

过去一年，“AI 赋能安全”被说了太多遍。有人把它当万能钥匙，有人觉得它是高级玩具。我们不想讨论概念，只想把一次授权攻防演练里真实发生的事摊开：哪些环节 AI 真的省了时间，哪些环节它差点把我们带沟里，哪些环节离开人它什么都不是。

先给结论：AI 没有让我们“一键日站”。它真正改变的，是把人的时间从“找线索”挪到了“做判断”。这两件事的价值，差一个数量级。

一次演练里，我们面对三百多个前端 JS 文件、七百多个接口、五百多条可测路径。人工逐个读，短时间内读不完；人工逐个请求，既慢又容易触发 WAF。最后真正起作用的，是一套**“AI 负责铺开、人负责收敛”**的工作方式。

下面按四个环节讲：挖 SRC / 渗透、开发小工具、应急响应、代码审计。每一段都有真实过程，也有真实的坑。

· · ·

一、AI 挖 SRC：它最强的不是“打”，是“读”和“收”

▍先纠正一个期待

很多人对“AI 渗透”的想象是：输入一个域名，AI 自动打穿。

真实情况是：AI 不擅长“灵光一现地打进去”，它擅长三件事——

* **读得多：**

  几百个 JS 文件、几千行混淆代码，它可以不知疲倦地逐段解释；
* **铺得开：**

  把资产、接口、参数、调用关系一次性摊平，不漏；
* **写得快：**

  把验证思路变成可执行的脚本，把结果整理成可复现的报告。

而“这个点值不值得追”“这个 200 是不是假阳性”“这条链能不能写进报告”，仍然是人来做。

▍真实过程：从三百个 JS 到一个加密链路

目标是一个业务系统的 Web 端。打开首页，几乎看不到明文接口，所有业务响应都是密文。

如果按老办法，安全工程师会打开工具，一个一个看请求，猜加密方式。这个过程很慢，而且容易漏。我们换了个顺序：

**第一步，让 AI 帮忙“摊平资产”。**用浏览器把页面真实加载一遍，记录所有请求；再把主包和懒加载 chunk 全部抓下来。这里有个细节：很多系统的主包会暴露 chunk 映射表，顺着映射表可以把动态加载的文件枚举完整。最后拿到三百多个 JS 文件。

然后写一个基于 AST 的提取脚本，把代码里的接口路径、请求方法、参数字段、外部域名全部抽出来。AI 在这里做的是“解释和归类”：哪些是业务接口，哪些是静态资源，哪些是第三方 SDK，哪些只是错误提示文案。

结果：七百多个接口、一百多条路由、几十个外部地址，一张表摊开。

**第二步，让 AI 顺着“加密”这条线做代码考古。**全站加密的系统，密钥一定在某个地方。人读混淆代码很痛苦，AI 读起来快得多。我们把关键文件切片喂给它，让它回答三个问题：响应是怎么加密的，算法、模式、填充分别是什么？密钥从哪里来，是硬编码、接口下发，还是本地派生？解密发生在哪个函数，调用链是什么？

顺着这条线，问题很快就出来了：

* 前端 JS 里硬编码了一组“包装密钥”，用来解密密钥接口的返回值；
* 密钥接口本身不需要任何登录态，谁都能取；
* 解出来的主密钥是明文十六进制；
* IV 由另一个接口下发，而那个接口同样不校验身份，甚至不校验签名参数。

也就是说，这套“全站加密”只防了明文抓包，没有形成任何访问控制。攻击者不需要账号，就能把加密响应还原成明文。

这不是 AI “猜”出来的，是 AI 把散落在几个文件里的常量、函数和调用关系拼到了一起。人会做同样的推理，但需要更长时间，也更容易在第三个文件时放弃。

**第三步，让 AI 生成验证脚本，但由人来定边界。**验证阶段我们给自己定了规矩：只读、低速率、不做写入、不批量拉取真实数据。

AI 根据前面的分析，生成了一个带自动加解密的 HTTP 客户端：请求前加密参数，响应后自动解密。原本需要手工复制的密文，现在一条命令就能看到明文。

然后对五百多条可测路径做未授权访问验证。结果里有二十多条返回 200，其中一部分是公开配置，另一部分确实返回了不该给未登录用户看的数据。我们只把“无凭证 + 返回真实业务数据”的那几条写进报告，公开的协议文本、银行字典、菜单配置，一律不算漏洞。

这一步最值钱的不是“扫出了多少条”，而是“每条都有明文证据、有请求、有响应、有复现步骤”。

▍真实的坑：WAF 制造的“假阴性”

演练中有一个必须讲的教训。

目标有 WAF。在高频请求之后，我们的出口 IP 被临时封禁，所有路径都返回 403，包括首页和 favicon。

如果这个时候让 AI 直接总结，它会很自然地写出一句：

“对四百多个接口进行未授权测试，均返回 403，接口鉴权有效。”

这句话是错的，而且错得很危险。

全站 403、连静态资源都 403，更像是 IP 级封禁，而不是“每个接口都做了鉴权”。正确的动作是：停止请求、保存拦截页和响应头、换出口或等待冷却、降低速率后用小样本复测。

我们最后在报告里明确写了：这批 403 是假阴性，不能作为“接口受保护”的结论。

AI 能帮你把证据摆齐、把时间线对齐，但“这是不是假阴性”的判断，必须由人做。这也是我在反复强调的一句话：

AI 可以提高你的覆盖度，但不能替你承担结论的责任。

▍给 SRC 选手的三个实用建议

如果你用 AI 辅助挖 SRC，这三条能少走很多弯路：

**第一，先让 AI 读 scope，再让它动手。**把项目的授权范围、禁止行为、收录标准贴给它，让它先输出一份“测试计划”和“越界风险清单”。很多事故不是技术问题，是边界问题。

**第二，让 AI 帮你查重，而不是帮你吹危害。**它可以读公开披露、历史报告、同类漏洞的收录情况，帮你判断这个点是不是“别人早报过”。但它很容易把“可能”写成“可导致 RCE”，这类夸大必须由人删掉。SRC 最反感的就是无法复现的危害描述。

**第三，负向结论也要写。**哪些方向测过、怎么测的、为什么排除，这些内容 AI 整理起来很快。一份可信的报告，不只是“我挖到了什么”，还包括“我确认了什么不是漏洞”。

二、AI 造工具：把一次性分析变成可复用能力

▍为什么一定要造工具

演练里最浪费时间的，不是“想不出漏洞”，而是“重复劳动”：

* 每次请求都要手工加密、手工解密；
* 每次扫接口都要重新拼 URL、带 Header；
* 每次出报告都要重新整理证据、算哈希、写索引；
* 每次换一个目标，前面写的脚本全作废。

AI 写代码很快，但“快”不是重点。重点是把一次性的分析，沉淀成下一次还能用的工具。

还有一个前提：先看有没有现成的，再让 AI 造。目录扫描、端口探测、AST 解析、HTTP 客户端，开源社区都有成熟实现。AI 最适合做的是“胶水”——把现成工具的输出接起来，适配这个目标的加密方式、鉴权头、分页规则。上来就让 AI 从零写一个扫描器，通常是在重复造一个更差的轮子。

▍我们真实留下的四类小工具

1. **第一类：协议客户端。**

   前面说的自动加解密客户端，就是这个思路。它把“密钥协商 → 请求加密 → 响应解密”封装成一个函数，上层只管调接口。这类工具的关键不是代码量，而是可验证。我们用它跑了一组已知明文的回归：同一段密文解出来必须和预期一致，否则直接报错。没有回归验证的“解密工具”，很容易在换环境后悄悄解出乱码，然后让你得出错误结论。
2. **第二类：资产与接口提取器。**

   基于 AST，把 JS 里的接口、方法、参数、调用点抽成结构化数据。它的价值在于“可重复”：换一个目标，改一下入口，几分钟就能重新跑一遍。我们在一次演练里用它抽出了七百多个接口。人工做同样的事，不是做不到，是无法保证不漏。
3. **第三类：证据固化器。**

   每个关键请求和响应都落盘，记录时间、状态码、响应头、正文哈希，最后生成一份清单。这东西看起来不“智能”，但在真实项目里极其重要。报告里的每一条结论，都要能回到原始证据。AI 可以帮你写索引、算哈希、检查文件是否齐全，但“证据链完整”这个标准，是人定的。
4. **第四类：报告与复核器。**

   把发现按“已确认 / 待验证 / 已排除”三档整理，自动检查每条发现是否具备：请求、响应、复现步骤、影响说明、修复建议。AI 很适合做这种“格式警察”。它不会替你想漏洞，但会提醒你：“这条发现缺响应证据”“这条影响描述和实际数据对不上”。

▍让 AI 写工具的正确姿势

很多人让 AI 写工具，得到的是一段“看起来能跑”的代码。要让它真的能用，提示词里必须包含四件事：

1. **（1）验收标准。**

   不要只说“写一个扫描器”，要说“输入是什么、输出是什么、什么情况下必须报错、什么情况下必须停止”。
2. **（2）失败行为。**

   明确要求：遇到 403 停止并落盘，不要重试到被封；遇到解密失败保留原始密文；遇到超时记录并继续，不要静默吞异常。
3. **（3）安全默认值。**

   默认单线程或低并发、默认只读、默认不跟随跳转、默认不写入目标。这些不是“优化项”，是“不惹事”的底线。
4. **（4）可回归的样例。**

   给它一组已知输入和期望输出，让它自己写测试。没有测试的工具，下一次用的时候你不敢信。

一个真实的感受：AI 写工具，三十分钟能跑起来；但要让它“可信”，往往还要再花两小时做回归、加限速、补异常。**这两小时不能省。**省了，工具就会在关键时刻给你一个错误的答案。

三、AI 应急响应：先保命，再保证据，最后才是“智能”

▍应急现场，AI 最不该做的事

先泼一盆冷水。

应急响应不是“让 AI 自动处置”。真实环境里，一条错误的隔离命令、一次误封的生产 IP、一个被覆盖的日志文件，造成的损失可能比攻击本身还大。

所以在应急场景，我们给 AI 划了三条红线：

* **不自动执行破坏性操作。**

  隔离、封禁、杀进程、改配置，AI 可以写脚本，但必须人审核、人执行。
* **不把推测当结论。**

  “可能是横向移动”和“确认横向移动”是两回事，报告里必须分开写。
* **不把敏感日志贴到公网模型。**

  日志里有内网地址、账号、令牌、客户信息。要么脱敏，要么用本地/私有化模型。

▍演练里的真实一幕：全站 403 到底是不是被打了

前面提到，演练中目标突然对所有请求返回 403。

当时的现场信息很混乱：扫描脚本在跑、WAF 在拦、部分接口本来就有鉴权、还有一堆 SPA 的 fallback 页面返回 200。

AI 在这里干的活，是把混乱的信息排成一条线：

* 把同一时间段的请求、响应码、响应体大小、拦截页特征对齐；
* 标出“哪些 403 是 WAF 拦截页，哪些是应用自己的 403”；
* 指出“连 favicon 都 403，且封禁持续超过冷却时间”这个异常；
* 给出验证假设：换一个不存在的路径、换一个静态资源，如果仍然 403，更像是 IP 级封禁。

最后人做的判断是：这是 IP 级临时封禁，不是每个接口都做了鉴权。之前的批量 403 结果全部作废，不能写进报告。

这个过程里，AI 没有做任何“处置”，它做的是降噪、对齐、提出可验证的假设。这三件事，恰好是应急现场最耗人力的部分。

▍企业应急响应的 AI 闭环

把视角从演练拉到日常企业应急，AI 真正能落地的，是下面这个闭环：

1. **第一步：告警降噪。**

   把几万条告警按资产、时间、行为、IOC 聚类，压成几十条“事件线”。AI 擅长做相似度归并和摘要，但聚类规则要人定，否则会把真正的高危告警合并掉。
2. **第二步：时间线重建。**

   从 EDR、防火墙、WAF、应用日志、账号日志里拉齐时间，找出空白点和矛盾点。AI 可以快速对齐不同格式的日志，标出“这个账号在 A 系统登录，却在 B 系统出现了不可能的时间差”。
3. **第三步：IOC 提取与狩猎。**

   从样本、告警、流量里提取域名、IP、哈希、UA、文件路径，生成排查清单。AI 可以帮你写狩猎脚本，但“哪些 IOC 值得全网排查”需要人判断，否则很容易把公开 CDN 地址当成恶意基础设施。
4. **第四步：影响面评估。**

   哪些资产中招、哪些账号失陷、哪些数据可能外泄。AI 可以根据日志和资产表做初筛，但“数据到底有没有被拿走”这种结论，必须靠流量、数据库审计和业务方确认。
5. **第五步：处置与复盘。**

   隔离脚本、封禁规则、取证清单，AI 可以起草；复盘报告的时间线、根因、改进项，AI 可以整理。但每一条处置动作，都要有人签字。

▍一个可直接套用的应急提示词框架

角色 / 输入 / 任务 / 约束

**角色：**你是企业应急响应分析师，只做分析和建议，不执行任何处置。

**输入：**以下是我提供的日志片段 / 告警 / 流量记录（已脱敏）。

**任务：**

1. 按时间顺序重建事件线，标出不确定的时间点；
2. 列出所有可验证的假设，每个假设给出验证方法；
3. 区分“已确认事实”与“推测”，不要混写；
4. 输出 IOC 清单，标注置信度；
5. 给出处置建议，按“立即 / 短期 / 长期”分级，并说明每条建议的风险。

**约束：**不要编造日志中不存在的字段；不要给出自动执行命令；信息不足时明确说“不足以判断”。

这个框架的核心不是“让 AI 更聪明”，而是逼它把“事实”和“猜测”分开。应急报告最怕的，就是两者混在一起。

四、AI 代码审计：别把整个仓库丢给它

▍为什么“整仓丢给 AI”效果差

把几万行代码直接塞给模型，通常会得到两种结果：

* **泛泛而谈：**

  “这里可能存在 SQL 注入，建议参数化查询”；
* **一本正经地胡说：**

  “第 1234 行存在反序列化漏洞”，打开一看是个常量定义。

不是模型不行，是上下文没组织好。代码审计需要的是**“数据流 + 鉴权边界 + 可达路径”**，不是“把代码读一遍”。

成熟团队的做法通常是三层：规则引擎先扫一遍（Semgrep、CodeQL 这类工具负责已知模式和危险函数），AST 把接口和调用关系摊平（解决“漏”的问题），AI 再做跨文件的数据流推理和语义解释（解决“看不懂”的问题）。三层各干各的活，比让 AI 从零读几万行代码靠谱得多。

▍我们真实用的四步法

**第一步：AST 先摊平，再让 AI 读。**

先用脚本把接口、参数、调用点、外部地址抽出来，形成结构化清单。AI 拿到的是“有边界的切片”，不是“一锅粥”。在一次前端审计里，我们用这个办法从三百多个 JS 文件里抽出了七百多个接口。哪些接口带 token、哪些接口走签名、哪些接口在路由守卫之外，一目了然。

**第二步：按切面审，不按文件审。**

把审计拆成五个切面，每次只让 AI 看一类问题：

* **鉴权切面：**

  哪些接口没有统一鉴权？哪些把权限判断放在客户端？
* **加密切面：**

  密钥从哪来？硬编码还是下发？签名到底校验了什么？
* **文件切面：**

  上传、下载、预览、导出，路径和权限是否可控？
* **跨域切面：**

  postMessage、iframe、CORS，有没有 origin 校验？
* **注入切面：**

  SQL、命令、模板、SSRF，参数有没有进入危险函数？

按切面审的好处是：AI 不容易跑偏，人也容易复核。

**第三步：每条发现必须给“三件套”。**

我们要求 AI 对每条候选发现输出：

* **位置：**

  文件 + 行号 + 函数名；
* **可达路径：**

  从入口到危险点，经过哪些函数、哪些判断；
* **反例：**

  什么情况下这个点不成立（有鉴权、有白名单、参数不可控）。

没有“反例”的发现，一律进“待验证”，不进报告。

**第四步：动态验证，人做最终判断。**

静态审计只能证明“代码看起来有问题”，不能证明“线上可利用”。所有高价值发现，都要回到真实请求里验证：无凭证能不能访问、换个 ID 能不能越权、签名乱填能不能过。

▍真实案例：三个值得复盘的发现

**案例一：签名校验只校验“有没有”，不校验“对不对”。**

代码里有一段逻辑：请求必须带 Signature 头，否则 401；但只要带了这个头，值是什么都行。AI 读代码时标出了这个分支，人做了一次实测：把签名改成任意字符串，请求正常进入业务层。这条最终成立，因为“有代码 + 有实测”。

**案例二：前端硬编码的“签名盐”。**

AI 在混淆代码里找到了一个 32 位字符串，被用于拼接签名。它一开始把这当成“高危密钥泄露”。人复核后发现：这个盐本来就设计成公开的，真正的问题不是“盐泄露”，而是“服务端只校验签名头存在”。同一个现象，错误的归因会写出完全不同的报告。

**案例三：AI 报了一堆“私钥泄露”。**

扫描结果里出现了 -----BEGIN RSA PRIVATE KEY-----。AI 很兴奋。打开一看，是前端加密库里的模板字符串，用来生成密钥对的示例代码，不是真实私钥。

类似的误报还有：把 localStorage 的键名 PASSWORD 当成口令、把地图服务的公开 AK 当成云凭证、把 SPA 的 fallback 200 当成“接口可访问”。这些误报如果直接进报告，轻则被打回，重则影响可信度。

▍审计提示词的关键：要求它“自证伪”

不要问 AI：“这里有没有漏洞？”

要问：

请分析这个函数是否存在越权风险

**要求：**

1. 先列出所有前置条件（鉴权、参数校验、白名单）；
2. 给出从外部入口到该函数的可达路径；
3. 如果存在风险，给出最小验证请求；
4. 如果不存在风险，说明哪个校验阻止了它；
5. 不确定的地方明确标注“需要动态验证”，不要下结论。

最后一句很重要。让 AI 学会说“不确定”，比让它学会说“有漏洞”更有价值。

五、AI 赋能的边界：三个不变，三个变化

▍三个不变

1. **第一，授权边界不变。**

   AI 不会替你获得授权。测试范围、禁止行为、数据处置方式，必须白纸黑字写清楚。本文所有案例都来自已获授权的攻防演练，且全程只读、低速率、未破坏业务数据。
2. **第二，人的判断不变。**

   AI 可以铺开线索，但不能替你判断“这是不是假阳性”“这条链能不能写”“这个风险要不要立刻上报”。越是高危场景，越需要人签字。
3. **第三，证据链不变。**

   报告里的每一条结论，都要能回到原始请求、响应、日志、代码位置。AI 可以帮你整理，但不能帮你“补”证据。
