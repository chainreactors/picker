> 模块一 · 安全能力重构365天 · 第2周 应用、API与数据基础

你排查登录问题时大概率见过这种场面：前端同学说“我明明带上 Cookie 了”，后端同学说“我这边 Session 里就是空的”，运维同学补一句“网关只透传了 Authorization，Cookie 没转发”。三方都没说谎，但四条链路——注册、登录、下单、支付——里总有一条在某个边界上把身份状态弄丢了。Cookie、Session和Token是什么关系，这个问题之所以反复被问，不是因为概念难，而是因为大部分人把它们当成三个可以互相替换的名词，而不是三件分别落在不同边界上的东西。

## 先把定位说清楚：它们是三层不同职责的机制

Cookie 是浏览器侧的存储与回传机制，属于传输载体；Session 是服务端侧的会话状态记录，属于状态存储；Token 是自包含的凭证格式，属于身份声明。三者不是并列关系，更不是版本迭代关系。

真正容易混淆的是把它们都叫“登录态”。登录态是一件事，怎么记住它、存在哪、怎么带回来、谁来验，是三件不同的事。Cookie 回答“怎么带”；Session 回答“服务端记在哪”；Token 回答“凭证本身能不能自证”。

这也决定了它们的失效方式完全不同：Cookie 过期是浏览器不再回传；Session 过期是服务端记录被清掉；Token 过期是签名里的时间字段失效。三种过期在日志里长得不一样，排查时如果混着看，就会得出“登录态不稳定”这种没法修结论。

## 核心矛盾：状态该放在链路的哪一侧

这组机制要解决的核心矛盾只有一个：HTTP 是无状态的，但业务需要连续识别同一个人。于是产生一个取舍——状态放客户端，还是放服务端。

放服务端（Session），好处是可控：能主动踢人、能改权限、能审计。代价是服务端要有存储，且在多实例部署时必须做共享存储或粘性会话，否则请求打到另一台机器就“不认识你”。

放客户端（Token），好处是无状态、易横向扩展、跨服务传递方便。代价是撤销困难：签发出去的 Token 在过期前天然有效，想让它立刻失效就得引入黑名单或短有效期加刷新机制，等于又把状态加回来了。

Cookie 在这个矛盾里是中立的：它只是把“服务端给的标识”或“客户端持有的凭证”在浏览器和服务器之间来回搬。问题往往不出在 Cookie 本身，而出在“谁负责写、谁负责读、中间谁可能不转发”。

## 拆开看四条链路：依赖、责任与异常影响

基于当前可见信息，用脱敏模拟场景把注册、登录、下单、支付四条链路过一遍，重点不是流程本身，而是每条链路上身份状态由谁负责。

注册链路通常只在最后一步建立会话，责任在应用服务；异常影响是“注册成功但未登录”，用户需要再登一次，属于可接受降级。

登录链路是身份状态的生产环节，责任最重：校验凭据、生成会话或签发 Token、决定用 Cookie 还是响应体返回。这里出错，后面三条链路全废。

下单链路是身份状态的消费环节，依赖登录链路的产物。它最容易暴露边界问题：如果下单服务和登录服务不是同一个域，Cookie 的 Domain 和 SameSite 设置就直接决定能不能带上；如果是跨服务调用，Token 的传递和校验责任就落到调用方。

支付链路在身份之外还叠加了更强的安全要求，通常会做二次校验或短时效凭证。这里的典型错误是复用下单链路的长期凭证，把“方便”当成了“可用”。

把这四条链路画成调用图和数据流图，你会发现一个规律：故障几乎都发生在“状态交接的那一跳”，而不是状态本身。

## 能力点对比：三种方案各自适合什么

| 能力点 | 适合场景 | 接入成本 | 主要限制 |
| --- | --- | --- | --- |
| Cookie + 服务端 Session | 同域 Web 应用、需要主动踢人和细粒度权限控制 | 低，框架普遍内置；多实例需共享存储 | 跨域和跨端支持差；有 CSRF 面；水平扩展要额外设计 |
| Token（放 Authorization 头） | 前后端分离、多服务调用、移动端与开放 API | 中，需要设计签发、校验、刷新与撤销 | 撤销难；凭证泄露窗口长；需要处理时钟与密钥轮换 |
| Cookie 承载 Token | 浏览器场景下想兼顾自动携带与自包含校验 | 中，需处理 SameSite、HttpOnly、CSRF | 两种机制的坑都要踩；调试时容易分不清是哪层失效 |

这张表的用法不是选一个“最好的”，而是先确认你的边界：同域还是跨域、浏览器还是多端、要不要主动撤销。边界定了，方案基本就定了。

## 真实限制与接入成本，别只看热度

第一个限制是跨域。Cookie 受同源策略约束，跨域场景要配 CORS 加凭证、设置 SameSite=None 和 Secure，任何一环漏了就是“带不上”。这不是配置繁琐的问题，而是每次新增域名都要重新确认一遍。

第二个限制是撤销。Session 天然可撤销，Token 不天然可撤销。如果业务里有“封号立即生效”“改密后旧设备下线”这类需求，选 Token 就必须额外做黑名单或版本号机制，这部分成本经常被低估。

第三个限制是可观测性。Cookie 在浏览器开发者工具里可见，Session 在服务端存储里可查，Token 需要解码才能看内容。三者混用时，日志里如果只记“未授权”，等于什么都没记。接入现有流程时，至少要在网关和应用两层分别记录“是否收到凭证、凭证类型、校验结果”，否则排障只能靠猜。

不适用场景也要说清楚：纯静态站点不需要这套；内部单机工具用 Session 就够，上 Token 是过度设计；对时效要求极高的支付类操作，不应依赖长期凭证，而应走短时效二次凭证。

## 怎么接入现有流程：从调用图和清单开始

落地建议按产出物推进，而不是按概念推进。先画应用调用图，标出身份状态在哪些节点产生、哪些节点消费；再画数据流图，标出凭证在每一跳的形态（Cookie 头、Authorization 头、内部签名）；最后列 API 清单，逐个标注该接口依赖哪种凭证、失效后的行为是什么。

这三份产出物做完，Cookie、Session和Token是什么关系就不再是概念题，而是一张能指着说“这里归谁负责”的图。Cookie、Session和Token是什么关系这个选题的价值也在这里：它训练的是边界判断，而不是背定义。

## 给读者的实践建议

先别急着改代码。拿你手上一条真实的登录链路，回答三个问题：凭证存在哪一侧、由谁签发、失效时谁负责清理。三个问题有一个答不上来，就先补文档再动手。

然后在本地授权靶场里做一次“故意弄丢凭证”的演练：去掉 Cookie、改错 Token 签名、清空 Session，分别观察四条链路的报错位置。能准确定位到“哪一跳丢了什么”，才算真的掌握了这组关系。

下一步动作：把应用调用图、数据流图、API 清单三份产出物落成团队可 review 的文档，再据此决定是继续用 Session 还是引入 Token。判断标准不是热度，而是你的边界和撤销需求。
