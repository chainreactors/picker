## 前言

做 AI 代码审计的人很多，方案也很多。
这篇文章不讨论“谁领先”，只回答一个工程问题：**怎样让审计结果在团队里可复核、可执行、可持续。**

我们在实践里反复遇到三类问题：

1. 静态规则方法对业务语义理解有限，逻辑漏洞容易误判或漏判；
2. 把整仓代码一次性交给 LLM，在大仓库里容易出现上下文漂移与幻觉；

3. 报告输出和研发修复脱节，结论看起来完整，但落地效率低。

如果这三类问题不先处理，后面谈“报告质量”基本无从谈起。

---

## 一、先讲边界：我们做的不是“规则引擎替代”

本文方法有两个明确边界：

* 不是代码 SAST 规则库方案，不依赖长期维护大规模规则来裁决漏洞；
* 不是纯 LLM 全文阅读方案，不把“整仓读完”当成可信结论前提。

我们采用的是：**AI 主导的语义审计流程 + 严格流程约束 + 证据校验机制。**

其中可选能力是组件依赖漏洞扫描（CVE 匹配），它和代码语义审计是两条线，不能混为一谈。

---

## 二、核心痛点：为什么常见做法在大项目里不稳定

### 2.1 逻辑漏洞不是“再加几条规则”就能稳定解决

对象级授权、租户边界、业务状态机、回调可信性这类问题，常见特征是：

* 需要跨文件、跨模块理解调用语义；
* 需要结合业务前置条件判断是否真实成立；
* 结论依赖“谁能调用、何时调用、参数怎么来”。

这类问题天然不适合只靠模式命中做最终裁决。

### 2.2 大仓库下，LLM 的主要风险不是“看不懂”，而是“状态不稳”

常见表现：

* 前后轮次结论冲突；
* 引用代码与真实文件不一致；
* 覆盖范围难以量化；
* 中断后无法准确续跑。

关键不是继续堆提示词，而是把流程做成可验证状态机。

### 2.3 报告不可执行，是很多审计流程的终点问题

研发最关心的是：

* 这个问题是否真实成立；
* 触发条件是什么；
* 修复改哪里、怎么回归。

如果报告只有“风险描述”，没有“证据闭环 + 可行性结论 + 修复落点”，落地就会卡住。

## 三、方法主干：七个机制，把流程“卡实”

### 机制 1：审计对象建模（先建图，再审计）

先建模，再审计。至少要有三份基线清单：

1. 资产清单：业务代码、依赖代码、测试与构建产物；
2. 入口清单：HTTP/RPC/MQ/回调/定时任务等可触达入口；

3. 边界清单：匿名、低权、高权、租户、系统边界。

作用：

* 明确应审范围；
* 给覆盖计算提供基线；
* 为断点续跑保留最小状态。

### 机制 2：双引擎并行（行为链 + 控制链）

**A. 行为链引擎（危险行为驱动）**从危险落点逆向追踪输入链路，判断：

* 输入是否可控；
* 约束是否有效；
* 是否可到达真实危险行为。

适合发现：注入、命令执行、文件/网络操作、反序列化等。

**B. 控制链引擎（入口与控制面驱动）**从入口正向检查控制是否缺失，判断：

* 认证是否存在；
* 授权是否按对象/租户生效；
* 校验、验签、防重放是否完备。

适合发现：未授权访问、越权、租户边界绕过、回调可信性缺陷等。

**协同规则**

* 同一模块至少经过一次行为链检查和一次控制链检查；
* 高风险结论需要交叉验证；
* 交叉失败则降级到“待复核”。

### 机制 3：覆盖完整性检查（Coverage Completeness Check）

把覆盖从描述性指标改成放行条件。

定义：

* 应审集合：由资产清单 + 入口清单得到；
* 已审集合：每批次审阅清单；
* 差集集合：未覆盖对象。

计算：

```
Coverage = |已审集合| / |应审集合| * 100%
```

放行条件：

* 差集不清零，不进入最终验证和报告；
* 无漏洞也要记录“已审无发现”；
* 大项目按批次补扫，直到差集收敛。

必须强调：
**文件覆盖率不等于风险路径覆盖率**。

覆盖完整性检查解决“有没有审到”，双引擎 + 验证机制解决“有没有审透”。

### 机制 4：证据状态机（反幻觉的流程化实现）

反幻觉不是口号，而是状态流转约束。 每条候选发现必须完成三步检查：

1. 存在性检查：路径/函数/配置真实存在；
2. 链路检查：输入 -> 处理 -> 落点可闭环；

3. 可行性检查：触发条件在当前场景可达。

输出状态只允许三类：

* `已确认`
* `待复核`
* `已排除`

任一步不满足，就不能进入确认项。

### 机制 5：可行性优先验证（避免“技术成立、业务不成立”）

验证阶段不只看代码可利用，还要看业务可成立。 每条问题要回答：

* 需要什么权限/身份；
* 关键参数是否可获得、可枚举、可预测；
* 依赖配置在生产是否可能存在；
* 是否有前置防护（网关、拦截器、服务层二次校验）。

结论模板：

* `成立`
* `部分成立（条件）`
* `不成立（原因）`

### 机制 6：组合风险分析（链式放大）

真实事故里，严重后果常来自多个中低风险串联，不是单点漏洞。

最小流程：

1. 列出已确认与待复核项；
2. 建立“上游输出 -> 下游输入”关联；

3. 评估链路成立条件；
4. 输出组合后优先级与修复顺序。

常见组合：

* 标识泄露 + 对象授权缺失；
* 回调可信性缺陷 + 状态写入接口；
* 可控外联 + 内网弱面；
* 上传控制不足 + 解析链缺陷。

### 机制 7：一致性约束（避免前后结论冲突）

长流程审计里，最容易被忽视的是判定口径漂移。 约束规则：

* 同类问题采用统一判定基线；
* 新结论若与历史结论冲突，必须给出差异原因（入口变化、边界变化、证据新增）；
* 正文只保留最新状态，历史判断放附录便于复盘。

## 四、执行框架（跨语言通用）

### 输入

* 代码仓库；
* 技术栈识别结果；
* 审计范围（模块/分支/时间窗）。

### 过程

1. 对象建模（资产/入口/边界）；
2. 双引擎并行审计；

3. 批次覆盖对账与补扫；
4. 证据状态机验证；

5. 组合风险分析；
6. 报告归一化输出。

### 输出

* 覆盖统计与差集说明；
* 已确认/待复核/已排除清单；
* 每条确认项的触发前提、链路证据、修复建议；
* 优先级与回归建议。

## 五、实战案例（已脱敏）

> 我们团队在开源社区选取了几款源码，包含3k+ star的也包含只有几十个star的项目进行测试，并对比的人工复核审计的结果，准确度（不误报率）可达到99.99%，检出率（不漏报率）可达到90%+，但是这有很大一部分因素来自LLM本身的能力效果，故案例仅供参考。

### 案例 A | 逻辑漏洞，未授权创建管理员用户

#### 基本信息

| 属性 | 值 |
| --- | --- |
| **状态** | 已确认 |
| **漏洞类型** | 权限提升 / 未授权访问 |
| **CWE-ID** | CWE-306 |
| **严重程度** | 严重 |
| **判级依据** | 影响面：可直接获取后台管理员权限；可利用难度：单次 HTTP 请求即可；前置条件：无需登录。 |
| **威胁评分** | 威胁评分 9（基础分 9，实战阻力 0，武器化 0，版本修正 0） |
| **受影响组件** | 登录与初始化管理接口 |
| **文件位置** | `*/app/src/main/java/com/*/*/controller/*LoginController.java:379` ；`*/app/src/main/java/com/*/*/controller/LoginController.java:392` |

#### 触发条件

1. 应用公开可访问。
2. 调用 `/*/*` 并提交用户名/密码参数。

3. 接口未被鉴权、白名单或一次性开关保护。

（**触发条件可行性**：成立）

#### 所需权限

无需认证

#### 漏洞原理

`/*/*` 对未认证请求可达，服务端逻辑直接创建用户并设置管理员标记，缺乏“仅首次安装可用”或“高强度二次校验”保护，导致任意攻击者可创建高权限账户。

#### 代码证据

* `LoginController` 中 `/*/*` 处理流程直接执行管理员属性赋值与落库（来源：机制2 B1-VULN-001 代码定位）。

#### 调用链

HTTP `/*/*` → `LoginController` 管理员创建逻辑 → `userRepository.save(...)`

#### POC

```
POST /*/* HTTP/1.1
Host: target.example.com
Content-Type: application/x-www-form-urlencoded

username=pwnadmin&password=Pwn%40123456&email=pwn%40example.com
```

若返回成功并可用新账号登录后台，则漏洞成立（代码层已确认逻辑可达）。

#### 修复建议

1. 删除该接口或仅在“首次安装 + 本地回环 + 一次性令牌”三重条件下开放。
2. 强制要求已认证超级管理员才能执行管理员创建。

3. 对管理员创建行为增加审计告警与限速。

### 案例 B | 逻辑漏洞：垂直越权（API 可将任意用户提升为管理员）

#### 基本信息

| 属性 | 值 |
| --- | --- |
| **状态** | 已确认 |
| **漏洞类型** | 垂直越权 / 权限提升 |
| **CWE-ID** | CWE-863 |
| **严重程度** | 严重 |
| **判级依据** | 影响面：任意 token 用户可夺取管理权限；可利用难度：低；前置条件：只需一个普通 API token。 |
| **威胁评分** | 威胁评分 9（基础分 9，实战阻力 0，武器化 0，版本修正 0） |
| **受影响组件** | API 用户管理 |
| **文件位置** | `*/app/src/main/java/com/*/*/controller/api/*UserController.java:126` ；`*/app/src/main/java/com/*/*/controller/api/*UserController.java:263` |

#### 触发条件

1. 获取任意有效 API Bearer Token。
2. 调用用户更新接口并提交 `admin=true` 或等效管理员字段。

3. 后端未执行管理员权限校验。

（**触发条件可行性**：成立）

#### 所需权限

需登录（任意 API token）

#### 漏洞原理

`/api/**` 仅做“是否带 token”校验，`*UserController` 写接口缺乏管理员授权检查，导致普通账号可修改高敏感权限字段。

#### 代码证据

* API 鉴权链以 token 存在性为主，未在用户高危写接口增加角色校验（来源：机制2 B4-VULN-001）。

#### 调用链

HTTP `PUT /api/*/user/...` → `*UserController` 更新逻辑 → 用户权限字段持久化

#### POC

```
PUT /api/*/user/*/save HTTP/1.1
Host: target.example.com
Authorization: Bearer <LOW_PRIV_TOKEN>
Content-Type: application/json

{"id":"targetUserId","admin":true}
```

若请求成功且目标用户管理员属性变更，则漏洞成立（代码层已确认）。

#### 修复建议

1. 在 API 层为所有高危写操作增加强制角色校验（仅 superadmin）。
2. 对 `admin`、`roles` 等敏感字段做服务端不可越权校验。

3. 审计所有权限变更并增加告警。

### 案例 C | 传统漏洞：不安全反序列化（ActiveMQ 消费端 readObject）

#### 基本信息

| 属性 | 值 |
| --- | --- |
| **状态** | 待验证 |
| **漏洞类型** | 不安全反序列化（潜在 RCE） |
| **CWE-ID** | CWE-502 |
| **严重程度** | 高 |
| **判级依据** | 影响面：若消息可控可能导致高危代码执行；可利用难度：取决于消息投递权限与类路径 gadget；前置条件：可向目标队列/主题投递恶意对象消息。 |
| **威胁评分** | 威胁评分 6（基础分 8，实战阻力 -2，武器化 0，版本修正 0） |
| **受影响组件** | ActiveMQ 消费订阅链 |
| **文件位置** | `*/app/src/main/java/com/*/*/util/SerializeUtil.java:70` ；`*/app/src/main/java/com/*/*/activemq/*.java:66`；`*/app/src/main/java/com/*/*/activemq/*.java:68` |

#### 触发条件

1. 攻击者可向指定 ActiveMQ 目的地投递 Java 序列化对象。
2. 消费端使用 `ObjectInputStream.readObject()` 反序列化未受限数据。

3. 类路径存在可利用 gadget 链（需结合依赖版本确认）。

（**触发条件可行性**：部分成立（需确认消息投递边界与可利用 gadget））

#### 所需权限

需具备消息投递能力（Broker 访问权限）

#### 漏洞原理

多处 MQ 消费逻辑对消息体执行 Java 原生反序列化，且未见 `ObjectInputFilter` / 白名单控制。若消息输入可控，存在反序列化执行风险。

#### 代码证据

* `SerializeUtil.deserialize(...)` 使用 `ObjectInputStream.readObject()`（来源：机制2 B10-VULN-002）。
* 若消费端传入 payload 到该函数，则形成潜在危险 sink。

#### 调用链

恶意 MQ 消息 → 订阅器 `onMessage` → `SerializeUtil.deserialize` → `ObjectInputStream.readObject`

#### POC

（代码验证请求包，示例为向 Broker HTTP 管理端投递；具体端口/接口视部署而定）

```
POST /api/message/*/*/* HTTP/1.1
Host: mq.example.com:8161
Authorization: Basic <BASE64_USER_PASS>
Content-Type: application/octet-stream

<SERIALIZED_OBJECT_BYTES>
```

当前结论：代码层确认存在危险反序列化点；是否可被外部直接利用仍需部署与依赖链进一步验证。

#### 修复建议

1. 禁止 Java 原生反序列化，改用 JSON 且做 schema 校验。
2. 如短期无法替换，启用 `ObjectInputFilter` 与严格类白名单。

3. 将 MQ 目的地隔离到内网并限制生产者 ACL。

### 案例 D | 三个组合漏洞

在审计完全量的单项漏洞后，根据已知的漏洞结果，按照实际代码和逻辑进行组合漏洞的识别。

| 组合 | 涉及漏洞 | 攻击场景简述 | 组合后严重程度 |
| --- | --- | --- | --- |
| C-001 | VULN-001 + VULN-004 | 利用管理员任意创建直接接管后台，再滥用任何漏拦截管理接口 | 严重 |
| C-002 | VULN-002 + 内网可达环境 | 先用 SSRF 探测内网，再访问内部管理/元数据服务 | 高 |
| C-003 | VULN-006 + VULN-003 | 根据未授权接口获取检索附件 ID，结合任意附件下载漏洞扩大敏感数据泄露 | 高 |

#### C-001: 任意管理员创建 + 全局安全放行

* 组合: `VULN-001`（未认证任意创建管理员） + `VULN-004`（框架层全局放行）
* 攻击链: 攻击者匿名创建管理员账号后，利用“默认放行 + 业务层漏拦截”访问更多后台敏感接口。
* 组合后影响: 可直接后台接管，严重程度提升为**严重**。

#### C-002: 未认证 SSRF + 内网服务可达

* 组合: `VULN-002`（未认证 SSRF） + 部署侧内网可达
* 攻击链: 先探测内网与管理端点，再结合环境误配扩大攻击面。
* 组合后影响: 可能导致内网信息泄露/横向探测，严重程度提升为**高**。
