WEB 漏洞精讲 · 第 42 篇

注册一个账号，昵称栏里填 `{{7*7}}`。提交，刷新个人主页。

昵称显示成了 **49**。旁边同事还在笑"这网站有 bug"，我已经开始写报告了——因为服务器肯替你算一道数学题，就肯替你执行一条命令。

这篇讲 SSTI：它为什么被低估、怎么在三十秒内认出模板引擎、以及两个能救命的小技巧。约 3000 字，2 个干货。

01｜模板引擎，就是网站的"填空题"机器

先讲清楚模板引擎是干什么的。你打开一个商品页，页面上大部分东西是固定的：导航栏、按钮、页脚。只有价格、库存、用户名在变。开发不可能为每个用户写一个页面，于是做了个"半成品页面"：

```
<h1>你好，{{ username }}</h1> <p>当前余额：{{ balance }} 元</p>
```

这个带花括号的半成品叫**模板**，负责把 `{{ }}` 换成真实数据的东西叫**模板引擎**。用奖状的比喻最贴切：奖状上印好了"祝贺 \_\_\_\_\_\_ 同学获得一等奖"，把名字填进去打印出来的工作人员，就是模板引擎。

正常流程是：**模板是模板，数据是数据，数据永远只当字符串**。你名字叫"张三"，就印"张三"；你名字叫"李四"，就印"李四"。哪怕你名字里带花括号，也该原样印出来。

SSTI 出问题，是因为开发者把这两件事搞混了：**把用户输入先拼进了模板字符串本身，再交给引擎去渲染**。这时候你的输入不再是"要填的数据"，而变成了"模板的一部分"——也就是代码。

02｜49 是怎么被算出来的

![SSTI 靶场探测页面](https://mmbiz.qpic.cn/mmbiz_png/8m3icSM3btkfoR9Vu9D9ZcaWfPtROpg531UhZ7nNkVBR5zHUwpO32lB859UsnA2n3srPv7OQzLoYgf1iaouPps4Bic4OfibpZwKWsUR5kvra5Bc/640?wx_fmt=png&from=appmsg)

图 1｜一个只有输入框的页面，名字为空时回显 Hello None

看两段代码的差别，一眼就明白。有问题的写法（Flask + Jinja2）：

```
name = request.args.get('name') t = '<h1>Hello %s</h1>' % name      # 先把用户输入拼进模板 return render_template_string(t)     # 再整段交给引擎解析
```

安全的写法：

```
return render_template('index.html', name=name)   # name 只作为变量传入
```

区别就在 `render_template_string` 和 `render_template`。前者会把你拼进去的内容当模板代码解析，后者只把变量当数据填空。很多教程讲"关闭自动转义会怎样"，其实重点不在这——**真正的分界线是：用户输入有没有进入"模板源码"这一层**。只要进了，转义与否都救不了。

所以验证只需要一件事：**输入一个只可能被"计算"出来的表达式，看回显**。填 `{{7*7}}`，回 `49` 就是中了；回原样一串花括号，说明它只当字符串处理。

再加一个小技巧区分引擎：填 `{{7*'7'}}`。Jinja2 会给你 `7777777`（字符串重复七次），Twig 给你 `49`。这一个字符的差别，能省掉后面半小时瞎试。

03｜从 49 到命令执行：顺着族谱找"钥匙"

![SSTI 查看 subclasses 回显](https://mmbiz.qpic.cn/sz_mmbiz_png/8m3icSM3btkevEtf4bafUDwV3KKtdBjnh7p9rLvLQibxUMIfPAiaCsOPm3iakQd0OC7ZDbJibwtJwlqrL13ThumyU9bOFf2ZEO3GFHHg5jude95M/640?wx_fmt=png&from=appmsg)

图 2｜用魔术方法把当前加载的类列出来，索引 132 命中 os.\_wrap\_close

能算 49，说明引擎在执行表达式。但表达式能力有限，要走到命令执行，得借 Python 自己的对象体系。这条路径的思路叫"找族谱"，听着玄，其实逻辑很顺：

* **起点**

  ：一个空字符串 `''`，随便找个对象；
* **问它属于哪个类**

  ：`__class__`；
* **往上找父类**

  ：`__base__`，一路走到万物之源 `object`；
* **把子孙全叫出来**

  ：`__subclasses__()`，这里会返回当前进程已经加载的所有类；
* **挑一个能碰系统命令的**

  ：比如 `os._wrap_close`，再用 `__init__.__globals__` 翻它的全局命名空间；
* **拿到 popen**

  ：这个命名空间里有 `os.popen`，执行命令、读回结果。

关键细节：**索引号不是固定的**。图 2 里是 132，换个环境可能是 128、156。因为 `__subclasses__()` 返回的是"当前进程已经加载"的类，跟启动顺序、装了哪些库都有关。所以别抄别人的数字，自己先列表、再定位。这个坑我见过太多人踩：payload 没打出来，就以为洞是假的。

同样的思路在各语言都成立：PHP 的 Twig 有 `_self.env` 之类的研究路径，Java 的 Freemarker 能摸到 `Execute` 工具类，Node 的 EJS 能通过 `process` 摸到主进程。**原理完全一样：模板语法本身能力有限，但语言的对象图没有边界。**

04｜别瞎试：先认出这是哪家的模板

SSTI 最耗时间的不是利用，是**认引擎**。不同引擎的定界符不一样，试错顺序不对，可能填二十个 payload 全是原样回显，然后误判"没有漏洞"。

干货**模板指纹对照表：一次填对定界符**

按这个顺序试，命中率最高（都在授权靶场里用）：

```
Jinja2 (Python)      {{7*7}}        → 49 Twig (PHP)           {{7*7}}        → 49 Smarty (PHP)         {7*7}          → 49 Freemarker (Java)    ${7*7}         → 49 Velocity (Java)      #set($x=7*7)$x → 49 Thymeleaf (Java)     ${7*7}         → 49 EJS / ERB (Node/Ruby) <%= 7*7 %>    → 49 Pug (Node)           #{7*7}         → 49
```

判断技巧：Jinja2 和 Twig 都用双花括号，用 `{{7*'7'}}` 区分——前者返回 `7777777`，后者返回 `49`。`${7*7}` 也同时适用于 Freemarker 和 Thymeleaf，再填 `${7*7*7}` 配合错误回显就能分。

干货**页面不回显，不代表没有：三种确认方式**

**延时判断**：让引擎自己算一个耗时表达式，比较响应时间差。表达式各引擎不同，得先认出引擎；

**带外判断**：把结果拼进一个域名去触发 DNS 查询——回显被过滤时最可靠；

最有用的其实是**报错信息**：故意提交一个语法错误的表达式，很多引擎会在 500 页面里把模板路径、引擎名、甚至版本吐出来。这一步比盲试 payload 快十倍，而且它同时把"这里确实在渲染模板"给证明了。

05｜为什么"过滤花括号"防不住

![SSTI 命令执行回显](https://mmbiz.qpic.cn/sz_mmbiz_png/8m3icSM3btkdxPIHfbUY9E2oPtdpTGhCvMTK1DPiaqeLCIG7Lh7qxKczWw2lwzDNfTbIIeTgoSX2QfJ292DChqm12h41IjlhSuAqw4oSrfLBY/640?wx_fmt=png&from=appmsg)

图 3｜同一条链走到 popen，命令输出直接回在页面上

很多开发者的第一反应是把 `{{`、`}}`、`${` 拉进黑名单。没用，原因有三个：

* **模板引擎自己有编码和拼接能力**

  ：引擎允许在表达式里做字符串拼接，你的黑名单只挡字面量，挡不住运行时组装；
* **上下文会变**

  ：同一个花括号，在属性里、在 URL 参数里、在 JSON 里，经过一层层解析后形状就不一样了；
* **黑名单永远漏**

  ：换行、注释、别名、编码，任何一种没进名单就是一条路。安全不能靠"穷举坏人长什么样"。

正确的修法只有一条：**永远不要把用户输入拼进模板源码**。用 `render_template` 传变量，不拼字符串；如果业务真的需要"用户自定义模板"（比如邮件模板、CMS 主题），那就必须上沙箱——Jinja2 的 `SandboxedEnvironment`、Twig 的 sandbox 扩展，而且沙箱本身也会被绕过，要持续跟版本。

顺带说一个开发容易忽略的点：**模板注入不一定在页面上**。邮件模板、PDF 导出、报表生成、工单通知，这些"后台渲染"的地方同样吃用户输入，而且往往没有 WAF 保护，日志也不记。做资产排查时，这些位置值得单独列一行。

还有一个判断上的细节：**报 SSTI 的时候，别只写"存在模板注入"**。甲方最想知道的其实是三件事——能不能读到文件、能不能执行命令、需不需要登录。这三档的危害差得很远：只能算数的叫"表达式注入"，能读配置的叫"信息泄露"，能执行命令的才是 RCE。报告里把这三档分开写，比笼统写一句"高危"专业得多。

另外，很多人把 SSTI 和 XSS 搞混。区别很简单：**XSS 是代码在受害者的浏览器里跑，SSTI 是代码在服务器上跑**。一个影响的是某个用户，一个影响的是整台机器。看到"输入被原样回显"先别急着报 XSS，先确认它是在哪一层被解析的。

下一篇换个战场，从服务端回到浏览器：CORS 配置错误——一个响应头写错，别人的网站就能读走你用户的全部数据。
