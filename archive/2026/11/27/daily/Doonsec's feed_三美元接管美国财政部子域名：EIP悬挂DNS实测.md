# 2026年8月，Intruder完成了一轮针对AWS Elastic IP address（弹性IP地址，EIP）的子域名接管（subdomain takeover）实测。团队借助自动化脚本循环申请、释放EC2公网地址，在48小时内遍历45万个唯一IP，仅扫描不到1%的EIP地址空间，便在公开漏洞赏金（bug bounty）范围内确认28个仍可被接管的悬挂DNS记录（dangling DNS record），其中5个为US Treasury（美国财政部）子域名，解析已指向研究人员控制的地址。每成功接管一个有效目标，对应的公网地址费用约为3美元。相关发现已通过漏洞赏金与漏洞披露程序上报，受影响域名完成修复；截至研究文章发布时，这套攻击路径在实践中依然成立。

# 被遗忘的DNS记录指向哪里

AWS的EIP是可在云主机上使用的互联网可路由公网地址，任何AWS账户均可申请分配。DNS记录负责把域名解析到对应服务器地址，当企业下线某台云主机或释放某个公网地址后，如果指向它的A记录（IPv4地址记录）没有同步删除，这条记录便成为悬挂记录：它指向的资源已不属于原企业，域名解析却仍然停留在原处。

攻击者一旦重新申领到这条被释放的地址，用户访问该子域名时就会落到攻击者控制的主机上，子域名随之被接管。这类问题通常源于企业侧DNS运维残留，云服务商并不直接感知某条记录是否还指向客户自身的资源，一次常见的DNS配置疏漏便可能留下可被攻击者申领的入口，进而导致凭证窃取等后果。

# 测试目标：从公开赏金范围收集子域名

研究团队希望把发现的风险记录逐一上报，测试名单全部来自公开漏洞赏金范围。流程上，团队先通过bbscope接口拉取通配符范围（wildcard scope）条目，再交由subfinder枚举对应资产的子域名；随后解析每台主机的A记录，将不属于私有或保留网段的地址存入DynamoDB表，供后续比对流程调用。

# 地址遍历：循环申请、释放与比对

EIP总量上限约8000万个，实际可用规模可能只有一半左右；地址分配随机进行，攻击者无法直接指定要领用的IP。可行思路是从AWS的EC2地址池中反复分配、释放EIP，并把每个拿到的地址与目标DNS记录逐一比对。

默认情况下，一个新AWS账户在每个区域最多持有5个EIP，5个地址也足以跑通循环；配额越高，每轮遍历拿到的地址越多。Service Quotas（服务配额）允许在无需提交支持工单的情况下自动把单区域EIP配额提升到25个，团队据此在所有区域申请了提额。

提额完成后，团队运行Python脚本按以下流程逐轮领取地址：

1. 在当前区域分配25个EIP；
2. 记录每个地址并去重；
3. 在数据库中查询该地址是否命中目标记录；
4. 命中目标A记录的地址保留并写入日志；
5. 未命中的地址全部释放；
6. 切换到下一个区域，重复上述流程。

图3 EIP申请、比对与释放流程示意

单区域内释放地址后立刻重新申请，往往会拿回同一个地址，说明AWS会优先回收刚释放的地址。团队在不同区域之间轮换，给各地址池留出周转时间，等工具回到原区域时，分配到的已是一组新地址。

48小时后，团队在AWS封禁账户前共遍历45万个唯一地址，足以在赏金范围内确认28个可实时利用的EIP接管点。此时覆盖范围不足EIP总空间的1%，已拿到28个高影响发现。如果攻击者把范围扩大到赏金计划之外，并长时间运行这类遍历，大概率能找到数百甚至上千条可被劫持的DNS记录。

# 封禁后换账户继续

运行48小时后，账户收到Amazon的滥用警告，处置动作为“在所有区域封禁分配和关联Elastic IP的能力”。这不仅阻止了继续申请新地址，也让团队无法使用已命中的地址。为向上报对象展示接管成功的证据，团队需要在这些地址上托管PoC（概念验证，Proof of Concept）页面。

AWS允许在账户之间转移EIP，团队于是在测试组织内新建一个账户，把命中的地址转移过去；尽管新账户与被封账户同属一个组织，转移过程未遇到阻碍。组织下的新账户无需再次走完身份验证流程，账户被限制的攻击者只需再开一个账户就能接着操作。

为避免引发更多滥用投诉，团队没有从新账户继续完整攻击，而是向AWS提出两项让攻击更难落地的建议：

* 为每月可分配的EIP数量增设新配额，以硬性上限方式限制申请速率，对大型组织可设到合理水平，攻击成功率将明显下降；
* 把滥用限制施加在组织层级，而非账户层级，攻击者每次被封都要重新搭建整个组织，成本更高。

AWS随后回应称暂无改动计划，相关立场在披露部分展开。

# 真实接管记录：28个命中与5个财政部子域名

在这份有限的赏金目标名单上，团队成功领取并控制了28个与范围内实时DNS记录匹配的EIP，其中近半数归属政府机构。需要说明，自动化仅运行了48小时，继续运行大概率还会有新发现。

最受关注的是5个指向团队已控制地址的US Treasury子域名：

* ftp.treasury.gov
* irssearch.treasury.gov
* pcp.treasury.gov
* rdgw.treasury.gov
* ww5.treasury.gov

# 接管之后：攻击者能做到什么

一旦掌握悬挂DNS记录背后的IP，攻击者就完全控制了该子域名对外提供的内容。美国政府网站通常引导访客通过两个特征判断可信度：域名以.gov结尾，且启用HTTPS。域名被接管后，攻击者搭建的站点同样能通过这两项检查，用户不会产生额外怀疑。攻击者甚至可以通过证书颁发机构（certificate authority，CA）的域名验证（domain validation），为该域名申请到受信任的TLS证书，让站点外观完全正规。

依托这种可信外观，攻击者可以借用真实政府域名开展钓鱼（phishing），窃取用户凭证（credentials）；也可以在该域名上挂起服务收集流入信息，从仍指向该地址的老旧自动化流程中盗取数据，例如残留凭证。这类凭证可能直接打通与初始接管无关的其他系统，风险扩散范围更大。

被接管的子域名还能访问作用域限定在父域名下的Cookie。如果treasury.gov以Domain=treasury.gov方式写入Cookie，这些Cookie会被发送到每个子域名，包括攻击者控制的子域名，进而可能造成treasury.gov其他应用中的会话窃取（session theft）。

# 攻击可行性测算：单账户、多账户与定向扫描

AWS为EC2公布的IPv4地址约8000万个，团队分配的45万个地址占其中0.56%。按每小时约9400个地址的速率计算，单个账户遍历完所有公布地址需要一年，对单账户攻击者而言速度偏慢；多个账户并行后，周期会明显缩短。若封禁确实只作用于账户层级，正如本次实测所反映的那样，10个账户约五周即可扫完全部空间。

现实中可被领取的地址空间远小于账面规模。大量地址属于自动分配的公网IP，或被其他客户长期持有，实际遍历耗时会低于上述推算。机会型攻击者也不需要覆盖整个空间，本次仅0.56%的覆盖率就落地28个子域名。

针对特定组织的定向攻击会进一步缩小搜索面。攻击者先枚举目标子域名，筛出指向未使用EC2地址的记录；AWS公布了各地址段对应的区域，攻击者可以直接锁定要搜索的区域。以eu-west-2区域的目标为例，候选地址约220万个，而非8000万个。不过在同一区域反复分配时，重复率明显更高，搜索速度随之下降，定向攻击面对的是更小的草堆，找针的过程反而更慢。

AWS确认暂无改动计划。其判断是，这类接管取决于客户侧DNS记录，而非自身服务存在缺陷；同时说明快速申请与释放地址属于违反政策的行为，平台已有对应控制措施。团队认为这一判断成立，但AWS仍有空间进一步缓解问题，在现有立场下，这一整类漏洞仍然敞开。

黑鸟认为，对企业而言，当下应尽快盘点自有DNS记录，清理指向已释放云资源、已下线主机的悬挂记录；对外包商、历史项目遗留的子域名尤其需要逐项核对。云服务侧的改进空间集中在配额管理与组织层级封禁两处，而这两点目前仍依赖平台方决策。
