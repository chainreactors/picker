## Background

PR [#62](https://github.com/esrrhs/spp/pull/62) fixed the random `REVERSE_PROXY` ~30s read timeouts in FullMatrix with test-only measures (matrix-wide concurrency cap + `warmupReverseEcho` readiness probe), and explicitly noted the underlying product race was still open. This PR fixes it in the product.

## Root cause

In `Server.processLogin` the order was:

1. `iniService(...)` — for reverse clients the server-side inputer starts listening **immediately**, and an accepted connection relays `OPEN` via `SendFrame`.
2. `sess.SendFrame(LOGINRSP)`.

`LOGINRSP` and `OPEN` both enter the session `sendq` as `prioControl`, and `prioQueue` drains each priority bucket with strict FIFO. An `OPEN` enqueued in that startup window therefore reached the wire **before** `LOGINRSP`. On the client, `processConn` popped `OPEN` before `processLoginRsp` had built the outputer, and `routeOpenToOutput` silently dropped it (empty `outputs`) — leaving the connection half-open until the read timeout (~30s).

Forward modes never showed the asymmetry: only reverse inputers start listening on the server side during login.
