**披露时间**

2026年11月17日。研究方公开漏洞技术报告，Oracle与OpenJDK于同日发布安全更新。CVE记录的发布时间为2026-11-17T21:32:03Z，即美国太平洋时间当日13时32分[2][4][6][7]。

**摘要**

Java4Shell是CVE-2026-114938的公开别名，漏洞位于OpenJDK HotSpot的x86-64 Base64 intrinsic。畸形Base64尾部会使解码长度发生整数下溢并形成全1写入掩码，随后AVX-512向量指令向解码数组之外写入64字节。该缺陷属于CWE-122堆缓冲区溢出，Oracle给出的CVSS3.1评分为8.1分。研究方已经演示从受限越界写扩展至堆信息泄漏和远程代码执行的利用路径，但稳定利用仍依赖处理器指令集、JDK构建、JIT编译状态、应用解码入口、堆布局及可观测反馈通道。本文分析漏洞形成机理、上游修复方式、受影响范围、评分差异和处置策略，并讨论内存安全语言依赖本地优化代码时所形成的运行时治理风险。

**关键词**

Java4Shell、OpenJDK、HotSpot、Base64 intrinsic、AVX-512、堆缓冲区溢出、运行时安全

## 一、漏洞概况与风险判断

Java4Shell由Calif Research公开披露，CVE编号为CVE-2026-114938。漏洞组件属于OpenJDK HotSpot编译器中的x86-64 Base64加速代码，而不是Java标准库中以Java语言实现的通用解码逻辑[2][6][7]。这一区别决定了漏洞的触发方式。业务代码即使没有直接调用JNI或本地库，只要经过热点调用进入C2编译后的intrinsic，也可能进入存在缺陷的机器码路径。

Oracle在CVE描述中将该问题归入Java SE的Compiler组件，并指出成功利用可能影响机密性、完整性和可用性。CVE记录中的弱点补充将问题归类为CWE-122，即堆缓冲区溢出[6]。漏洞的核心后果是解码缓冲区后方62字节被越界覆盖。在特定堆布局下，这种写入能够破坏相邻Java对象的长度字段，并成为进一步读取堆数据或实施代码执行的起点。

### 1.2风险形成条件

漏洞风险不能仅由Java使用量推导，也不能仅凭CVE别名中含有Shell一词判断所有Java服务器均具备同等暴露程度。可利用性取决于若干相互独立的条件。硬件决定机器码路径能否执行，运行时决定是否存在缺陷实现，应用决定攻击者能否控制输入并反复命中热点方法，堆状态则决定内存破坏能否转化为可稳定观察的原语。

| 判断维度 | 必要条件 | 对风险的影响 |
| --- | --- | --- |
| 处理器 | x86-64且支持AVX-512 VBMI | 缺少相应指令集时无法进入该intrinsic的向量快路径 |
| 运行时 | 包含缺陷实现的OpenJDK构建或下游发行版 | Java8和Java11普通构建通常不在该CVE的受影响矩阵内 |
| 编译状态 | 相关解码方法已由C2编译并选用Base64 intrinsic | 调用频率不足时可能仍由解释器或通用Java实现处理 |
| 应用入口 | 攻击者可控数据能够进入Base64解码API | 未暴露解码路径的系统优先级较低 |
| 堆状态 | 相邻对象能够被稳定布局和观察 | 从崩溃或数据损坏提升为信息泄漏及RCE需要目标专属利用工作 |

### 1.3处置优先级

下表把漏洞条件转化为组织内部处置顺序。该优先级属于运行环境研判，不替代厂商CVSS评分。

| 优先级 | 同时具备的条件 | 建议动作 |
| --- | --- | --- |
| P0 | 支持AVX-512 VBMI的x86-64主机、受影响JDK、公网可达且未认证用户能够触发Base64解码 | 立即升级并重启。无法立即完成时启用临时缓解，限制未认证入口并加强JVM崩溃监测 |
| P1 | 受影响JDK和x86-64主机，但解码入口要求登录、位于内网或只允许低权限用户访问 | 按紧急变更处理，优先于普通应用补丁。同步排查横向访问和客户端连接路径 |
| P2 | 确认加载受影响JDK，但主机不具备VBMI，或者暂未发现Base64解码入口 | 纳入近期补丁计划。资产扩容、迁移和基础镜像更新前重新评估硬件和调用路径 |
| P3 | ARM64主机、普通Java8或Java11构建，或者确认运行时不含缺陷实现 | 保留资产记录并持续复核，防止后续镜像或运行环境变更改变判断结果 |

从处置角度看，同时具备公网入口、未认证Base64输入、受影响JDK和支持VBMI的x86-64主机的系统应列入紧急修复范围。硬件条件不满足或应用无法到达相应API时，实际利用概率会明显降低，但运行时资产仍应纳入清单，因为迁移、扩容和基础镜像更新都可能改变原有条件。

## 二、OpenJDK Base64 intrinsic跨越的安全边界

Base64按照每三个二进制字节生成四个ASCII字符的规则编码数据，并使用等号补齐最后一个编码组。由于认证令牌、文件内容、消息载荷、配置数据和协议字段经常采用Base64，OpenJDK对编解码吞吐进行了长期优化。Muła和Lemire的研究表明，SIMD指令能够并行完成字符分类、位重排和打包，从而提高Base64处理性能[1]。

普通Java代码执行数组访问时会受到边界检查，对象分配和回收由垃圾回收器管理。HotSpot的intrinsic位于这一安全模型内部，却使用C++生成桩代码和机器指令直接访问内存。它减少了方法调用、对象创建和逐字节处理开销，也因此绕过了Java解释器或JIT通常插入的部分安全检查。

热点方法经过解释执行、C1和C2分层编译后，C2可能将Base64解码调用内联为专用桩代码。在支持AVX-512 VBMI的x86-64平台上，相关实现使用64位掩码寄存器控制向量加载和存储，一次处理64字节。JIT依赖调用前已经确认的数组类型、输入长度和输出范围，GC也依赖这些本地操作不破坏对象布局。

漏洞说明Java语言的内存安全保证并不能自动覆盖JVM自身。Java应用可能没有显式本地代码，但运行时仍包含HotSpot、JNI、密码学、图形栈和设备驱动等本地组件。只要其中某个组件违反长度或对象边界，Java异常机制只能在破坏发生后终止当前操作，无法自动修复相邻堆对象。

## 三、填充长度下溢与64字节越界写

研究方在技术报告中指出，缺陷位于Base64 intrinsic处理最后不足一个完整向量块的代码。解码器先按较大输入块推进，再根据剩余字符和填充数量计算有效输出长度。公共分析所描述的核心逻辑可以概括为以下伪代码[7]。

```
output_len = floor(remaining_input_len / 4) * 3
if last_char == '=':
    output_len -= 1
    input_mask >>= 1
    if second_last_char == '=':
        output_len -= 1
        input_mask >>= 1

output_mask = bzhiq(~0, output_len)
```

正常尾块至少包含一个完整四字符组，或者由Java通用路径处理。存在缺陷的尾块在计算出output\_len为零以后，又因等号填充执行减法。无符号长度由0变为0xffffffffffffffff或0xfffffffffffffffe。bzhiq使用该值作为零高位起始位置时，索引超过64位数据宽度，源操作数不会被截断，最终形成全1掩码。

全1掩码使evmovdqub或对应的VMOVDQU8向量写操作覆盖全部64字节。研究方给出的典型输入是64个A后接一个等号。Java按照输入长度计算解码缓冲区容量。

```
ceil(65 / 4) * 3 - 1 = 50
```

目标数组因此只有50字节。前48字节由64个A正常解码产生，缺陷尾块从偏移48开始执行64字节写入，覆盖范围延伸至偏移111。数组边界之外共有62字节被写入。在较早的OpenJDK17构建中，进入该快路径的剩余长度阈值不同，研究方给出的触发形式为128个A后接一个等号。

解码完成后，Java方法可能抛出IllegalArgumentException，表示输入不符合Base64语法。这个异常发生在本地写入之后，并不代表堆内容已经恢复。若数组后方是紧凑对象、数组头或长度字段，异常路径只会终止请求，已经写入的常量字节仍可能污染相邻对象。

上游修复采用长度门控，而不是继续修补负长度掩码。OpenJDK变更JDK-8393212在最终尾部处理前增加length < 4判断，将不足一个完整四字符组的填充尾部交给Java通用逻辑处理[3]。该修复直接阻止畸形短尾部进入向量写操作，也为补丁核验提供了明确依据。

## 四、从受限内存破坏到信息泄漏和代码执行

该漏洞初始阶段只提供受限写入，并不等同于任意地址写入。研究方公开的利用分析认为，越界64字节中只有第一个字节可完全控制，第二个字节具有4位可控性，其余内容大多来自解码中间值，末尾16字节固定为0x9a。攻击者能够重点影响的是覆盖发生位置。

第一阶段利用对象长度字段。如果越界写覆盖相邻Java数组的长度字段，该数组便可能接受超过原有容量的数据。研究方将这种被扩大的对象称为writer。writer能够继续覆盖后面的对象，使固定值溢出逐步转化为范围更宽、内容更可控的线性写。

第二阶段利用数组回读形成信息泄漏。若另一个对象的长度字段被破坏，应用在复制、序列化或返回响应时可能读取数组边界之外的堆内容。研究方将这一效果称为JavaBleed。泄漏数据可能包含会话标识、身份断言、密钥材料、业务对象或其他进程内存内容。信息泄漏不要求先获得代码执行，因此即使后续控制流劫持失败，也可能造成严重的机密性损失。

第三阶段将读写能力用于Java堆内对象破坏和控制流目标。研究方的路径包括修复临时破坏的对象、利用应用级数据流改变安全判断、扩大地址控制范围，并最终触及Code Cache或其他JVM内部结构。该过程具有明显的目标依赖性。不同产品对数组的创建顺序、对象大小、响应序列化和业务动作并不相同，同一套堆布局策略无法直接迁移。

G1垃圾回收器按region管理堆，线程通常先在TLAB中分配对象。请求线程、工作线程和异步任务可能产生不同分配游标，因此攻击者需要控制请求分段、连接时序和对象生命周期，才能提高目标对象相邻排列的概率。研究方通过对象喷洒、重复尝试和响应差异筛选布局，并在网络往返稳定、延迟可控的条件下提升可靠性。代理缓冲、负载均衡、TLS终止位置、WebSocket帧处理和后端连接复用都会改变这种时序假设。

研究方声称已在Keycloak、Atlassian Jira、Atlassian Confluence、JFrog Artifactory、Jenkins和PingFederate等产品的默认配置上演示未认证代码执行，并在Kafka、Solr、Elasticsearch、Gerrit和Spinnaker上演示认证后代码执行。这些结论属于研究方的目标环境复现，不能直接替代各产品厂商对具体版本和部署模式的确认。相关演示说明Java运行时的内存破坏可以穿过上层应用逻辑，最终影响业务系统。

完整利用通常需要攻击者能够到达特定解码入口，反复预热C2，构造目标专属堆布局，获得可观察响应或其他反馈，并执行与产品匹配的后利用动作。研究方公开材料明确说明不存在universal payload，同时暂未公开各产品的武器化链。该限制并不削弱漏洞的严重性，但意味着风险排序不能简化为是否曾出现某个产品的公开利用代码。

## 五、版本范围与硬件条件

OpenJDK于2026年11月17日发布安全公告。公告发布说明列出该批次覆盖的27.0.1.0.3、25.0.5.0.3、21.0.13.0.3、17.0.21.0.3、11.0.33、8u512及更早版本，风险矩阵则只将CVE-2026-114938映射到JDK17、21、25和27[2]。解读此类矩阵需要区分发布批次覆盖范围与特定CVE的受影响分支，不能把同一公告中的其他Java版本全部视为存在Base64 intrinsic缺陷。

Oracle安全公告列出的受影响产品包括Java SE8u511b33-perf、17.0.21.0.3、21.0.13.0.3、25.0.5.0.3和27.0.1.0.3，并涉及Oracle GraalVM for JDK及GraalVM Enterprise Edition的相关版本[4]。这些字符串属于厂商风险矩阵中的产品版本范围，不能仅凭公开版本号后缀判断某个构建已经安全，也不能把11.0.33或8u512等同一公告中的其他版本误写成该CVE的受影响版本。补丁核验应结合发行商更新记录、构建哈希和更新后的二进制日期。

研究方称OpenJDK17.0.6及之后的实现包含相关快路径。该结论与其他独立测试相符，但下游发行版可能存在补丁回移、裁剪或自定义编译。Amazon Corretto、Eclipse Temurin、Microsoft Build of OpenJDK、Azul Zulu、BellSoft Liberica、SAP SapMachine和Red Hat OpenJDK等基于OpenJDK的发行版应依据各自安全公告判断。普通OpenJDK8和11构建未包含该Base64加速实现，Java8的特殊情况是Oracle Enterprise Performance Pack中的8u511b33-perf。
