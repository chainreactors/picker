# 3小时、200美元，AI挖出Java致命0day

发布时间 : 2026-11-27 18:25:40

**x**

##### 译文声明

译文仅供参考，具体内容表达以及含义原文为准。

11月24日晚上，美国CISA发了一条不算长的通知：请各机构立刻排查Java环境，优先处理对公网开放的系统。通知指向的漏洞编号是CVE-2026-114938，圈里给它起了个外号——Java4Shell。让安全团队连夜爬起来的，不只是9.2分的评分。真正扎心的是发现过程：一家叫Calif的安全公司说，从找到漏洞到写出第一个可用利用，总共花了3个小时，token成本不到200美元。

# 一、先把严重性说清楚

Java4Shell是OpenJDK里Base64解码器的内存破坏漏洞。攻击者构造一段恶意Base64数据，就可能让JVM崩溃、泄露堆内存内容，在特定条件下实现**无需账号密码的远程代码执行**。CVSS 4.0给了9.2，CVSS 3.1给了8.1，Oracle在11月的补丁更新里已经修了。

它和当年的Log4j不太一样，利用门槛高一些。Calif说得很明确：受影响的前提是CPU支持AVX-512 VBMI和BW指令集；不支持这套指令集的机器会走另一条解码路径，根本碰不到这个洞。即便CPU符合，要稳定拿到RCE，还得做堆布局，再找到一个能泄露内存地址的应用入口来绕过ASLR。所以目前没有“一把梭”的通用exp，也没有公开的应用级利用链。

名字叫Java4Shell，是因为它和当年的Shellshock一样，打的是基础设施层。国内企业的Java存量比很多人想象得大：核心交易系统、ESB总线、OA、报表、统一身份认证，往下数几乎全是Java。很多系统上线五六年没人动过，JDK版本还停在8，运维只知道“能跑就别碰”。这类系统平时不出事，一出事就是全线告警。

但“没有通用exp”不等于“没人打得进来”。Calif已经在**Keycloak、Atlassian Jira、Confluence、JFrog Artifactory、Jenkins、PingFederate**上验证了预认证RCE。这几个名字摆在一起，基本就是大部分企业的研发底座和身份入口。Java官方口径是支撑约90%的财富500强，银行、航空、电信、国家安全系统都在里面。一个洞打到这个位置，影响面不用多解释。

# 二、真正让人后背发凉的，是那3个小时

Calif的研究员Quang Luong用一个小时找到漏洞，又用两个小时做出第一个可用利用。公司特别说明，他们用了AI，和上个月挖PHP2Shell是同一套方法，总token花费不到200美元。他们还提到，这个洞是在研究某款手机厂商的0-click利用时顺手撞见的。

把这个数字和过去的节奏放一起看，冲击就出来了。一个资深研究员啃JVM底层，几个月不出结果很正常；现在是一顿午饭的时间，加一张不到两千块人民币的账单。过去漏洞挖掘是手艺活，靠人盯代码、靠经验;现在更像一门算力生意，只要有目标、有预算，就能批量开工。

这不是说AI已经能独立打穿一切。Calif自己也承认，利用链要针对具体应用做适配，他们暂时不公开应用级exp和武器化链条。但漏洞发现的边际成本已经被打到接近零，这个变化不会退回去。

更能说明问题的是，Calif上个月用同样的方法挖出了PHP2Shell。那次直接导致部分政府网站临时关站，事后统计的攻击尝试达到数百万次。一个团队、两个月、两个基础组件的高危漏洞，成本加一起还不够一次渗透测试的报价。这不是“AI辅助”，这是把漏洞挖掘从项目制变成了流水线。

对厂商来说，压力同样在传导。以前一个组件的高危漏洞，从研究员提交到厂商确认、修复、发公告，走完流程要几周。现在研究员可能上午挖到、下午就写完exp，留给你反应的时间被压缩到以天计。安全响应中心如果还按季度排期，下一次可能连公告都来不及发。

> 过去甲方做漏洞管理，隐含假设是“漏洞被发现的速度是有限的”，所以补丁晚两周问题不大。现在这个假设正在失效：AI可以在一个下午把某个组件的攻击面翻个底朝天，而你的变更窗口还是两周一次。

# 三、今晚能做的四件事

**第一，盘清楚Java在哪。**别只看服务器上装的JDK。第三方应用自带的JRE、容器基础镜像、CI构建机、甚至安全设备的管理后台，都可能有。CISA特意提醒要查“捆绑在第三方应用里的Java”，这句话背后是无数次资产台账对不上的教训。

**第二，优先处理对公网开放的系统。**Jira、Confluence、Jenkins、Keycloak、Artifactory、PingFederate这些管理面，本来就不该直接暴露在互联网上。先收口，再打补丁，顺序别反。很多团队一上来就排升级窗口，结果最该关的端口还开着。

**第三，按Oracle 11月补丁更新升级。**Linux发行版用户别只盯版本号，发行版经常回移补丁但不改版本字符串，去看包更新日志更靠谱。自研应用还要确认依赖的JRE是不是被一起带上了，别只升了宿主机。升级前留好回滚包，JVM这种底座一旦起不来，业务恢复时间比漏洞本身更让人头疼。

**第四，别把WAF当解药。**内存破坏类漏洞靠几条正则挡不住，WAF只能帮你拖时间。真正该看的是JVM异常崩溃、异常大的Base64请求，以及Web进程拉起的可疑子进程。如果Java进程突然起了bash，那比任何告警都真实。

再补两个容易漏的动作。一是让运维跑一遍进程清单，看每台机器上到底有几个Java进程、分别加载了哪些jar包，很多“影子JRE”就是这么翻出来的；二是去问一遍采购和业务部门，最近有没有新上的SaaS或一体机，厂商附带的运行环境同样在影响范围内。资产不全，后面所有修复都是空的。

# 四、当挖洞变成一门算力生意

Project Zero这个月也改了披露政策：2028年起转向“全30天”，理由是AI让漏洞发现和利用都变快了。两个信号放在一起，指向同一件事——攻防的时间尺度在缩短。以前是“漏洞公开了，我们排期修”；以后可能是“漏洞刚被AI挖出来，利用就已经在路上了”。

这对甲方安全团队其实很残酷。人还是那么几个人，预算还是那点预算，但对面挖洞的速度翻了倍。你不可能靠加班追上算力，只能靠减少暴露面、缩短修复链路、把管理面收进内网这些“笨办法”。笨办法不酷，但有用。

Java4Shell目前没有公开的通用利用，这是好消息。但它用3小时和200美元证明了一件事：漏洞的供给速度已经换挡。以后评估风险，可能不是问“我们有没有这个漏洞”，而是问“从漏洞公开到我们完成修复，需要多少小时”。这个数字，才是接下来最该被摆上桌面的指标。补丁窗口不会因为大家忙就变长，今晚能盘的Java，别留到下周。
