Cursor 这次被入侵，没有 0day，没有人攻破它的生产系统。攻击者拿到的第一把钥匙，来自一个第三方推理供应商泄露的密钥；真正的金矿，是一堆开发者和 AI coding agent 的历史对话记录，里面躺着没被清理掉的凭证。我想说的是：当你把终端、环境变量、报错栈一股脑丢给 AI 时，那段对话已经成了一个没人当回事的凭证仓库。

Cursor 这次出事,网上基本都在说供应链又被打穿了。这话没错,但我觉得没说到点子上。

一次入侵里,真正又慢又危险的活,其实是攻进一台机器之后,在里面到处翻凭证那一段。这次攻击者基本没干这一步。因为开发者平时跟 AI 排错,顺手就把密钥、连接串、报错栈贴进了对话,而 Cursor 默认会把这些对话存下来,一部分还拿去训练、共享给了第三方。他等于捡了个现成的。

所以这篇我想聊的不是“供应链很危险”,而是另一件事:我们是怎么一点点,把入侵里最费劲的那部分,替攻击者给做掉的。

## 先把事情压成一段

一把 Cursor 发给 Fireworks 的访问密钥,从 Fireworks 那边漏了出去。攻击者拿它读了两家共享的一个只读存储桶,桶里是 2025 年、没开 Privacy Mode 的 coding-agent 历史对话,其中一部分夹着没脱敏的凭证。顺着这些凭证,他进了 Cursor 的几个 SaaS 工具,拿到归档的非生产仓库、客服数据和邮件,最后把一个改过的 Claude Code 扩展(2.1.312 / 2.1.313)塞进了市场缓存,在线大概 11 个小时,最多约 5000 人可能下到。

事实就这些,哪篇报道里都有,我不展开。下面说点报道没怎么讲的。

## 平时找凭证,到底有多麻烦

要看出这次攻击者占了多大便宜,得先知道他正常情况下要干多少活。

拿到一台机器的立足点,只是开头。接下来真正值钱的事是找凭证,而这件事一点都不省心。你得在硬盘里一遍遍 grep,翻 `.env`、`~/.aws/credentials`、`.ssh`、bash 历史、浏览器存的密码,一处处试。翻得越多动静越大,容易惊动 EDR;在一台机器上待得越久,被发现的概率越高。更麻烦的是,费这么大劲,拿到的也只是这台机器上碰巧存着的东西,想要更多就得横向移动,换台机器从头再来一遍。最后还得把捞到的数据悄悄送出去,一路躲着 DLP。

这在渗透里是公认的苦活,又慢又容易露馅。攻击者最想跳过的,就是这一段。

## 这次,这些麻烦基本都没了

还是按上面那几项,一条条对下来。

落脚点不用了。数据压根不在目标机器上,它在一个第三方的桶里,有把合法密钥就能读。整个过程攻击者没碰 Cursor 的生产系统,也没碰任何一台开发者的电脑。

搜索也省了,而且省得比想象的多。开发者贴进对话的,通常不是随便一个密钥,而是当下正在用、老连不上、拿来调试的那一把,旁边还附着主机名、服务名和报错。换个说法,会话记录不是你数据的随机抽样,它专挑那些正在被使用、又刚好出了问题的凭证往里收。攻击者在陌生硬盘里翻半天,翻到的还未必是活的;这里给他的,基本都是热乎的、验证过能用的。

规模反倒更大。桶里不是一台机器的残留,是成千上万次真实排错的沉淀,跨用户、跨时间攒着。单台机器你只能拿到一个人的一角,这里是一大群人在日常工作里漏出来的凭证。

检测几乎为零。读一个你有合法密钥的桶,不会触发什么,没有 EDR 告警,没有异常登录,也没有横向移动的痕迹,看起来就是一次普通的数据访问。

搬运这步,受害者替他做了。存下来是默认策略,共享给第三方是架构设计,长期留着是因为训练用得上。防御方自己搭的那条数据管道,刚好就是现成的外带通道。

把这几条连起来看,结论其实挺朴素的。平时要攻击者亲自动手去翻的凭证,这次是用户在日常排错里一点点替他攒好的,顺带还把存储和外带都解决了。他要做的,就是在管道另一头,等一把密钥漏出来。

## 问题不在那把密钥

讲到这,很多复盘会把矛头对准那把 Fireworks 密钥:供应商没管好。这没错,但我觉得这么说反而把问题讲小了。

密钥会漏是常态,你做系统的时候就该假设它迟早会漏。真正该追问的是另一句:为什么一把供应商的密钥漏出去,能牵出全体用户的凭证?这是那个桶的设计决定的,不是谁一时大意。把所有人真实对话里的敏感信息,汇到一个第三方也能读的地方,这件事本身就埋了雷。

再往上追一层,这个桶为什么会存在。因为真实使用数据是这类产品变好的主要燃料,合成的替代不了,模型得看人到底怎么用它、在哪卡住、怎么把它问崩。所以留存真实会话,对每一家 coding agent 都是刚需,不是 Cursor 一家的毛病。这个桶不是谁疏忽攒出来的,是整类产品的生意本身要求它攒。指望靠下次注意点把它消掉,不现实,只要这门生意还在,这堆数据就一直在。

还有更要命的一层,在数据定级上。这些对话论敏感程度是公司里数一数二的,里面全是活凭证和内部信息;可它在系统里被归进遥测、训练数据这一类,拿的是日志级的待遇,留存松、共享广、谁都能读。一份秘密级的数据,套着日志级的管理规矩,这个错配才是这次能一路通到底的根子。你把生产数据库锁得死死的,却让它的密码以明文躺在一个标着分析用的桶里,真漏的时候,前面那把锁就白上了。

Privacy Mode 是 opt-in,这个细节也挺说明问题。意思是,你不主动去关,默认就是拿你的对话去训练。这次没事的那批人,恰好是当初手动关掉的。安全得靠用户自己记着去改设置,这就有点本末倒置。

还有那句“不到 0.01% 的客户凭证暴露”,听着让人安心,但我不太当真。所谓脱敏,是拿正则去扫自由聊天文本,而聊天里的密钥,原则上就扫不干净。像“帮我看下为什么 `psql postgres://user:hunter2@prod-db:5432` 连不上”这种话,脱敏器大概率接不住。这个 0.01% 不是脱敏做得多好,是它碰巧抓到的那一点。真实数字只会更多,多多少没人知道,Cursor 自己也说不清。

再说这个比例,对攻击者其实没意义。几百万次会话,哪怕只有 0.01% 带着活凭证,绝对数也是好几千把能用的钥匙,还都挑好、标好了开哪扇门。防守方爱用百分比给自己宽心,可攻击者算的从来是到手多少,几千把够他忙活很久了。

## 另外两个小点

一个是,扩展挂着谁的名字,跟谁做的没关系。被投毒的是 Anthropic 的 Claude Code 扩展,但这个恶意版本不是 Anthropic 构建、也不是它发布的,是从 Cursor 的市场缓存里分发出去的,Anthropic 的系统没被碰。你以为自己信的是 Anthropic,可实际把文件递到你手上的,是 Cursor 的分发环节,而这一环你平时压根没单独防过。

另一个是问责。这件事横跨 Fireworks、Cursor、用户三方,密钥是 Fireworks 漏的,桶是两家共享的,没脱敏的凭证是 Cursor 收进去的,中招的是用户。每一方都说自己那边处理好了,可 Fireworks 11 月 9 日自己那份安全更新里,根本没提 Cursor。一环一环看都有人认领,连起来却没人真正对整件事负责。所以读这类通报,对每家的“已处置”都得留个心眼。

## 那该怎么办

先说句不太好听的:光劝人小心点,基本没用。贴 .env 的人图的是当下省事,真出事买单的是公司和同一个桶里的其他用户,而数据的价值被厂商拿走了。做决定的人不承担后果,这种结构下,再多安全意识培训也拦不住,下回赶时间该贴还是贴。所以能指望的不是人更自觉,而是系统层面先兜住。

对个人,能做的其实有限,主要是止损。你贴给 AI 的东西,当成会被永久存档、还会流到你管不着的地方去看待。要贴配置、贴连接串,先把真凭证换成占位符;能开 Privacy Mode 就别用默认。如果你在 10 月 29 日那个窗口里从 Cursor 市场装过或更新过 2.1.312 / 2.1.313,光卸载没用,去 `~/.ssh/authorized_keys` 里找那把注释写着 `svc-telemetry` 的公钥删掉,清掉持久化任务,再把这段时间碰过的凭证轮换一遍。另外提一句,这次不少机器没真中招,是因为恶意代码写得有 bug、很多系统默认没开 SSH 没被打通,那是运气,别当成自己防得好。

真正该改的在平台这边,就是前面说的那个定级错配:把 AI 对话记录从日志那一档,挪到秘密那一档去管。具体说,脱敏要放在数据进库的那一刻就做,别指望事后再扫,更别指望用户自己换占位符;留存期要短,共享给第三方要走审批和审计,访问控制按秘密级来,而不是按分析数据来。顺便回头盘一下,你跟第三方的推理或基础设施供应商之间,到底共享了哪些数据、用的什么密钥、权限开多大。这次的整条路,就是从这儿开始的。

## 最后

把这件事放长了看,Cursor 其实不算特别。这次是 Fireworks 的密钥先漏,下次可能是另一家的桶、另一把密钥。只要大家还这么用 AI,把最真实的代码、最头疼的报错、手边刚好能用的那把密钥,随手丢给一个会记录、会训练、还会转给第三方的工具,那座替所有人攒着的凭证仓库就一直在,剩下的只是哪把钥匙先掉下来而已。攻击者真正尝到的甜头,不是攻破了谁,而是我们把入侵里最难的那一步,改成了日常习惯,替他天天做。

我不是劝你别用,它确实好用,我自己也离不开。只是这笔交易得看明白:你省下的每一点麻烦,背后都搭进去一点对自己数据的掌控。话一旦贴出去,它去哪、留多久、谁能看,就不归你说了算。前面讲了半天怎么清后门、怎么改架构,可对大多数人来说,真正还攥在自己手里的,只有一个时刻,就是你把整段 `.env` 粘进对话、手指还悬在回车上的那一下。
