入侵检测与防护的核心，并不在于传感器“看到了多少流量”，而在于它能否在可接受的延迟内，准确指出“哪些包或会话值得告警、甚至应该阻断”。在 Snort 3 中，这份判断力几乎完全由规则（rules）承载：管理员提供的规则会在启动时被翻译为多模式搜索引擎（MPSE, Multipattern Search Engine），从而在对单个数据包的一次搜索扫描中同时匹配多条模式。没有规则，传感器只是昂贵的流量旁路；规则写得粗糙，系统则在巨额 CPU 开销与海量误报之间左右为难。

许多现成规则已由 Snort 社区长期维护，用于检测后门、命令与控制（C2）服务器、缓冲区溢出，以及对已暴露服务与 Web 应用的常见利用。这套规则集称为 Snort 3 Community Rules，可从 Snort 开发者站点下载并挂载到本地实例。对大多数团队而言，合理的起点不是从零发明签名，而是把社区规则跑稳，再在本地号段补上贴近业务风险的少量定制规则。

值得先明确一点：社区规则集的默认动作以**监控**为主——命中后产生告警，但不会主动切断与攻击者的连接。后文会说明如何改变这一行为，以及如何编写自己的规则。若要在 inline 模式下实施防护，必须理解规则语法、服务识别机制、匹配选项与 inspector 绑定，再借助 PulledPork 等工具做规则集的生命周期管理。本文基于 Snort 3 规则体系，从语法到 Hyperscan，再到 PulledPork 运维实践，给出面向实战的编写与管理指南。

## 一、规则语法

一条 Snort 规则由**头部（header）**与**主体（body）** 组成。Header 描述动作用于什么协议、哪一侧地址与端口、流量方向；Body 则以选项列表尽可能精确地刻画可疑通信量。可用选项取决于已加载的插件以及规则中声明的协议——也就是说，没有绑定对应 inspector 时，某些协议专用选项根本不会生效。

### 1.1 Header

Header 沿袭自 Snort 2 的设计，依次声明：

1、**动作（action）**：`pass`、`alert`、`block`、`drop`、`rewrite`、`react`、`reject` 等；
2、**协议**：对应希望检查的协议栈层次（如 `tcp`、`udp`，或下文的 `http` 等服务名）；
3、**源地址/网段与源端口**；
4、**方向**：`->`（单向）或 `<>`（双向）；
5、**目的地址/网段与目的端口**。

例如，一条在任意主机访问任意 80 端口时告警的粗粒度写法如下（Snort 3 中 Body 亦常用花括号）：

```
alert tcp any any -> any 80 {
    sid:100001;
    msg:"Illegal access to setup.php";
    content:"setup.php";
}
```

这条规则“能工作”，但对性能不友好：几乎所有发往 80 端口的 TCP 都会进入同一类搜索组。Snort 在启动时会根据 Header 中的信息对规则进行分组，并为各组构建相应的 MPSE。编写 Header 时应**尽量具体**，否则会制造非常庞大的搜索组，被迫对（几乎）所有包执行昂贵的多模式匹配。生产环境中可把监控范围收窄到关键网段、合法服务端口，或改用服务标识（见第二节约 Service Rules），从源头控制搜索组规模。

可把 Header 视为“预过滤条件”：它决定这条规则会不会被拿来对当前流做检查。Body 再在已入组的流量上描述“可疑内容长什么样”。很多环境里的性能事故，根因并不是某条 `pcre` 写得差，而是成百上千条规则共享了过于宽泛的 Header，把 MPSE 撑到离谱。
