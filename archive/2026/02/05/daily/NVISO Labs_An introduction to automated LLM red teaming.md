## Introduction

As large language models become increasingly embedded in production applications, from customer service chatbots to code assistants and document analysis tools, the security implications of these systems have moved from theoretical concern to practical necessity.

Unlike traditional software security testing, LLM red teaming addresses unique challenges: prompt injection attacks, data leakage through carefully crafted queries, jailbreaking attempts that bypass safety guardrails, and subtle manipulations that cause models to produce harmful or unauthorized outputs. These vulnerabilities emerge from the fundamental nature of language models, and their flexibility and responsiveness to natural language input become a liabilities when that input is adversarial.

In this article, I will showcase how to automate the process of hunting for vulnerabilities in LLM-based systems in a vulnerable **ChainLit** application with the **promptfoo** CLI tool.

### What is LLM red teaming?

Nvidia[1](#1a7673e7-265b-4cfd-b34d-b0e672d4b19d) gives the following definition of LLM red teaming:

> Systematically testing AI models and systems containing AI models to identify vulnerabilities and behaviors that pose threats or risks to the systems running or using those models.

LLM red teaming comes in two different forms: **security** and **content-based** red teaming.

In a security-oriented LLM red team, the attacker assesses the overall security of the LLM system. Uncovered vulnerabilities range from classic web vulnerabilities like broken access control or injection issues to AI-specific findings such as model extraction or prompt injection.

In a content-based red team, the focus is on assessing the content generated by the model. In this type of exercise, the red teamer will try to make the LLM generate harmful, biased, or simply undesired content.

## How to test an LLM system

Because of the probabilistic nature of LLMs, testing an LLM-based application manually is a cumbersome task. Depending on your objectives, you may need to try a variety of different prompts many times. Since identical inputs can produce different outputs, a prompt that fails multiple times may succeed on a subsequent attempt.

To address the effort required to test an LLM system effectively, tools that automate this process are quickly gaining traction. These tools help the LLM red teamer gain efficiency and test coverage by automating complex attack scenarios through different techniques.

### Systematic approach

Automated red teaming tools follow a systematic process to assess the security of applications. The approach can vary depending on the tools, but it usually involves three different types of LLMs:

* **target:** the LLM that we want to assess
* **adversarial**: the LLM that generates adversarial prompts that will be sent to the target
* **grader**: the LLM that is used to grade the responses of the target to decide if an attack was successful or not

The assessment process can be summarized as follows:

1. An adversarial prompt is generated by the **adversarial** LLM based on the application context.
2. The prompt is sent to the **target** and its response is captured.
3. The **grader** reviews the **target**‘s response and decides if the test case passes or not using the LLM-as-a-Judge[2](#0b251f40-a923-451f-8324-6d8db6f021c2) approach.

### Promptfoo’s approach

**Promptfoo**[3](#207c97b8-ec45-4465-bfba-b22f2204a6da)uses a modular architecture to test for a variety of vulnerabilities. This architecture is composed of a mix of plugins and strategies that are used to test for vulnerabilities in AI systems. A **plugin** is a module that produces malicious payloads targeting specific vulnerabilities. Plugins are divided into six categories: *brand*, *compliance and legal*, *dataset*, *security and access control* and *trust and safety*. Depending on what you want to test, you would use one or more categories.

**Strategies** determine how these inputs are delivered to maximize attack success rates. They are also divided into categories: *single-turn, conversational, agentic, multimodal, custom* and *regression.* The strategies to use will depend on a variety of factors, such as the available budget (as some of these strategies require a lot of tokens to show usefulness) or the target model.

For example, we could select the plugin *harmful:hate* with the strategy *leetspeak* to generate malicious payloads formatted in leetspeak that will try to make the target output hate speech.

## Hands-on demonstration

### Lab set-up

To demonstrate content-based LLM red teaming, I created a lab environment which consists of a minimal vulnerable ChainLit application. **ChainLit**[4](#7f303f23-c98e-4e9c-9ab2-067198c30621) is a Python framework that allows developers to easily spin up a chatbot application without the need to set-up a web server or front-end themselves.

Before going further, it is important to understand what *tools* are in the context of LLMs. To expand an LLM system’s capabilities beyond basic question answering, tools can be provided to the LLM. These tools are functions defined in the chatbot’s codebase that the LLM can decide to call whenever it feels it is necessary to answer the user’s question.

In the case of my vulnerable lab, we have three different tools:

* **get\_weather**: returns the weather depending on the provided location
* **retrieve\_sharepoint\_document**: returns a document from a SharePoint environment
* **send\_mail**: sends an email to the provided recipient email address

To keep things simple, none of these tools will actually interact with an external service, and each of them returns mock data instead. What matters is that the model knows about the tools so it can decide to use them when necessary.
