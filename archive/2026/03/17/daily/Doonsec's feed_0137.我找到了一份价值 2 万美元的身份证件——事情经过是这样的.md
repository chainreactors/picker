类型：IDOR

**各位平安！**

在本文中，我将分享我如何通过深入挖掘旧的侦察数据和 JavaScript 文件，在一个意想不到的域中发现了一个**隐藏的攻击面**。最初看似一个测试环境，最终却暴露出一个**不安全的直接对象引用 (IDOR)** 漏洞，该漏洞通过 API 端点泄露了高度敏感的**个人身份信息 (PII)** 。

该漏洞允许未经授权的人员访问敏感用户信息，包括姓名、电话号码、地址和其他机密信息。通过篡改 API 请求中的对象标识符，攻击者可以检索属于多个用户的记录，从而显著增加该问题的潜在影响。

这项发现之所以特别引人注目，在于其发现过程。它并非传统的手动搜索，而是通过**分析历史侦察数据、探索 JavaScript 文件、识别侦察过程中发现的异常域名，并利用搜索引擎索引来挖掘隐藏的 API 端点而得出的**。这凸显了通过开源情报 (OSINT) 和创造性侦察来扩展攻击面，往往能够发现自动化扫描或表面测试可能遗漏的漏洞。

本文将介绍：

* 如何通过分析旧的侦察数据来发现新的攻击面
* 为什么侦察过程中发现的异常域名可能是漏洞的宝库？
* Google 搜索技巧如何帮助我们发现隐藏的 API 端点
* 一个简单的 **IDOR 漏洞如何导致大规模 PII 泄露**
* 在 API 测试中，直觉和坚持的重要性

让我们一起来看看这个漏洞是如何被发现的，发现问题的测试过程，以及在此过程中吸取的教训。

简要介绍

在深入探讨漏洞细节之前，先简单介绍一下我自己。

我叫 **Mohaseen** ，是一名**网络安全研究员和漏洞赏金猎人，** 主要专注于 **Web 应用程序安全、云安全、人工智能安全和 Web3 安全**。我于 **2019 年**开始从事道德黑客和漏洞赏金猎人的工作，从那时起，我一直在通过实际的安全测试不断学习、实验和提升我的技能。

多年来，我的漏洞研究和负责任的信息披露为我赢得了多项荣誉，其中包括：

* **4次入选苹果名人堂**
* 获得多家**全球领先组织的认可**
* 行业认可的认证，例如 **BSCP、eWPTX、eJPT、CRTA、CCSP-AWS、CAPen** 等。

网络安全对我而言不仅仅是一份职业，更是我真正热爱的事业。我乐于发现那些常被忽视的安全漏洞，并与各组织合作，帮助他们保护关键系统和敏感用户数据。

## 虫害——一切是如何开始的

##

由于工作繁忙和搬到海德拉巴，我短暂地暂停了漏洞赏金猎人的工作。但最终，我还是感受到了那股熟悉的冲动，想要重新开始。任何在漏洞赏金领域待过足够长时间的人都知道，好奇心永远不会真正消失。一旦你不再用安全的视角审视应用程序，就会感觉好像少了点什么。

但这一次，我决定换一种方式来处理。

我没有像往常那样直接进行手动测试，而是觉得重新审视之前收集**的侦察数据**会很有意思。随着时间的推移，侦察脚本会积累大量信息，包括域、子域、JavaScript 文件和端点等等，其中很多都尚未被深入探索。有时候，真正的宝藏就隐藏在你已经收集但从未深入分析过的数据中。

于是我开始挖掘。

我逐行检查了之前收集的域名、抓取的端点和 JavaScript 文件，试图了解应用程序的内部工作原理。我发现的大部分内容都是预期的 API 参考、配置文件和标准路由，但随后一些不寻常的东西引起了我的注意。

有一个领域不太符合这种模式。

为了本文的讨论，我们假设主域名类似于 **redacted.com** 。但在侦察过程中，我的脚本发现了另一个域名： **stageredacted.com** 。有趣的是，它并非像 *stage.redacted.com* 那样的典型子域名，而是一个完全独立的域名，但似乎与主域名属于同一生态系统。

在漏洞赏金猎人中，发现**新的或被忽略的攻击面，** 就像在你以为已经完全绘制好地图的建筑里发现一个隐藏的入口。我的好奇心自然而然地被激发了出来。

我在浏览器中打开了这个域名。

**404 未找到。**

乍一看，这似乎没什么大不了的。但经验丰富的研究人员知道，**在不熟悉的域名上出现 404 错误有时可能是一个非常好的迹象**。这通常意味着基础设施存在，但关键的端点并未在根路径上暴露出来。

于是我开始测试。

我尝试了模糊测试目录、探测常用 API 路由、检查典型的开发端点，并尝试了不同的路径。但经过多次尝试，仍然没有发现任何特别有趣的东西。所有请求要么返回空响应，要么返回相同的 404 页面。

![](https://mmbiz.qpic.cn/mmbiz_png/MW9pCm89BusmlsFLia8T0mu2ELreibN5ZuFLHP20y54v3BrFWDALawI5BqmLoGoucEiazCxaxiaAWvEU8HbficKuAmic2la5n6puKEhUtQWvbAPXM/640?wx_fmt=png&from=appmsg)

到那时，许多研究人员可能会转向下一个目标。

但总觉得这个域名哪里不太对劲。

我没有放弃，而是决定尝试另一种**搜索引擎**方法。

搜索引擎有时会索引开发者原本并不希望公开的端点。所以我运行了一个简单的 Google 搜索语法：

```
site:*.stageredacted.com
```

事情就是从那时开始变得有趣的。

搜索结果中出现了一些 **API 接口**。它们显然是测试环境的一部分，直接访问时似乎会返回**测试或演示数据**。我开始尝试修改这些接口中的参数值，观察 API 的运行情况。

最初，返回的响应仅包含**示例或演示记录**，没有任何敏感信息，也没有任何与生产环境相关的内容。乍一看，似乎不足以构成上报的理由。许多测试环境都包含模拟数据，这看起来也属于这种情况。

但随后我脑海中又闪过另一个想法。

如果这些相同的端点**在暂存环境之外的**行为有所不同呢？

> 译者：例如发现https://stageredacted.com/api/v1/user?userid=xxx，使用相同路径和参数去请求https://redacted.com/api/v1/user?userid=xxx

出于好奇，我尝试对**主生产域名**发出类似的请求。可惜的是，这并没有成功。响应要么返回错误，要么返回空结果。

然而，我的直觉告诉我，这里面还有更深层次的原因。

所以我尝试了另一种方法，即自动化生态系统内多个子域的请求。我编写了一个简单的脚本来以编程方式测试端点，希望 API 在基础设施的某个环节上能够做出不同的响应。

但是，一切努力都徒劳无功。

至此，最简单的结论就是：这个想法根本行不通。

然而，当我仔细查看脚本输出时，我注意到一个虽小但很重要的问题：脚本在请求中使用了**随机或占位符 ID** 。如果 API 需要有效的标识符，这就能解释为什么所有请求都失败了。

所以我决定手动测试。

我将占位符 ID 替换为**从主应用程序获取的真实标识符**，然后重新发送了请求。

从那时起，一切都改变了。

某个特定子域名上的一个 API 端点突然返回了一个包含**真实用户数据的**完整 JSON 响应。不是演示数据，也不是示例记录。

**实际生产信息。**

回复中包含高度敏感的**个人身份信息 (PII)，** 例如用户名、电话号码、地址、身份证号码、银行卡相关详细信息等。

我愣愣地盯着屏幕看了一会儿。

这不仅仅是一次测试数据泄露，而是一个**对象级授权（IDOR）漏洞，** 允许访问真实用户记录。

如果该端点容易受到 ID 篡改，那么下一个问题就显而易见了：

**可以访问多少数据？**

这时，脆弱性的真实规模才开始显露出来。

![](https://mmbiz.qpic.cn/sz_mmbiz_png/MW9pCm89Bus3cBJ2nKE6u59YGLetWXgN6IOflZNFsMfKhDeumr61j6ic67TJcYHYLhCzRj9meerQaE5Er3g60sGZKFK4nY2UoDehqz5CL1xI/640?wx_fmt=png&from=appmsg)

确认影响——以及意想不到的结局

至此，情况变得非常清楚：这并非只是一个暴露无害演示数据的测试环境。API 返回的是**真实的生产用户信息**，而且没有执行适当的授权检查。

然而，在妄下结论之前，我需要仔细确认其影响。

返回敏感数据的请求包含一个数字标识符参数。如果这确实是一个 **IDOR（不安全直接对象引用）** 漏洞，那么修改该标识符可能会导致返回属于其他用户的记录。

为了验证这一点，我拦截了请求并将其发送到 **Burp Suite Intruder** ，配置了一个较小的标识符范围来测试 API 的行为。我没有进行大规模扫描，而是从 **xxx00 到 xxx99 的**有限范围开始，仅足以观察端点是否存在漏洞。

很快，各方回应就暴露了问题所在。

每次请求都返回了**不同用户的记录**。

该 API 泄露了高度敏感的**个人身份信息（PII），** 其中包括：

* 全名
* 电话号码
* 住宅地址
* 识别号码
* 卡片相关详情
* 以及其他机密用户信息

该 **API 没有设置任何授权检查机制**。只要提供有效的标识符，API 就会直接返回关联用户的数据。这意味着攻击者可以自动发起请求，并获取大量敏感的用户信息。

换句话说，这不仅仅是一起小规模的信息泄露事件，而是**由对象级授权缺陷（BOLA / IDOR）导致的大规模个人身份信息泄露漏洞**。

在这个漏洞赏金计划中，涉及大规模泄露敏感用户数据的漏洞通常属于 **P1 级别**，赏金最高可达 **2 万美元**。当然，我仔细记录了发现的情况，收集了概念验证请求和响应，并准备了提交的报告。

一切准备就绪后，我向程序提交了漏洞报告。

有趣的是，**大约四个小时**后，这个问题就得到了解决。

起初，我以为快速响应意味着报告已被优先处理，安全团队已立即采取行动修复漏洞。但后来我收到项目组的回复后，发现情况与预期略有不同。

根据他们的回复，内部安全团队已经通过其安全运营中心 (SOC) 监控系统检测到与该终端相关的异常活动，并在我提交报告之前就开始调查此事。现在看来，很可能是我在 **Burp Intruder 测试**期间产生的请求激增触发了警报，从而使他们的团队能够迅速识别并修复漏洞。由于在他们审核我的报告时，修复程序已经部署完毕，因此他们无法重现我报告中的问题。

因此，该报告被撤销，没有支付赏金。

因此，虽然该漏洞本身有可能造成 **20,000 美元的 P1 问题**，但最终的奖励却为 **0 美元**。

![](https://mmbiz.qpic.cn/sz_mmbiz_png/MW9pCm89BuuibkhsG0S5vMVxtuiboIwEQwyIibu16aC0PsmGn6237XON7vQQIJ50IczhRuG94CICsccRBsbxKu0ZrFMDreT6KK8JeNp9tHSH7g/640?wx_fmt=png&from=appmsg)

虽然这听起来令人沮丧，但这次经历也凸显了漏洞赏金猎人的一个重要现实：有时，即使你发现了一个关键漏洞，确认了其影响，但如果该问题在报告处理之前已被内部识别或修复，你仍然无法获得赏金。

而这只是游戏的一部分。

## 教训

这一发现提醒我，一些最有趣的漏洞往往出现在你开始探索他人可能忽略的领域时。就此而言，一切都始于侦察过程中发现的一个不寻常的域名，以及在挖掘旧数据时产生的一丝好奇心。扩大攻击面并相信你的直觉，往往会带来意想不到的发现。

这也凸显了漏洞赏金猎人工作中的一个重要现实：有时即使你发现了一个严重的漏洞，也可能因为时机不对或内部检测不到而最终一无所获。虽然这令人沮丧，但每一次这样的经历都会丰富你的学习过程，并帮助你改进未来的漏洞赏金猎人工作方法。
