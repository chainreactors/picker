一个 Agent 怎样才能逐渐熟悉一个项目? 通用模型提供了代码和推理能力, 但具体项目里的概念, 约定和历史, 还需要从团队的材料与实际工作中获得。 拿到这些信息之后, Agent 还要判断它们在什么条件下成立, 应该怎样影响当前任务。

这涉及两个不同的问题。 一个是如何表达项目知识, 让模型理解我们在讨论什么。 另一个是如何利用执行反馈, 让后续任务受益。 本体和 RSI 分别从这两个方向提供了思路, Memory 则承担知识保存与复用的工作。

我们先从这些基本概念讲起, 再看相关研究如何把它们联系起来, 最后展开我们在内部研发 、Loop 中的实践。 我们关心的落点很具体: 能不能让 Agent 少花一些重新理解项目的时间, 少犯一些团队已经弄明白的错误。

### 1. AI 时代的本体, 到底是什么

#### 1.1 从词的含义, 到一个领域的共同模型

这里说的本体, 即 Ontology, 是知识工程中的概念, 不展开哲学里关于「存在」的讨论。 可以先这样理解: **本体把一个领域中有哪些概念, 概念之间是什么关系, 有哪些成立条件, 明确表达成一套可以共享的模型。**

「共享」很重要。 一个人心里知道什么叫订单完成, 不代表仓储系统, 财务系统和客服使用同一种含义。 同样, 模型知道中文里的「完成」是什么意思, 不等于知道某家公司以支付, 出库还是签收作为完成标准。 本体要把这种领域内的约定表达出来。

用一个简化的订单系统来说明。 「订单」和「发货单」是概念或类型; 某一笔订单是具体对象; 「订单对应发货单」是一种关系; 金额, 币种和创建时间是属性。 如果业务允许拆单, 一个订单就可能对应多张发货单。 如果业务规定所有有效发货单签收后订单才完成, 这个条件也需要明确。

这样一来, 「一张发货单已经签收」和「整个订单已经完成」就不能随意互换。 区别来自对象和关系, 不来自两句话看起来有多相似。 拆单规则若随业务版本变化, 条件还要带上适用范围。

更严格地说, 本体要让概念和关系具有明确的语义。 哪些对象属于同一类, 哪种关系可以连接哪些对象, 什么条件下能够推出某个结论, 都应有一致解释。 [W3C 的 OWL 2](https://www.w3.org/TR/owl2-overview/) 提供了类, 属性, 个体及逻辑公理的表达方式。 这说明本体并不是大模型出现后才发明的东西。

工程实践未必一开始就使用完整的形式化语言。 有版本的概念定义, 关系类型, 数据映射和规则文件, 也可以逐步承担这些职责。 关键在于含义能被核对, 模型不必每次从散落的材料里临时猜测。

这里还要分开两件事: 表达规则, 与确认实际数据满足规则。 本体可以表达订单和发货单的关系, 但当前订单是否满足完成条件, 还需要查询数据并检查。 [SHACL](https://www.w3.org/TR/shacl/) 处理图数据的约束验证, 业务系统也可以通过普通程序和测试完成检查。 本体不会因为写下了一条规则, 就保证现实已经遵守它。

#### 1.2 它与 Schema, 知识图谱和 RAG 有什么不同

这些概念经常一起出现, 但关注点不同。 数据库 Schema 主要描述数据怎样组织, 知识图谱描述实体和关联, RAG(检索增强生成) 把检索内容提供给模型, 本体则强调对象与关系的共同含义。 它们可以组合, 也可能在具体系统中有重叠。

仍以订单为例, 一张表可以有 status 字段, 但字段存在不代表我们已经知道它属于订单还是发货单, 哪些状态是中间态, 什么时候能据此认定业务完成。 如果这些知识只存在于某位工程师的记忆里, Agent 看到表结构之后仍然要继续寻找。

| **方法或资产** | **主要提供什么** | **单独使用时仍需回答什么** |
| --- | --- | --- |
| 数据库或接口 Schema | 字段, 类型, 数据结构和部分约束 | 字段在业务中代表什么, 与其他系统如何对应 |
| CodeGraph | 符号, 调用, 依赖和代码位置 | 调用链承担什么业务职责, 哪些约定不能破坏 |
| 知识图谱 | 实体及其关系实例 | 关系是否有明确含义, 适用范围和依据 |
| 文档与 RAG | 与当前问题相关的材料 | 多段材料是否在谈同一对象, 是否适用当前场景 |
| 本体 | 共享概念, 关系语义和相关公理或约束 | 当前事实是否符合这些定义, 动作是否产生预期结果 |

这张表并不意味着 RAG 只能搜索文本, 或 Schema 不能表达语义。 一个好的 RAG 系统也可以利用图谱, 规则和结构化过滤。 区别在于, 增加检索能力与补齐领域含义是两项不同的工作。 检索找到了一份政策, 还需要判断它是否适用于当前车型, 年款, 地区和时间。

本体与知识图谱也不是互斥的两种技术。 图谱可以按照本体组织事实, 本体本身也可以用图表示。 但如果一张图所有边都叫「相关」, 模型仍然不知道两端究竟是实现关系, 依赖关系, 还是一方违反了另一方的约束。 连接更多节点与表达更准确的关系, 不是同一个目标。

**我们真正需要补的是: 找到一段知识之后, 还能判断它在说哪个对象, 在什么条件下成立, 能支持哪一步推断。** 存储在图数据库, 关系表还是文件里, 是之后的实现选择。

#### 1.3 为什么 Palantir 和 FDE 会反复遇到这个问题

[Palantir 的 Ontology 系统](https://www.palantir.com/docs/foundry/architecture-center/ontology-system/) 把 data, logic, action 和 security 联系起来。 它不只组织可查询的数据, 还将业务对象与逻辑, 操作和权限结合。 模型或应用通过业务对象理解系统, 也通过受控的操作影响系统。

例如, 「迁移一个实例」涉及实例与节点的关系, 目标区域限制, 迁移状态, 可执行的动作和操作权限。 仅知道实例对应哪张表, 还不足以完成迁移。 对象模型需要与实际流程连接, 执行后还要核对结果。 动作和权限属于这类产品系统的扩展, 不应直接当成所有经典本体的定义。

Palantir 的[建模建议](https://www.palantir.com/docs/foundry/ontology/ontology-best-practices/) 强调从现实领域出发, 再映射源数据。 这一点对研发很有启发。 业务上的同一个对象可能分布在多个系统, 一个数据表也可能混合多个业务概念。 直接把表搬成图上的节点, 并不会自动补出这些含义。

由此也就容易理解 FDE, 即 Forward Deployed Engineer, 为什么会关注本体。 这类工程师深入具体业务现场, 需要把用户的目标, 既有系统和交付标准连接起来。 用户说「这个流程成功了」, 工程师得继续确认: 哪个对象成功, 哪个阶段成功, 是受理成功还是业务结果已经生效?

我们的理解是, Agent 越接近实际操作, 这类工作就越难省略。 含义不一致, 会继续传到工具参数, 代码实现和验收断言里。 本体提供了一种把业务澄清沉淀为共享模型的方法, 不必每个功能都在自己的 Prompt 里重新解释一遍。

所以, 「AI 时代的本体」并没有改变本体的基本含义。 变化在于它开始更直接地参与 Agent 的检索, 判断和行动, 并需要随业务与执行反馈持续维护。 这也引出了下一个问题: 这些理解能否在任务之间积累, 甚至让系统改善自己获得理解的方法?

### 2. 从 Loop 和 Memory, 理解 RSI

#### 2.1 任务反复执行, 不等于系统已经学会了

先解释这里的 Agent 和 Loop。 Agent 可以利用模型作判断, 调用工具执行动作, 再根据环境反馈继续推进。 Loop 就是这段「行动, 观察, 调整」的循环。 对 coding 任务而言, 写代码, 执行测试, 读取失败, 修改后重测, 已经构成一个执行 Loop。

这个循环能把当前任务做得更好, 但任务结束后, 下一轮未必有所不同。 如果新会话再次从相同信息出发, 它可能重新搜索同一条链路, 再误解一次相同的业务约定。 当前任务的完成与跨任务学习, 需要分别设计。

Memory 的作用是保存可以跨轮次使用的信息。 保存的内容可以是发生过的事件, 已确认的知识, 也可以是处理任务的方法。 模型权重保持不变, Agent 系统仍然可能因为获得了更合适的知识与工具而表现更好。

[Reflexion](https://arxiv.org/abs/2303.11366) 给出了利用语言反馈的一个例子。 Agent 根据任务反馈形成反思, 将其保存在情节记忆中, 指导后续尝试。 [Agent Workflow Memory](https://arxiv.org/abs/2409.07429) 进一步关注可复用工作流, 从历史经历中归纳操作方法, 再选择性提供给后续任务。 前者说明反馈可以成为记忆, 后者说明记忆也可以是「怎样做」。

但保存不等于学会, 复用也不保证改进。 一条错误经验被更稳定地召回, 反而可能让错误重复得更稳定。 因此我们把 Memory 称为自改进的方法和燃料时, 还要补上后半句: **经验需要改变后续行为, 并通过后续结果检验它是否有用。**

反馈也不能只留下「成功」或「失败」。 相同的失败可能来自代码缺陷, 环境异常, 观察器错误或业务概念混淆。 对这些情况使用同一种反思模板, 很容易形成宽泛但不能指导行动的建议。 有价值的反馈应保留发生条件, 判断依据和被排除的解释。

#### 2.2 RSI 中的「递归」, 究竟体现在哪里

RSI 是 Recursive Self-Improvement, 即递归自我改进。 自改进意味着系统改变自身的某些部分, 改善后续表现; 递归性进一步指向, 产生改进的过程也能够成为改进对象。 讨论时最好直接问: 改了什么, 谁根据什么反馈来改, 改完怎样验证?

我们可以按改动对象区分三个层次。 这是帮助分析工程系统的视角, 不代表所有论文采用统一分级。

| **层次** | **变化发生在哪里** | **一个研发例子** |
| --- | --- | --- |
| 执行内迭代 | 当前任务的计划或产物 | 测试失败, 修改这次需求的代码 |
| 跨任务自改进 | 持久知识, 工具或工作方法 | 保存已验证的兼容经验, 供下一轮使用 |
| 改进过程的自改进 | 生成, 选择和验证改进的方法 | 根据后续表现, 修改经验抽取或 Skill 优化策略 |

[Darwin Gödel Machine](https://arxiv.org/abs/2505.22954) 研究了迭代修改 Agent 自身代码的路线。 系统维护候选 Agent, 通过编码评测筛选改动。 它改变的是解题系统的工具和工作机制, 而不只是某道题的代码。 这与普通的「测试失败就改补丁」有明显区别。

预印本 [Skill∞](https://arxiv.org/html/2610.35434v1) 则把递归关系表达得更直接。 它用 task skill 保存解决任务的方法, 用 meta-skill 描述如何优化这些 skill。 meta agent 根据执行轨迹诊断问题, 提出候选, 请求独立审查并分配搜索预算。 随后, 同一种优化过程还可以作用于 meta-skill 自身。

因此, 一个版本可能改进「如何定位 Bug」, 另一个版本则改进「如何分析定位失败, 并生成更好的定位方法」。 后者是否有效, 要看它能否在给定预算下产出更好的 task skill。 Skill∞ 将评分放在自改进范围之外, 候选还需要经过独立审查。 允许改进方法, 与允许改低评分标准, 是两件事。

这些研究让 RSI 有了可以实验的具体对象, 但都在限定任务, 预算和验证条件下工作。 我们在企业研发中可以从外部记忆, 工具和流程开始探索, 无需先改基础模型权重; 同时, 一次正向实验也不足以说明系统能够持续, 无限地变强。

到这里, 本体和 RSI 的分工已经比较清楚: 本体帮助系统表达与使用领域知识, RSI 关注系统怎样根据反馈改进自己。 两者不是互相成立的前提, 但当主要卡点来自概念理解时, 本体就成为一个值得改进的对象。

### 3. 本体与 RSI 可以怎样结合

#### 3.1 EvoOntology: 让本体根据 Agent 的使用反馈演进

一个直接相关的研究是预印本 [EvoOntology: A Self-Evolving Ontology Layer for Data Agents](https://arxiv.org/html/2609.15779v1)。 它讨论的场景是数据分析和 text-to-SQL, 即将自然语言问题转成 SQL 查询。 Agent 面对数据库或文件时, 经常反复确认字段含义, 表间关系和过滤条件。 即使某次已经查明白, 后续任务仍可能重新发现一遍。

论文将可演进的本体系统拆成 Content, Schema 和 Tool 三部分。 Content 保存领域概念, 到数据字段的映射, 使用约束和支撑证据; Schema 规定这些对象及关系怎样表达; Tool 决定 Agent 怎样找到和展开这些信息。 这里的三部分与后文我们的三层项目图谱划分不同, 不能按名字直接对应。

它提供了两类访问: browse 找到语义上相关的对象, resolve 取得所需对象及关联记录。 会话开始时只提供简要说明, 具体知识由 Agent 按需查询。 本体因此既是可维护的知识, 也是 Agent 实际会使用的接口。

论文附录中的一个卡牌查询案例很直观。 任务要找到在某种游戏赛制下被禁用的卡牌。 初始本体已经知道卡牌与合法性记录的关联, 也知道状态存放在 legalities。status, 但没有明确状态相对于赛制成立。 Agent 能找到字段, 却还要自己重新确认如何使用。

演进过程把问题定位为语义内容缺失, 增加状态值的含义, 对应字段, 观测证据及约束。 要找目标赛制的禁用卡牌, 需要同时满足 legalities。status = 'Banned' 与 legalities。format = target\_format。 只检查「禁用」会丢掉适用范围。 这次改动补充的是内容, 不需要修改查询工具或整个 Schema。

更重要的是, 论文没有把每次失败都处理成「再加一段提示词」。 它先分析执行轨迹, 判断限制来自内容缺失, 工具暴露不合适, 还是当前 Schema 无法表达所需知识。 每个候选针对其中一个层面作局部修改, 然后让候选与原版本在相同模型, 验证集和交互预算下比较。 改善达到设定幅度才保留, 未通过的修改记录下来, 不直接部署。

这项设计同时区分用于构建和选择候选的材料, 与最终测试任务。 本体在最终测试前冻结, 不能一边看到测试答案, 一边补充语义后再报告同一批成绩。 完整查询仍由工具执行并验证, 本体只提供有依据的解释与使用条件。

**这个方法提供的关键思路是: 本体既可以帮助 Agent 理解任务, 也可以因 Agent 的实际使用结果而被修订。** 但修订本体与递归改进修订机制仍有区别。 EvoOntology 直接研究了前者, Skill∞ 则提供了理解后者的参照。 数据任务中的结果也需要重新经过实验, 才能迁移为研发 Loop 的结论。

#### 3.2 我们的想法: 让经验有归属, 让反馈找到具体改进对象

把前面的研究放在一起, 可以看到一条逐渐具体的路线。 Reflexion 关注如何从反馈留下经验, Agent Workflow Memory 关注如何形成可复用方法, EvoOntology 关注语义知识及其访问方式怎样演进, Skill 进一步把优化过程本身变成可修改对象。

对于我们, 这里最值得借鉴的地方是, 不要把所有失败统一归为「模型还不够聪明」或「Memory 还不够多」。 同样表现为定位失败, 背后可能有完全不同的原因: 代码关系没找到, 业务含义理解错, 旧经验的条件不匹配, 或者已经知道约束却没有执行相应检查。

本体可以让这些反馈有更明确的归属。 一次失败不只关联一个会话, 还可以关联到某个业务概念, 某条跨仓映射, 某个状态条件, 或者某项错误推断。 下一次优化就有了具体对象, 不必把整份记忆重写一遍。

比如, 把「请求受理」和「业务完成」混为一谈, 需要补充或拆分概念; 概念已经准确, 但搜索只返回相似旧案例, 需要调整索引或适用性过滤; 检索和解释都没有问题, 却仍省略数据面检查, 则要检查工作流程和验证工具。 这几种问题不能只靠增加同一句提醒来解决。

我们希望形成的关系是: Loop 提供行动与真实结果, Memory 保存经验及来源, 本体组织概念和经验的适用条件, 后续任务检验这些知识是否改变了行为。 如果还能据此改进抽取, 检索和使用策略, 就进一步进入学习机制的改进。

这里有一个容易忽略的代价。 语义组织会增加抽取和维护成本, 图关系也可能放大错误经验的影响。 所以, **本体与 RSI 的结合需要同时具备「能关联」和「能纠正」的能力。** 系统应该能够收紧一条经验的适用范围, 拆开被误合并的概念, 或撤回不成立的结论, 而不是只能继续增加内容。
