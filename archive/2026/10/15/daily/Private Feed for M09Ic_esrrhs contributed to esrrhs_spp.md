## 背景

按「加固现有测试 + 引入 fuzz」的要求，给 `proxy` 加了原生 Go fuzzing，覆盖代码里所有由客户端输入驱动的解析边界。

## 新增 5 个 fuzz target（`proxy/fuzz_test.go`）

| target | 覆盖点 |
| --- | --- |
| `FuzzMarshalUnmarshalFrame` | 帧编解码往返，跨 codec 矩阵 |
| `FuzzUnmarshalFrameBytes` | 任意字节输入必须报错，绝不 panic |
| `FuzzWireSealOpen` | AEAD seal/open 往返（ChaCha20-Poly1305 / AES-GCM） |
| `FuzzParseHost` | 请求行 / Host 头 → 拨号地址 |
| `FuzzCompressRoundTrip` | zlib/zstd 往返，重点压阈值边界 |

## FuzzParseHost 发现并修复了 4 个真实缺陷

`parseHost` 是全客户端可控的字符串入口，fuzz 找到它把垃圾输入拼成了既不可拨号、日志里也读不懂的地址：

| 输入 | 修复前 | 修复后 |
| --- | --- | --- |
| `":]"` | `"[:]]:0"` | `""` |
| `"[["` | `"[[:0"` | `""` |
| `"[:]"` | `"[:]:0"` | `""` |
| `":"` + 非法默认端口 | `"::"`（已不再是合法地址） | `""` |
| `"host:abc"` / `"host:99999"` | 原样交给 `net.Dial` | `""` |

最后一类由新增的 `validPort` 拦截：请求行里的端口必须是数字且 ≤ 65535。生产调用方传的是 `"80"` / `"443"`，正常流量不受影响；畸形请求现在在解析阶段就被拒，而不是到 dial 时才抛一个含糊的错误。

## 回归固化

* `TestParseHost` 表格补了 12 个用例（含 fuzz 发现的每一个输入）。
* 5 条 fuzz 语料落到 `proxy/testdata/fuzz/FuzzParseHost/`，`go test` 会自动跑种子语料，所以这些发现是长期回归测试，不是一次性结果。

## 验证

* 5 个 target 各跑 60–150s 全部 PASS（`FuzzParseHost` 150s / 187 万次执行）。
* `go vet ./...` 干净。
* `go test -count=1 ./...` 全绿；`go test -race ./proxy/` 全绿。

## 发现但未改动（等你定）

`UnmarshalSrpFrame` 解压没有输出上限：zstd 对全零数据约 5000:1，一个 1MB 帧理论上能展开到 GB 级。修法是流式 `io.LimitReader`（zstd 需要把 `klauspost/compress` 从 indirect 提为 direct）。这属于「加上限」一类，与刚定的「不搞最大限制」是同一族决策，所以没擅自改，fuzz 里用 `fuzzMaxBlob` 规避了。要修我另开一个 PR。
