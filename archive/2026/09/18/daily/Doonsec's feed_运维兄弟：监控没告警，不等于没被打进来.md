# 监控没告警， 不等于没被打进来

监控大屏安静，从来不是"系统安全"的证据，只是"还没看见"的代名词。

监控盲区护网自查安全预警

🔑 一句话提醒：监控大屏安静，从来不是"系统安全"的证据，只是"还没看见"的代名词。

每年护网、每次重保，最容易被忽略的不是攻击多猛，而是一个错觉——态势感知没弹窗、WAF 没拦截、IDS 没噪音，就默认一切正常。真实入侵往往安静得像影子：不扫端口、不暴破、不触发任何规则，只是悄悄改了几个文件、留了个后门、加了条计划任务。等告警响的时候，人家已经在里面待了半个月。

这不是吓唬人。光 2025 年，腾讯安全就披露 SkidMap 病毒借 Redis 未授权访问把数千台云主机变成矿机；Mandiant 的应急数据里，超过一半的组织是被外人提醒才发现中招的。沉默，往往是入侵正在进行时的状态，不是安全的证明。

下面这条提醒，写给每一个守着大屏、写着"无异常"日报的甲方运维和安全工程师。

## 01监控覆盖的是"攻击行为"，不是"攻击结果"

这是最容易踩的坑。SIEM、WAF、IDS 这些设备，本质是看"动作"：有没有扫描、有没有注入、有没有外连可疑地址。但攻击者真正留下的"结果"——核心文件被改、后门被植入、计划任务被加——这些发生在操作系统层面，监控默认照不到。

行业数据把这件事说得很直白。Mandiant 在 M-Trends 2026 报告（基于 2025 年 50 万小时应急数据）里给出：全球入侵中位驻留时间（攻击者潜伏未被发现的天数）已经回升到 14 天；更刺眼的是，只有 52% 的组织是靠自己发现入侵的，剩下近一半是别人（监管、友商、攻击者自己）通知才知道。Picus 的 Blue Report 2026 更直接：攻击者一旦进入内网，只有 37% 的活动被拦截；他们 2025 年跑了 1.6 亿次攻击模拟，平均 每 7 次攻击只有 1 次被检测到。

⚠️ 注意：CrowdStrike 2025 年全球威胁报告提到，75% 的入侵是"无恶意软件"的——靠偷来的凭据、靠社工、靠会话劫持。文件不落盘，传统杀毒和沙箱全盲。你的大屏上干干净净，很可能只是因为人家压根没用你能看见的手法。

更扎心的是"发现速度"和"攻击者速度"的反差。Mandiant 同份报告显示，从拿到入口到把权限转交下一波人，2025 年中位时间已经压缩到 22 秒（2022 年还要 8 小时以上）。攻击者跑得比你的告警快得多，而你平均要 14 天才能察觉。Picus 的模拟还指出，凭据窃取这类"低调"动作，侦察阶段只有 10% 被识别、从内存读凭据也只有 22%——人家在你眼皮底下摸凭据，监控多半没反应。

## 02最危险的入口，是"临时用一下"的配置

讲一个反复出现的真实隐患：Redis 未授权访问。这不是新漏洞，但年年中招。2025 年 11 月，腾讯安全威胁情报中心披露 SkidMap 病毒变种借 Redis 未授权访问打穿云主机，约数千台云服务器沦为矿机，且这批失陷主机大多没部署云原生防护。同年 10 月披露的 CVE-2025-49844（代号 RediShell，CVSS 满分 10.0）影响所有 Redis 版本；研究者扫描发现，全网约 36 万个公网 Redis 实例里，有 约 6 万个完全不设密码。

攻击手法一点都不花哨。安全团队用蜜罐观测到，高达 87% 的入侵走的是同一条路：利用 Redis 合法的备份功能，执行 `CONFIG SET dir /var/spool/cron/`再 `SAVE`，直接把计划任务写进系统目录，重启即拉起挖矿木马。整个过程没有利用任何漏洞，只是"功能被滥用"。

换成甲方视角就是一句话：那台护网期间临时拉起来做压测的机器，Redis 绑了 `0.0.0.0:6379` 又没开认证——它就是攻击者最顺手的那扇门。

同一批观测还记录到另外几种"借鸡生蛋"的玩法：用 `LPUSH` 命令去打 Apache Airflow 的 Celery 消息队列（CVE-2020-11981），借它执行宿主机命令；把 ELF 木马伪装成 `.png` 图片文件下载，骗过基础内容过滤；甚至在 cron 里用 `echo ...|base64 -d|bash` 把真实下载地址藏起来，躲过简单字符串匹配。说到底，Redis 一旦不设防，它自己合法的备份、队列功能全都能被当成攻击通道。

容器场景更要当心。CPO Magazine 援引 Wiz 的研究：约 75% 的云环境部署了 Redis，其中 57% 是以容器镜像方式跑的，而官方 Redis 容器默认就不要求认证——没仔细配置，实例从一开始就空密码。

## 03文件被改了，你的大屏不会告诉你

文件篡改是"攻击结果"里最隐蔽的一类。系统该长什么样，攻击者偷偷改了样，监控层几乎没有对应告警。Linux 上最朴素也最有效的自查命令是 `rpm -Va`：拿 RPM 数据库里的元信息跟磁盘实际文件比对。

⏺ Shell · 文件完整性校验

rpm -Va

输出里每个标记代表一类异常：

**S**文件大小变了

**5**MD5 校验和不匹配（内容被改）

**T**时间戳变了

**M**权限或文件类型变了

正常系统几乎没输出，滚出来一大片就要警惕。但要记住，rpm 只查"包管理器装过的文件"，黑客自己塞的新文件它看不见。补一刀按时间筛：

⏺ Shell · 按时间捞最近改动的文件

find / -mtime -7 -type f -not -path "/proc/\*" -not -path "/sys/\*" -not -path "/var/log/\*"

把最近 7 天改过的文件捞出来（护网一到两周就改 `-mtime -14`），排掉虚拟文件系统和日志，剩下的挨个看。经验里，后门常伪装成 `.sshd`、`.cache` 这种带点号、混在正常目录旁边的名字。

💡 提示：光靠 `rpm -Va` 还不够稳。攻击者要是连 RPM 数据库一起改了，这招就失灵。更靠谱的是用 AIDE 建一份"干净基线数据库"，存到只读介质，之后每天 `aide --check` 比对。基线之外的任何改动，都该有工单解释。

AIDE 部署就三步：装好之后初始化基线，再把数据库挪到安全位置，日常只跑检查。

⏺ Shell · AIDE 基线三步

# 安装

yum install -y aide        # 或 apt-get install aide

# 建基线（系统刚装好、还没联网时做最准）

aide --init

cp /var/lib/aide/aide.db.new.gz /var/lib/aide/aide.db.gz

# 每天检查

aide --check

关键原则：基线数据库别留在被监控的那台机器上，刻到光盘或传到独立服务器，否则攻击者改了系统顺手也把数据库改了，检查就毫无意义。

## 04后门藏在你以为"正常"的角落

攻击者进来一定留后门，目的就一个：下次还能进来。这几处是高频藏匿点，自查时别跳过。

**权限后门（SUID）**。属主是 root 的 SUID 文件，谁执行谁就是 root。正常系统里就 su、sudo、passwd、mount 那几个，多出来的二进制八成有问题：

⏺ Shell · 查 SUID 文件

find / -perm -4000 -type f 2>/dev/null

更阴的玩法，是给 `/bin/find` 加 SUID，再用 `find . -exec /bin/sh \;` 直接起 root shell。应对办法：拿一份干净系统的 SUID 列表做 diff。

**计划任务**。只看当前用户不够，所有用户的都要查：

⏺ Shell · 查所有计划任务

cat /etc/crontab && ls -la /etc/cron.d/ && ls -la /var/spool/cron/

重点看每隔几分钟执行一次、调用 `/tmp` 下文件的任务。见过有人把文件命名为 `sysstat` 放进 `/etc/cron.d/`，每 5 分钟跑一次 `/tmp/.systemd`，名字像系统服务，不细看根本发现不了。

**系统服务**。现在攻击者越来越爱用 systemd 做持久化，比 cron 还隐蔽，重启自动拉起：

⏺ Shell · 查已启用的系统服务

systemctl list-unit-files --state=enabled

留意 Description 写得像系统服务的，比如"System Security Monitor"这种——正经服务不起这种名。

**反弹 shell 落点**。`/tmp`、`/dev/shm` 是反弹 shell 最爱待的地方：

⏺ Shell · 查临时目录可执行文件

find /tmp /var/tmp /dev/shm -type f -executable

真实案例里，有样本把自身伪装成 `[kworker]`、`crond` 这类系统进程名（RotaJakiro 后门、Xnote/FZX 家族都这么干），甚至直接替换掉 `/usr/sbin/crond`本体。进程名能改，但 `/proc/[pid]/exe` 的真实路径改不了，怀疑时就查：

⏺ Shell · 查伪装进程的真实路径

ls -l /proc/\*/exe 2>/dev/null | grep -i tmp

**SSH 公钥后门**：攻击者拿到权限后，常把自家公钥写进 `authorized_keys`，之后免密直登，连密码都不用。排查所有账号的家目录：

⏺ Shell · 查可疑 SSH 公钥

grep -R "ssh-rsa\|ssh-ed25519" /home/\*/.ssh/authorized\_keys /root/.ssh/authorized\_keys 2>/dev/null

不认识的指纹一律清掉。

**动态库预加载**：`/etc/ld.so.preload` 能让所有程序优先加载某个恶意 .so，用来劫持认证函数、偷密码、藏文件。看一眼有没有可疑内容：

⏺ Shell · 查动态库预加载

cat /etc/ld.so.preload 2>/dev/null

空文件才正常，有路径就要追根问底。

**正在跑什么**。`ps auxf` 看进程树，nginx 突然 fork 了 bash、sshd 起了 python，都不正常。`ss -antp` 看网络连接，重点盯 ESTABLISHED 的外连——看到连 `xxxx:4444`（metasploit 默认端口）基本就坐实了。除了 4444，常见 C2 端口还有 53、80、443 这类伪装成正常服务的，配合域名或云 IP，光看端口反而容易漏，得结合进程归属一起判断。

## 05每天 10 分钟，把四步走一遍

上面这些不是让你出事后才翻，而是当成日常巡检。护网期间，至少每天花 10 分钟把下面四步复制粘贴走一遍，比临阵翻文档强十倍：

|  |  |
| --- | --- |
| R1 | **文件篡改**`rpm -Va` 看异常标记，find 按时间捞新文件 |
| R2 | **权限与后门**`find -perm -4000` 查 SUID，翻 /tmp、/dev/shm 的可执行 |
| R3 | **持久化**`/etc/crontab`、`/etc/cron.d/`、`systemctl list-unit-files` 逐一看 |
| R4 | **进程与连接**`ps auxf` + `ss -antp` 找异常进程和外连 |

更进阶的做法，是把 `rpm -Va` 和 find 写成脚本，挂上 cron 每天自动跑，结果 diff 一下，有变化就告警——不用多复杂，一个 shell 加一行 crontab 的事。AIDE 基线数据库建好之后，`aide --check` 也接进定时任务，每天邮件或推送到群里。

护网期间这些命令的输出本身就是证据。白队要看的，是你从哪台机器、哪个时间、揪出了哪个被改的文件、哪个可疑外连——把每次排查的结果留痕归档，提交材料时才拿得出完整链路，而不是一句"我们查了，没问题"。

## 06把"配置类入口"也堵上

监控盲区补上了，配置类入口不能留。针对 Redis 这类高频被滥用的服务，几条硬规矩：

• 绑定 `127.0.0.1`，绝不对 `0.0.0.0` 公网暴露；必须跨网络访问就走 VPN 或内网隔离

• 开启 `requirepass` 强密码，必要时上 ACL 分账号授权

• 关掉不必要的 Lua 脚本执行（`EVAL`/`EVALSHA`），非可信用户禁用

• 容器里跑 Redis 默认不认证，57% 的云环境用容器镜像却没加固——部署时一定显式加密码和网络限制

• 定期扫一遍资产，看有没有"临时机器""测试环境"忘了收尾

日志也要集中。端点没进程日志、防火墙不保留日志、服务器缺认证日志，攻击者在里面待几个月都没痕迹。哪怕先上开源的 Wazuh、ELK 把日志聚起来，也比各自散落强。具体先做三件：Linux 开 `auditd` 把关键文件和提权行为记下来，Windows 上 Sysmon 补进程与网络连接细节，再把认证日志、cron 日志统一收进 SIEM 并设留存期。没有日志，就等于没有证据，事后连"什么时候进来的"都答不上来。

📌 老宋数据：监控盲区三件事，今天就能动手：
① 在干净分析机上把 `rpm -Va` + find 自查脚本挂上 cron；
② 给核心服务器建一份 AIDE 基线，存只读介质；
③ 全量扫一遍资产，把 Redis 等服务的 `0.0.0.0` 暴露和空密码清零。

// 老宋说：
第一，别把"没告警"当成"没进来"。监控看的是攻击行为，文件篡改、后门、持久化这些"结果"它默认照不到。把"无异常"三个字写进日报之前，先问自己：我今天下到系统层看过没有？

第二，配置类入口比 0day 更该防。Redis 不认证、测试机不收尾、压测环境忘关——这些"临时用一下"的疏忽，年年送来真实入侵。攻击者懒得跟你拼漏洞，门开着他就直接进。

第三，自查要变成肌肉记忆。每天 10 分钟四步走，加上 AIDE 基线和定时 diff，成本低到可以忽略，换回来的却是"被进来"和"被进来半个月"的天壤之别。工具会过期，自己动手查的习惯不会。

你单位的服务器，做过文件完整性基线吗？核心资产上那句 `rpm -Va`，上一次跑是什么时候？
