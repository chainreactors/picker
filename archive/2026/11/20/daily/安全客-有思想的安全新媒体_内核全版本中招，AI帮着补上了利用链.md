# 内核全版本中招，AI帮着补上了利用链

做运维的最怕两种通知：一种是”影响范围很小”，一种是”影响几乎所有版本”。11 月 18 日工信部漏洞平台发的这条提示，属于后者，而且它罕见地把”AI 能加速利用”写进了正文。

11 月 18 日，工业和信息化部网络安全威胁和漏洞信息共享平台（NVDB）发布风险提示：监测发现 Linux Kernel 存在远程代码执行漏洞，危害严重，远程攻击者可利用该漏洞获得目标系统的最高权限。

漏洞编号为 **CVE-2026-98432**。官方给出的影响范围是：Linux Kernel 4.4 及以上几乎所有主线版本，主要 Linux 发行版普遍受影响。

## 一、这次的范围为什么值得认真对待

Linux Kernel 是操作系统内核，负责进程调度、内存管理、文件系统、设备驱动和系统调用。它出问题，不是某个业务应用挂掉，而是**底下那一层同时对所有上层软件失效**。

4.4 是 2016 年发布的长期支持版本，也就是说，这个范围覆盖了从十年前的存量服务器到今年新装的云主机。国内大量政企环境的 CentOS 7 停在 3.10，不在官方表述的范围内，但基于 4.x 及以后内核的 Ubuntu、Debian、麒麟、统信、Deepin，以及各家云厂商的定制镜像，基本都在影响区间里。

更麻烦的是”远程”和”最高权限”这两个词同时出现。远程意味着不需要先拿到一个低权限账号，最高权限意味着打进去就是 root。对暴露在公网的服务来说，这中间少了好几道必须跨过的门槛。

## 二、补丁在哪：官方给了完整清单

目前 Linux 内核社区和部分操作系统厂商已发布安全公告，修复了部分版本。NVDB 在提示里附了各家公告的直达链接，这一点很实用，省去了在一堆镜像站里找对应版本的时间。

* 内核主线：git.kernel.org 上共有 8 个修复提交，覆盖不同稳定分支。
* Debian / Ubuntu / Red Hat / SUSE / Oracle：各自的 CVE-2026-98432 跟踪页均已上线。
* 国产发行版：麒麟、统信、Deepin 分别对应 UTSA-2026-150178 与 DPSA-2026-018001 等公告。

这里要提醒一句：内核补丁不是打个包重启就完事。生产环境升级内核要考虑驱动兼容、容器运行时版本、以及那些编译过第三方模块的机器——升级前先在灰度机上验证一遍，比事后回滚便宜得多。

云主机用户还要多一步：宿主机内核由云厂商维护，租户能控制的是镜像里的内核和容器运行时。先确认云厂商是否已发布修复公告、是否支持在线热补丁，再决定是等厂商升级还是自己重建实例。容器环境尤其容易被漏掉——很多人以为”容器隔离了就没关系”，但容器共享宿主机内核，这一层从来不在隔离范围之内。

## 三、最值得注意的一句：AI 能快速生成利用代码

官方提示里有一句罕见的表述：该漏洞影响面广、风险等级高，且**可利用 AI 模型快速生成利用代码、构建利用链**。

这句话的分量，做漏洞响应的人最能体会。过去一个内核级 RCE 从公告发出到出现稳定利用，通常要几天到几周，防守方还有窗口期做排查和修补。现在这个窗口正在被压缩：模型可以帮着读补丁、比对差异、定位触发条件，把原本需要资深研究员几天的活压到几个小时。

这不是推测。同一份提示里还提到，近期 PHP、Node.js、Apache、Linux、Chrome、GitLab、MySQL 等多款基础组件和软件的中高危漏洞数量大幅增加，且部分漏洞信息披露不完整，容易被忽略修补。

披露不完整这件事，对甲方是个陷阱。很多单位的安全运营靠漏洞库推送驱动，库里没收录、或者描述写得含糊，扫描器就扫不出来，工单也就不会生成。**攻击者不需要等你的漏洞库更新。**

这也意味着，靠”等厂商通知”的被动模式正在失效。更现实的做法是把资产清单做准，把版本采集做成常态，然后用官方的 CVE 编号直接去比对手里的版本库。版本比漏洞库更可靠——漏洞描述可能写错，版本号不会。

> 过去是”漏洞公开了，攻击者开始研究”；现在是”漏洞公开了，工具已经在跑”。防守方的时间预算，要按后者来算。

## 四、排查与处置：从今晚开始能做的

第一步是摸清资产。在内网跑一遍内核版本采集，重点看公网可达的机器：

```
uname -r                    # 查看内核版本
cat /etc/os-release         # 确认发行版与版本号
rpm -qa kernel | sort -V    # RHEL 系已安装内核
dpkg -l 'linux-image-*'     # Debian 系已安装内核
```

第二步是收边界。NVDB 的建议里明确提到关闭非必要公网暴露、加强网络边界和访问控制。落到执行上，就是把那些”为了临时方便”开出去的端口重新过一遍：调试用的管理口、测试环境的数据库、临时开的跳板机。

第三步是看痕迹。远程 RCE 利用成功后，常见动作是写入持久化、创建高权限账号、外联下载二阶段载荷。把最近一周的异常登录、异常外联、以及内核日志里可疑的崩溃记录拉出来筛一遍，特别是那些说不清来源的成功登录。

第四步是管好凭证。这条和漏洞本身无关，但每次大规模漏洞事件里，真正造成二次伤害的往往是泄露的密钥。把密钥当成会过期的东西来管，而不是当成配置项。

这次提示里最该被记住的不是版本号，而是那句”AI 可快速生成利用代码”。它意味着从现在起，漏洞公告发出到第一波扫描之间，可能只隔几个小时。补丁窗口在缩短，资产台账不准的单位会最先吃亏。今晚能做的三件事：拉一遍内核版本、关掉一个不必要的公网端口、确认灰度升级的窗口排期。
