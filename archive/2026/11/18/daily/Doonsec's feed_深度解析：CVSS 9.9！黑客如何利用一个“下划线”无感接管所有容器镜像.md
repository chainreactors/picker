大家好，如果你公司里正在使用 **Red Hat Quay** 作为容器镜像仓库，或者把它集成在 OpenShift 里跑 CI/CD 流水线，那你今天得赶紧自查了。红帽连发两个致命漏洞预警（**CVE-2026-123710** 和 **CVE-2026-110697**），CVSS 评分分别高达惊人的 **9.8** 和 **9.9**。

这两个漏洞加在一起是什么概念？简单来说：**黑客不需要任何特权，甚至在默认配置下连账号都不用，就能随意读取、篡改、甚至覆盖你所有的私有容器镜像。**

这可不是闹着玩的，今天我就带大家扒一扒这两个漏洞的底层逻辑，看看大佬们是怎么发现这种“史诗级”神坑的。

## 💣 漏洞一：伪造身份的“幽灵密钥” (CVE-2026-123710 / CVSS 9.8)

咱们先看第一个漏洞。Quay 作为一个镜像仓库，在处理镜像拉取和推送（Push）时，靠的是**签名访问令牌**。而它用来签名这些令牌的，是系统内部信任的密钥。

正常逻辑下，验证体系是没毛病的。但开发老哥在密钥管理服务器的代码里留了个致命的盲区。

### 技术还原与攻击路径：

当你请求替换一个密钥时，Quay 的密钥服务器会检查你的请求里有没有带上受信任的令牌，并校验对应的发行者和受众。这看起来很严谨对吧？

**但是！系统唯独漏掉了一个核心校验：它没有检查这个令牌到底是不是为了“密钥轮换”签发的！**

这意味着什么？攻击者只需要去 Quay 的 `/v2/auth` 接口申请一个匿名的普通令牌。因为是系统自己签发的，所以它自带“受信任密钥”的背书，且攻击者可以自定义令牌的受众。拿着这个令牌去请求密钥服务器，居然直接放行了！

这导致了一个可怕的后果：

* **注入永不过期后门：**

  攻击者可以直接把自己的密钥强行塞进 Quay 的信任列表里，并且**没有过期时间**。
* **通杀所有仓库：**

  以后攻击者用这个“伪造密钥”签发的任何 Token，Quay 都会无条件信任。你的私有镜像、里面藏着的硬编码密码和敏感凭证，瞬间成了公开资源。
* **鸠占鹊巢：**

  这个伪造的密钥哪怕重启机器也依然存在。攻击者甚至能用它删掉 Quay 真正正常运行的密钥。到时候，正常用户的 Push/Pull 疯狂报错，黑客却在后台来去自如。

顺便提一嘴，这逻辑漏洞其实从 Quay 的第一个公开 Commit 就存在了，潜伏了这么多年才被红帽的 Dave O'Connor 挖出来，真的是细思极恐。

## 🕳️ 漏洞二：一个“下划线”引发的血案 (CVE-2026-110697 / CVSS 9.9)

如果说第一个漏洞是权限校验的疏漏，那第二个漏洞就是典型的“老司机翻车”——死在了基础的 SQL 语法上。

这个漏洞出在 Quay 枚举“机器人账户”的代码逻辑里。在执行数据库查询时，系统用到了 SQL 的 `LIKE` 语句来匹配命名空间。

懂 SQL 的小伙伴肯定知道，在 `LIKE` 语法里，**下划线 `_` 是一个通配符**，代表匹配任意单个字符。要命的是，Quay 在拼接查询条件时，居然**没有对通配符做转义！**

### 实现难点与利用过程：

攻击者不需要任何提权操作。假设你的项目命名空间叫 `proj-prod`，攻击者只需要恶意注册一个叫 `proj_prod` （把横杠换成了下划线，或者任何能在正则表达式逻辑上匹配的地方放上下划线）的命名空间。

当系统去查询时，`LIKE 'proj_prod'` 里的下划线被当成了通配符，结果把受害者 `proj-prod` 下所有的机器人账户连带着**解密后的 Token** 全查出来，返回给了攻击者！

拿到 Robot Token 之后能干嘛？在 OpenShift 环境下，Quay 通常是默认集成的。黑客可以用这套凭证把带有后门的恶意镜像推送到你的 CI/CD 流水线里。只要受害者的节点一拉取新镜像，整个系统瞬间沦陷。最毒的是，如果攻击者删除了自己的假命名空间，还会连带把受害者的合法机器人账户也删了，直接给你搞一波业务中断。

## 🛡️ 我们该如何自救？(修复指南)

目前红帽已经在 Quay 3 和 Quay 5 的多个分支发布了修复版本。官方补丁的核心思路就是补上了缺失的轮换校验、强制服务器添加的密钥必须有过期时间、禁止调用者自选 Audience，顺带把 SQL 查询的通配符转义给修了。

但在你把补丁打上、系统重启完成之前，**关闭匿名访问是防不住 CVE-2026-123710 的！** 只要别人曾植入过密钥，修改密码或轮换 Token 依然能用。

建议大家立刻执行以下应急止血操作：

1. **WAF/负载均衡层拦截：**

   在 Proxy 或负载均衡器上，封堵对 `/keys` 端点的访问，只允许受信任的内部组件调用。
2. **清查审计日志：**

   立刻去查系统审计日志，重点搜索 `service_key_rotate` 和 `service_key_delete` 事件，并且过滤出 `expiration_date` 为 `null` 的记录。
3. **清理后门：**

   发现任何不认识的已批准服务密钥，直接删除。
4. **控制命名空间权限：**

   在打好补丁前，限制谁可以创建包含下划线 `_` 的组织或命名空间；对那些名字里本来就有下划线或容易被匹配的命名空间，立刻轮换其 Robot Token，并监控异常拉取/推送行为。
5. **终极方案：**

   赶紧升级安装官方的 Fixed Release。
