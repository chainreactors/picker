## 01为什么攻击文章要谈密码学

这不是为了显得专业，而是因为在真实项目中，**密码学缺陷是唯一一个「不依赖任何外部输入」的漏洞类别。**

| 漏洞类别 | 是否依赖外部输入 | 修复方式 |
| --- | --- | --- |
| 注入类 | 依赖 | 改代码 |
| 越权类 | 依赖 | 改鉴权逻辑 |
| 配置错误 | 依赖 | 改配置 |
| 密码学缺陷 | 不依赖 | 只能改密码学设计与实现 |

换句话说，你不需要找到一个黑客，不需要任何外部威胁，**只要等待足够长的时间，一个设计不当的密码系统就会自己泄露信息。**

更进一步：2018 年之前的比特币钱包被逐个攻破，2013 年被曝光的 NSA 密码学后门，以及 Heartbleed 这样的心跳漏洞——这些事件的共同点都是**「攻击者需要的不是入侵，而是时间和算力」。**

**⚠️ 注意**　这条认知对安全建设有直接影响：**传统漏洞有「打上补丁就没事」的窗口期，而密码学缺陷往往没有补丁期。**它需要你重新审视整个数据生命周期——历史数据、备份数据、已经离开系统的旧密钥——是否还有暴露风险。

## 02CryptoHack 是什么：定位与关卡结构

CryptoHack（cryptohack.org）是 NCC Group 出品的在线密码学挑战平台，特点是**完全免费、无需虚拟机、浏览器里直接交互**，但关卡设计的专业程度很高。

| 级别 | 主题 | 核心问题 | 对应实战 |
| --- | --- | --- | --- |
| Introduction | 编码、编码绕过 | Base64/URL 编码不是加密 | 识别「假加密」 |
| Level 1 | 古典密码与现代密码分析 | 维吉尼亚、凯撒、频率分析 | 弱密码破解 |

| Level 3 | 对称加密 | AES 模式、IV/nonce、填充 | 存储加密设计 |

## 03注册与使用方式

CryptoHack 的使用极其简单：注册账号后，直接在浏览器里选择关卡、在线输入答案即可。

* **方式一：在线解题**

  ——每关自带在线编辑器与运行控制台，改代码 → 运行 → 拿 flag。适合快速推进。
* **方式二：本地求解 + 在线提交**

  ——用本地 Python 环境写脚本分析，把答案填回网页。**推荐这个方式**，因为你能在本地反复调试，能打印中间值，能用任意库。

推荐的本地解题环境

```
# 推荐用法：本地 Python 环境 python3 -m venv cryptohack-env source cryptohack-env/bin/activate     # Windows: .\Scripts\activate pip install pwntools gmpy2 sympy  # 然后在本地写脚本分析，在网页上提交答案
```

**💡 提示**　强烈推荐本地环境。**因为密码学的学习价值不在「拿到 flag」，而在你把中间值打印出来看懂那一步发生了什么。**纯在线改代码容易变成「试到对为止」，而那正是密码学学习最需要避免的方式。

## 04核心机制：从「跑通」到「理解」的关卡设计

CryptoHack 关卡的难度曲线很陡，但它有一个非常值得学习的教学设计：**每关都有简明的前置知识说明，但不给解题步骤。**

这个设计意味着你必须真的去推导，而推导过程才是能力形成的地方。我给的学习方法分三步：

1. **读前置知识，但不要读题解**

   ——题解会毁掉这一关的学习价值。
2. **手写推导 + 手算一遍**

   ——哪怕只是加解密的手动计算，也比直接跑库理解得深。
3. **用不同的方式验证同一个结论**

   ——比如用两种不同的数学途径求出同一个明文，交叉验证能极大增强你对正确性的信心。

## 05Level 1：编码不是加密（最危险的安全幻觉）

这一关只有几行代码，但它包含**整个安全行业最普遍、危害最大的认知错误之一**。

Base64 编码冒充加密的典型场景

```
import base64  print(base64.b64encode(b'crypto{...}'))  // 典型场景：接口返回 {   "username": "YWRtaW4=",   "password": "MTIzNDU2" }  // 解出来是 username = "admin" password = "123456"  # 关键事实：Base64 是编码（Encoding），不是加密（Encryption） # 它没有密钥 anyone 都能解，唯一的目的是传输安全
```

这个问题的危害在于**它制造了一种虚假的安全感**：开发者在代码里看到 `base64_encode`，会自然而然地认为「这里做了加密处理」。而它在密码学意义上的性质是：**零**。

**⚠️ 注意**　在渗透测试中，**Base64/URL 编码是最高频的「解码陷阱」**。几乎每个 CTF 和每个渗透里都会出现。但真正要注意的是它背后的工程问题——如果你的系统把密码 Base64 后存数据库，那么这不是「弱加密」，**而是「根本没有加密」**，属于严重的设计缺陷。

## 06Level 2：哈希与口令存储的正确姿势

哈希是密码学里最容易被滥用的部分，也是与业务系统关系最直接的部分。

### 一、哈希的性质与常见误用

| 性质 | 含义 | 常被误解为 |
| --- | --- | --- |
| 单向性 | 无法从哈希反推原文 | 「所以很安全」 |
| 确定性 | 相同输入永远同一输出 | 「所以可以用来加密密码」 |
| 抗碰撞性 | 难以找到两个同哈希的输入 | 「所以碰撞也没事」 |
| 不可逆性 | 不含原文信息 | 「所以加盐没用」 |

口令哈希的正误对比

```
# 错误做法：直接哈希密码 hashlib.md5(password.encode()).hexdigest() hashlib.sha256(password.encode()).hexdigest()  # 问题：现代硬件每秒能算几十亿次 MD5/SHA256 # 用 GPU 对 8 位数字密码空间（10^8）暴力枚举只需数秒 # 彩虹表更是让常见密码无需任何计算即可查表命中  # 正确做法：专用口令哈希算法 # PBKDF2（标准库自带，可调） hashlib.pbkdf2_hmac(     'sha256',     password.encode(),     salt,             # 每个用户独立随机盐     310_000,          # 迭代次数     dklen=32 )  # 或使用 Argon2id / scrypt / bcrypt（推荐 bcrypt 或 Argon2id） import bcrypt bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12))
```

### 二、四个必须知道的参数

1. **盐（salt）**

   ：每个用户独立、随机、不重复。作用是让彩虹表失效、让相同密码产生不同哈希。
2. **成本因子**

   ：控制计算量。它的设定原则是**「在你的最强服务器上，单次计算耗时约 100–250 毫秒」**。太低则可被离线爆破，太高则正常登录也会被拖垮。
3. **算法选择**

   ：优先 Argon2id，其次 bcrypt/scrypt。**绝不要用 MD5、SHA1、SHA256 直接哈希口令。**
4. **校验方式**

   ：必须用恒定时间比较（timing-safe compare），防止时序侧信道。

**💡 提示**　第二个参数是最需要工程权衡的。**OWASP 建议的口令哈希成本因子，本质上是一个「让攻击者成本永远高于你」的博弈。**攻击者是并行的（几千张 GPU），你是串行的（每个用户一次登录），这个不对称是密码哈希仍然有效的原因。但如果你的成本因子设得太低，这个不对称优势就荡然无存。

## 07Level 3：对称加密——AES 的四种模式抉择

这是本系列最有技术密度的一节，也是我建议读者**反复回看**的一节。AES 本身没有弱点，**模式的选择决定了安全性。**

| 模式 | 全称 | IV/Nonce 要求 | 并行性 | 完整性保护 | 建议 |
| --- | --- | --- | --- | --- | --- |
| ECB | 电子密码本 | 不需要 | 可并行 | 无 | 禁止使用 |
| CBC | 密码块链接 | 随机 IV，长度=块大小 | 可解密不可并行 | 无 | 已不推荐 |
| CTR | 计数器 | Nonce 不可重复 | 可并行 | 无 | 仅在有独立 MAC 时 |
| GCM | Galois/Counter | Nonce 绝对不可重复 | 可并行 | 有认证标签 | 推荐 |

### 一、为什么 ECB 必须禁止

ECB 模式的模式泄露原理

```
# ECB 模式加密相同明文块 → 相同密文块 # 原文（字母分组，相同字母用相同密文块表示）： ABCDEF  ABCDEF  XYZ123 # ECB 密文： K7mQ2p  K7mQ2p  Lw9Rt0 #          ↑ 重复模式暴露，即使没有密钥也能看出结构  # 这就是著名的"松鼠鹰"图片 # ECB 加密后，图片轮廓依然清晰可辨
```

ECB 的问题不在于它「能解密」，而在于它**泄露了明文结构**。任何攻击者即使拿到密文，也能看出重复模式、推测出哪些字段相同、哪些位置是固定值。对于结构化的业务数据，这是致命的。

**⚠️ 注意**　实测提醒：**你在现代语言库里几乎不应该再直接使用 ECB。**Python 的 pycryptodome 虽然支持，但标准库没有提供 ECB 接口——这个设计本身就说明官方不推荐。如果你的项目里出现了 ECB，这几乎必然是一个高危问题。

### 二、CBC 的填充预言机：最值得记住的经典案例

CBC 模式的解密流程是：**密文块异或前一块密文 → 再用密钥解密 → 校验填充。**看起来很安全，但如果你的应用**在填充错误时返回了不同的错误信息或响应时间**，攻击者就能利用这个差异，逐字节地把明文「猜」出来。

填充预言机攻击的原理链条

```
# CBC 填充预言机攻击的原理（不含具体利用代码）  1. 攻击者修改密文的最后一个块 2. 服务端解密 → 填充校验    ├─ 填充合法 → 返回成功（200）    └─ 填充非法 → 返回错误（500）← 这就是"预言机" 3. 差异存在 → 可以逐字节尝试 256 种取值，    通过响应差异判断哪个值使填充合法 4. 重复若干轮 → 还原出完整的明文块  关键前提：服务端对"填充错误"和"其他错误"的响应可区分 （不同状态码、不同响应长度、甚至不同耗时）
```

这条原理的价值在于**它揭示了一个通用原则：**

**💡 提示**　**密码系统的安全性，不仅取决于算法，还取决于它的失败行为是否泄露信息。**填充预言机、松散比较、详细错误信息、超时差异——这些都是「侧信道」家族的一员。在审计中，看到「解密失败返回详细错误」这类实现，无论算法多强，都应该直接标为高风险。

### 三、GCM 的唯一致命注意点

GCM 是当前对称加密的首选，它同时提供机密性与完整性（AEAD）。但它有一个**绝对不能违反的规则**：

GCM Nonce 重复导致的灾难

```
# 致命错误示例 # 用固定 nonce 加密多条不同消息 for msg in messages:     cipher = AES.new(key, AES.MODE_GCM, nonce=b'\x00'*12)  # ← 灾难     ct, tag = cipher.encrypt_and_digest(msg)  # GCM 内部逻辑： #   keystream = CTR(计数器由 nonce 初始化) # 同样的 key + 同样的 nonce → 同样的 keystream # → 两条消息的密文异或 = 两条明文的异或（信息直接泄露） # → 且认证标签可被移植（可篡改任意一条消息）
```

| 方案 | 实现方式 | 适用场景 |
| --- | --- | --- |
| 随机 nonce（96 位） | 每次生成随机数，加密时保证不重复 | 一般场景，前提是并发安全 |
| 确定性 nonce | 如 AES-GCM-SIV，用 nonce 派生抗碰撞 | 数据库字段加密等高并发场景 |
| 每把密钥独立计数 | 严格管理密钥使用次数 | 高安全场景（需谨慎设计） |

**💡 提示**　数据库字段加密这个场景特别值得说：**如果系统需要用加密字段做等值查询（比如「按手机号查用户」），那就必须用确定性加密，而确定性与 GCM 的随机 nonce 是冲突的**——这就是 SIV 模式存在的原因。工程上常见的一条链是：查询用确定性哈希（如 HMAC-SHA256）存索引，存储用 AES-GCM 存密文。两条路分开走，各司其职。

## 08Level 4：RSA 的数学结构与常见误用

RSA 是非对称密码学的基石，也是企业系统里最常见的「被误用」的算法。

### 一、RSA 的基本结构

RSA 密钥结构与关键数学事实

```
# 密钥生成 p, q = 两个大素数 n  = p * q φ = (p-1)(q-1) e  = 公钥指数（通常 65537） d  = e 在模 φ 下的乘法逆元   (e·d ≡ 1 mod φ)  # 公钥：(n, e)   → 加密很快 # 私钥：(n, d)   → 解密很快  # 关键数学事实： #   n 分解为 p 和 q 是困难的（RSA 安全性假设） #   但 (n, e, d) 同时公开 → 可以直接算出 φ(n) → 算出私钥 #   这就是"共享模数攻击"和"共模攻击"的原理
```

### 二、RSA 的五个经典误用

| 误用 | 技术本质 | 后果 | 正确做法 |
| --- | --- | --- | --- |
| 小指数 e=3 | 明文无填充直接三次方 | 开三次方或模数根攻击 | 使用 OAEP 填充 + 大指数 |
| 共享模数 (n) | 两个公钥同一 n | 指数互质时可交叉恢复明文 | 每对密钥独立生成 |
| 无填充 RSA | 直接幂运算，无随机性 | 选择密文攻击成立 | 必须使用 OAEP |
| RSA 加密口令 | 每次都用公钥加密同一口令 | 同一明文 → 同一密文，可比对 | 用对称加密或加入随机数 |
| 自签名证书即信任 | 证书无法验证身份 | 中间人攻击 | 使用受信任 CA 体系 |

**⚠️ 注意**　第五行值得特别强调：**「用了 HTTPS」不等于「通信是安全的」。**如果客户端无条件信任一个自签名证书，那么任何中间人都可以用自己的自签名证书冒充服务端。在企业环境中，正确做法是**通过内部 CA 分发证书，并让客户端做校验**——这是等保中「应采用密码技术保证重要数据传输的保密性与完整性」的直接落地方式。

1. **证书是否由受信 CA 签发**

   （信任链）
2. **证书是否在有效期内**

   （时间有效性）
3. **主机名是否匹配**

   （CN/SAN 检查）
