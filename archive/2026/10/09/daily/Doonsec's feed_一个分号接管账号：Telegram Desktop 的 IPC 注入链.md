## 01 · 执行摘要

**先给结论**：Telegram Desktop 在 7.2.9 之前存在一条链式漏洞。受害者**只需点一个链接**，攻击者就能读取这台机器上的本地文件并上传到自己的频道；而 Telegram 的登录凭据就存在本地文件里，于是**文件读取直接变成账号接管**。

**先说清证据边界**：完整链路由原作者在 **Windows、客户端 6.9.3** 上确认，并依赖若干默认设置（见第 06 节）；NVD 虽然已收录该编号，但状态为"待分析"，其条目描述同样转述自作者的分析，**尚无第三方独立复现**，**也没有已知的在野利用案例**。

|  |
| --- |
| `漏洞速览`  `漏洞编号：CVE-2026-107181（2026-10-07 收录，NVD 状态为待分析）`  `影响版本：Telegram Desktop 7.2.8 及更早`  `修复版本：7.2.9（2026-09-17 发布），修复提交 db3405699f`  `评分：CVSS 3.1 = 8.1（高危），向量 AV:N/AC:L/PR:N/UI:R/S:U/C:H/I:H/A:N`  `危害：远程任意本地文件读取 → 文件外传到攻击者频道 → 账号接管`  `根因：两个缺陷串联——IPC 记录分隔符未转义 + interpret: 协议缺少授权检查`  `利用条件：受害者点一次链接（需要一次用户交互）` |

**一个必须提醒的细节**：这次修复**没有写进更新日志**。7.2.9 的官方更新日志全文只有一句 "Fix some tlottie incorrect renderings"（修了一些 tlottie 渲染问题），而修复提交的标题是"移除遗留的 interpret 路径辅助函数"——**更新日志里没有任何安全提示**。也就是说，如果你只看更新日志，你根本不会觉得这次升级跟安全有关。

## 02 · 两个缺陷，一条链

这条漏洞不是单点缺陷，而是两个各自"看起来没那么严重"的问题串起来的结果：

|  |  |  |  |
| --- | --- | --- | --- |
| 缺陷 | 位置 | 机制 | 单独看 |
| 缺陷一：分隔符未转义 | 单实例通信（`Core::Sandbox`） | 进程间传输的命令用分号分隔，但写数据时没有转义；数据里的分号在接收端被当成了**指令边界** | 只能注入几条固定命令，本身危害有限 |
| 缺陷二：特权通道无授权 | 内部协议 `interpret:`（`Support::InterpretSendPath`） | 读取一个指令文件里指定的本地文件，并把它发到指定聊天，**既不校验调用者，也不弹确认** | 从命令行调用时需先拿到机器权限，意义不大 |

**关键在于：缺陷一把缺陷二变成了"从链接可达"。** 单独存在的第二个缺陷，前提是攻击者已经在机器上；一旦它可以从一个被点击的链接到达，前提就消失了。

![从点击到接管的完整链路](https://mmbiz.qpic.cn/sz_mmbiz_jpg/XFXUibSGA3gbfwLNo0JyzoPen2DAdvyUH8hXAaMLCt9yuAC7nyPMDPqZp7Iv4cAsr78OAy5oVL7u0kGkq0k8Ssag02S8k4xEyCbNGfmicLjSk/640?from=appmsg)

## 03 · 缺陷一：把数据当成了指令

**先解释两个概念。**

**IPC（进程间通信）**：同一台机器上不同进程之间交换数据的方式，可以用本地套接字（socket）、管道等实现。

**单实例机制**：桌面软件通常只想跑一个实例。以 Telegram 为例，系统注册了 `tg://` 协议——你点这种链接时，操作系统不检查程序是否已在运行，**照旧启动一个新进程**。新进程自己发现"我已经是多余的那个"（办法是尝试连接本地套接字），于是把链接交给正在运行的老进程，然后退出。

问题就出在"交接"这一步：**套接字传的是字节，不是对象**。内存里的 URL 对象必须先变成一行文本才能送过去——这个过程叫**序列化**，接收端再把它还原。Telegram 用的格式很朴素，每条指令是"关键字 + 参数 + 分号"：

|  |
| --- |
| `单实例通信的记录格式（概念示意）`  `打开一个链接的记录形如：OPEN:<链接>;（分号表示这条记录结束）`  `接收端拿到字节后，按分号切分，把每一段当成一条独立指令处理`  `凡是 OPEN: 开头的段，后面的内容会被还原成一个 URL，就像它刚从命令行传进来一样` |

**于是问题来了**：如果被传输的链接里本身就带一个分号呢？发送方把它当作"链接里的一个普通字符"整体写出去，接收端却在这一刀切下去——**一条记录变成了两条指令**。这就是**注入**：数据的含义在跨越边界时被重新解释成了指令。

|  |
| --- |
| `正常情况`  `发送端写入：OPEN:<链接A>;`  `接收端切分：① OPEN:<链接A>`  `结果：一条指令`    `被注入的情况`  `链接A 的查询串里含一个分号，发送端仍按原样写出：`  `接收端切分：① OPEN:<链接A 的前半段>  ② <分号后面的内容被当成第二条指令>`  `结果：两条指令，第二条由攻击者控制` |

**这是一个典型的协议设计缺陷**，而且它的教训不限于 Telegram：

![正常数据流与注入数据流的对比](https://mmbiz.qpic.cn/sz_mmbiz_jpg/XFXUibSGA3ganz6XbY3OQV9T4kFD8XbAQARjKqhSqFFYKo3JqkY8wibpBTuiaBV5lduMWUdvfmIZZGzkPbpKqcxffQRyebOzN1HxmkH3YwQS6o/640?from=appmsg)

**只要用某个字符做分隔符，就必须在写入时对它转义；更稳妥的做法是不用字符分隔，改用长度前缀或结构化编码（JSON、TLV 等）。** 用字符做边界、又不做转义，等于让数据有机会伪装成指令。

## 04 · 缺陷二：interpret: 是一条特权通道

Telegram 内部有一个叫 `interpret:` 的协议，它**没有在操作系统注册**——也就是说，外部点 `interpret:` 链接是没反应的，它只存在于 Telegram 自己的代码里。

**它本来是干什么的**：Telegram 官方发布新版本时，需要把一个安装包发到频道里，并把更新说明作为配文。与其手工操作，发布脚本干脆生成一个小文本文件，写清"发到哪个频道、发哪个文件、配什么说明"，然后让 Telegram 打开这个文件路径去执行。这个内部协议就是为此存在的。

指令文件包含四类信息（**本文只说明用途，不给可用模板**）：用哪个账号发（`from`）、发到哪个频道或超级群（`channel`）、发哪个本地文件（`file`）、配什么文字（`caption`）。

**危险点有三个，缺一不可**：

|  |
| --- |
| `interpret: 为什么危险`  `① 无授权检查：执行发送的函数不判断"是谁要求发的"`  `② 无用户确认：不弹任何确认框`  `③ 入口无过滤：注入进 OPEN: 之后，OPEN: 并不限制协议类型，`  `所以这个内部协议可以从外部链接"绕到达"` |

还有两个细节让攻击更省事：**`from` 这一行是可选的**——它的作用是校验"当前登录账号是不是发布者"，如果不写这一行，校验直接跳过；而 **`channel` 只能指向频道或超级群**，这一点在后面反制措施里有用。

**这条缺陷的教训同样通用**：一个"内部/脚本用"的特权功能，只要它挂在一个通用入口（这里是"打开任意 URL"）后面，它就不再是内部的。**特权功能必须自己校验调用者，而不是依赖"外部到不了这里"这个假设。**

## 05 · 从"读一个文件"到"拿到你的账号"

读到一个文件并不等于接管账号。真正的关键是：**Telegram 的登录凭据就存在本地，而它默认是用一个"空密码"保护起来的。**

**先解释密钥包装。** 本地数据用一个随机生成的**数据密钥（DEK）**加密；

![本地数据的密钥包装链](https://mmbiz.qpic.cn/sz_mmbiz_jpg/XFXUibSGA3gZK0mImWe1HN8iaNpXPicl6PfEWz0jHkcghjcozub3GWoQJD2GXborU2bRHRzIjeicdvwUSm8cpaadttLgkybgJs2HAASYwiaheOao/640?from=appmsg)

而 DEK 又被另一把**密钥加密密钥（KEK）**加密，KEK 由用户的**本地密码**通过密钥派生函数（KDF）加上一段**盐**算出来。盐和加密后的 DEK 一起存在本地文件里。

|  |
| --- |
| `本地数据的密钥链（概念）`  `本地密码 --KDF(密码, 盐)--> KEK --解开--> DEK --解开--> 本地数据（含账号会话）`  `盐 + 加密后的 DEK 存放在 tdata/key_datas` |

**致命之处在于默认值**：Telegram Desktop **默认没有本地密码**，需要你自己去设置里开。没有密码时，参与派生的是**空字符串**——而盐是**明文**存在 `key_datas` 里的。也就是说，**只要拿到 `key_datas` 这一个文件，就能算出 KEK、解开 DEK，然后用 DEK 解开其他所有数据。**

|  |
| --- |
| `涉及的三个本地文件`  `key_datas：盐与加密后的 DEK（含密钥材料，最关键）`  `D877F783D5D3EF8Cs：MTProto 的会话授权文件，用 DEK 加密（含会话，最关键）`  `D877F783D5D3EF8C/（目录）：账号数据的索引，本身不含密钥` |

注意那个目录名 `D877F783D5D3EF8C`：它**不是随机的，也不是每台机器独有的**，而是由默认数据名 `data` 这个字符串派生出来的，**在任何安装上都一样**。索引文件本身不含秘密，理论上可以自己重建，攻击者顺手一起偷只是为了省事。

**结论**：拿到这三个文件后，把它们放进一个新的 `tdata` 目录、启动 Telegram，**受害者的会话就直接打开了**——不需要验证码，不需要密码。这也是为什么本文把它定性为"账号接管"而不是"信息泄露"。

**顺带说清一个常见误解**：设置本地密码**并不能阻止**文件被偷走，它只是让偷到的会话**用不了**。所以在"已经怀疑被偷"的情况下，设置密码是补救的一部分，但不能代替升级。

## 06 · 攻击为什么能成立：三个前提

这条链要跑通，需要**若干关键条件**，而它们**大多落在默认设置上**：

|  |  |  |
| --- | --- | --- |
| 前提 | 依赖的默认行为 | 用户可改的设置 |
| 指令文件要落到**可预测路径** | 群聊里收到的文件**默认自动下载**（8MiB 以内），文件名由发送方指定，落盘位置由客户端自己拼出、可以预测 | 开启"每次询问保存位置"，自动下载即失效 |
| 路径里的**用户名不用知道** | `interpret:` 接受**相对路径**，而相对路径从客户端自己的数据目录解析，因此不必知道本机用户名 | 无需改，属实现细节 |
| 链接必须**从 Telegram 外部点击** | Telegram 聊天里点击 `tg://` 链接是**进程内处理**的，不经过套接字，注入没有落点；而普通 `https` 链接会用系统浏览器打开 | 无法通过设置规避，属交互设计 |

把注入送进套接字，必须用一条**从应用外部发起**的链接来触发——**具体交付手法本文不展开**。另外**拉人进群不需要对方确认**（默认隐私设置允许任何人把你加入群组），而外传目标必须是频道或超级群——**这两点合起来，刚好构成了一端投递、一端回收。**

## 07 · 检测与处置

### 立即做的事

|  |
| --- |
| `处置优先级（从高到低）`  `① 升级到 7.2.9 及以上（当前最新为 7.3.0）——这是唯一真正关闭该问题的动作`  `② 开启"每次询问保存位置"：自动下载失效，指令文件无法落盘，`  `这是不升级情况下最有效的缓解`  `③ 把"谁可以把我加入群组"限制为"仅联系人"：`  `被偷文件只能发到频道/超级群，这一步抽掉了攻击者的回收端`  `④ 设置本地密码（按真实密码强度选）：不阻止窃取，`  `但让已经偷走的会话无法使用` |

### 如果你怀疑已经中招

顺序很重要：**先把客户端升级到 7.2.9 及以上，再处理凭据**。如果还停在受影响版本就先去终止会话，攻击者仍可能用同一条链再打一次。升级之后：在设置里**终止其他活跃会话**，启用两步验证、更换密码、设置本地密码；同时排查本机是否收到过来源不明的群文件、是否有大量文件被"自己"发到某个频道。

**注意一个容易踩的坑**：被偷走的是**会话授权**，不是你输入的密码。所以"改密码"本身不一定能把攻击者踢下线——**必须先显式终止会话**。

### 检测思路（**以下为待验证的检测假设，非作者结论**）

|  |
| --- |
| `可落地的检测点`  `① 进程链：浏览器/系统处理器拉起 Telegram 进程，且命令行参数里带 tg:// 链接`  `——数据源：EDR 进程命令行、Sysmon 事件 1`  `② 异常外传：文件在短时间内被连续上传（该链路走加密流量，**仅靠网络侧难以判定"上传到频道"，需配合端点侧遥测**）`  `——数据源：EDR 与终端网络遥测为主`  `③ 本地痕迹：tdata 目录被读取/复制、以及"询问保存位置"未开启时的自动下载目录`  `——数据源：文件审计、EDR 文件事件`  `④ 群组异常：用户被拉入陌生群、群内出现来源不明的纯文本附件`  `——数据源：终端侧客户端数据目录审计、用户上报` |

## 08 · 结论与启示

这条漏洞的技术含量并不高——**没有内存破坏，没有加密绕过，全是用错了一个字符和少了一次校验**。但它的结果是一键接管账号。三点值得记住：

01  **进程间的"内部通信"也是信任边界。** 很多人下意识认为"同一台机器上的两个进程之间是可信的"，于是序列化格式能省就省。但只要输入可能来自外部（这里是操作系统用链接参数启动进程），这条通道就必须按**不可信输入**处理：**用字符分隔就必须转义，或者干脆不用字符分隔。**

02  **特权功能不能靠"外部到不了"来做防护。**`interpret:` 是发版脚本的辅助功能，它的危险不在于功能本身，而在于它挂在"打开任意 URL"这个通用入口后面，而那个入口不限制协议。**内部协议要么显式鉴权，要么显式确认，不能依赖调用路径的隐蔽性。**

03  **静默修复把风险留给了不升级的人。** 7.2.9 的更新日志只提了一句渲染修复，没有任何安全提示；用户没有动力升级，企业也没有依据去打补丁。**安全修复不发公告，等于把"是否受影响"的判断题留给了一线人员。**

对国内做客户端和工具的团队，这条链还有一层对照意义：**自定义 URL scheme、本地单实例套接字、内部命令通道**，这三样东西在很多产品里都存在。这次的教训可以直接套用——**检查你的本地套接字协议有没有转义、检查你的内部命令有没有鉴权、检查你的特权功能有没有确认。**
