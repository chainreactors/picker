我陷入了迷茫和不安，一个想法在脑海里慢慢成形：

> 与其被动地让 AI 替代我，我不如主动构建一个工具，先把我自己替代了。

后来我想明白了一点：模型会继续变强，厂商做的 agent 也会越来越好用。我要是做个工具去跟模型比推理、跟厂商比 harness，下个版本一出它就没用了。所以 Treasure Map 只做一件事：把固件里的事实整理清楚，交给 agent。它自己不跑模型，不需要 API key，也不判断哪里是漏洞。

![](https://xzfile.aliyuncs.com/2026/11/19/1626/c8d905a8-5e4.png)

# 第一版：一千多个“漏洞”

最早我的想法是把固件抽象成一本书，每个二进制就是其中一页。用 Ghidra 把所有二进制反编译一遍，伪代码和函数调用关系存进数据库，再让模型给每个二进制、每个函数写摘要，列出可能的漏洞，最后导进 Obsidian，用双链表示调用关系。打开以后可以像读书一样，看每个程序是干什么的、哪里可能有问题。同时构建一个对话agent，读取数据库的内容，用自然语言对话的方式完成漏洞挖掘和逆向分析。

这一版不到一个月就做出来了。拿一个固件试跑，650 个二进制、8 万多个函数，模型给其中 80496 个写了摘要，标出了 1017 个"漏洞函数"。我抽样复核了几十条，几乎全是误报：有的输入在前面就被过滤了，有的入口根本走不到，还有不少是模型编出来的。

![](https://xzfile.aliyuncs.com/2026/11/19/1627/cb201dfb-801.png)

反思后，问题出在几个地方。

* 结论建立在不准确的判断上，自然不可信。
* 每条事实只有"是"和"否"，没有地方写"不知道"。
* 数据量这么大，做成给人读的知识库，除了截图满足虚荣心似乎没有其他用处。
* 大模型厂商做出的 agent 越来越好用，应该站在巨人的肩膀上。

于是我换了方向，做一个给 agent 用的 MCP 服务器：Treasure Map - 给 AI agent 的固件藏宝图。

# 地图上记了什么

`tmap scan` 对解包后的固件文件系统里的每个二进制跑一遍 Ghidra，找出四类调用：命令执行、缓冲区拷贝、格式化字符串、按路径打开文件。每一处调用是一个候选，带六项记录：

| 选项 | 记录的内容 |
| --- | --- |
| 来源 | 数据是否来自外部 |
| 可控 | 攻击者能控制多少 |
| 写入者 | 这个值是谁写的 |
| 可达 | 这处调用能不能被走到 |
| 过滤 | 途中有没有过滤 |
| 完整 | 所在函数是否完整分析 |

每一项只有三种值：是、否、未知。写"未知"时会附上原因，比如"没找到直接调用者，可能经由分发表调用"。查不清的就写查不清，不替 agent 猜。

# 图怎么看，由 agent 定

做到这里我踩过一个坑。一开始我还是按危险程度排序，结果排在前面的几乎都是误报，真正的漏洞埋在一堆"未知"里。数据要真实，未知就少不了；未知一多，排序就没有意义了。

改了很多版都解决不了这个问题时，是项目的名字提醒了我。对啊！**这是一张地图，不是一本书。** 书从第一页读到最后一页，只有一种读法。地图没有固定的顺序，测绘员看等高线，司机看路网，用的是同一张图。

所以现在的候选列表没有分数。默认视图把影响最大、又没有被证明安全的调用排在前面，agent 可以按任何一项重新排序或筛选。换排序只换顺序，候选一个不少。只有被证明安全的调用，比如命令参数是个常量字符串，才会往后排。"未知"不会让候选往后排，因为未知不等于安全。

![](https://xzfile.aliyuncs.com/2026/11/19/1628/9bf44752-7aa.png)

# 为什么 agent 需要地图

agent 读单个函数已经读得不错了。但把整个根文件系统交给它，上百个二进制、几万个函数，它通常看几条线索就停下来，说"没发现问题"，其实大部分代码没看过。

有些问题本来就要跨程序看。一个程序读的 nvram 值，往往是另一个程序写进去的。地图里记了每个 nvram 键由谁写、由谁读、能不能从网页上改。一个守护进程是谁启动的，取决于 Web 服务和启动脚本，地图也记了每个程序被哪些二进制和脚本拉起，`/bin/sh → busybox` 这种符号链接已经解析好。

进度也是按整个固件算的。Treasure Map 统计全部候选的进度，没能完整分析的函数和二进制单独列出来。这样"看过了，没问题"和"根本没看"不会混在一起。

# 标注层

只给事实，就会留下很多"未知"。有些未知只有靠推理才能补上，但推理出来的东西不能混进事实里。

正当我苦恼怎么精简候选数量时，思绪突然回到了小时候。我想起了当年最爱看的《冒险小虎队》，印象最深的是书里附的解密卡：把它放在书页上，摆对角度，就能读出藏着的答案，书上印的字一个没变。

![](https://xzfile.aliyuncs.com/2026/11/19/1659/eebec895-337.jpg)

等等，解密卡盖在书页上，既不改动原来的内容，又能读出新的内容，这不正是我要的、能筛选候选的东西吗？

Treasure Map 的数据就这样分成两层。事实层是只读的，scan 和 diff 得出的每条事实都对应具体的二进制、函数和地址。标注层是可写的，之前拿不到的数据，现在可以通过推理补上。agent 的判断写在这里，每条判断必须引用它依据的事实。两层数据完全隔离，标注层怎么改都不会影响只读的事实层。每条判断随时都能拿底图的数据来核对，分析、判断、核验就这样连成了一个闭环。

# 补丁对比

有了标注层，噪音少了很多，但候选还是太多。让 agent 每条都过一遍不现实，成本也负担不起。

后来我想到了以前复现 1day 时常用的办法：补丁对比。两个版本放一起，只看变了的地方。地图里本来就存着危险调用的可达性和过滤情况，所以不只能看出补丁改了哪里，还能看出修得完不完整。

`tmap diff` 并行对比两个版本里所有内容有变化的二进制，Ghidra、BinExport、BinDiff 全程自动完成，不用碰中间文件。它先排除两边逐字节相同的二进制，再对变了的做函数级对比。比较时用的是地址归一化后的伪代码。重新编译会让大量函数的地址整体移动，BinDiff 会把它们都标成变化；反过来，BinDiff 有时给出 `similarity=1.0`，拷贝长度却已经从 `0x40` 改成了 `0x3f`。这两种情况 Treasure Map 都会区分并识别出来。

结果按函数列出，按危险调用附近发生了什么分组：调用目标换了，危险调用还在原处，或者两边对不齐没法判断。找不到对应函数的标为"未定"，不会报成删除或新增。脚本和配置文件按路径对比。没能对比的二进制单独列出，不算作没变。

![](https://xzfile.aliyuncs.com/2026/11/19/1652/59697a14-c79.jpg)

审查过程也由服务器管着。它从所有改动里挑出必读项，按工作单元一份份发给 agent，记下判了多少。必读项没判完，审查就没结束；没读的改动标"未读"，不标"没问题"。最后它输出一段覆盖声明，审到了哪里、哪里没审，都写在上面。

后来我在几款不同架构的设备上都这样审过。补丁公开修掉的漏洞能找到，没公开、被悄悄修掉的也能定位，新功能和新代码带进来的问题和攻击面也能看到。下面用一个公开固件的例子说明。

# 一次实际运行

CVE-2021-26614 是 ipTIME C200 摄像头上一个不用登录就能执行命令的调试后门，厂商在 1.060 里修了它。我对比的就是 [c200\_1\_058](https://iptime.com/iptime/?pageid=2&page_id=126&keyword=C200&uid=24007&mod=document) 和 [c200\_1\_060](https://iptime.com/iptime/?pageid=2&page_id=126&keyword=C200&uid=24015&mod=document) 这两个版本，两个固件都能从厂商官网下载。

模型用的是 DeepSeek-V4.1-Flash，一个通用模型，不是安全专用的，也不是最强的那一档。没有人在旁边指导，也没写长提示词，任务就一句话：对比这两个版本，找出补丁修了什么，每处修得完不完整，新代码有没有带来新的攻击面。

前面几步是 Treasure Map 自己做的，不经过模型。110 个二进制里，106 个两边完全相同，只剩 4 个进入对比。主服务进程 `Challenge` 有 2262 对函数被标为变化，地址归一化以后，几乎全是重新编译造成的位移，危险调用处真正有改动的只有 23 对。所有对比对象一共 3502 个，Treasure Map 从里面挑出了 144 条必读项。

![](https://xzfile.aliyuncs.com/2026/11/19/1629/8b8259f7-117.png)

agent 开了 8 个 worker 并行，把 144 条必读项全部判完：23 条有实质代码改动，121 条没有，0 条无法判断。

![](https://xzfile.aliyuncs.com/2026/11/19/1653/0fe2f8fd-ace.jpg)

报告的结论是：这次补丁里有三处改动看起来像安全修复，三处都没修完整。

第一处是这个 CVE 本身。补丁删掉了进入后门的那个分支，请求走不进去了，但后门的处理函数没删，原样留在固件里，只是没有调用者了。Treasure Map 给它打的标记是"失去了全部直接调用者"。我后来又拿 2026 年 6 月的最新版 1.094 对比了一次，这段代码还在。

第二处是一个栈缓冲区被改大了，单看很像在修溢出，但往里拷数据的那一步两个版本完全一样，拷贝长度仍然没有限制。

第三处是输入校验从黑名单换成了白名单，但只改在浏览器端的 JavaScript 里，服务端接收这些字段的 CGI 两个版本 sha256 相同。同一个表单上还有一个更敏感的字段，前后端都没有校验。

![](https://xzfile.aliyuncs.com/2026/11/19/1632/3d6982c5-95c.png)

这三处都是把事实摆在一起看出来的。"缓冲区变大了"和"拷贝没有长度限制"放在一起，"前端加了校验"和"服务端一个字节没变"放在一起，结论就很明显了。

任务里问的新攻击面，报告里也有一条。1.060 第一次把 ONVIF 事件订阅服务开放给了客户端，这部分代码在 1.058 里已经写好，只是没有对外。agent 检查了相关的 `sprintf` 和缓冲区，判断新代码本身没有溢出，但它是一块以前碰不到的协议面，值得单独审。同一个二进制里的 ONVIF 代码后来确实出过问题：KVE-2023-5458 是 `Challenge` 解析 ONVIF 请求时的内存破坏，2024 年 1 月在 1.086 里修复。

还有两个小问题。1.060 的包里多了一个 vim 交换文件 `.ChkOned.sh.swp`，里面有脚本原文和开发者的源码路径。另外，NVD 把这个 CVE 涉及的文件名写成了 `ius_get.cgi`，固件里实际叫 `iux_get.cgi`。

覆盖声明写得很清楚：144 条必读项全部判完，第二层的 3358 条没有扫。抽样看这些都是构建时间戳和地址位移，但 Treasure Map 不会因此把它们算成"没问题"。

![](https://xzfile.aliyuncs.com/2026/11/19/1632/2d0cfb7d-b86.png)

这个流程跑过两遍，模型费用一次 ¥3.55（DeepSeek 闲时价），一次 ¥7.57（忙时价）。

![](https://xzfile.aliyuncs.com/2026/11/19/1632/509058c8-e20.png)

这次运行也有看不到的地方，Treasure Map 在输出里都列了出来。函数指针表和间接调用目前看不透，所以"后门处理函数不可达"只是说沿着已经读到的路径不可达，不是证明。跨二进制的调用链不跟。多跳数据流超过一定深度会断。局部缓冲区有多大推不准，需要人去看反编译。

完整的命令、原始输出和截图都在案例页：[CVE-2021-26614“已修复”，但后门代码一直都在](https://tmap.tools/zh/showcase/iptime-c200-patch-diff)

# 用法

安装是一条命令：

```
curl -LsSf https://github.com/JoeyZzZzZz/treasure-map/releases/latest/download/install.sh | sh
```

装完会自动运行 `tmap init`，配置工具链，把 MCP 服务器注册到你的 agent，再装上 diff 审查用的 skill。Claude Code、Codex、Cursor、Claude Desktop 和 dsh 可以直接配好，其他支持 MCP 的 agent 也能接。`tmap init` 会先列出要做的改动，你确认以后才执行。

之后用 `tmap scan` 扫固件，用 `tmap diff` 比两个版本，剩下的交给 agent。scan 最慢，每个二进制要跑一遍 Ghidra，中断了用同样的 `-w` 再跑一次会接着来。

目前支持 Linux x86\_64（包括 WSL2）和 Apple Silicon 的 macOS，Apache-2.0 协议。现在还是开发者预览版，命令、数据库和 MCP 字段在版本之间可能会变。

Treasure Map 用于防御性的固件审计和漏洞研究，输出的是分析线索，不生成 PoC、payload 或 shellcode。请只分析合法持有的固件，结果需要人工复核。
