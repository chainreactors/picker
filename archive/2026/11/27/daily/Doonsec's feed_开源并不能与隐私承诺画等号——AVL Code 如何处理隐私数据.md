AI 编程智能体正在成为开发者的日常工具。它能读取文件、执行命令、接触密钥和整个代码仓库，权限之高，超过以往任何一类开发工具。用户把这样的工具装进自己的电脑，最关心的问题之一是：我的数据会不会被传出去，传给了谁。

11 月 24 日至 25 日，两款开源 AI 编程工具先后被曝外发用户数据。

一是 T3 Code。该项目在 GitHub 上约有 8 万星，采用 MIT 协议。国内开发者在 X 上发文，逐条列出 PR 与提交记录：项目自 3 月起默认开启遥测，而官网首页此后三个多月一直写着「No telemetry / Unless you opt in. Full stop.」（不开启就没有遥测，没有例外）。

二是 DeepSeek Harness。该项目约有 28.7 万星，同样采用 MIT 协议。有用户发现，其桌面版在调用 DeepSeek 官方 API 时，会将完整的会话日志——包括工具调用结果——附在每次模型请求中上传，且默认开启。

此前，7 月的 Grok Build CLI 事件我们[专门做过技术核验](https://mp.weixin.qq.com/s?__biz=MjM5MTA3Nzk4MQ==&mid=2650215022&idx=1&sn=77496defba538a08d0885e11cb5d3bbe&scene=21#wechat_redirect)*[1]*：它将整个代码仓库连同 git 历史，经一条独立于模型对话的通道上传至 xAI 的云存储。事发时 Grok Build 是闭源产品；曝光三天后，xAI 宣布将其以 Apache-2.0 协议开源。

三起事件，事发时两个开源、一个闭源，如今三款工具的源码都已公开，暴露的却是同一个问题：工具实际外发的数据，与用户所知道的不一致。由此，我们的观点是：**开源解决的是代码可见，不等于数据处理公开透明、知情同意、最小必要。** 把开源等同于隐私承诺，是一种需要纠正的认识误区。

## 一、事件回顾

### T3 Code：承诺零遥测，代码默认上报

以下时间线均来自 pingdotgg/t3code *[2]*仓库的公开记录（日期为 GitHub 记录的 UTC 时间）：

| 时间 | 记录 | 内容 |
| --- | --- | --- |
| 3 月 6 日 | PR #174 合并 | 加入 PostHog 遥测，默认开启 |
| 6 月 18 日 | 提交 3bdaa6e | 官网首页改版，删除「No telemetry / Unless you opt in. Full stop.」 |
| 6 月 23 日 | Issue #1397 以 not planned 关闭 | 用户请求增加关闭开关，维护者答复：「We will not make this easier to opt out of」（不会让关闭变得更容易） |
| 10 月 18 日 | PR #15028 合并 | 遥测改经自建的 `ingest.t3.codes` 上报 |
| 10 月 20 日 | PR #21506 合并 | 为统计装机数，读取 `~/.codex/auth.json` 和 `~/.claude.json` 中的账号标识，经 SHA-256 处理后作为身份上报 |
| 11 月 17 日 | PR #27077 未合并关闭 | 社区提交的「在设置中关闭遥测」被拒 |
| 11 月 24 日 | 提交 #42299 | 事件曝光当天：遥测不再读取、上报 Codex 和 Claude 的账号 ID |

按其遥测文档，上报内容为模型名、权限模式、耗时、token 数等使用事件，不含提示词、回复、文件内容和凭据。但上报内容少，不能抵消三个问题：一是对外承诺与代码行为相反；二是关闭方式只有环境变量（`T3CODE_TELEMETRY_ENABLED=false` 或 `DO_NOT_TRACK=1`），桌面版至今没有设置开关，社区补交的开关被拒；三是为统计用途读取了其他工具的账号文件。

### DeepSeek Harness：会话日志随模型请求默认上传

deepseek-ai/deepseek-harness *[3]*仓库中保存着团队的设计记录，过程清楚可查：

* 8 月 21 日，请求扩展决策：在发往 DeepSeek 官方 API 的请求体中增加 `dsh_session_log` 字段，携带「完整的权威 `SessionEvent` 对象」，「不执行投影或脱敏」。当时需要用户主动启用。
* 9 月 14 日，默认上传决策：改为在所有进程中默认开启。记录写明，上传内容「包括消息文本、工具参数与结果、工作区路径和反馈」。
* 9 月 24 日，上限决策：单次请求最多附带 8 MiB，积压部分在后续请求中续传。

工具结果意味着，智能体读过的文件内容、执行过的命令输出，都在这份日志中。关闭方式是配置项 `session-log-deepseek.enabled: false`，桌面版设置中也有对应开关，但默认开启。这些数据只发往 DeepSeek 官方 API，即原本就会收到提示词的一方；增加的部分是完整的执行轨迹，包括早已移出上下文的内容。

这起事件的关键在于默认值的改变：一项将完整执行轨迹交给服务方的功能，由「用户主动开启」改为「用户主动关闭」。对绝大多数用户而言，默认值就是他们实际的选择。

### Grok Build：整库打包上传

7 月的 Grok Build CLI v0.2.93 事件中，安全研究者 cereblab 抓包测得：一次会话中模型对话仅用 192 KB 流量，后台却经独立通道上传了约 5.1 GiB 的完整仓库包；用户对文件设置的「拒绝读取」，拦不住文件被打包上传。我们用 AVL Code 对同版本离线样本做了静态分析，确认上传链路的各个部件均存在于二进制中，详见当时的核验报告*[1]*。

7 月 15 日，xAI 发布公告《Grok Build is Now Open Source》，将源码以 Apache-2.0 协议发布在 xai-org/grok-build。公告介绍了智能体循环、工具、终端界面和扩展系统，对此前的上传事件未作说明。开源后的仓库中仍保留着按轮次向云存储上传会话轨迹的模块（`crates/codegen/xai-grok-shell/src/upload/`），是否上传由服务端的数据收集判定和账户的隐私设置控制。

## 二、我们的观点：开源不等于隐私承诺

将三起事件放在同一组问题下对照：

![](https://mmbiz.qpic.cn/mmbiz_png/XBFaicYdOHk8IwCaNjwb9ycTO8dpB4qyukzziakxOqylBWjzhMxe8tJrBB6vdB91c15QyvkaPg5dsvOJGWJu4WNFoLlxgBZg8kmnIrf0RibnGY/640?wx_fmt=png&from=appmsg)

我们认为，至少有三点需要厘清。

**第一，开源只能让问题事后被发现，不能保证问题不发生。** T3 Code 的默认遥测从合入到引起广泛关注，历时八个多月，其间源码始终公开，但阅读的人很少；DeepSeek Harness *[3]*的默认上传，也运行了两个多月才被注意到。在此期间，用户的数据照常外发。Grok Build 则从另一面说明了同一问题：它在事件曝光后选择开源，开源成了重建信任的手段，但公开代码本身并不改变数据外发的设计，用户需要的仍是清楚的说明、合理的默认值和可用的关闭方式。

**第二，开源协议不包含隐私承诺。** MIT 协议约定的是代码的使用与免责，不涉及数据如何处理。DeepSeek Harness 的 SAFETY.md 也写明，项目未经安全审计，不对数据泄露承担责任。我们在[《我们为什么选择闭源》](https://mp.weixin.qq.com/s?__biz=MjM5MTA3Nzk4MQ==&mid=2650215096&idx=2&sn=f97759c6542caf8de3eeca837494e5f8&scene=21#wechat_redirect)*[4]*中谈到，绝大多数用户运行的是预编译的发布物，既不通读源码，也不从源码自行编译。「可以审计」只是一种可能，不代表已经有人审计过。

**第三，隐私保护的标准，应当以法律确立的原则来衡量。** 我国《个人信息保护法》*[5]*对此有明确规定：

* 第七条：处理个人信息应当遵循公开、透明原则，「明示处理的目的、方式和范围」；
* 第十四条：同意「应当由个人在充分知情的前提下自愿、明确作出」，处理目的、处理方式和处理的个人信息种类发生变更的，「应当重新取得个人同意」；
* 第十五条：个人有权撤回同意，个人信息处理者「应当提供便捷的撤回同意的方式」；
* 第六条：收集个人信息，「应当限于实现处理目的的最小范围，不得过度收集个人信息」。

以此对照：首页承诺零遥测而代码默认上报，不符合公开透明；把上传从「主动开启」改为「默认开启」，处理方式变了，却改由用户自行关闭，而不是重新征得同意；明确表示「不会让关闭变得更容易」，与提供便捷撤回方式的要求相悖；为统计装机数去读取其他工具的账号文件，超出了必要范围。这些问题，与项目是否开源无关。

因此，衡量一款 AI 编程工具是否值得托付数据，应当看它能否回答以下五个问题：

1. 哪些数据会离开本机，发给谁；
2. 默认开启还是关闭；
3. 如何关闭，关闭后是否彻底；
4. 对外的说明与代码的实际行为是否一致；
5. 用户在不阅读源码的情况下，能否从外部核验以上各点。

这五个问题，开源项目和闭源产品都必须回答。以「代码是公开的，可以自己去看」作答，等于把核验的责任交给了用户。

## 三、AVL Code 的数据处理机制

AVL Code 是闭源产品，我们不能请用户去读代码，能做的，是把每一条会让数据离开本机的途径如实列出，写明默认状态和控制方式，供用户逐项核验。我们的数据处理遵循四条原则：本地优先、最小外发、明示可控、可供核验。以下内容依据 AVL Code 当前版本的代码整理。

### 3.1 本地优先：不做的事

* **不做行为埋点，不上报崩溃信息。**

  客户端未集成任何分析或崩溃上报组件（PostHog、Sentry、Mixpanel、OpenTelemetry 导出器等均无）。界面中的统计面板，数据仅在本机进程内传递，不联网。
* **会话只保存在本机。**

  会话记录存于 `~/.config/avlcode/workspaces/<工作区>/sessions/`，产品没有会话云同步功能。
* **不读取其他工具的账号文件。**

  AVL Code 不读取 `~/.claude.json`、`~/.codex/auth.json` 等凭据文件，也不读取系统钥匙串。出于兼容需要，它会读取 `~/.claude/skills` 下的技能说明文件，以及安装插件时插件自带的 MCP 配置，均不含账号信息。
* **模型请求不携带用户、设备或会话标识。**

  请求体只包含模型名、消息、工具定义和采样参数；请求头包含客户端版本 `X-Client-Version`、协议类型 `X-Client-Protocol`，以及末尾带 `avlcode/<版本号>` 的 User-Agent，用户手册*[6]*对此有说明。每轮对话会注入一行可见的「当前时刻」（含时区），供模型判断时间；除此之外不存在隐藏标记。我们在[核验 Claude Code 时](https://mp.weixin.qq.com/s?__biz=MjM5MTA3Nzk4MQ==&mid=2650215022&idx=1&sn=77496defba538a08d0885e11cb5d3bbe&scene=21#wechat_redirect)*[7]*发现的那种借日期格式和 Unicode 字符差异编码信息的做法，AVL Code 没有。

### 3.2 最小外发、明示可控：会离开本机的数据

![](https://mmbiz.qpic.cn/mmbiz_png/XBFaicYdOHkic4QfTQaNOSl67n3ZWrMv1rd6njdcoRURZn3xoCJENiaQrQacJR6YA2OQ5AhOlQ49uD10WcSvvk6SeoIohrxR3wibdbZXpBtft2U/640?wx_fmt=png&from=appmsg)

其中两项需要特别提示用户。

一是辅助模型调用不一定走当前会话所选的模型。以反编译为例，样本的字节片段会发给内置澜砥模型；即使会话接的是内网模型，这一项默认也不会随之改走内网。要求数据只流向自己指定的模型时，请开启本地模式。

二是智能体读取的文件会进入发给模型的上下文。这一点所有编程智能体都一样，AVL Code 也不例外：工作区中的 `.env` 或密钥文件一旦被读取，就会随对话发给模型服务。密钥不应放在工作区内；确有需要时，可将模型端点指向本机或内网。

### 3.3 本地模式：将外发途径收窄到指定模型

本地模式按会话开启，开关位于输入区。开启后：

* 网页抓取、必应搜索、GitHub 搜索、VirusTotal 系列、漏洞库同步等内置联网工具，不再出现在模型可用的工具列表中，子代理同样继承；
* 反编译、代码问答、记忆提炼改用当前会话的模型，不再走内置澜砥模型。

本地模式不覆盖的部分同样说明清楚：终端中执行的 `curl`、`wget` 等命令；外接 MCP 服务自身的网络请求；SBOM 在线审计的数据源；以及模型 API 本身。因此，本地模式与指向本机或内网的模型端点配合使用，模型相关数据才会留在用户自己的网络中。

### 3.4 国密保护与访问边界

* **凭据加密存储。**

  登录令牌、SSH 凭据、VirusTotal Key、MCP 令牌，使用国密 SM4-GCM 加密后落盘。加密密钥由本机机器 ID 与每次安装随机生成的盐值，经 HKDF-SM3 派生；机器 ID 仅用于本地派生，不上传。模型服务的配置文件（含 API Key）以仅当前用户可读写的权限（0600）保存。
* **工作区边界。**

  家目录本身、`~/.ssh`、`~/.gnupg`、`~/.aws`、`~/.kube`、`/etc` 等目录及其子树不能设为工作区，判断在解析软链接之后进行。工作区之外的目录须由用户在界面中显式附加，分只读和读写两档，智能体不能自行附加。
* **样本区不可执行。**

  工作区下的 `samples/` 目录禁止执行任何内容，即使开启无限制模式也不解除。
* **过程可追溯。**

  每一次工具调用和审批结果都写入本机会话记录；VirusTotal 的查询与上传另有独立审计日志，存于 `~/.config/avlcode/vtai-audit/`。

更多细节见用户手册第二十六节「安全与隐私」*[8]*，以及[《AVL Code 的设计如何避免发生"GPT-5.6 一键清空创业者全盘数据"》](https://mp.weixin.qq.com/s?__biz=MjM5MTA3Nzk4MQ==&mid=2650215191&idx=1&sn=f8e81d1fd407245191f4157cf0491a14&scene=21#wechat_redirect)*[9]*。

### 3.5 数据不出网：澜砥模型与 AVL Code 私有化部署

对数据不能出网的政企单位，客户端层面的承诺并不足够——客户端无法证明服务端如何处理收到的请求，这一点对任何工具都成立。内置澜砥模型服务端的处理，由隐私政策*[10]*约束，我们对此负责；而更彻底的做法，是把模型掌握在自己手里。澜砥模型与 AVL Code 均为安天澜砥团队自研，澜砥模型支持私有化部署：将模型端点指向本单位的部署，配合本地模式、关闭威胁情报、改用内部更新源，对话、代码和样本等数据的处理就留在本单位网络内，对外只保留账号服务的连接。

## 四、如何核验

我们不要求用户相信上述说明。核验不需要阅读源码，可以从以下三个方面进行：

1. **抓包比对。**

   使用 mitmproxy、Charles 或单位出口的流量审计设备，对照 3.2 节的表格逐项比对。出现表外的出站连接，或表内某项的发送内容超出所写范围，均可作为缺陷向我们反馈。
2. **查看公开会话。**

   官网每个公开案例*[11]*都附有未删减的会话回放，工具调用、读取了哪些文件、发出了哪些请求，逐条可查。这样做的原因，见[《为什么 AVL Code 敢把 AI 会话挂在官网上》](https://mp.weixin.qq.com/s?__biz=MjM5MTA3Nzk4MQ==&mid=2650215058&idx=1&sn=b92e904705833bc2a1e93f8518d3d17f&scene=21#wechat_redirect)*[12]*。
3. **验证数据不出网。**

   将模型端点指向内网或本机，开启本地模式，关闭威胁情报，把更新源改为内部地址。完成后再抓包，出站连接应只剩账号服务（含公告查询）。

## 结语

T3 Code 和 DeepSeek Harness 都是开源项目，问题在默认上传运行数月之后才被发现；Grok Build 在事发后转为开源，上传相关的模块依然在代码中。开源让问题被看见，却没有阻止问题发生：代码公开，不代表默认设置合理；协议宽松，不代表作出了隐私承诺；可以审计，不代表已经有人审计。

作为一家安全企业，我们认为，AI 编程工具的隐私保护应当做到三点：把会让数据离开本机的每一种情况说清楚，讲明发给谁、发什么、默认开还是关、怎样关闭；对外的说明与代码的实际行为保持一致；让用户无需阅读源码，就能从外部核验。这三点与开源还是闭源无关。AVL Code 选择了闭...
