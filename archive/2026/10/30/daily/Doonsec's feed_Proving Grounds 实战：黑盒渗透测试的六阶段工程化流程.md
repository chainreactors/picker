前几篇我们写了大量免费靶场。但免费平台有个绕不开的局限：**靶机质量参差，维护状况无法预期，难度标签主观，更重要的是——它们几乎全都是「CTF 化的」，而不是「企业化的」。**

什么 是「CTF 化」？指的是靶机的设计假设：有一台机器，有一条明确的利用路径，拿到 flag 就结束。而真实的企业环境是：**一个补丁不及时的老系统、一个被遗忘在角落的老应用、一个配置奇怪的 Java 中间件——它不保证只有一条路径，它甚至不保证真的有漏洞。**

这一章的主角是 **Proving Grounds**，OffSec 官方的渗透实战平台。它的设计哲学一句话概括：**「不告诉你有什么漏洞，只告诉你它是一台真实运行的系统。」**

**🛡️ 授权声明**　Proving Grounds 需要注册账号。其中 **PG Practice 需要付费订阅**，**PG Play 可免费使用**。本文介绍的方法均用于授权环境下的个人技能训练。请严格遵守各机器的使用条款，禁止对真实目标使用本文内容。

## 01免费靶场的三个天花板

在开始讲 PG 之前，我想先把免费平台的价值说清楚——它们不是「低端替代品」，而是解决另外一类问题。

| 平台类型 | 代表 | 解决什么问题 | 天花板 |
| --- | --- | --- | --- |
| 社区自制 VM | Vulnhub、Hack The Box | 全流程渗透手感 | 靶机设计质量不可控 |
| 官方教学靶场 | DVWA、WebGoat、SQLi-Labs | 单个知识点的深度 | 缺少真实系统的不确定性 |
| 漏洞复现库 | Vulhub | 漏洞原理与检测验证 | 没有真实业务逻辑 |
| 商业实战平台 | Proving Grounds | 接近真实的黑盒环境 | 需付费、有订阅门槛 |

免费平台的天花板具体在哪？我认为有三个，而且都是**结构性的**：

1. **信息缺失：靶机有「说明书」**

   。Vulnhub 的机器描述会告诉你机器名、难度、作者甚至提示。真实测试中你拿到的只有「一个 IP 和一个范围说明」。
2. **路径唯一：设计者预设了一条通关路**

   。真实测试中可能是三条路，也可能是零条路（系统本来就是安全的）。
3. **环境干净：没有无关噪声**

   。真实服务器上有无关业务、过期的补丁、别人的进程、以及可能随时崩溃的服务。

**💡 提示**　第三条是新手最容易低估的。**真实服务器上的「噪声」才是最大的挑战**——一个装满了三年历史配置的 Java 中间件，其 classpath 里有几十个 jar 包、配置目录里有几份互相冲突的配置文件。这种「乱」，是任何精心设计的靶场都模拟不出来的。

## 02Proving Grounds 是什么：两个板块的定位

Proving Grounds 的官方入口是 portal.offsec.com，整体分为两个板块，定位完全不同。

| 板块 | 内容 | 难度范围 | 订阅要求 |
| --- | --- | --- | --- |
| PG Practice | 以 Linux 与 Windows 为主的实战机器 | 覆盖入门到较高难度 | 付费订阅 |
| PG Play | 由 OffSec 官方构建、明确标注为免费使用的机器 | 以入门与基础为主 | 注册即可使用 |

两个板块的存在很重要。它意味着你**不订阅也能开始**——PG Play 提供了足够多的机器，让你在建号初期就能练手，而不必先付钱才知道这个平台是否适合自己。

**💡 提示**　需要提醒的是：**平台的机器库与可用范围会随订阅档位变化**，不同时间点登录看到的列表可能不同。具体内容请以你登录后的实际界面为准，不要基于本文的描述去规划具体进度。

## 03PG Play 与 PG Practice 的选择

对不同阶段的人，我的建议如下：

| 你的情况 | 建议路径 | 理由 |
| --- | --- | --- |
| 完全零基础 | 先 OverTheWire Bandit，再进 PG Play | 基本功不牢时上实战平台会处处碰壁 |
| 有 Linux 基础 | PG Play 全刷一遍 | 建立黑盒测试的工作节奏 |
| 熟悉 Linux，想练 Windows | PG Practice 订阅档按需选择 | Windows 是企业环境的主力系统 |
| 已有渗透经验 | PG Practice 较高难度机器 | 训练复杂场景下的思路与耐心 |
| 企业安全岗 | PG Practice + 自己做内部复盘 | 把训练内容转化为团队方法论 |

有一个判断标准值得推荐：**当你在 PG 上「不知道下一步该干什么」的时间，超过「正在操作」的时间时，说明难度选对了；反之则说明机器太简单或太难。**

## 04订阅档位与目标人群

PG Practice 采用订阅制，档位差异主要体现在**可用机器数量与难度上限**上，而不是功能差异。

从投入产出比的角度，我的建议是：**不要在没试过的情况下长期订阅**。先用 PG Play 体验平台的机器风格，确认它适合自己，再决定档位。这是对学习投入最负责的方式。

**💡 提示**　补充一个常被忽略的角度：**如果你的公司有安全培训预算，让公司统一订阅是更划算的选择**——因为它同时解决了「个人学习」和「团队能力对齐」两个问题，而且团队账号便于统一管理训练进度。

## 05核心机制：黑盒方法论的完整训练

PG 与社区靶场最大的不同，在于它几乎**不给你任何前置信息**。

| 信息项 | Vulnhub 社区靶场 | PG 实战平台 | 真实项目 |
| --- | --- | --- | --- |
| 机器描述 | 通常有说明与提示 | 基本没有 | 只有范围说明 |
| 目标系统提示 | 常常透露技术栈 | 不透露 | 不透露 |
| 难度 | 主观标注 | 有粗略分档 | 无难度概念 |
| 通关标准 | root / user flag | user / root flag 或域管 | 按合同约定的目标 |
| 可用时间 | 不限 | 按订阅期限制 | 受测试窗口限制 |

注意最后一行。**「按测试窗口限制」这一条，是所有靶场都没法模拟的**——而它恰恰是企业渗透测试中最真实的约束：你必须在客户指定的时间段内完成测试，不能像在实验室里那样想到哪打到哪。

这一点直接影响你的工作方式：在有时间压力的情况下，**信息收集必须做得更系统，而不能靠「随便扫扫试试运气」。**这也是平台训练最有价值的部分。

## 06实战方法论：一次标准渗透的六阶段

这一节是全文最核心的内容。不管在哪个平台，一次标准的渗透测试都可以拆成这六个阶段。

1. **范围确认**

   ——在动手之前，先明确打哪些、不打哪些。这是职业与业余的分水岭。
2. **信息收集**

   ——端口、服务、版本、目录、源码、接口、账号线索。
3. **漏洞假设**

   ——把信息转化成可验证的假设，而不是无差别地跑工具。
4. **验证与取证**

   ——确认漏洞真实存在，并留下可复现的证据。
5. **影响评估与扩展**

   ——在授权范围内评估影响，确定是否需要进一步扩展。
6. **报告与修复建议**

   ——把技术发现转化为可执行的整改项。

**⚠️ 注意**　第一个阶段「范围确认」值得单独强调。**在真实项目中，这一步通常对应一份双方确认的测试方案**，里面包含：测试的 IP 范围、允许的测试手法、禁止的操作（尤其是可能造成服务中断的操作）、测试时间窗口、应急联系人。没有这份文档就开始动手，在法律和职业上都存在风险。

## 07实战演练：Windows 场景的信息收集节奏

Windows 是企业内网占比最高的系统，也是实战平台里占比很高的目标类型。这里给出 Windows 场景的信息收集节奏。

| 阶段 | 动作 | 关注点 | 时间占比 |
| --- | --- | --- | --- |
| 快速扫描 | 识别开放端口与服务版本 | 先建立最小可用画像 | 10% |
| 服务深挖 | 逐个服务识别版本与配置 | 老版本、默认配置、异常端口 | 25% |
| 内容发现 | Web 目录、备份文件、源码 | config、backup、.git、.svn | 20% |
| 身份线索 | 用户名收集、域信息推断 | 为后续认证类测试做准备 | 20% |
| 漏洞验证 | 针对已识别的版本与配置验证 | 严格记录请求与响应 | 25% |

这张表里最容易被新手跳过的是**「身份线索」这一步**。很多人在拿到 Web 漏洞后直接开打，却忽略了**在企业环境里，「用户名列表」本身就是重要资产**——它决定了后续认证类测试的效率，也决定了密码策略评估的准确性。

* 从登录页的用户名枚举差异推断有效账号
* 从邮件格式、员工姓名规律推断命名规则
* 从代码仓库、配置文件、历史泄露信息中提取账号
* 从域结构推断（admin.xxx 这种格式很常见）

**⚠️ 注意**　关于这些方法的合规提醒：**账号枚举与密码尝试类测试，必须在授权范围内进行，并严格遵守约定频率与账号范围。**很多测试方案里会明确写入「仅允许对指定测试账号进行验证」或「禁止任何形式的口令猜测」——因为在生产环境中，高频的登录尝试会触发锁定策略，直接影响真实用户。

## 08实战演练：Linux 场景的提权思路

拿到初始权限之后，**提权阶段才是真正拉开差距的地方**。因为初始漏洞的利用大同小异，而提权考的是对系统的理解深度。

| 提权方向 | 典型检查项 | 需要的知识 | 耗时 |
| --- | --- | --- | --- |
| SUID/SGID | 带特殊位的可执行文件 | 文件权限模型 | 5 分钟 |
| sudo 配置 | 当前用户可执行什么 | sudoers 语法 | 5 分钟 |
| 可写文件与服务 | 计划任务、定时任务、systemd unit | Linux 服务机制 | 20 分钟 |
| 环境变量劫持 | PATH、二进制路径优先级 | 执行机制 | 15 分钟 |
| 内核与软件版本 | 内核版本、已装软件的历史漏洞 | CVE 与利用条件 | 30 分钟 |
| 凭据文件 | 配置中的密码、密钥、history | 文件查找技巧 | 10 分钟 |

请注意这张表的最后一列。**在真实企业项目里，提权环节常常是耗时最长的部分**，因为目标机器上不会有那种「一个命令直接 root」的标准答案配置。你要从一堆历史遗留的配置里拼出攻击路径，这个过程本身就是耐心与经验的考验。

图：Linux 提权检查清单：从低成本的快速检查到高成本的分析

**💡 提示**　一个提权的实用心法：**「先找低成本的」**。SUID 检查、sudo -l、history 文件、配置文件里的密码——这些检查加起来不超过十分钟，却能解决相当比例的实际问题。在时间紧张的测试窗口里，先把这些便宜的检查做完，再考虑需要深入分析内核或编译环境的方案。

## 09排错清单

| 现象 | 根因 | 处理建议 |
| --- | --- | --- |
| 看不到机器列表 | 账号未登录或订阅状态异常 | 重新登录平台确认账号状态 |
| RDP 连不上 | 端口或网络策略限制 | 确认连接方式与是否需 VPN |
| 机器响应变慢 | 机器同时被多人使用 | 选择低峰时段或选择其他机器 |
| Pwnbox 掉线 | 本地辅助虚拟机异常 | 重启 Pwnbox 确认网络配置 |
| Pwnbox 桥接失败 | 虚拟网卡权限不足 | 以管理员身份启动并检查防火墙规则 |
| Payload 执行无回显 | 监听端网络不通 | 改用本机回环或确认出网规则 |

这里要特别说明 **Pwnbox**：它是平台提供的本地辅助 Linux 虚拟机，作用是承载你的攻击工具，并负责与目标建立连接。这种「攻击机与目标隔离」的架构，**与企业真实渗透测试的架构完全一致**——你从不在目标机上放工具，所有攻击流量都来自独立的攻击机。

**💡 提示**　这一点很多人忽视了。**攻击机隔离不是靶场的设计，而是专业测试的基本规范**：一是防止工具在目标机上留下痕迹，二是避免你的本地环境（尤其是个人笔记本）成为目标机的跳板。

## 10从「拿到权限」到「证明影响」

这是初学者和技术人员之间最大的差距之一。拿到 root 或 user flag 之后，很多人就认为「这个洞很严重」；但真实企业关心的是**「这个洞能造成什么后果」**。

| 漏洞类型 | 「我拿到了 shell」 | 「我证明了什么」 |
| --- | --- | --- |
| SQL 注入 | 能执行 union 查询 | 能否读取特定业务数据、数据量与敏感度 |
| 文件读取 | 能读到 /etc/passwd | 能否读到配置中的数据库凭据或密钥 |
| 命令执行 | 能执行 id 命令 | 能执行的操作范围、影响的业务、是否有持久化可能 |
| 越权访问 | 能看到别人的订单 | 能看到的数据量级、是否跨组织、是否可批量 |
| 弱口令 | 登录成功一个账号 | 该账号权限范围、是否涉及敏感系统 |

第二列和第三列的差距，就是「技术报告」和「业务报告」的差距。而**企业真正需要的是第三列**。这也是我在开篇强调角色能力差异时说的那件事——技术能力和工程能力，是两种不同的东西。

**⚠️ 注意**　这里有一个极其反直觉但极其重要的原则：**「证明影响」的过程，往往比「验证漏洞」的过程更需要边界感。**读取一条用户信息来证明影响是合理的；批量导出十万条数据来证明影响，就是另一回事了——后者可能在法律上被认定为超出授权范围的数据获取。**证明要充分，但永远不要超出必要。**

## 11等保视角：渗透测试报告该怎么写

前面所有内容最终都要落到一个产物上：**测试报告**。而这份报告的质量，直接决定了你前面的工作有多少价值。

| 报告章节 | 内容要求 | 常见问题 |
| --- | --- | --- |
| 测试概述 | 范围、时间、方法、依据 | 范围描述含糊，后续争议的根源 |
| 风险评级 | 评级标准与逐项定级 | 所有问题都标「高危」，失去优先级 |
| 漏洞详情 | 复现步骤、证据、影响分析 | 只有 Payload，没有原理与影响 |
| 修复建议 | 可执行的整改方案 | 只写「升级版本」，不写如何验证修复 |
| 整改验证 | 复测方法与结论 | 缺失，导致问题反复出现 |

结合等保 2.0 的要求，一份合格的渗透测试报告至少要能支撑：**「安全问题已发现并通报」与「整改已完成并复测通过」**这两个结论。

1. **对应「安全审计」条款**

   ：报告证明已开展渗透测试；测试范围与方法需可核查。
2. **对应「入侵防范」条款**

   ：漏洞清单与定级支撑整改优先级。
3. **对应「漏洞管理」条款**

   ：报告应可追溯到整改项与复测结论。
4. **对应「管理制度」条款**

   ：测试方案与授权文件是管理落地的重要证据。

**💡 提示**　一条很实用的建议：**把漏洞编号贯穿全流程。**发现时给编号 → 报告里用编号 → 整改工单里带编号 → 复测时按编号验证 → 最终归档时按编号统计。这一个动作，能把「发现问题」和「解决问题」之间的断点彻底消除。

## 12总结

写完这一篇，我想回到开头那个问题：**付费实战平台到底值不值？**

我的回答是：**它提供的不是内容，而是环境约束。**

内容——你可以在任何地方找到免费的漏洞教程。环境约束——信息缺失、路径不唯一、环境有噪声、还有时间压力——**这四样东西，只有在真实的约束下才能训练出来，而它们恰恰是区分「会打靶」和「能干活」的分水岭。**

所以我一直认为，安全能力的构成可以粗略分成三层：

1. **知识层**

   ：漏洞原理、协议、密码学、系统机制。这一层靠阅读和靶场。
2. **技能层**

   ：信息收集、漏洞验证、提权、报告。这一层靠动手，但可以在任何环境练。
3. **工程层**

   ：范围管理、边界意识、影响评估、沟通协作。**这一层只能靠真实约束来训练。**

免费平台能给你前两层的一部分，而第三层，你必须在带约束的环境里慢慢长出来。这可能就是实战平台真正的价值所在。
