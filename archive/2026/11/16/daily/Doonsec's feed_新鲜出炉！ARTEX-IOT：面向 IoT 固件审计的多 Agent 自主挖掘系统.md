## 0x00 写在前面

一年前我还坚信，AI 短期内干不了安全工作。直到年初的某场 CTF，我和蔡师傅还在手搓 exp，甚至才刚写下 `from pwn import *`，学弟说他已经打完了——直接把题扔给 GPT 网页端，exp 就出来了，稍微调一下 libc base 即可。给我俩都听懵了，从此道心破碎：打不过就加入，既然注定要被 AI 淘汰，不如拥抱 AI。

后来一段时间一直在用 hermes 挖洞，挖久了就发现一开始审的组件经常被上下文压缩给吞掉，导致总是东打一头西打一头。在尝试了渗透 Agent ARTEX 之后，被其设计架构深深吸引，所以保留其核心架构进行二开，有了今天的 ARTEX-IOT。

**「这次二开，最想解决的几件事：」**

* **「「组件」而不是「资产」」**：固件审计的目标是单个固件，里面最麻烦的就是各种各样的服务程序，找的正是这些组件自身的漏洞，以及组件之间相互调用、相互通信产生的漏洞。
* **「让每个任务的经验可以复用」**：不同 worker 往往在重复造轮子，ARTEX-IOT 内置经验系统，任务中的试错与通用方法沉淀后即可复用，既省 token，也避免工作区混乱。
* **「能力尽量前移到界面」**：前端直接查看 IDA 导出的伪代码，支持双击跳转函数；PoC 在线阅读、一键复制；对漏洞发起复测后自动录制复现视频——再也不用自己录复现视频了。

个人感觉效果还行，但目前有点烧 token——四个任务并行跑一小时，按 DeepSeek 高峰价要一百多元。降低消耗的设计已经做了一部分，也是后续主要的优化方向。

## 0x01 不只是换一个审计对象

ARTEX-IOT 是一套围绕单个固件、以组件为单位推进的自主审计系统。

它不是更懂 IoT 的渗透工具。上游 ARTEX 面对的是公网资产，讨论单位是暴露面与攻击面；这里面对的是一个固件包，以及包里大量零散的组件，对象一换，很多默认设计就不成立了，这次二开的大部分改动，都是被这件事逼出来的。

### 继承来的骨架：两张图，一个循环

从ARTEX中保留了**「双图架构」**：把「测什么」和「想到哪了」拆成两份互相独立、又通过锚点相连的数据。

**「组件库」**是跨任务共享的真值库。一行 = 固件里一个可指认的组件；同一个固件在哪个任务里被分析，组件清单都是同一份。

**「探索图」**是每个任务独立的推进链。节点是 goal / intent / fact / finding / hint，边是 spawns / derived\_from / yields / proves，记录一次任务「想到了什么、凭什么这么想、最后证明了什么」。

两边靠锚点连起来：一条意图或一条漏洞可以锚到具体组件上。于是既能从探索方向看它打了哪些组件，也能从某个组件反查它在本任务被哪些意图测过、得出过哪些事实，从而得到覆盖度。

围绕这两张图是一个事件驱动的闭环：图一变，planner 被唤醒，读态势、派意图；worker 领一条意图，用真实工具执行；执行结果把新组件、事实、漏洞写回两张图；图再变，进入下一轮。直到目标被 `prove_goal` 证明，或者没有新方向可派。

![探索链路：goal / intent / fact / finding 的血缘关系，右侧是组件与覆盖情况](https://mmbiz.qpic.cn/mmbiz_png/PkfClzhSYiczFFdUlM8OyjDiaEukWVtib3TAEuIem5hOgexvKyZia80BShd9mt07QHJuicXMhNft7JIxfWwtZ94iccZiaDH0bibiaXSWQtJwOQJdL6WU/640?wx_fmt=png&from=appmsg)

### 换掉对象之后，要改的四件事

骨架不动，改的是喂进去的东西，真正需要重新设计的主要有四处：

* **「审计对象」**：从「企业 / 域名 / IP / 服务 / 接口」换成「组件」。覆盖度、技能挂载、跨组件链路，都依附在这个概念上。
* **「固件」**：从任务描述里的附属信息，变成带 sha256 身份、有独立元信息和唯一解包路径的实体。
* **「第一轮」**：从「多点并行打点」改成「先做完一次全局探测」。解包和清点是所有后续工作的前置条件，重复一次就是几百次工具调用和一堆互相干扰的目录。
* **「试错」**：从「靠 worker 自己翻记录」改成「强制沉淀 + 按需检索」。不强制写，就没有可复用的东西；强制读，又会把上下文挤爆。

这四件事定下来，一条任务就有了固定的走向。

### 一条任务的完整生命周期

1. **「建任务、传固件」**——sha256 成为固件身份，厂商与版本绑定到固件而不是任务
2. **「首轮全局探测」**——解包、组件清点、版本提取、架构识别、历史 CVE 检索，一次做完
3. **「组件入库」**——状态即进度；组件库跨任务共享，覆盖图给出已测与未测
4. **「派发意图」**——planner 按 todolist 逐步派发，worker 并行领取
5. **「执行与沉淀」**——真实工具、命令审批、经验读写、过程互查
6. **「产出漏洞」**——fact / finding 写回探索图，判重 Agent 合并重复项
7. **「复测收口」**——独立会话重新验证，自动录像，结论回写状态

这条链上最容易出错的是开头：对象没建模对，后面全是返工。

## 0x02 审计对象：固件与组件

拿到一个固件，第一件事不是扫端口。你手里是一个固件包，不是一台能 ping 通的设备；得先拆开，看清楚里面跑着什么，再决定打哪。

### 固件要成为独立实体

通用渗透里，「目标」是任务的一部分：这次打这个域名，下次打那个。固件不是。同一个固件会被反复建立任务——先粗扫一遍，再针对某个组件深挖，过几天换个思路再来一次。如果厂商、版本、解包路径都挂在任务上，三次任务就会有三份不一致的元信息和三套解包目录。

所以固件按内容 sha256 建身份，厂商与版本挂在这个身份上：人工修改会同步该 sha 的全部记录，Agent 写入只能补空、不能覆盖已有值。理由很实际——多个 worker 同时识别同一个固件，很容易一个填 `Tenda`、一个填 `tenda`、一个填 `V1.0`，最后没人知道该信哪行。厂商名也做了规范化，`TENDA` / `tenda` 统一成 `Tenda`。

解包路径同理：由第一个解包成功的 worker 登记回任务范围，后续的路径解析、组件登记、反编译都以它为基准，不再各解各的。

代价是，改固件元信息不再是「改这个任务」，而是「改这个固件」。界面上多一步确认，换来后面所有环节不分叉。

### 组件是覆盖度的计量单位

组件是固件里一个可指认的程序实体，字段包括类型、组件名、版本、二进制路径、配置文件、启动方式、端口和状态。去重键是（固件 sha256、类型、组件名、版本），状态直接当进度用：待审、在审、已完成、已忽略。

![组件库：一行一个组件，组件版本与固件版本分列](https://mmbiz.qpic.cn/sz_mmbiz_png/PkfClzhSYicwyPKjIad4hsdPCULyfCm4vaA4nXIbwQW61hKZd3LwO3VKg5dL2TPvE9HIqZLGFvJFvicF0hahMDcMprXmA44OULT3oSicPnqlDQ/640?wx_fmt=png&from=appmsg)

组件库：一行一个组件，组件版本与固件版本分列

这张表解决的并不是「看起来更像 IoT」，而是三个具体问题。

**「一、进度可以计量。」** 「这个固件审了多少」在资产模型里没法回答，在组件模型里就是「已完成 / 总数」，按类型还能再分。覆盖图按「组件类型 → 组件」两层展示，已测高亮、未测灰着，比一句「还在跑」有用得多。

**「二、技能有了挂载点。」** 针对 mqtt 挂匿名接入与越权检查，针对 ssh、busybox 这类通用组件挂 CVE 检索，针对 Web 挂路由测绘。技能不再是一份大而全的提示词，而是按组件类别按需注入。

**「三、跨组件链路有了描述对象。」** 过去固件分析基本只审 Web 服务：web 和守护进程之间怎么传参、怎么校验，研究成本太高，几乎没人做。两侧都建模成组件、再用锚点把意图和事实锚到组件上之后，这条链路就可以被派成一条意图。这是「组件」相对「资产」最实质的收益——不是换个名字，是原来不可派发的东西变得可派发。

表格支持列宽拖拽、悬停看全文，也支持 DSL 查询：

## 0x03 审计过程：意图、worker 与经验

对象清楚之后，接下来是它怎么被审。真正决定效率的往往不是模型多强，而是活怎么派、试错怎么不重复。

一条固件任务里，固定在场上的有这么几个角色：

* `goals`——把任务目标拆成若干独立、可验证的子目标
* `planner`——唯一生成意图的角色，读态势、按 todolist 派发
* `worker`——领一条意图执行，把事实与漏洞写回两张图后停止
* `mainagent`——人机接口，把你说的话落成 hint 或高优先级意图
* `reporter`——发现漏洞时自动触发，取证据与执行过程写成 Markdown 报告
* `retester`——从漏洞详情手动启动，独立复测并保存结论

另有 `auto`（平台操作助手）和 `pentest`（单 Agent 走完整条链）两个可独立使用的角色。每个角色的提示词、技能、工具与运行预算都能在 Agent 管理里单独配置。

![Agent 管理：每个角色的提示词、技能与工具都可独立配置](https://mmbiz.qpic.cn/mmbiz_png/PkfClzhSYicwtgSmBUxsdx9uTKhKdgX9APDAujln1ibh0NTaBEGP3TGD6uKd2LLmrmL9MWpcs21fG6P74pFOicLBlYbxsct8BicHLLwfY7JR3vA/640?wx_fmt=png&from=appmsg)

### 第一轮只派一条全局探测意图

通用渗透允许多点并行：十个子域同时打，互不影响。固件审计不行。

解包、架构识别、模拟方式确认、组件清点，是后面所有工作的前置条件。如果第一轮就派两条意图——「解包固件，审 httpd」和「解包固件，审 mosquitto」——两个 worker 会各自解包一次，产出两套目录。重复的几百次工具调用只是浪费 token，真正麻烦的是路径串扰：后面的 worker 不知道哪个目录才是准的。

所以第一轮只产出一条意图，而且它必须是全局探测，不是具体挖洞。

这条约束没有在 harness 层做成硬限制。原因有三：planner 每轮是全新会话、没有历史上下文，输出基本可控；即使多派一条，也只是多花一点 token，流程不会错；一旦固化成硬闸门，后续调提示词就没有空间了。

第一轮之后才允许并行。组件已经清点完，planner 派意图时会带上 `component_ids`，worker 领取时直接拿到这些组件的类型、版本、路径作为初始信息，不用自己再找一遍。默认每个任务 3 个 worker，可在系统设置里改。

### 经验写入是强制的，读取是自愿的

qemu-user 起一个服务要补一堆依赖，某个 worker 摸索半天，写出了一个启动脚本；另一个 worker 遇到同一个服务，虽然有权限看前者的记录，但它不会主动去找「有没有人模拟成功过」，于是从头再补一遍。gdb 调试方式、固件信息收集也一样。

写入端做成硬约束：每个 worker 结束前必须调用一次经验写入工具，harness 层校验，没写不允许结束。所以每个意图至少沉淀一条经验。

读取端不做强制注入。`read_experience` 接收自然语言（比如「qemu-user 模拟相关的经验」），工具内部再调一次模型，从历史经验里筛出相关的返回。实测 worker 在任务开头几轮普遍会主动调用，所以没有硬性注入；只限制每个意图最多调三次，避免经验把上下文挤爆。

**「检索质量交给模型判断，工具不做本地打分。」**

本地关键词打分在两种情况下会静默失效——中文查询没有空格、同义不同词（「模拟」和「仿真」）。失效时它会退化成「最近 N 条」，而调用方看不出退化。所以这类工具只做确定性过滤和原样返回，相关性判断交给模型。宁可多花一次模型调用，也不要一个悄悄变傻的检索。

## 0x04 结果收敛：判重、复测与 PoC

审出来的东西不会自动变成结论。

多 Agent 并行有个副作用：同一个问题会被不同 worker 各发现一次。放到列表里就是三条一模一样的漏洞，各自带一份证据和 PoC，连复测记录都各记各的。人工去重比挖洞还烦。

### 判重为什么必须是一个 Agent

最简单的做法，是在写入 finding 的工具里加一次模型调用，判断「是否与已有条目重复」。但真要判断两条漏洞是否本质相同，需要读原文、读证据、对比入口 URL 与组件，还要能输出「不合并，但记录理由」这种形态。这需要独立的 system prompt、独立的工具循环和一个收尾结论——也就是一个 Agent，而不是一次函数调用。系统里这个角色叫 `auditor`。

判重按批次触发：一批新漏洞对应一个会话，会话里可以合并多组，也可以读完全部条目后判定都是独立漏洞。批次语义要宽松，否则 Agent 会被迫为了「有输出」而合并。

合并是真实整合，不是打个 duplicate 标指向旧行：新建一行，重写整合后的摘要、报告与证据，迁移流量绑定与复测记录，详情页显示「整合自 N 条」。这样列表长度对应的是真实问题数量，而不是发现次数。

权限上做了收敛：这个 Agent 只有四个工具，不给 Shell，也不给文件写入。判重只需要读和写漏洞条目，多给的能力都是风险面。

### 复测与自动录像

复测是独立会话，不重启原任务。填好可选的修复版本、测试条件后发起，跑完留下独立结论：仍可复现 / 已修复 / 无法确认。

结论为「已修复」时，系统自动更新漏洞处置状态；执行中、失败、停止或其他结论都保留原状态。原始证据和报告始终保留——复测是叠加一层判断，不是覆盖历史。

复测结束，系统会把复现过程录成视频，前端直接播放和下载。只有复测过的漏洞才会产出复现视频，这个限制是有意的：录屏不是「跑过就有」，而是「验证过才有」。

### PoC 与报告

PoC 落在任务目录并关联到对应漏洞，详情页可以直接看、一键复制、下载。报告由 `reporter` 在发现漏洞时自动触发，取证据与执行过程后写成 Markdown 回写，不必等整个任务结束再手写。

## 0x05 人机界面：把工具搬进页面

系统自己跑得再顺，人还是要能随时插手。

这些功能都不改变系统能力边界，但决定日常使用的成本。判断标准很土：这个动作原来要不要切窗口？要切到终端、切到 IDA、切到录屏软件，就值得搬进来。

### 反编译

组件表每行有反编译入口，点一下建导出任务，完成后跳转。界面三栏：左侧函数列表、中间反汇编与伪代码、右侧函数详情（callers / callees）。双击函数名跳转，跳转来源的 caller 高亮，点它回到上一层——和 IDA 里按 `Esc` 是同一个行为。
